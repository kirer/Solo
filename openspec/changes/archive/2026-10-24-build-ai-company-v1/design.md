# Design

## Context

动机见 `proposal.md - Why`。本设计只描述实现路径与取舍。

当前仓库状态：无业务代码，只有调研文档（`docs/`）、九个可行性验证脚本（`spikes/`）与 OpenSpec 结构。`spikes/` 里的脚本已用可运行代码验证了本变更依赖的全部机制，是设计的事实依据而非推测。

技术约束（来自底层库与运行环境）：

- `@earendil-works/pi-durable@1.4.0` 标注 experimental，`1.1→1.4` 每个 minor 都带破坏性变更。它的公开面是 `Harness` / `Conversation` / `Task` / `Document` 四个概念。
- 底层库只有会话、任务、文档三种持久化抽象，**没有**「项目」「角色」「组织」这些领域概念，也没有 skill、MCP、cron、会话删除、认证。
- 单进程独占存储，无跨进程锁。
- 存储层错误是致命的：一次失败整个运行时自我关闭，不重试。
- 恢复语义是「至少一次」：任务阶段崩溃后从检查点重跑，外部副作用必须幂等。
- 进度提交按 100 毫秒节流，不是 token 级流式。

## Goals / Non-Goals

**Goals:**

- 把底层库的四个抽象映射成一套清晰的领域模型，使业务代码读起来是「公司、项目、员工」，而不是「会话、任务、文档」。
- 把 experimental 依赖的全部使用面收进一层边界，使升级只需改动该层。
- 界面完全由已提交状态驱动（订阅变更而非轮询），保证多客户端一致。
- 让「员工不被老板中断」「成本不重复计账」「沟通可追溯」这三个容易出错的地方由结构保证，而非靠开发者自觉。

**Non-Goals:**

- 不做多进程或多机部署。单进程单存储是本变更的既定前提。
- 不做认证与多租户。v1 假定单用户本机运行。
- 不做图形界面。本变更只保证数据形态（节点与边、活跃任务结构）可直接被图形界面消费。
- 不做成本硬预算拦截。底层库的请求前钩子无法拒绝请求（实测抛异常只记一条错误后继续），硬约束需要业务层拒绝派活，留给后续变更。
- 不追求 token 级流式渲染。100 毫秒粒度对本场景足够。

## Decisions

### 决策 1：组织层级全部用会话表达，用「归属」区分物种

**选择**：老板以外的所有实体都是会话。CEO 与六位高管为无主会话；项目为无主会话且绑定工作目录；项目员工为归属于一个后台任务的会话。

**理由**：底层库只有会话这一个执行单元。试图引入「agent」「subagent」两个类型会制造不必要的抽象——它们在底层是同一个东西，差异只在三件事：生效配置（模型、能力、职责描述、工作目录）与归属关系。用归属表达差异，语义清晰且直接对应底层的所有权树（中断传播、空闲等待都由归属决定）。

**备选方案**：

- *员工用前台子会话*：被否决。前台子会话会被上级的中断操作取消，而员工必须能跨上级的一次对话存活。`spikes/02` 实测证明后台归属下老板中断 CEO 后员工仍完成。
- *给每类实体定义不同的封装类型*：被否决。会增加映射成本，且底层变更时改动面变大。

**后果**：员工的「后台任务归属」是结构性的安全保证，不依赖调用方是否记得传参数。

### 决策 2：一个公司级索引文档 + 若干会话级小文档

**选择**：公司级索引用一个会话范围之外的全局文档（角色名册、项目索引、员工名册、归档标记、默认模型、模型清单）。每个会话另有小档案（标题、类型、上级、工作空间路径）与审计记录。

**理由**：组织关系是全局的，放在会话级文档里会导致「查一个项目要遍历所有会话」。全局文档在单次原子提交内更新，与对应的会话创建同生共死——这解决了「会话已建但名册未记」这类不一致。

**备选方案**：*完全靠遍历会话推导组织关系*：被否决。每次渲染组织树都要全量扫描，且无法表达「归档」这类不在会话本身的信息。

**后果**：全局文档是组织状态的唯一真相源，但它的写入会成为提交线上的热点。缓解：只在组织变更时写，不在每次对话时写。

### 决策 3：能力边界靠「装什么能力包」而非提示词

**选择**：每个角色是一个能力包（职责描述 + 工具集合 + 行为钩子）。员工的能力包不含任何管理类工具；管理层的包才含。派活、招聘、立项这些工具只装在管理层与项目负责人的包里。

**理由**：只靠提示词说「你不能越级」是不可靠的——模型可能编造。工具不存在则物理上无法执行。`spikes/06` 实测：员工的生效工具集合为空，管理层为 `["hire"]`。

**备选方案**：*用钩子在工具调用时拦截*：作为第二道防线保留（用于预算、危险操作），但不作为主要机制——它依赖每个调用点都记得装钩子，容易漏。

**后果**：角色能力的调整意味着改能力包配置，而不是改提示词。这也让「同一岗位不同授权级别」成为配置问题。

### 决策 4：升级链用多阶段任务，每个层级一个阶段

**选择**：升级流程是一个持久化任务，阶段依次为「直属管理层」「CEO」「等待老板」。每次跃迁提交检查点，记录当前层级。

**理由**：升级链天然是串行的、可能跨天的、必须可恢复的——正是持久化任务的定义。每层一个阶段使「从哪一层继续」由检查点直接给出，不需要额外的状态推断。等待老板的阶段用休眠而非轮询，不占执行名额（`spikes/05` 实测状态为休眠，时钟推进后自动续跑）。

**备选方案**：*用父子任务的等待机制串联各层级*：被否决。那适合并行收集，而升级是串行决策；用它表达会引入不必要的任务层级。

**后果**：老板拍板的响应延迟由界面轮询或订阅驱动，而非任务自身阻塞。

### 决策 5：成本只从用量文档取，绝不由历史消息求和

**选择**：所有成本聚合都读会话的用量文档；界面上的单条消息消耗只用于展示，不参与任何跨会话求和。

**理由**：`spikes/09` 实测发现——分叉会话的可见历史包含父会话的消息，但它的用量文档从零开始计。按历史消息求和会重复计账（实测虚高：分支真实 19，求和得 26）。这个错误非常隐蔽，因为单看每个会话都「合理」。

**备选方案**：*在每条消息上打标记区分是否属于本会话*：被否决。需要修改底层写入路径，且底层已提供正确的用量文档。

**后果**：成本取数路径唯一，且必须写进代码规范与测试。

### 决策 6：沟通留痕用自定义条目，双向各写一条

**选择**：定义一种自定义的沟通条目类型（时间、发送方、接收方、类型、正文、关联标识）。每次沟通在发送方与接收方会话各写一条，用共同标识对应。

**理由**：底层条目不可变且永不删除，天然满足审计要求。双向留痕让任一端都能看到完整往来——只写一端的话，从接收方视角看就是「凭空出现一条指令」。`spikes/07` 实测跨会话追溯成功。

**备选方案**：*只写发送方，接收方靠关联查询*：被否决。查询时要把所有会话扫一遍才能拼出一条消息，成本高且实现复杂。

**后果**：写入量翻倍，但每条记录都很小。另外需要维护一个全局时间线文档以避免全量扫描（见风险一节）。

### 决策 7：界面由订阅驱动，不轮询

**选择**：界面附着到会话时先取当前状态，此后由变更订阅推送增量；组织树与任务面板订阅任务结构文档。

**理由**：底层保证「只有已提交状态可观察」，订阅返回的每一帧都是完整一致的快照，界面不需要做乐观更新或冲突合并。这也直接满足多客户端一致——将来加图形界面时，同一套订阅可以转发给远端。

**备选方案**：*定时轮询*：被否决。延迟不可控，且切换会话时会产生大量无效读取。

**后果**：切换会话必须显式停止旧订阅，否则资源泄漏。慢消费者会丢中间帧（底层最多缓存 100 帧后降级为整帧快照），所以界面不能假设「收到每一帧」，只能假设「收到最新状态」。

### 决策 8：执行环境按会话懒创建并缓存

**选择**：执行环境工厂按会话标识返回对应工作目录的环境实例，用映射缓存，会话关闭时清理。

**理由**：底层每次工具调用、每次职责描述渲染都要构建执行环境，重复创建会带来可观的系统开销（进程、文件句柄）。缓存让同一会话复用同一实例。

**备选方案**：*每次调用新建*：被否决。文件句柄与进程会快速耗尽。

**后果**：工作目录变更后需要失效缓存。缓存的键是会话标识，值是环境实例，需要明确的清理时机（运行时关闭时）。

### 决策 9：中断与恢复的语义边界写进规格而非靠文档说明

**选择**：把「中断上级不波及后台员工」「恢复前不执行任何处理器」「同一请求重复提交返回原记录」这三条写进能力规格，并配测试。

**理由**：这三条是底层行为，但业务代码很容易破坏它们（例如为了「立即响应」而在恢复前主动调度，或给派活用随机请求标识）。写进规格后，破坏它们会导致测试失败，而不是在生产环境表现为诡异行为。

**后果**：派活的请求标识必须由业务语义推导（例如「派活任务标识 + 员工标识」），不能随机生成。

## Risks / Trade-offs

**[底层库破坏性变更]** → 全部调用收进防腐层；锁精确版本；契约测试覆盖本规格的每条要求；升级前备份存储（1.4.0 的 schema 迁移不可回退）。

**[存储错误导致运行时失效]** → 宿主监听关闭事件，因故障关闭时自动重开；派活与投递全部使用语义化请求标识，重开后重复投递由底层去重。

**[反复崩溃的任务被暂停后静默卡死]** → 启动时巡检受阻任务并在界面显著标记；提供手动重试；把「受阻」作为一种可见状态而非隐藏异常。

**[全局索引文档成为提交热点]** → 只在组织变更时写索引；对话推进不触碰它。若将来成为瓶颈，可拆成按项目分片的文档族。

**[沟通留痕写入量翻倍]** → 每条记录保持精简（正文截断，完整内容留在会话条目里）；维护全局时间线文档以避免追溯时全量扫描会话。

**[成本数字全为零]** → 使用官方模型提供方时成本自动有值；自建提供方必须声明价格；界面在检测到「有 token 无成本」时给出提示。

**[提示词缓存被破坏导致成本翻倍]** → 角色职责描述必须是纯函数（不含时间戳、不含随机内容）；不在会话中途改动能力包选择；监控缓存读取占比。

**[切换会话时订阅泄漏]** → 订阅句柄的生命周期绑定到界面当前选中项，切换即停止；退出时统一停止。

**[恢复语义是至少一次]** → 所有外部副作用（写文件、发消息）都要么幂等，要么用底层的幂等记录去重。派活天然幂等（同请求标识返回原提交）。

## Migration Plan

本变更是从零建立代码，无历史数据迁移。部署与回滚：

1. **首次启动**：打开空存储即完成初始化，创建根会话、六个管理层会话、公司索引文档。失败则整体回滚（原子提交保证不会留下半成品）。
2. **版本升级**：先备份存储文件，再升级依赖，运行契约测试，最后启动。底层 1.4.0 的 schema 迁移不可回退，因此备份是强制的。
3. **回滚策略**：回滚依赖版本 + 恢复备份文件。若已发生不可逆的 schema 迁移，只能前滚修复而非回退。

## Open Questions

- 项目负责人的具体职责边界（能给自己项目员工派活，能否跨项目协调）——v1 先按「只管本项目」实现，跨项目协调留到会议机制变更时一并设计。
- 管理层授权范围的具体阈值（哪些技术决策 CTO 可自行拍板）——v1 把授权范围做成配置项，默认全部上转 CEO，待真实使用后再调。
- 老板拍板的界面交互形态（在任务面板直接答复，还是进入专门的待办视图）——v1 先在任务面板提供答复入口。
