# Proposal

## Why

我们要做一个「一人公司」：老板通过一个终端界面指挥一家由 AI 组成的公司——CEO 与六位高管（CTO/CFO/CPO/COO/CMO/CHRO）构成管理层，每个项目是一个独立工作空间，项目内配员工，员工只对接管理层。

现有工具都不合适。Pi 本体是「一个人的终端 agent」，进程退出即丢失全部员工会话与在跑的工作；Pi SDK 的 SessionManager 是单会话结构，多角色并发、崩溃恢复、任务状态机都要自研。而我们的核心诉求——**员工长期在岗、跨天等老板拍板、进程重启不丢工作、按项目与角色分账**——本质是持久化执行（durable execution）问题，不是提示词问题。

`@earendil-works/pi-durable` 正好提供这套运行时（持久化会话 + 持久化任务 + 持久化文档 + 崩溃恢复 + 所有权树 + 成本记账）。可行性已用 9 个可运行脚本验证（见 `spikes/`）。现在需要把它变成一个真正能用的产品：有组织模型、有三栏终端界面、能派活能升级能看进度。

**为什么是现在**：技术选型与可行性验证已完成，架构决策已定稿（`docs/PLAN.md`），老板已确认三项关键决定（默认统一模型 + CHRO 可按员工分配模型、三栏常驻 TUI、首个真实项目为网页坦克大战）。可以进入实现。

## What Changes

本变更交付 **v1 可用版**（对应 `docs/PLAN.md` 的 M0-M3）：老板能打开界面、看到组织、立项、配人、派活、看进度、被升级请示并拍板。

- **运行时地基**：单一入口打开公司（SQLite 存储），进程崩溃后自动恢复未完成的工作，`pi-durable` 的调用全部收敛在一层防腐层内（因为它是 experimental，API 会不兼容变更）。
- **组织模型**：老板直连 CEO；六个管理层岗位为常设会话；项目为独立工作空间会话；项目员工为项目下的常驻会话。全公司名册与项目索引存在一个 session 级文档里。
- **模型分配**：全公司默认统一模型；CHRO 招聘员工时可单独为该员工指定模型。
- **项目工作空间**：立项时创建真实文件夹（含立项文档），项目内所有员工的读写操作落在该文件夹内。
- **派活与回报**：管理层/项目 leader 可给员工派活并等待答复；员工的产出回流给派活者。员工的工具集不含任何管理能力，物理上无法越级。
- **升级链**：管理层按授权范围自行拍板或上报；上报逐级到 CEO；CEO 也拍不了时转为「等待老板拍板」，老板离线也不丢，回来再答。
- **成本可见**：界面常驻显示当前会话 / 当前项目 / 全公司的 token 与成本；成本取数遵循 fork 会话不重复计账的规则。
- **沟通留痕**：角色之间、角色与员工之间的每一条指令与回报都落成不可变记录，可按会话追溯，为将来做图形界面预留数据形态。
- **三栏终端界面**：左侧组织树（CEO / 管理层 / 项目 / 员工）、中间会话流（含流式生成与工具调用）、右侧任务与成本面板，底部输入框。

不在本变更范围（后续增量变更）：

- 分阶段会议机制与定期例会
- 成本预算硬约束与超支拦截
- 会话删除 / 归档的完整实现（v1 只做软删标记）
- 图形界面（本变更只保证数据形态可支撑）
- 多用户、认证、多租户

## Capabilities

### New Capabilities

- `company-runtime`: 公司的运行时生命周期——打开与关闭、存储选择、崩溃后恢复未完成工作、任务卡死巡检、以及隔离 experimental 依赖的防腐层边界。
- `org-structure`: 组织模型——老板与 CEO 的关系、六个管理层常设岗位、项目与项目员工的创建与归属、全公司名册与项目索引、默认模型与按员工分配模型。
- `project-workspace`: 项目工作空间的创建与隔离——立项时建真实目录与立项文档，项目内会话的文件操作限定在该目录内。
- `delegation`: 派活与回报——管理层给员工派活并等待结果、员工产出回流、员工能力边界（不得越级）。
- `escalation`: 决策授权与升级链——管理层按授权范围自行拍板或上报、逐级升级至 CEO、CEO 无法决断时转为等待老板拍板并支持跨天等待。
- `cost-accounting`: 成本记账与聚合——按会话取 token 与成本、按项目与角色聚合、fork 会话不重复计账。
- `communication-trail`: 沟通留痕——角色与员工之间的指令与回报落成不可变记录，支持跨会话追溯与时间线重建。
- `tui-workspace`: 三栏终端界面——组织树导航、会话流渲染（含流式输出与工具调用）、任务与成本面板、输入与中断。

### Modified Capabilities

（无。项目此前没有 OpenSpec 规格。）

## Impact

**新增代码**（当前仓库只有调研文档与验证脚本，无业务代码）：

```
src/runtime/      防腐层：打开/注册/环境/恢复/幂等 ID
src/company/      业务层：文档定义、角色、工具、任务、公司操作
src/tui/          界面层：布局、组织树、会话流、输入、面板
test/             契约测试、单元测试、端到端剧本
workspace/        运行时生成的公司工作空间
```

**依赖**：

- `@earendil-works/pi-durable@1.4.0`（锁精确版本，不用 `^`）
- `@earendil-works/pi-ai@1.4.0`
- `@earendil-works/chord@1.4.0`
- `@earendil-works/pi-tui@1.4.0`
- Node >= 22.19（ESM only）；SQLite 走 Node 内置 `node:sqlite`，无需原生编译

**风险与影响面**：

- `pi-durable` 标注 experimental，每个 minor 版本都带破坏性变更（1.4.0 有 6 条）。所有调用必须收敛在 `src/runtime/` 内，并配契约测试；升级前需备份 SQLite（1.4.0 的 schema 迁移不可回退）。
- 单进程独占存储（无跨进程锁）：一台机器一个进程，横向扩展不在本变更范围。
- 存储错误是致命的（一次失败整个运行时自我关闭），宿主必须实现自动重开与幂等重放。
- 成本硬预算无法通过请求前钩子实现（实测抛异常不能阻断请求），本变更只做可见性，硬约束留给后续变更。

**既有产物**：`docs/PLAN.md`（技术选型与实现计划）、`docs/ANSWERS.md`（七个关键问题）、`docs/research/*`（三份调研）、`spikes/*`（9 个验证脚本）均保留，作为实现依据。
