# Design

## Context

本次变更记录的是已经落地的实现决策，并把它们固化成规格契约。核心问题不是单个工具写错，而是「同步等待另一个自主 agent」这个交互模式本身会制造死锁。

对应代码：

- `src/company/delegation-guard.ts`：等待图与环检测
- `src/company/org.ts`：`delegate_to_role` / `delegate_to_leader` 的忙碌快速失败、Context 透传、`app.delegate` 来源条目
- `src/company/delegation.ts`：派活来源标记、派活序号兼容 `app.delegate`
- `src/server/http.ts`：`/api/interrupt` 的 5 秒上限与队列保全
- `src/server/feed.ts`：实时工具参数回填、去重、`interrupted` 状态、`queued.origin`
- `ui/js/chat.js`：agent 来源排队卡不提供「立即处理」

## Goals / Non-Goals

**Goals:**

- 任何 A 等 B 的同步转交都不能形成闭环
- 任何等待都必须可被 abort 取消
- 中断不能让老板已经发出的消息消失
- 让「谁在等谁 / 谁在问谁」在界面上可辨认
- 规格与实现重新对齐

**Non-Goals:**

- 不把同步派活改成完整的异步任务编排（需要独立的回调与状态机，留给后续变更）
- 不改变「员工只对接管理层」的组织边界

## Decisions

### 决策 1：用进程内等待图做环检测，而不是给每次转交加超时

**选择**：登记 `caller → target` 的同步等待边，转交前沿目标的方向检查是否会回到 caller；有环直接拒绝并返回可执行的替代方案（先回复对方，或 escalate）。

**理由**：超时只能把死锁从「永远」变成「很慢」，而且会误伤合法的长任务。环检测在**进入等待之前**就拒绝了不可能完成的等待，语义更准确。

**代价**：等待图是进程内状态，重启后归零。但重启本来就会把遗留同步等待标成中断，图从空开始是对的；跨进程的环不在本系统部署模型内（单进程单库）。

### 决策 2：目标忙碌时快速失败，不排队

**选择**：`delegate_to_role` / `delegate_to_leader` 在目标仍有未结束任务或排队消息时直接返回「正在忙，本次未执行」。

**理由**：同步转交 + 排队等待 = 调用方无限期挂住。环检测能挡住闭环，但「等一个正在跑长任务的 agent」同样会占着调用方不放。让模型拿到「忙」的即时反馈，它可以稍后再转或改走 escalate。

**备选方案**：*改为异步派活，立即返回任务号*。更彻底，但改动面大；先堵住不可用状态，把异步化留给后续。

### 决策 3：把工具 Context 一路传进 `submission.wait()`

**选择**：工具执行时的 `Context` 经 `management-tools` → `org.ts` → `submission.wait(context)`。abort 时 waiter 立即取消。

**理由**：这是「立即处理」能真正生效的关键。旧实现用 `BACKGROUND_CONTEXT`，abort 只能标记任务，工具里的等待永远感知不到，`abort()` 自然永远等不到 idle。

### 决策 4：中断最多等 5 秒，并保全队列

**选择**：`/api/interrupt` 先读队列，abort 与 5 秒超时赛跑，然后把「被点击的消息 + 其它排队消息」重新投递。

**理由**：
- 无上限的 abort 会把 HTTP 请求挂死，界面一直「处理中…」；
- 底层 abort 会撤掉全部排队输入，只重投一条会吞掉老板的其它消息。既然这些消息已经被读出来了，就一并补回去。

### 决策 5：排队与转交都要带来源

**选择**：转交写成 `app.delegate` 条目（带 `from` / `to` / `text`），`feed.queued` 返回 `origin: "owner" | "agent"` 和 `from`；agent 来源不提供「立即处理」。

**理由**：「排队中 / 插话 / 立即处理」是老板消息的语义。把 agent 派来的任务渲染成同一张卡，会让老板误以为员工在向自己请示，点下去还会把任务当成老板的话重投一遍。

### 决策 6：工具卡以已提交条目为准，实时状态只补状态

**选择**：`pi.live` 里的工具只作实时状态来源；若该 `callId` 已有已提交的 assistant toolCall，就不再生成第二张卡，参数从已提交条目回填；没有 tool-result 且无实时任务的调用标记为 `interrupted`。

**理由**：`pi.live` 不存 arguments，直接渲染就会出现「（无参数）」；同时提交条目和实时条目各渲染一次会出现两张重复卡。中断后的调用如果没有结果，也不应永远显示「运行中」。
