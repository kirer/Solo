# 写技能

## 什么时候该写

不是「做完一件事就写」。问自己一句：**下次遇到同样的形状，我还会从零想一遍吗？**

会，就写。典型的几种：

- 同一类判断做过第三次（「这个需求要不要单独建团队」「这个人该不该招」）。
- 踩过一次坑，坑的形状会重复（「部署前一定要先看端口被谁占了」）。
- 有一步容易漏，且漏了代价大（「团队建完必须确认频道里有人」）。

只有一次性的、形状不会重复的事，别写 —— 那只是流水账，写下来也不会再读。

## 写在哪一层

- **全员层**（`<workspace>/skills/<名字>/SKILL.md`）：所有人都该这么做的。
  判断标准是「如果我明天走了，这条规矩还成立吗」。
- **个人层**（`members/<slug>/skills/<名字>/SKILL.md`，默认就写这一层）：只有我这么干、或者我在试的做法。
  个人层会**覆盖**全员的同名技能 —— 想改一条全员规矩但还没把握时，先写个人层。

## 怎么写

`SKILL.md` 的 YAML 头只有两个字段：

```
---
name: 名字
description: 一句话说清「什么时候该用我」。这句话会出现在所有人的提示词里，正文不会。
---
```

正文建议四段（不必拘泥，但缺了会难用）：

1. **什么时候用** — 具体到可判断的情形，不写「需要的时候」。
2. **怎么做** — 步骤，每一步都能落成一个动作（跑哪条命令、写哪个文件）。
3. **怎么算做对了** — 可验证的标准，不写「做好了」。
4. **踩过的坑** — 这一条最值钱。别人（和你未来的自己）靠它避开你已经付过的代价。

## 判断写得好的标准

检验办法：**一个没做过这件事的人，只看这份技能，能不能做对？**

- 写「要考虑清楚 XX」＝ 没写。
- 写「先跑 `npm run check`，报错就贴进频道问助理」＝ 写了。

## 踩过的坑

- 把「结论」当技能写下来。技能是「怎么做」，结论属于记忆。
  混淆的后果：技能目录里堆满一次性判断，真正的做法反而找不到了。
- 描述写得太宽（「处理各种问题」），等于没写：提示词里那一行是别人决定「读不读」的唯一依据。
