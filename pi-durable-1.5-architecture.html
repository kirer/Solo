先落盘，再展示

一个 durable agent 运行时：把 Entry + Document + Task + Submission 放进同一次原子提交；进程挂了，从最后一个 checkpoint 继续。 它不靠 prompt 技巧做多 agent，靠的是 ownership 树 + 子会话 + 后台任务。

L2

Session kernel

session/session.ts · transaction.ts · forks.ts

一条 mutation line + 原子提交 + 发布。Entry、Document、Task、Submission 在**同一次 commit** 里落盘；group commit 把并发提交合并成存储批次，deferred commit 把流式进度晚一点存。

SessionImplTxgroup commitdeferred commitpublicationforkcaches
细分 · 原子性是怎么来的
  • Session.commit(change, ctx)一个回调内读表、读文档、写表、写文档；提交前所有写都在内存 staging。
  • Storage.commit(batches)一次调用存多个批次，每批一个 seq；前一批的写入对后一批的检查可见；驱动错误整批回滚。
  • Group commit存储调用在途时到达的提交一起走下一批；碰到前一批写过的 key 才等待；结果按 line 顺序交付。
  • Deferred commit只改 conversation 文档且 history:"latest" 的提交先在内存采纳、立刻给 watch 看，下一次提交或 persistWithinMs（默认 1000ms）才落盘。
  • Tx表：conversations / entries / submissions / tasks；文档：pi.agent / pi.live / pi.inbox / pi.usage / pi.provider / 自定义。
  • Doc 语义scope：session / conversation / task；history：latest / rewindable；fork：current / initial / asOf；checkpointWhen 决定何时写 checkpoint。
durable 边界一次 commit = 一个存储事务

一条不变式

Entry + Document + Task + Submission 在同一次 commit 里。
所以进程被杀之后，打开 storage 就能从最后一个 checkpoint 继续； 不会出现「消息写了、任务没写」的半截状态。

核心数字

  • 3 个内置 task：Generation / Tool / Compaction

从一条输入到一条答案，中间是一个 durable 的 GenerationTask；工具轮次、重试、排队、收尾都在同一个状态机里。

done · 下一轮

移除 pi.live.run；放置队列里的输入；如果有下一条，创建新的 GenerationTask。一次 run 真正结束。

run removedplace queuednext run

失败：runFailure

没答上来时写 pi.live.runFailure：reason + detail + 这次 run 的 inputs / task / first。inputs 结算为 unanswered；afterFailedRun 决定队列是 keep / continue / withdraw。

继续：continue

只在 idle 时接受，不排队。失败 run 留下的队列项会先被放置，再一起加入新 run；上下文停在答案上时返回 nothing_to_answer。

中止：abort

conversation.abort() 撤掉 queued inputs、标记并等待普通 ownership scope 空闲；background:true 能穿过后台边界。run 以 aborted 结束。

崩溃：从 checkpoint 继续

打开时非终态 task 从 checkpoint 恢复；在途模型请求算失败尝试；重试用尽 → interrupted；restartLimit 次 → restart_limit。详见 05。

提交、排队与结算

1.5.0 把「检查忙闲 + 准入」合成一次 admission；冲突直接抛出，不再靠宿主先查后提交。

ADMISSION · QUEUE
Draft / 选项时机结果
input + whenBusy: steer run 正在跑 插进当前 run；空闲时直接启动 run。Solo 的 wake 用的就是这个。
input + whenBusy: followUp run 正在跑 留在 pi.inbox，等当前 run 的 boundary 再放置。
input + whenBusy: reject run 正在跑 抛 ConversationBusy，什么都不写；空闲时正常启动。
input + whenIdle: reject 会话空闲 抛 ConversationIdle，什么都不写——它永远不会自己启动一个 run。和 steer 合起来是一次 admission。
write display-only 直接追加 entry 并结算 done；否则进 inbox，等 boundary。
continue + type: continue 只在 idle 不排队；在现有上下文上启动 run；失败 run 的队列项先放置。busy 时抛 ConversationBusy。
submit(tx, draft) + 事务准入 调用方 commit 内 准入和调用方的写一起提交或一起丢；必须在第一笔表写之前，一次 commit 只能准入一次。
maxTurns + agent 配置 run 的工具轮次 达到上限的那一轮跑完工具后，run 以 turn_limit 结束；continue 可以在结果上继续。

一个 submission 的四个状态

它是表里的一行，不是一个内存 Promise；进程重启后还能等到结算。

SETTLEMENT
queued

已准入，但还没进 transcript；在 pi.inbox 里等 boundary。

placed

已进 transcript，被一个活跃 run 拥有；等待答案。

done

答案已落盘；wait() resolve。afterRun 任务还在跑也不影响这个结算。

unanswered

终态但没答案；带 reason 和可选 detail，可被 continue 接上。

失败之后队列去哪：afterFailedRun

keep      队列留着，等下一次输入或写操作（默认）
continue  自动开始下一轮，把队列项带进去（像 answer 一样）
withdraw  队列项结算为 unanswered，reason = run_failed

注意：continue 是 submission，不是“重试同一个 task”。它在现有上下文上开一轮新 run； 如果上下文停在答案上，只会得到 nothing_to_answer。

崩溃恢复：至少一次，不是恰好一次

Task phase 崩溃后从 checkpoint 重跑；副作用必须幂等，或用 runtime.memo() 去重。工具默认 replay unsafe，崩溃后模型拿到 interrupted 而不是重跑。

RECOVERY · AT-LEAST-ONCE
01 · OPEN

打开 storage

Harness.open 加载所有非终态 task；running 改回 pending，并给它的 restart 计数 +1。close 不算 crash：close 时 task 回到 pending，下次 open 不计 restart。

↓
02 · RESUME

从 checkpoint 继续

每个 task 从最后一个已提交 phase 继续。已经 durable 的副作用不会重放；未完成的工具调用按 replay 策略处理。

↓
03 · RETRY

模型请求在途

宿主死在模型请求上：这次请求记为一次失败尝试，按 retry 策略退避，不会重发同一个请求。deferred poll 也一样，下次 poll 同一个响应。

↓
04 · END

用尽重试 / 重启超限

retry 用尽 → runFailure.reason = interrupted；restartLimit（默认 5）次连续被切断 → restart_limit。内置 task 还会发 task_interrupted 报告（带 reason 与 restarts）。

readOnly viewer

HarnessOptions.readOnly: true 打开成另一个进程的观察者：不恢复运行中的 task，所有写提交抛 ReadOnlySession。

不再 park

1.5.0 删除了 task_parked 和 retryTask()。被切断太多次的 task 直接结束，宿主看 runFailure / task_interrupted。

continue 接管

宿主可以在 idle 时提交 continue，在失败 run 的上下文上再开一轮；队列项先放置。它不是自动重试，什么时候 continue 由宿主决定。

幂等是你的责任

phase 可能重跑。外部副作用（发邮件、扣款、写第三方）要用 runtime.memo() 或自己的幂等键；不要假设“恰好一次”。

1.5.0 改了什么

不是一堆新 API，而是四个方向：提交吞吐、崩溃恢复、run 的可解释性、观察面的收敛。

CHANGELOG · 1.5.0

Group commit

吞吐

Session 不再在存储调用期间占住 line；并发提交合并成下一批，每个 commit 仍有自己的 seq 和结果。碰到前一批写过的 key 才等待。

128 conversations / 4ms storage：~5 → ~440 runs/s；本地 SQLite 约 +30%，纯内存最多 −25% runs/s。

Deferred commit

吞吐

流式 partial 先在内存采纳、立刻给 watch 看；下一次提交或 persistWithinMs（默认 1s）才落盘。崩溃最多丢约 1 秒流式内容。

32 路并行工具：存储事务 5.7× 更少、磁盘写 2.9× 更少；长答案 27× / 9×。

pi.live v3

可解释

run 增加 turns；run 没答上来时保留 runFailure；回答后等待 afterRun 任务时保留 run。idle 判断改成看 run === undefined。

迁移：pi.live v1/v2 → v3；run.turns 补 0。

Submission v2

准入

continue、whenIdle:"reject"、submit(tx,draft)、maxTurns。忙闲检查与准入合成一次，不再有“先查后提交”的竞态。

submit(tx) 在第一笔表写之前，一次 commit 一次准入。

崩溃恢复

恢复

宿主死在模型请求上不再无限重发；记为失败尝试，重试用尽 → interrupted。restart-limited task 不再 park，直接结束并报 task_interrupted。

task_parked / retryTask() 删除；restartLimit 默认 5。

View 收敛

观察

watchEvents() 删除；ConversationView.entries 变成窗口（50/100）；新增 ConversationTranscript 拼接、before、from 窗口。

渲染器渲染状态，不再组装事件流。

Hooks 扩展

扩展

afterRun 返回 durable 的 RunEndTask；beforeProviderRequest 改单次请求 body；afterTool 现在也跑在错误结果与中断结果上。

runEndTask() · HookApi.entries() · 崩溃可恢复。

工具与存储

底座

工具 schema 改用 pi-schema（JSON Schema，默认 closed）；新增 StoreStorage（Chord store 上的 Storage）；readOnly 支持 viewer。

typebox 移除；Memory / SQLite / JSONL / IndexedDB / Store 五种实现。

Solo 站在哪

如果目标是“最大限度依赖 1.5.0”，这四处是收益最大、也最需要验证的接点。

SOLO · INTEGRATION

01 拆掉 serializedHarness

它把同进程所有 harness.commit 串行化，正好抵消 1.5.0 的 group commit。先做一个裸 harness 的并发回归（同文档读改写 + 并发 postMessage），全绿再删；post.ts 自己的闸保护 commit 前的读，不能一起删。

02 把写频道 + 记 wake 做成事务

用 submit(tx, draft) 把「记 wake + 入队」放进同一次提交；每次 commit 只能准入一次，所以按收件人拆提交，靠 group commit 合并存储往返。目标是消掉 rememberWake 与 submit 之间的顺序不变式。

03 用 continue 接管重启续跑

现在 resumeInterrupted 是 note + wake，会多一条用户消息。1.5.0 的 continue 能在失败上下文上直接再开一轮；先处理 nothing_to_answer 和 busy 的兜底，再替换。

04 用 afterRun 做 durable 收尾

把 finishTurn 从宿主回调搬进 afterRun 返回的 RunEndTask：答案落盘后即使进程崩溃，收尾也能恢复；再用 maxTurns 给 run 设上限，配合 continue 续跑。

顺序建议：先拆全局串行（01）拿到吞吐；再做事务准入（02）消掉顺序竞态； 然后才动重启续跑（03）和 durable 收尾（04）。前两步是后两步的地基。
