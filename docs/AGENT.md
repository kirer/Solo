# AGENT：agent 是什么、能做什么、谁说了算

> 这份文档定义「一人公司」的**概念地基**。它不描述现有实现，它描述要实现的东西。
> 现有代码是成长路上的经验，不是约束 —— 冲突时以本文档为准。
>
> 配套阅读：`docs/SYSTEM.md`（现在的系统怎么运转，用于对照）。

---

## 0. 一句话

**公司不是代码，公司是一堆文档。代码只负责读文档、执行动作、把结果写回文档。**

推论：改公司 = 改文档。不必改代码，不必重新部署。
推论：文档写错了，公司就错了 —— 所以文档的**写权**是整个设计的核心，比文档内容更重要。

---

## 1. 一个 agent 是什么

一个 agent = 一个文件夹 + 三份文档。

```
agents/<conversationId>/
├── identity.md    我是谁、我向谁汇报、我负责什么
├── skills/        我会做哪些事（一个技能一个目录，各有 SKILL.md）
│   ├── write-tests/SKILL.md
│   └── review-pr/SKILL.md
└── memory.md      我学到的东西
```

- `identity.md` **由上级创建时写初稿**，之后本人可以改。
- `skills/` 与 `memory.md` **本人完全自主**。
- 三份文档都是给人读的普通 Markdown，不是配置文件，不解析、不校验 schema。

**身份不是字段，是文字。** 没有 `role: "cto"` 这种枚举 —— 有就是一段话说「你是技术负责人，你向 CEO 汇报，你管两个项目」。系统不解析它，只把它放进提示词。

---

## 2. 三层：公共 / 项目 / 个人

三层不是按「重要性」分的，是按**写权和「不一致的代价」**分的。

| 层 | 内容 | 谁能写 | 不一致的代价 |
|---|---|---|---|
| **公司公共** | 组织架构、项目清单、名册、所有人的身份 | 被授权的岗位（见 §5） | 公司散架 |
| **项目** | 这个项目的共识：目标、客户、设计决策、进度 | 项目内所有人 | 项目内理解分裂 |
| **个人** | 我是谁、我的技能、我的记忆 | 只有本人 | 无害，甚至有益 |

**关键区分：公共事实是「渲染出来的」，不是「写下来的」。**

每个 agent 的提示词里都有「你现在的位置」那一段 —— 你有几个下属、你在哪个项目、谁是你的上级。这段**不存进 `identity.md`**，每次请求时从公共数据渲染。理由：组织架构会变，写死的话没人去改旧文档，agent 会按三周前的架构认真工作，而你看不出来它错了。

`identity.md` 只写**不可推导的部分**：你怎么理解自己的职责、你偏好什么工作方式、你被交付的使命。

---

## 3. 能力：拉平

**能力 = 一个能在机器上做某件事的功能**（执行命令、读文件、发 HTTP、查库）。

**所有 agent 拥有同样的能力。** 没有「CTO 能跑测试、CFO 不能」这种事 —— 那不是在管权限，是在制造摩擦。

唯一例外是**确实危险、且没有正当用途**的操作。目前只有一条：不允许启动/停止平台服务（单进程单库，第二个实例会把库抢崩）。这类例外应该极少，每加一条都要写清理由。

**能力不是稀缺资源，也不是激励手段。** 想让某人做某事，写在 `identity.md` 里，不要靠工具的有无。

### 唯一的技术边界

能力是**真代码**（一个函数）。`identity.md` 里写「你可以执行命令」，并不能凭空造出一个执行命令的工具。这条边界绕不过去，也不该绕 —— 让 agent 自己写代码然后执行，等于把机器交出去。

所以：**「能力是否存在」是代码，「用能力做什么」是文档。**

---

## 4. 技能：可积累

**技能 = 一件有步骤、有方法、有判断的事。**（怎么审一个 PR、怎么设计数据库 schema、怎么验收一个前端页面）

技能是**知识资产**，数量无限，这才需要「谁有」。

### 技能长什么样

pi 的 skill 规范：一个目录 + `SKILL.md`，frontmatter 里 `name` + `description`，正文是指令，可带 `scripts/`、`references/`、`assets/`。

```markdown
---
name: write-tests
description: 给现有模块补测试。当任务是「加测试 / 提高覆盖率 / 复现 bug」时使用。
---

先读被测模块的公开接口，再读已有的同类测试保持风格一致。
……
```

`description` 决定**什么时候被加载**：平时只占提示词里的一行，匹配上任务时才读正文。**所以写不好 description 的技能等于不存在。**

### 规则

| 动作 | 个人技能 | 项目 / 公司技能 |
|---|---|---|
| 新建 | 随时，零门槛 | 随时，立刻生效 |
| 修改 | 随时 | 随时，**但每次留一份版本** |
| 删除 | 随时 | **只允许标记废弃**，不真删 |

**没有审批。** 审批会让改进停止 —— 而技能的价值全在被不断改写。一个三个月没被碰过的技能基本就是死的。

**为什么删除更严：** 删除是不可见的损失。没人知道那份技能存在过，所以没人会为它说话。标记废弃保留了「它存在过」这个事实，还能被搜到。

### 公共技能要少而精

技能靠 `description` 抢注意力。五十条描述会让模型开始选错。所以**公共层只放被验证过的**：某个做法在项目里跑通两次以上，才值得从个人层提上来。这是判断标准，不是制度。

### 技能与记忆共用同一套归属

公司 / 项目 / 个人，和 §2 完全同构。否则会出现「我记得这个项目怎么做，但我的技能里没有」这种割裂。

## 5. 记忆：会变聪明

| 层 | 写什么 | 谁写 |
|---|---|---|
| **个人** | 我的经验、我踩过的坑 | 只有本人 |
| **项目** | 这个项目的共识与决策 | 项目内所有人 |
| **公司** | 跨项目、长期有效的东西 | 项目结项时由负责人写入 |

### 一条硬规则

**项目结项 → 负责人必须写一份「这个项目学到了什么」进公司层，然后项目记忆归档。**

没有这一步，公司永远不会变聪明：每个项目都从零摸索，这正是「记忆落盘」最想避免的。这一步不需要新机制，只需要 `project_terminate` 时要求填一段 `lessons`。

### 归档不删除

项目记忆在结项后归档，不删。它是一个真实发生过的事件的记录。

## 6. 层级：文档里的一句话

**层级不是代码里的特权，是 `identity.md` 里的一句话。**

CEO 和 CTO 在「能做什么」上完全一样（§3 拉平）。区别只在：CEO 的 `identity.md` 写「你直接对老板说话，你决定公司做什么」，CTO 的写「你向 CEO 汇报，你管技术」。

### 但有一份公共事实必须唯一

组织架构、谁是谁的上级、名册 —— 这些**不能各说各话**。

如果 CEO 重组了架构，但没人去改已经写好的旧 `identity.md`，agent 会按过期文档行事。**而你看不出来它错了** —— 它很认真地按三周前的架构工作。

所以：

- **公共事实**（组织架构、名册、项目）→ 一份权威来源，**渲染**进每个人的提示词
- **私有身份**（我怎么理解自己）→ 各人自己的 `identity.md`，**写**下来

这两者不能混。混了就是上面那种静默失效。

---

## 7. 通信：频道

agent 之间通过频道消息通信，不是函数调用。

- 频道是**房间**（一份共享的、有序的消息流），不是点对点管道
- `@某人` 是**唤醒**（把消息推到他的下一次请求），不是「指派任务」—— 指派是任务文档
- 私聊 = 两人的房间

平级：任何 agent 都能给任何 agent 发消息。**没有代码级的「不许跨级通信」**，汇报线是 `identity.md` 里的约定。

---

## 8. CEO

CEO 是**唯一直接对老板说话的人**，也是公司里唯一由老板直接驱动的人。

他的职责只有四条：

1. 把老板的意图变成公司的动作
2. 决定做什么、不做什么
3. 拆解、指派、收口
4. 在事情跑偏之前叫停

**他不做具体工作。** 他不写代码、不审 PR、不算账 —— 那是别人的事。

除了这四条，他和其他 agent 没有任何区别。他不是「最高权限」，他是一个位置。

## 9. 仍然没定的问题

按依赖顺序排列。定了一条，后面的跟着定。

1. **新公司开局，CEO 的 `identity.md` 从哪来？** 这是唯一一处「必须由代码产生一份文档」，也是唯一绕不过的引导点。
2. **谁能改公共事实？** CEO 独占，还是管理层各自能改自己那一块？决定「重组公司」这个动作长什么样。
3. **agent 能不能改自己的 `identity.md` 里的「上级是谁」？** 如果能，它能不能把自己写成 CEO？这一条决定 §6 的「公共事实唯一」靠什么保证。
4. **变更什么时候生效？** 下一个请求？正在跑的任务呢？两个 agent 同时读一份正在被写的文档，谁赢？
5. **技能升级的「留版本」具体是什么？** git？文档 revisions？每次改动追加一份历史文件？
6. **项目记忆「项目内所有人可写」的粒度。** 员工能不能改掉负责人写的决策？还是只能追加？

## 10. 与现有实现的关系

本文档是**目标形态**，不是现状。现状见 `docs/SYSTEM.md`。

已知的偏离（未来要拆的）：

- 组织架构硬编码为 7 个岗位枚举，岗位职责写在 `src/company/roles.ts` 的常量里
- 能力按岗位分配（`capabilities.ts` 的目录 + 每人手写的能力名清单）
- 没有 `agents/` 文件夹，身份散在数据库文档里
- 技能不存在（只有 `capabilities.ts` 里的一句话 summary）
- 记忆有三层但没有归档与结项总结的动作
