## Q2 组织图 vs 频道首页（明确结论）

**数据比我以为的更全，我这条反驳得更难成立。** `src/server/org-view.ts` 的 `ActorView` 逐行（`sed -n '18,42p'`）：

| 行 | 字段 | 含义 |
|---|---|---|
| `src/server/org-view.ts:22` | `export type NodeStatus = "busy" \| "waiting" \| "error" \| "idle"` | 四态 |
| `src/server/org-view.ts:30` | `status: NodeStatus` | 谁正在忙 |
| `src/server/org-view.ts:32` | `awaitingYou: number`（注释「等你拍板的条数」） | **待办已经画在节点上了** |
| `src/server/org-view.ts:33` | `activity: string`（注释「最近在做什么（一句话）」） | 忙什么 |
| `src/server/org-view.ts:36` | `tokens: number` | 成本 |

也就是说：**组织图不只有「谁忙」，连「等你拍板几条」和「最近在做什么」都已经算好下发了。** 我首轮「组织图缺乏动态信息」的论据被自己查证推翻了——它不缺。

**但我撤回那条让步。** 理由不是缺数据，是**首页要回答的问题不同**：

- 组织图回答「**谁是谁的下属**」——这是**结构**，一次学会、几乎不变。
- 频道回答「**刚才发生了什么、要不要我动手**」——这是**事件**，每次都变。
- 老板打开界面的第一诉求是后者。组织图能告诉你「谁忙、等你拍几条」，但**给不出「说了什么」**——`activity` 是一句话摘要，不是原文；而你拍板前一定要看原文（频道 `MessageView`）。**摘要 + 跳转的路径比直接读原文长一步，且那一步每次都要走。**
- 更致命的一点：组织图是**瞬时快照**。公司多数时刻大量 agent 处于 `idle`/`waiting`，此时首页就是一张**几乎全灰的树**，信息价值≈0；而频道视图在任何时刻都有内容。
- 再者，把「忙」画到节点上，等于**把事件流塞进静态结构图**，每来一条消息都要重排/重绘整棵树——用最贵的视图承载最频繁的更新，方向就是反的。
- 还有一个可核的成本事实：组织图是**拓扑布局**，节点位置随层级/人数变化，重绘要重算坐标；频道列表是**线性列表**，重绘只是重排 DOM。同一频率下两者的代价不在一个量级。

**结论（不和稀泥）：组织图不该当首页。我撤回首轮「能承载变化就有资格当首页」这条让步——资格成立（数据齐全，`src/server/org-view.ts:30/32/33`），我依然不同意它当首页。** 组织图改为第二标签页：它是「我要找谁」时的查询工具，不是「现在怎么了」的默认视图。`ui/js/app.js:363`（`let stored = "org"`）、`:365`（`?? "org"`）、`:367`（catch 里 `"org"`）三处默认值都要改成频道；`stored` 保留用户显式选择即可。

## Q5 回答

**让我觉得「我原来太保守了」的一条：C 席的轮次窗口合并。** 134 条 → 0.5min 窗口 77 / 1min 58 / 2min 40 / 5min 17。也就是说**一个参数级改动（5 分钟合并窗口）就能把 134 次唤醒砍到 17 次（-87%）**，比我那套「删文件、删接口、删 mock」的清单值钱得多，而且不删一行代码。我首轮只敢在「删代码」上使劲，没敢主张「同一个改动覆盖 87% 场景」——这是保守。

**我认为别人明显错了（事实/推断错）的一条：C 席把「老板 -273 次」定性为「纯浪费」，证据是「老板在 `proj:system` 一条消息都没发过（`from=0` 计数 0）」。** 这是**把「不发言」等同于「不消费」**，推断不成立：
- `from=0` 只测了**出站**，没测**入站**。老板的用途是**监督**，监督者天然不发言。
- 系统自己就假设老板是消费者：`src/server/channels-view.ts:205` 专门写 `viewer===OWNER_ID ? await ownerPendingForChannel(...) : []`，给老板单独下发待办（`:229` 进视图）。如果老板不消费，这段是死代码。
- 正确表述应是：**那 273 次「唤醒」不值得为它做面板**（老板读消息靠打开看，不靠被叫醒），而不是「那 273 次投递是浪费」。前者是产品判断，后者是关于老板行为的、没有证据的事实断言。差别在于：按 C 席的说法，可以顺手把老板从 `proj:system` 的投递名单里删掉；按正确说法，老板仍应在名单里，只是不该触发 LLM 唤醒——**显式 `to[]` 恰好就是这个语义**，而 C 席的措辞会把路由修成「老板收不到项目群」，那是另一种事故。
