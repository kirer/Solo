# 架构决策记录（ADR）

记录**不可轻易更改**的工程约定。要改一条，追加新条目说明为什么，不要直接改旧条目。

> 这些决策只对当前代码（`src/core/` + `ui/web/`）成立。第一代核心（`src/company` +
> `src/domain` + `src/server` + `src/tui`）连同它那 41 条 ADR 一起在 V2 删除了 ——
> 当时的推理仍在 git 历史里（`main` 分支）。

## ADR-001：底层运行时库只允许在 `src/core/runtime` 内导入

**状态**：生效

**背景**：`@earendil-works/pi-durable` 标注 experimental，1.1 → 1.4 每个 minor 都带破坏性
变更（删过 `TaskRuntime.sleep()`、改过 `Storage.commit()` 签名、把
`ToolExecutionResult.content` 改成 `output`、把 `checkpointWhen` 改成必填）。

**决策**：只有 `src/core/runtime/` 可以 import `@earendil-works/pi-durable` /
`pi-ai` / `chord`。其余所有代码通过它暴露的接口使用。

**执行**：`npm run check:boundaries`（已并入 `npm run check`）静态检查，违规即失败。

**理由**：升级时改动集中在一个目录。这是应对 experimental 依赖的唯一可扩展做法。

## ADR-003：组织是文件，不是代码

**状态**：生效

**背景**：第一代把组织写进代码 —— 七个管理层岗位是枚举、每个岗位的提示词是模板字符串、
能力是工具名数组、待办/任务/成本/升级链各有自己的文档。改一个岗位要改代码，改一句提示词
要重新部署。

**决策**：一个人 = `agents/<slug>/` 一个文件夹，里面只有 `identity.md`（必需）、
`memory.md`、`skills/`。没有岗位枚举，没有第五个 YAML 字段。组织架构是把所有人的
`manager` 连起来得到的树，断链/成环都只是「这条线断了」，不崩。

**理由**：改组织应当和改一个句子一样便宜。而且「谁是技术负责人」是**某个人写下的判断**，
不是代码常量 —— 让它可以被组织自己改写，组织才能演化。

## ADR-004：公共事实是渲染出来的，不是写下来的

**状态**：生效

**背景**：第一代把组织架构存进每个 agent 的身份文档。CEO 重组架构后没人去改旧文档，
agent 会按三周前的架构认真工作，**而你看不出来它错了** —— 这是最贵的一类失效：静默、
持续、看起来正常。

**决策**：

- **公共事实**（组织架构、项目成员、名册）→ 一份权威来源，每次请求**渲染**进提示词。
- **私有身份**（我怎么理解自己的职责、我的工作方式）→ 各人自己的 `identity.md`，
  **写**下来。

`renderAgentPrompt()` 的「你在组织里的位置」一段全部由 `identity.md` 的 `manager` 与
`project` 现场推导，一个字都不存进身份文档。

## ADR-005：提示词必须确定性，否则打穿 prompt cache

**状态**：生效

**决策**：`renderAgentPrompt()` 同输入必逐字节同输出。不许注入时间戳、不许用
`Object.keys()` 的顺序碰运气、排序规则写死（人按 slug 排序、技能按名字排序）。

**理由**：cacheRead 比普通输入便宜一个数量级，cacheWrite 更贵。一段会抖的提示词会让
每次请求都全额付费；而且抖动往往不可见（少一个空格也算）。

## ADR-006：能力拉平，不分层

**状态**：生效

**背景**：第一代按岗位发工具包 —— 「员工不能越级」靠少给工具实现，「管理层」有
`delegate_to_role` 而员工没有。结果是同一件事在两处实现，纪律靠工具缺失来保证。

**决策**：工具只有一套，人人都有。`registeredTools(registry)` 从注册表实拍，
**不读任何清单文件**。「你能做什么」写进 `identity.md` 的正文与技能里。

**代价**：`bash` 这类能力一旦装上就是人人可用（含读写别人的记忆）。这是**已知且被接受**
的 —— 隔离靠目录归谁的约定，不靠沙箱。

---

## ADR-007：能力是代码，技能是文档

**状态**：生效

**决策**：

- 一个**能力**（tool）= 一个 TS 函数，注册在 `src/core/channel/tools.ts`。
- 一门**技能** = `skills/<名字>/SKILL.md`，正文是 markdown。

想教 agent「怎么做一件事」，写技能，不要写工具。只有「需要机器真的动手」（发消息、写
文件、跑命令）才配一个工具。

**理由**：能力是**编译期**的东西，技能是**运行期**的东西。落地一道工序应该不重启进程。
`identity.md` 里写「你可以执行命令」造不出工具 —— 让 agent 自己写代码然后执行，等于把
机器交出去。

---

## ADR-008：每条消息只有一条投递路径，且发送方不等回复

**状态**：生效

**背景**：第一代为长跑攒了一整套投递设施：回执、看门狗、重投、同步派活 + 异步派活两条
路径、`whenBusy` 的多档语义。其中「投递成功 ≠ 已读」那条（ADR-034）是对的，但为了它
写的 400 行回执机器大半没被读过。

**决策**：`deliver()` 是唯一的跨 agent 原语。它 `submit` 一次 `input` 事件，
`whenBusy: "steer"`，**不等待回复**。发送方拿到的是 `{delivered, failed, skipped}`，
不是对方的答案。要答案就 `say`（带 `mention`）然后等对方在下一条消息里说。

**代价**：没有「确认对方读到了」。实测依据：468 条 `done` 的提交里只有 11 条回执带了
`deliveredTo` —— 那套机器基本没被用上。

## ADR-009：唤醒是在频道里点名，不是派任务

**状态**：生效

**决策**：`recipientsOf()` 四条规则 —— ①显式 `@` 且是频道成员；②老大发言且没 `@` 任何人
→ 第一个非老大成员；③`wakeOnAll` 成员；④减去发件人自己。

**引用回复等于 @ 作者**（`appendMessage` 里把被引用者并进 mentions，自己除外）。

**理由**：「@」是**唤醒**（把消息推到他的下一次请求），不是「指派任务」。私聊 = 两人的
房间。没被唤醒的人不会错过 —— 下次因任何原因醒来时，输入前缀带未读摘要。

## ADR-010：频道集中存储，一条消息只存一份

**状态**：生效

**决策**：一个 session 级文档（`core.channels`）装全部频道。一条公司群消息只存一份，
而不是往 15 个会话里各写一份。

**性能坑（实测）**：`tx.doc()` 返回可写 overlay，按**路径**生成 delta。最初用「清空所有
键 + `Object.assign` 整个 state」写回，导致每追加一条消息都把整个文档（21 频道、几百条
消息、130KB）当一次 delta 写盘。改为只赋值 `doc.messages[id]` 后，delta 只含那个频道。

**注意**：`tx.doc()` 读到的是**副本**。对取回的数组 `push()` 不产生任何 op ——
必须整体替换那个键（`doc.messages[id] = [...list, message]`）。踩过一次，症状是消息写进去
了又没了。

## ADR-011：`dm:` 频道统一为一类

**状态**：取代旧版（`personal` / `direct` 分两类）

**决策**：所有 `dm:` 频道统一为一类。个人频道（`dm:owner-<slug>`）= 与老大的私聊，
也是工作台：执行记录落在这里，老大插话就是在找他对话。不需要区分「个人频道」和
「私聊」—— 收件人规则、未读、渲染完全一样。

## ADR-012：项目负责人是 `README.md` 的字段，频道成员是它的投影

**状态**：生效

**决策**：负责人的真相在 `projects/<slug>/README.md` 的 `owner`。项目频道的成员是这份
文档的投影（老大 + 负责人 + 所有 `project:` 指向它的人）。改负责人 → 立刻重投影。

**理由**：如果项目频道自己存一份成员表，它就会与项目文档漂 —— 漂了之后员工在项目频道
里 @ 不到刚任命的负责人，而没人知道为什么。

## ADR-013：记忆沉淀用单游标，问完即推进

**状态**：取代 ADR-013 旧版（双游标 + 定时补漏）

**背景**：旧版用两个游标（`awaiting` + `cursors`）+ 5 分钟定时补漏。问题：
①定时器删了之后 `awaiting` 的「别重复打扰」功能反而成了「永远不推进」——
负责人说「没有」时游标不动，下次再问一遍，体验差。②双游标逻辑复杂，维护成本高。

**决策**：单游标 `cursors[项目]` = 已处理到第几条 seq。`settleProject` 问完
一批后即推进到这批最后一条的 seq —— 不等 `remember(scope=project)` 落盘。负责人
说「没有需要沉淀的」也算处理过，不会重复打扰。`remember(scope=project)` 落盘后
`confirmedBy()` 做兜底推进。

**代价**：负责人没回话时这批 decision 不会被重复问。但消息仍在频道里，负责人
下次醒来读项目频道能看到未读 —— 信息不丢，只是不会自动再催一遍。

## ADR-014：形状用代码判，语义用模型判

**状态**：生效

**决策**：

- 代码只判**形状**：这条消息落在 `proj:<slug>` 频道、`kind` 是 `decision` / `report`、
  是否已读、谁能收到。
- 语义（「这句话是不是真的结论」「值不值得写进项目记忆」）交给模型：`settle` 把候选
  发过去，写不写、写什么由它决定。

**理由**：代码判得准形状，判不准语义。第一代写过一个自动摘要器 —— 它最终变成一堆
正则和阈值，然后在语义边界上错得毫无规律。

## ADR-015：唤醒记录必须在 `submit` **之前**落盘

**状态**：生效

**背景**：`deliver()` 在投递成功后记下「他是在哪个频道被叫的」。实测发现老大在公司频道
问话，对方在**个人频道**回答。

**根因两处**：①`ownerSpeak`（老大说话那条路径）漏传了 `rememberWake`；②记 wake 的时机在
`submit` **之后** —— 提交一入队对方就可能已经跑起来，此刻 wake 还没落盘。

**决策**：wake 先写，再 `submit`。任何新增的「发起对话」路径都必须走同一个记录点。

**推论**：不经过 `deliver()` 发起的对话拿不到唤醒频道 —— 例如自动沉淀那条「叫负责人来写
记忆」。此时它会回到**上一个**叫它的频道说话。实测出现过：沉淀的要求发给负责人，它把结论
说进了公司频道，因为那条路径没走 `deliver`。所以这类提示必须**在正文里点名回答的频道**，
不能指望模型猜。`renderSettlePrompt()` 因此带一行「回话发生在项目频道 `proj:<slug>` 里」。

**回归测试**：`test/core/shell-e2e.test.ts` 的「老大在哪个频道叫醒某人，就记下那个频道」。

## ADR-016：界面只画后端真的有的东西

**状态**：生效

**决策**：没有待办就不画待办卡，没有 trace 就不留占位块。宁可空着。

**理由**：第一代为了填满布局画了一堆恒空的块 —— 看的人分不清是「没有」还是「坏了」。
第一代的 `ViewOrg` 带 `projects` / `pending` / `costs` / `links` / `ceoQueue` 五个字段，
**一个消费者都没有**。

**推论**：`src/core/shell/view.ts` 的每个字段都必须有前端消费者。`check-boundaries.mjs`
的第三条规则就是据此写的：`serve.ts` 的每条路由都要在 `ui/web/js` 里被请求到，唯一的
白名单是 `/api/org`（Docker 健康检查用）。

## ADR-017：一个区域整体替换，不做增量 patch

**状态**：生效

**决策**：渲染用 `replaceChildren(fragment)`，不维护 diff。

**理由**：一个频道几百条消息时这比 diff 更快，也更难写错。第一代的增量渲染是「消息不停
往上跳」「已读点错位」这些 bug 的共同来源。

**配套**：`[hidden]` 必须真的藏住（`ui/web/css/app.css` 里有 `display: none !important`）
—— 类选择器里的 `display: flex` 会顶掉浏览器默认的 `[hidden]`。

## ADR-018：界面数据只走一个快照流

**状态**：生效

**决策**：组织快照由 `/api/stream/org`（SSE）推送，老大的操作走普通 POST。**不做细粒度
增量补丁，不轮询。**

**理由**：每帧都是完整快照，前端不需要维护 diff 逻辑，也不会因为丢帧状态错乱。组织规模
是一位老大 + 十几个 agent，全量快照只有几十 KB。帧率由提交频率决定 —— 空闲时零流量。

**实现细节**：任何文档提交都会触发一次推送，但**去抖 120ms**（一次提交可能连带几次改动），
空闲时每 15s 一个 `: ping` 心跳。浏览器断线重连靠 `EventSource` 自带机制（服务端给
`retry: 1500`）。

## ADR-019：标识生成必须支持 Unicode

**状态**：生效

**背景**：第一代 CTO 给员工派活全部失败，报 `无法从"林越"生成标识片段` —— `slug()` 只允许
ASCII，把中文名过滤成空串后抛错。而模型自发给员工起中文名（体验更好），这是常态。

**决策**：`slugify()` 字符集为 `\p{L}\p{N}`（含中文），只过滤真正危险的符号；重名加 `-2`。

**注意区分**：内部标识可以用 Unicode；**落到文件系统的路径**必须经 `slugify`（它会把
`/`、`..` 之类的字符过滤掉）。

## ADR-020：生产模型清单不能含测试模型

**状态**：生效

**背景**：第一代 CHRO 给员工选模型时选中了 `faux-1`（测试假模型，因为它「零成本」），
导致员工运行报 `no_model`。

**决策**：生产清单由 `setupModels()` 提供；测试清单由测试自己造，两者不混。

**教训**：任何「看起来更省钱」的默认值都会被模型优先选中。

## ADR-021：模型引用按**第一个**斜杠拆

**状态**：生效

**背景**：2026-10-27，整个公司发不出话，所有 `pi.generation` 任务失败于
`Model commandcode/auto/deepseek-v4.1-flash is not available`。三个因叠在一起：

1. 设置里的「内置模型覆盖项」被当成纯自定义模型又追加一遍 → catalog 里同 id 两条 →
   `resolveModelOption` 判 `ambiguous` → 默认模型回落成 `no_model`；
2. 覆盖项改了名，与内置 id 对不上；
3. 所有会话持久化的 `model` 是旧 id。

**决策**：

- `resolveModelOption()` 按 **`indexOf("/")`** 拆成 `provider/modelId` —— 不能用
  `lastIndexOf`，因为 `modelId` 自身含斜杠（`auto/deepseek-v4.1-flash`）。
- 同 id 多条时**宁可报 `ambiguous` 也不猜**，但代码不能造出同 id 两条。
- 内置模型的「覆盖 / 改名 / 删除」机制整个拆掉 —— 它只服务于已删除的设置页，
  而它正是上述事故的成因机器。

## ADR-022：删除文件前必须校验路径

**状态**：生效

**背景**：项目删除要做 `rm -rf`，目标路径来自持久化数据。踩到过：库是旧的、路径指向
别处，于是删掉了另一个目录。

**决策**：任何来自持久化数据的路径进入 `rm -rf` 之前重新校验 —— 解析后的绝对路径必须
落在预期的根目录之下，且最后一段必须等于预期标识。任一不通过就不删文件并明确报告。

**教训**：不能信任写入时的正确性。

## ADR-023：能删的都删

**状态**：生效

**决策**：没有消费者的文件、导出、路由、CSS 规则、配置项，一律删掉，不「留着以后可能
有用」。

**理由**：留着的死代码会骗人 —— 下一个人会以为「这里有业务概念」，然后照着它写新代码。
第一代攒了 `tasks` / `pending` / `costs` / `links` / `ceoQueue` 这类从没人读的字段，
以及 1952 行的 `ui/js/channels.js`。

**执行**：`check-boundaries.mjs` 的「每条路由都要有前端消费者」就是这条的机械化。

## ADR-024：项目频道含统筹链；老大只与知言私聊，公司频道预留

**状态**：生效

**背景**：第一版项目频道的成员 = 老大 + 负责人 + 所有 `project:` 指向它的人。问题：
① 负责人的上级（知言，统筹者）不在项目频道里，于是「知言在项目频道给负责人派活、负责人
向知言汇报」落不下，统筹者只能绕到别处；② 老大一开始误在公司频道下达任务，而公司频道的
语义是「预留、暂不承载任务消息」。

**决策**：

1. 项目频道成员 = 老大 + 项目负责人 + 负责人的整条汇报线（向上到老大，含统筹者）+ 所有
   `project:` 指向它的人。`syncProjectChannel`（`src/core/shell/assemble.ts`）按事实重算后
   **整体替换**成员表，不用「只加不删」——否则改名/重建后旧 slug 残留在成员表里，界面上
   显示成一个连不上会话的幽灵成员（`gunanyan` 踩过）。
2. 老大下达任务、知言回复老大，一律走**与知言的私聊**（`dm:owner-知言`），不进公司频道。
   公司频道（#公司）预留，目前不应有任何任务/汇报消息。这条规矩写进知言的 `identity.md`
   与 `立项` 技能，下一条消息就生效（不改代码）。
3. 项目里的日常协作（派活、汇报、验收）发生在**项目频道**：知言作为负责人的上级也在项目
   频道里；只有「知言定不了、需要老大拍板或交付给老大」才回到与老大的私聊。

**理由**：组织是文件，不是代码（ADR-003）。「谁和谁在项目频道协作」该由事实（负责人 +
它的汇报线 + 项目成员）推出，而不是写死；「老大↔知言走私聊」是沟通纪律，写进身份与技能
即可，不需要新工具或新字段。

**与 ADR-012 的关系**：沿用「项目负责人是 `README.md` 的 `owner`、频道成员是它的投影」
这一条，只是把投影扩到「负责人的整条汇报线」，并明确成员表用精确重算替换而非累加。

## ADR-025：启动时把强杀留下的半截任务树一次结算，不尝试恢复

**状态**：生效

**背景**：`Harness.open` 会加载所有非终态任务并尝试恢复。进程被 `kill -9` 时，一棵任务树
可能停在半截（父任务 `waiting`、子任务 `running`、还有 `placed` 的输入 submission）。恢复
时调度器重放这些任务，但它们背后的模型/工具调用已随进程消失，于是抛
`Task N invocation has ended`；这是异步未处理拒绝，直接崩进程，且库一直脏，下次照样崩。

**决策**：`openCore` 在 `Harness.open` 之后、`assembleCore` 之前调用
`reconcileZombieTasks()`：

1. **一次 commit** 把所有非终态任务结算成 `terminal`
   （`outcome: {status:"orphaned", reason:"restart"}`）。必须一次做完：只结算父任务会被
   级联把子任务改回 `pending`，仍然重放、仍然崩。terminal 状态要剥掉 `checkpoint`/`memos`。
2. 未结输入：`queued` 用 `abortSubmission` 撤销（连 inbox 项一起清）；`placed` 的 entry
   已在会话里、却没有活着的任务会回答它，就地 `settleSubmission` 为
   `unanswered`/`restart`，否则每次启动都会重复出现。
3. 自愈失败只打日志，不挡启动。

**理由**：强杀后的半截调用**无法**恢复——恢复需要重放一个已经不存在的模型/工具调用。
把它结算成 orphaned 是唯一符合持久化语义的终态。走 Harness 自己的 `commit`/`settleSubmission`，
与调度器共用连接和事务，避免外部 SQLite 连接被页缓存覆盖的竞态（实测旧方案无效）。

**代价**：强杀时正在跑的一轮工作会丢失，需要重新发起。这比进程起不来好。

## ADR-026：会话记录投影必须用 BACKGROUND_CONTEXT，不能用提交回调带来的任务上下文

**状态**：生效

**背景**：`startTranscriptSink()` 用 `harness.subscribeCommits()` 把 `pi.assistant` 条目投影进
个人频道。提交回调的第二个参数是**刚写完这次提交的那个任务的 context**。任务一结束，
调度器就会 abort 它，于是投影里紧接着的读游标/写消息会抛
`Task N invocation has ended`。这个监听是 fire-and-forget（`void sink(...)`），异常成为
**未处理的 Promise 拒绝**，直接崩进程；而且最后一条 assistant 文案（往往正是给老大的
交付结论）永远投影不进去 —— 症状就是「个人频道只有工具调用，没有最后那句话」。

**决策**：

1. 投影订阅一律在 `BACKGROUND_CONTEXT` 里跑，并给 `void` 的 Promise 加 `.catch` 打日志。
2. `projectEntry` 投影正文前做一次「刚说过」去重：同一人、同一频道、5 分钟内，正文相同
   或带同一个链接，就跳过这条 `say` 投影（思考与工具卡片照常显示）。
3. `hire` 的 `manager` 必须是名册里已有的 slug（含 `owner`），否则拒绝并列出可选值；
   不传仍是「你自己」。防止模型把「知言」写成 `zhiyan`，把整条汇报线弄断。

**理由**：投影是机械投影，不该继承任何一次具体任务的取消信号；「说过的话不再投影」是
显示层去重，不是业务规则。上级 slug 写错是事实错误，工具拒收比事后修组织图便宜。

## ADR-027：往频道里加一条消息必须是「单元素追加」，且频道文档必须定期压基线

**状态**：生效

**背景**：线上库 `core.sqlite` 长到 64 MB，其中 `core.channels` 一个文档的增量历史占
60.7 MB（971 条 delta），而它当时的真实状态只有 0.7 MB —— **85 倍放大，且随消息数平方增长**。

根因不是「存了什么」，是「怎么写下去的」。文档层用增量描述变化，而
`state.messages[id] = [...历史, 新消息]` 在它看来是**替换整个数组**，于是一条 300 字的
消息要重写该频道的全部历史。实测对比（`test/core/channel-write.test.ts`）：

| 写法 | 40 条消息累计 |
|---|---|
| 整值替换 `[...list, msg]` | 223,762 字节 |
| 原地 `list.push(msg)` | 约 4 万字节（≈ 消息本身） |

**决策**：

1. 写消息只走 `postMessage()`，它拿 `doc.messages[id]` 这个**文档代理给出的数组**直接
   `push` 一个元素。`appendMessage()` 返回的新 state 只用来算，不写回文档。
2. `push` 必须作用在代理对象上。`doc.messages[id] ??= []` 之后再 push 本地变量不算数 ——
   那不是代理，提交时不会产生任何 op，消息静默消失。
3. `ChannelDoc.checkpointWhen` 除了「单频道 ≥ 256 条」之外，**必须**在
   `info.deltasSinceBase >= 64` 时也压基线。
4. 不许把大块文本塞进单条消息：`run` 的输出落进频道前剪到约 3,000 字（头 1/4 + 尾 3/4），
   回给模型的剪到 8,000 字。

**理由**：这个文档是 `scope: "session"`，存储层写基线时会把该文档的旧 revision 全删
（`isCurrentOnly` 为真）。也就是说**压基线是这里唯一的回收机制** —— 不压，历史只增不减。
早先只按「消息条数 ≥ 256」判断，而实际最多 189 条，所以一次都没触发，库里只有一条
70 字节的初始基线，其余全是增量。

**代价**：压基线时把整份状态写一次（0.7 MB 纪律内），换来确定的空间上限与 O(1) 重放。

**注意**：这条决定的是「写下去多大」，不是「存几份」。过程记录仍然是双份（见 ADR-028）。

## ADR-028：会话记录投影必须**落库**，不做读时拼接

**状态**：生效

**背景**：曾经考虑过让个人频道的 think/tool 卡片在读接口里临时拼接（`entries` 里已经有
内容，为什么还要在频道里存一份？）。

**决策**：投影结果照旧写成频道消息。

**理由**：会话条目**没有时间戳**——存储层的 `entries` 表只有 `id`、`conversation_id`、
`head`、`commit_seq`、`record`，`EntryRecord` 类型里也没有 `at`。读时拼接无法回答
「这句思考插在哪两条消息之间」，只能把一整轮的过程堆在时间线末尾。落地时刻就是它发生
过的时刻，这是唯一的排序依据。

**代价**：同一条思考在 `entries`（模型当初看到/说过什么，续跑要用）与频道消息（老大什么
时候看到的，时间线要用）各存一份。两份都只按条数线性增长，且各自回答不同的问题。

## ADR-029：`write_file` / `read_file` 的路径围栏与静态服务保持一致

**状态**：生效

**背景**：`tools.ts` 早先直接 `join(workspaceRoot, path)`，`../../agents/别人/identity.md`
可以读写任何人的文件夹；而静态文件服务那边是有越界判断的。同一个仓库两套规则。

**决策**：工具侧也拦：`resolveInWorkspace()` 解析后必须落在工作区根之内，否则返回
「路径在工作区之外」，不抛异常。

**理由**：agent 有 `run`（shell），恶意拦不住 —— 这里拦的是**写错**。路径穿越几乎总是
「它对层级搞错了」，静默写到别人文件夹里比报错难查得多。两处规则一致，读代码的人也不用
猜「这里到底拦不拦」。

## ADR-030：`scanTasks` 必须翻页，一次启动自愈要看完整状态集

**状态**：生效

**背景**：`reconcileZombieTasks()` 早先对每个非终态状态只调用一次
`tx.scanTasks({ status }, 256, undefined)`，只要第一页。

**决策**：`while` 循环跟随 `page.next`，直到拿完该状态的全部任务。

**理由**：僵尸任务超过 256 条时，剩下的一次都清不掉 —— 每次启动都要重建现场、再崩一次。

## ADR-031：项目频道的 `wakeOnAll` 是负责人，因为「汇报」不 @ 人

**状态**：生效

**背景**：实测发现 agent 会调 `run` 执行 `sleep 120; echo waited`，然后去读频道 —— 用
shell 睡眠假装「等一会儿」。查它的思考记录，原话是：*"I can't sleep... I can run sleep
command. Let's wait ~120s then read channel."*

**根因**：项目频道的 `wakeOnAll` 是空的。员工做完说「✅ 做完了」时通常不 @ 上级，于是
**负责人永远收不到**，只能主动轮询。系统里没有定时器、没有「稍后再看」，它就拿 `run` 当闹钟。

**决策**：项目频道的 `wakeOnAll` = 该项目的负责人（没有负责人就是空）。成员表与唤醒表
统一由 `syncProjectChannel()` 按事实整体重算。

**理由**：项目频道只为这一个项目存在，负责人本来就要看见全部进展。这不是「多叫醒几个人」
的取舍，而是**唯一能让「汇报」这件事成立的接法**。老大不加进去：老大看的是未读，不需要
每条项目消息都起一轮会话。

**配套**：技能「工作规矩」里写清「派完活就收手，别用 `run sleep` 轮询」。

**回归测试**：`test/core/assemble.test.ts` 的「项目频道里谁说话都叫醒负责人」。

## ADR-032：打断式的投递要在正文里说明「这是插话，不是新任务」

**状态**：生效

**背景**：沈舟正在给游戏加音效，老大私聊问了一句「你是谁啊」。它答完就收工了 ——
音效改完了，但从没回项目频道汇报，协作链上看这个活凭空消失。（`whenBusy: "steer"`
会把插话并进当前这一轮，模型答完这一轮就结束了。）

**决策**：`deliver()` 先用 `harness.inspect()` 取「此刻手上有活（非后台任务）的会话」，
命中就在投递正文末尾加一句「这是插话，不是新任务：答完这一句就回到你手上的活，别停」。

**理由**：这是**时机**问题，不是纪律问题。写在技能里，模型在被打断那一刻不一定想得起来；
写在正文里，它就在被打断的那一句旁边。取不到「谁在忙」时当作没人忙 —— 宁可少一句话，
不能让投递整体失败。

**配套**：技能「工作规矩」里另有两节「做完要汇报」「别人插话的时候」。

**回归测试**：`test/core/deliver.test.ts` 的「插话要明说『不是新任务』」。

## ADR-033：沉淀不按 `kind` 筛，且「确认后才推进游标」

**状态**：取代 ADR-013 的推进时机、ADR-014 里「按 `kind` 判形状」那一条

**背景**：两件事都是实测出来的：

1. `settleCandidates` 只认 `kind ∈ {decision, report}`，于是项目频道里大量**普通发言里的
   结论**（老大顺口拍的板、讨论中定下的做法）永远不会进项目记忆 —— 沉淀覆盖率取决于
   agent 记得不记得给消息打标签。
2. `settleProject` 问完就 `advanceCursor`。负责人被别的事打断、或者写砸了，这批消息
   **永久不再被看**：游标已经越过它们了。

**决策**：

- `settleCandidates()` 只保留两条形状判据：`seq > since`、且不是**要去整理的那个人**自己
  说的（`exclude` 参数）。不看 `kind`。
- 问完只记一笔 `waiting[项目] = { seq, stamp }`（`stamp` = 提问那一刻项目记忆文件的 mtime），
  **不推进游标**。下次沉淀检查时：记忆文件变了 → 游标推进到 `waiting.seq`；没变 → 既不催
  也不推进。`remember(scope=project)` 落盘后 `confirmedBy()` 仍然兜底推进。
- 「什么该记什么不该记」的规则从 `renderSettlePrompt` 里搬到公司技能「记忆整理」，
  提示词只说「按那份技能整理这批消息，写进 `projects/<slug>/memory.md`」。

**理由**：`kind` 是「被打过标签」的形状，不是「值得记」的形状 —— 后者只有模型判得准，
而模型的判断规则属于**可迭代的文档**，不属于 TypeScript 字符串。游标是「处理过」的账本，
问过 ≠ 处理过；确认信号用文件 mtime 是因为 `conversation.submit()` 投递即忘（CONCESSIONS C-001），
没有回合结束钩子可以等。

**代价**：多一次 `stat`（每轮一条项目消息检查一次文件印章）；负责人一直不写记忆时，那批
消息会一直挂在 `waiting` 里、不再重复催，直到下一条项目消息把它重新捞起来。

**回归测试**：`test/core/settle.test.ts`（不按 `kind` 筛、排除自己）、`test/core/settle-e2e.test.ts`
的「消息落地后只记『问过』，游标等记忆真写进去才推进」。

## ADR-034：记忆留痕只记 before/after 全文，密钥在渲染出口统一脱敏

**背景**：`memory.md` 是「当前态、只追加」，改得动是它的优点，但改了没痕迹是缺点 ——
agent 把错的判断写进去之后，现场只剩一坨文本，人只能肉眼找。另一头，agent 手里有
`remember` / `write_file`，而 `identity.md` / 技能 / 记忆**每一轮**都会被渲染进 system 段，
一把 key 写进去就是永久、每轮都发给模型的泄露，且没人会想到去那里查。

**决策**：

- `agents/<slug>/.memory-journal.jsonl`，一行一条 `{at, by, op, before, after}`。存**整篇全文**
  而不是 diff：记忆有硬上限（一条 300 字、目录预算 4000 字），几 KB 的代价换掉自己算行、
  自己修的代码。写失败只 `console.warn` —— 日志是旁证，不能拖垮主写入。
- 三条底线写在 `memory.ts` 里而不是提示词里：一条 ≤300 字、重复不写、像密钥的内容拒收。
  这三件模型判断不了（它不觉得自己在泄密，也不知道目录预算有多紧）。
- 密钥放 `<workspace>/.secrets.json`（扁平 `{NAME: value}`，只认 ≥8 字符的值）。**只在渲染出口**
  脱敏一次，不给 agent `request_secret`、不做 `$SECRET_x` 引用替换、不做 UI —— 目标不是
  「让密钥参与工作」，是「密钥根本不参与对话」。另在 `remember` / `write_file` 落盘前也脱一次，
  免得密钥污染文件本身。

**理由**：出口只有一处，逐处检查不可能不漏。反过来，若在提示词各处逐个字段脱敏，
新增一个字段就会漏一条路 —— 而这条路的代价是不可逆的。

**代价**：每次渲染提示词多一次 `stat`（按 workspace 缓存 mtime+size，文件变了才重解析）；
`.memory-journal.jsonl` 会随记忆写入增长，需要人偶尔看一眼（暂时不做轮转）。

**回归测试**：`test/core/journal.test.ts`、`test/core/secrets.test.ts`、`test/core/memory.test.ts`
的「记忆的底线」。

## ADR-035：上下文压缩后的原文要能查回来（`read_history`）

**背景**：压缩交给 pi-durable 默认（`contextWindow: 1_000_000`、`reserveTokens: 16384`、
`keepRecentTokens: 20000`），压成 `pi.compaction` 条目后原文还在 storage 里，但**模型再也
看不见，也没有任何工具能读回**。于是它会凭记忆补路径、补数字、补原话 —— 看起来很像，
可能是错的，而且错得无法被发现。

**决策**：一个只读工具 `read_history`（`query` / `around` / `limit`，默认 12 条、上限 50），
按 `projector.ts` 那套 cursor 从新往回翻页，只取 `pi.user` / `pi.assistant` / `pi.compaction`
的 text 块；每行 clip 到 400 字，总输出 8000 字封顶并给出「用 around=<id> 继续往前」。
提示词里加一句「精确的路径、数字、原话不许凭记忆补」。

**理由**：压缩不可关闭（关掉就是每次都为全部历史付费），也不该由提示词承诺「我会记得」。
能查回来，模型才不必编 —— 这是唯一能根治「幻觉引用」的位置。

**代价**：一次查询最多扫 8 页 × 64 条；`read_history` 只看得到自己这个会话，看不到别人的。

**回归测试**：`test/core/history.test.ts`。

## ADR-036：`@` 别名解析放在 `channel/alias.ts`，成员过滤规则不动

**背景**：库里 980 个 mention token 有 **573 个（58%）是垃圾**，48 条消息写了 `@老大`
而没有任何人被叫醒。原因是成员表里存 slug（`owner` / `知言`），而人在正文里写的是
「老大」「CEO」「平台负责人」—— `parseMentions` 抓的是字面 token，`recipientsOf` 按成员
过滤时把它们统统丢弃。频道的两条老规矩（成员就是 `@slug`、不是这个房间的人 @ 不到）
本身没错，缺的是**名字到 slug 的那一层翻译**。

**决策**：

- 新增 `channel/alias.ts`：`resolveMention(raw, roster)` / `mentionRosterOf(agents)`（纯函数，
  不读盘）。顺序是 slug → 老大的叫法（`owner`/`老大`/`BOSS`/`我`/`YOU`，静态表）→ 真名 →
  岗位名 → `title`（整串或其中一段）。归一化走 `NFKC` + `toLowerCase()`，所以 `@ＣＥＯ`、
  `@Ceo`、` 周砚 ` 都能认。
- **岗位名的来源只有一处**：直属老大的人就是 `ceo`（`identity.md` 的 YAML 头只有 4 个字段，
  没有岗位缩写；而「老大唯一直接对话的人」是组织架构里的事实）。显式 `role` 优先。
- `parseMentions(text, roster?)` 返回**解析后的 slug**；不传 roster 时保留旧行为（字面
  token），老调用点（外壳留痕、老数据重投）不被打穿。传了 roster 就严格解析：解析不出来
  的（`@import` / `@media` / 邮箱 / 代码里的 `@x`）**丢弃**。
- `recipientsOf` 只加一层**兜底**：mention 不是成员时再用静态名册（只认老大）解析一次。
  **成员过滤规则一行不改** —— 否则 `@` 一个不在这个房间的人就能拿到别人房间的上下文。
- `postMessage` / `say` 落库前把 `@老大` 规范成 `@owner`（`mentions` 数组是规范 slug，正文
  原样保留：正文是模型的嘴，系统不该改字）。

**理由**：解析必须发生在这两个地方之间（写消息 / 算收件人），而它需要名册、名册来自磁盘 ——
放在 `channel` 内核里做成纯函数，外壳只管把身份喂进来，符合「shell → 内核」的依赖方向，
也让它能单测（不需要开运行时）。

**代价**：`say` 每次多读一遍 `agents/*/identity.md`（人只有个位数，且 `say` 不是热路径）；
老消息里 `@老大` 会被规范化成 `owner` 显示，与写入时看到的字面不同。

**回归测试**：`test/core/mention-alias.test.ts`（老大的 6 种叫法、CEO/真名/title、垃圾 token、
老数据兜底）、`test/core/say-contract.test.ts` 的「mention 写『老大』也能解析成 owner」。

## ADR-037：`decision` 与决策句式由代码补 `@owner`

**背景**：含「请确认 / 要不要 / 是 A 还是 B / 等你定」的消息里大量没有把老大写进 `mentions`，
老大的回复率只有 **1.06%**。这不是模型不会说，而是它写完「要你定」就以为说完了 ——
**「谁该看这条」是系统的责任，不是措辞的责任**。

**决策**：`say` 里加一条代码兜底：当 `kind === "decision"`，或正文命中 `needsOwner(text)`
（7 个信号：请老大 / 请确认 / 需你 / 等你定·你定 / 要不要 / 还是 / 怎么定），而 `mentions`
里没有 `owner` 时，把 `owner` **补进 `mentions`**（`postMessage` 的 `mention` 参数），
**不改正文**。老大没有会话时投递层会跳过（已知，见 C-001），红点靠 `mentions` 落在界面上。

**理由**：靠提示词说「记得 @ 老大」是概率；一条 `if` 是确定性。而「补 @」的唯一代价是
老大多看到一个红点，漏一个决策的代价是整件事静默停摆。

**代价**：`还是` 这种词会把少量「其实不是决策」的消息也标给老大（宁多勿漏）。

**回归测试**：`test/core/say-contract.test.ts` 的「要老大拍板就 @ 老大」（`decision` 补、
句式补、闲聊不补、正文不含 `@owner`）。

## ADR-038：全公司规矩放 `workspace/rules.md`，每轮渲染进提示词

**背景**：规矩原来住在 `seed/skills/工作规矩/SKILL.md`（5766 字节）。但技能正文**从不进系统
提示词** —— 每轮只渲染「名字 + 一句描述 + 三句用法」，正文要 agent 主动 `read_skill` 才看得见。
结果：「先给结论」「只在叫你的频道回话」「要老大拍板就 @ 老大」「别越级」这些规矩，实际上
一个都没到过模型眼前（审计：agent 发言 46% 是英文自言自语，长度中位数 195 字 vs 老大 15 字，
最长一条 21,568 字）。同一份规矩也不该被复制到十几份技能里去维护。

**决策**：`<workspace>/rules.md` 是**唯一**一份「每轮都在场」的规矩文案，由 `agent/rules.ts`
的 `loadRules()` 读取、`renderRulesSection()` 排成「## 规矩」一节，插在**身份之后、能力之前**；
文件不存在或为空 → 整段不出现（不是空标题）。渲染是纯函数，同一份文件逐字节相同（ADR-005）。

**理由**：这条内容和「你是谁」一样是**每轮都该生效的常量**，而 `.ts` 只能排版、不能写长篇
话术（本项目硬哲学：语义在文档，代码只排版）。写成常量字符串会：进代码库、要发版才生效、
让每次微调文案都变成一次代码改动，还诱使下一个人往里加制度条款。

**代价**：`rules.md` 每轮都占提示词（约 700 字节，token 成本可忽略但确实常驻）；改文案不需要
发版，也就没有 review 卡口 —— 靠 git diff 看。

**回归测试**：`test/core/rules-prompt.test.ts`（有 → 含「## 规矩」与「3 句」；无 → 整段消失；
两次渲染字节相同）。

## ADR-039：公司层技能每次启动按 hash 同步，改过的不覆盖

**背景**：`seed.ts` 自述「只在工作区空的时候播种一次」。于是新写的规则修正永远进不了已有
工作区：`seed/skills/工作规矩/SKILL.md` 5766 字节，`workspace/skills/工作规矩/SKILL.md` 4729
字节 —— 1037 字节的修正从没生效；`seed/skills/记忆整理/` 干脆没被拷过去，而
`project/memory.ts` 让 agent `read_skill "记忆整理"`（沉淀链路上的一环，静默失效）。

**决策**：`syncCompanySkills()` 每次启动都跑一遍，逐文件按三方比较：

- 工作区没有 → 拷贝，记账
- 工作区有、内容与账本里记的 hash 相同（= 上次同步给它的那份，用户没动）→ 覆盖成新版，更新 hash
- 工作区有、hash 对不上（= 用户改过）→ **不动**，`console.warn` 一行「技能 <name> 已被本地修改，未覆盖」

账本 `<workspace>/.seed-manifest.json`：`{ "version": 1, "skills": { "<name>": { "<relpath>": "<sha256 前 16 位>" } } }`。
整个同步幂等：跑两次结果一样，第二次不写一个字节。

**理由**：工作区里的技能是**用户的文件**（可以现场改，改完就该生效），不能每次启动被种子抹掉；
但种子改进也得能到达。hash 账本是唯一能区分「这是种子那次写的」和「这是人改的」的东西 ——
时间戳会漂（`cp -p`、git checkout、rsync），内容比对才是事实。

**代价**：多一个隐藏文件（`.seed-manifest.json`）；用户手工回滚某个技能后，账本 hash 仍指向
旧版本，那份文件会被当成「改过的」永久保留 —— 想要新版就删掉文件让同步重建。

**回归测试**：`test/core/seed-sync.test.ts`（缺的补上 / 未改的更新 / 改过的不动 / 幂等 / manifest 正确）。

## ADR-040：老大的私聊不落过程投影

**背景**：`projector.ts` 把 agent 会话里的 `pi.assistant` 条目投影成 think/tool/work/say 消息，
落到 `personalId(slug)` = `dm:owner-<slug>`，也就是**老大和这个人的私聊**。审计实测：一个人
每次被 @ 一次，私聊里半小时内平均多 76 条（最高 197 条）；老大在这些私聊里的回复率 1.06%
（51/4804）。私聊被当成日志垃圾桶用，真正要说的话被淹掉，而且这直接违反 ADR-036 那条
「群里一条消息最多 3 句」的意图 —— 对面看到的根本不是三句。

**决策**：投影落库前先过 `keptProjections(channel, projections)`：目标频道是老大的私聊
（`channel.id` 以 `dm:` 开头且成员含 `owner`）时**只留 `say`**，think/tool/work 不落库；
其他频道（项目频道）保持原样。判定只看 id 前缀 + 成员，不看标题或归档标记（那些会漂）。

**理由**：私聊是**对话**，不是观察窗。过程信息本身没有消失 —— 它在会话 feed 里（`pi.assistant`
条目没被删，前端有另一条路径能看到），只是不再复制一份进老大要读的那个频道。项目频道里
过程投影是有用的：别人接手时要看「他试过什么」。

**代价**：老大在私聊里看不到那个人的思考过程卡片，要看就得打开会话 feed。

**回归测试**：`test/core/projector.test.ts`（`keptProjections`：dm 只留 `say`，项目频道原样全留）。

## ADR-041：同事之间要能私聊（`say` 的 `to`）

**背景**：审计实测「员工↔员工」的发言只占全部 agent 发言的 **1.2%**（14/1136），而组织里
明明有该对接的事（音效要问开发、平台要问负责人）。根因不是模型不想说，是**没有地方说**：
`dm:owner-<slug>` 的成员只有老大和这个人，他找不到任何私聊入口，只能跑到群里喊 ——
而群里的喊话会把不相干的人叫醒，这正是「噪音太多」的另一半来源。反例：周砚在私聊里
收到「克隆并部署 DS-Bot」，因为没法私下问同事，只能去群里找上级，顾南雁与知言当场判
「查无此令」，五条消息耗了 15 分钟。

**决策**：`say` 增加可选参数 `to`（名字或 slug）。给了就换频道：

- `to` 是老大 → 落在 `personalId(from)`，也就是既有的 `dm:owner-<slug>`，**不新建频道**；
- `to` 是同事 → 频道 id 用**排序后拼接**的 `dm:<a>--<b>`，`members` 与 `wakeOnAll` 都是这两人，
  不存在就现建。排序是关键的：`A→B` 与 `B→A` 必须落在同一条，否则会长出两条平行对话，
  双方各说各的。
- 对方的 slug 进 `mentions`（界面的「@ 我」红点、未读口径都读这个字段），不靠正文里手写 `@`。

**理由**：这是「让同事之间说得上话」唯一不增加噪音的做法 —— 私聊没有第三方，所以不存在
「叫醒一堆人」。反过来说，群里 `@` 一个人的成本因此下降：真要单独问一句，不必再占用
公共频道。

**代价**：频道数量会随对接关系增长（目前 8 人，最坏 C(8,2)=28 条）。可接受：每条私聊只有
在真发过消息之后才存在（`ensureDm` 是「发的时候建」而不是「启动时铺满」）。

**回归测试**：`test/core/colleague-dm.test.ts`（只装两人 / 方向对称 / `mentions` 与 `wakeOnAll`
都指着他 / `to: owner` 不新建 / 发给不存在的人老实报错且不建频道）。

## ADR-042：接力上限「老大没说过话」也计数，但显式 @ 可以突破

**背景**：`botHopsSinceOwner` 原实现对「老大从没在这个频道说过话」返回 0（注释写着
「不惩罚」）。结果是：老大一次不开口的项目频道，**上限永远不触发** —— 而那正是唯一真会
烧钱失控的地方（A 回 B、B 又回 A，无限接力）。审计把它列为 G1。

另外，到达上限时 `post.ts` 会写一条 note：「这条只记下，没人被叫醒。老大说一句，或者
**自己 @ 人**，就能接着走。」但代码里 `capped` 一旦为真就无条件跳过投递 —— 文案在撒谎，
模型会以为自己能 @ 人而其实叫不醒。

**决策**：两处一起改。

1. `botHopsSinceOwner` 去掉 `if (last < 0) return 0`：老大没说过话时**从频道建立算起**。
   老大一开口就归零，所以新频道不会反而更严。
2. `capped` 增加 `!addressed` 条件。`addressed` = 正文里显式 `@` 了一个**本频道成员**
   （且不是自己），用原始 token 与名册解析结果两路合并 —— 原始 token 是为了让
   `@<slug>` 这种不需要名册就能认的写法也算数。

**理由**：上限要拦的是**自动接力**（没人指名，模型顺着上一条往下接），不是拦住一个
想清楚要叫谁的人。放宽「指名」，正是让 note 文案成真，而不是让模型猜。

**代价**：一个反复 @ 人的 agent 仍能绕过上限。接受：绕过是有意的动作、正文里看得见，
而且每次都得点名，成本比自动接力高得多。

**回归测试**：`test/core/relay.test.ts`（老大没说过话时从建立算起 / 老大一开口归零 /
显式 @ 突破上限并真的投递 / 不 @ 人照拦）。

## ADR-043：前端只画四种行，未知 kind 一个像素也不画

**背景**：V2 的前端整体重写（`ui/web/`）。重写的第一版倾向于「兜底渲染」——遇到不认识的
消息 `kind` 就当成普通气泡画出来，理由是「总比丢了强」。但 `kind` 是语义层的东西：它增长
很快（`src/` 里现在就有 say/chat/report/decision/question/note/think/tool/work 九种），形态
各不相同（气泡、一行小字、竖线旁注、待办卡）。把没登记过的类型画成气泡，等于用错的形状
说了一件看起来正常的事，而且没人会去核对。

**决策**：`ui/web/js/rows.js` 里一张表定死四种行（`say` / `event` / `note` / `pending`），
**未命中的 kind 一律 `return null`（不画）**。新增一种 kind 必须同时在 `rows.js` 登记，
否则它在界面上不存在。同理，工具调用只翻 `TOOL_PHRASES` 里那 17 个人话动词，未命中画
「在做一件事」——绝不画工具卡、不画参数、不画返回体。

**理由**：界面上出现的每一行都应该是有人决定过「它长这样」的。静默兜底会让新类型以错误
的形状上屏，而且错误是隐形的（页面会显得很完整）。

**代价**：语义层加 kind 时前端要改一行，忘了改就是「消息消失了」。接受：消失比错形状好
排查 —— 有数据、无 DOM，一眼能定位。

## ADR-044：全页只有一个 `h1`，它在顶栏

**背景**：纸（`#sheet`）里的频道标题原本是 `<h1>`。手机上列表态整个纸 `display:none`，
于是手机列表态**没有任何标题元素** —— 一屏只有名字和预览，用户不知道自己在哪一层。
把标题塞进纸里也解决不了：纸本身在列表态就是不存在的。

**决策**：`<h1 id="bar-title">` 放在顶栏、任何视图下都可见 —— 桌面显示产品名「一人公司」，
≤640px 显示当前区域名（列表态「频道」/ 会话态频道名）。纸里的频道标题降为
`<h2 class="pane-title">`，手机上隐藏（标题已经在顶栏）。

**理由**：`h1` 是「这一屏是什么」的唯一答案，它必须跟着「这一屏」而不是跟着「这块内容」。
桌面有纸的框可以说清层级，手机没有框，只能靠顶栏说。

**代价**：频道标题的语义级别降了一级（页面标题是产品名而不是频道名）。对读屏来说仍然
成立：`h1` = 应用，`h2` = 当前频道。

## ADR-045：头像的眼睛是「挖洞 + 眼窝垫底」，不是画上去的点

**背景**：`docs/DESIGN.md` §3 要求眼睛用 `<mask>` 挖洞「透出底色」，这样歪头、压扁时眼睛
跟着形状走。实测：挖洞在纯白纸上是成立的，但老大自己说的话整宽铺了一条 `--accent-wash`
色带（§5.1），挖出来的洞透的就是那条淡绿 —— 和头像 93% 明度的淡绿底几乎同色，**眼睛直接
消失**，40px 的头像变成一个空心圈。任何「深色/带底色块上的头像」都会撞上这个问题。

**决策**：`avatarSvg()` 在挖洞的身体路径**下面**多垫一层同形状的 `--ground`（纸白）
路径，叫「眼窝」。洞仍然是从身体上挖的（形变时跟着走），但它透出的永远是纸白，不是当下
的背景。群组头像另有一条：`size < 28` 时只排对角两张 —— 24px 里放 2×2，每张只剩 11px，
四个洞糊成一堆点，不如两张读得出「这是一群人」。

**理由**：眼睛是否可见不能取决于这条消息恰好落在什么底色上。垫一层纸白，等于把「透出
底色」定义成「透出纸的底色」，而不是「透出最近的祖先背景」。

**代价**：头像不再是完全「无底色」的图形（多了一个白色底层，只在洞的位置可见）。
`docs/DESIGN.md` §3 的「明度 > 92% / 相邻色相 ≥ 60°」不变。

## ADR-046：桌面启动自己落进一个频道，手机停在列表

**背景**：按 `docs/DESIGN.md` §1.3，≤640px 一次只显示一个区域，默认停在频道列表。桌面
双栏如果也停在「没选频道」的空态，第一屏右半边是一整块 780×780 的空白 —— 首屏什么都没
回答，而这正是交付检查（§10）第一条要挑的刺。

**决策**：`boot()` 里分成两条路：有深链就走深链；否则桌面端调
`firstInterestingChannel()`（有未读 `mentions` 的 → 最近活动的非私聊频道 → 公司频道 →
第一个）自动打开；手机端不自动打开，停在列表。

**理由**：桌面是「一直在用」的形态，进来就该看见今天的对话；手机是「点开看一眼」的形态，
先给列表比先给一段上下文更省事。

**代价**：桌面端的深链与「上次看到哪」不完全一致（没有持久化「上次频道」）。要补的话
是往 `localStorage` 多存一个 key，不是改这套判定。

## ADR-047：前端对 `/api/attention` 缺失做一次性降级，失败后不再重试

**背景**：顶栏「N 件找你」读 `GET /api/attention`（跨频道的待办/被 @ 索引）。服务端与
前端是分开部署的：跑着的那份服务可能还没有这条路由（实测就撞上了，404）。如果每 30 秒
的 tick 都重试，网络面板会被 404 刷满，真正的错误会被淹掉。

**决策**：`loadAttention()` **只尝试一次**；失败就置 `state.attentionBroken = true`，
把 `needItems()` / `needCount()` 退回「各频道 `mentions` 求和」。降级后顶栏那个数字仍然
是对的（只是少了精确的 `seq`，点一下只能跳到频道、不能跳到具体那一条）。

**理由**：这条接口是**增强**，不是依赖。它的失败不该让顶栏变成一个错误提示，也不该
变成日志噪音。

**代价**：服务端补上路由之后，老页面要刷新一次才会用上（不做后台重连）。

## ADR-048：频道写入走进程级串行闸，一次 `say` 只落一条消息

**背景**：线上出现过重复发言 —— 知言在群里回了一句「在。」，频道里出现两条一模一样的。
查 `entries` 表看到一个两次调用的痕迹：第一次 `say` 的 tool-result 是
`Cannot use a settled overlay`，第二次重试成功。而第一条消息**已经写进去了**。

错误来自 `@earendil-works/chord` 的 `delta/tracker.js:55`：读一个已经 settled 的上下文
（`overlayReleased` 或状态是 `consumed` / `aborted` / `stale`）会抛这个错。同一个进程里
所有 agent 的 `say` 是并发的，都往同一个 `ChannelDoc` 上提交；先提交的那次会让后来者的
读覆盖层失效。于是「报错 + 消息仍然存在」→ 模型看到报错就重试 → 重复。

**决策**：`src/core/channel/post.ts` 加一个模块级 Promise 链
（`let writing` + `serialized()`），`postMessage` 整体包进去，原函数体改名
`postMessageUnlocked`。

**理由**：频道是全局共享的单点，写入本来就该排队。代价是一次 commit 级的等待（毫秒），
换来的是「一次工具调用 = 一条消息」这条最基本的保证 —— 没有它，模型每次重试都会在频道
里留下一条重复发言，而重复本身又会被下游（沉淀、待办、通知）当成两件事。

**放弃的方案**：把 `say` 整体包进一个「可重入」的锁（全局 `depth` 计数器 + `depth > 0`
就放行）。不行的原因是 `depth` 是进程级变量：A 持锁期间 B 进来也会看到 `depth > 0`
直接放行，等于没有互斥。真正的可重入需要 async context 追踪，Node 里没有便宜做法。
所以只在 `postMessage`（唯一真正写频道的地方）加锁；`say` 前面那次 `snapshot` 即使失败
也是**在写之前**失败，不会产生重复。

**代价**：`test/core/channel-write.test.ts` 的并发用例**证明不了这个修复** —— 去掉串行闸
它照样过。真实的并发时序（读覆盖层被别的 agent 的提交释放）在单进程测试里复现不稳。
所以那道闸是防御性的，用例只钉住「并发调用不许撞 seq、不许丢消息」。这条要记住：
**它是靠推理和线上痕迹定位的，不是靠能复现的测试。**

## ADR-049：三处「一眼认出」的修正：老大的脸、头像的眼睛、「找你」只收发言

**背景**：交付后看渲染，三件事让界面读起来还是「一排识别不出的色块」：
1. `owner` 不在名册里（他是人，不是 agent），头像走哈希和另外六七个人撞成同一种脸；
2. 眼睛是 `<mask>` 挖的洞，洞里露的是 `--ground` 纯纸白 —— 24px 的白洞在淡绿脸上
   等于没有眼睛，整张脸读成一个空白气泡；
3. `/api/attention` 的 60 条里大半是模型的英文内心独白（温言 92% 的发言是英文），
   它们正好含有「要不要 / 还是 / 怎么定」，被 `needsYou` 判成「需要老大」。

**决策**：
- `ui/web/js/avatar.js` 增加 `OWNER_SLUG` / `OWNER_LOOK = { shape: 2, tone: "hsl(14 52% 91%)" }`，
  老大固定「方肩」+ 暖色，不走哈希。
- `ui/web/css/base.css` 新增 token `--av-eye: color-mix(in oklab, var(--ink) 58%, var(--ground))`，
  `.av-plate` 的 fill 从 `var(--ground)` 改成它 —— 挖洞的技法不变（形变时眼睛跟着脸走），
  只是洞里露出的是柔和的墨色，不是纸白。
- `src/core/shell/view.ts` 的 `attentionItems` 加两道闸：`SPOKEN_KINDS`（只收
  `chat/say/question/decision/report`，投影与 note 不是发言）+「明确点了别人而没点老大的不收」。

**理由**：这三条都是「识别性」问题，不是审美问题。老大的脸是这个产品的**主语**，
每次滚动都在出现；眼睛是二十来个人之间唯一的区分特征；「找你」如果一条都不能信，
它就不存在。判据宁可窄 —— 漏一条提醒的代价小于整页没人看。

**放弃的方案**：收紧 `needsOwner` 的信号词（去掉 `/还是/` `/要不要/`）。不行，因为
`test/core/say-contract.test.ts` 已经把「要不要加联机 → 自动补 @owner」「这个是 A 还是 B？→
补」定成了契约，而那个宽判据在**投递侧**是对的（模型忘 @ 老大的代价更高）。所以要窄的是
「找你」这个列表，不是 `needsOwner` 本身 —— 两处判据故意不同，这条要记住。

## ADR-050：附件只存引用，文件本体落在 `<workspace>/uploads/`

**背景**：老大要能发图、发文件。第一反应是把 base64 塞进消息里 —— 在这个仓库里这是
最坏的选择：频道是**一份**文档，每条消息都是一条增量 op，一条 3MB 的图片会让这个频道
之后每次写入都多背 3MB。这个代价已经付过一次（189 条消息把频道文档撑到 27MB，见
ADR-027 的平方放大）。

**决定**：文件落在 `<workspace>/uploads/<id>`，元数据落在 `<id>.json`，频道文档里只放
`{ id, name, kind, bytes }` 四字段。

**为什么是「一个文件一份元数据」而不是一个总索引**：索引要么频繁重写成一个大 JSON，
要么在并发上传时互相覆盖。一个文件一份，写入天然原子，并发无冲突，列目录即可校验。

**三个安全边界**：
1. `id` 走白名单 `/^[A-Za-z0-9-]+$/`，不是「过滤掉 `..`」—— 过滤法永远漏一种编码
   （`%2e%2e`、Unicode 归一化、Windows 反斜杠）。
2. `kind` 与 `mime` 由服务端按真实内容重算，客户端传什么都不算数。
3. SVG **不内联**（按文件下载）。SVG 是能跑脚本的文档，同源内联等于自己开一个 XSS 口；
   取文件时还额外发 `X-Content-Type-Options: nosniff`。

**代价**：附件不在文档里，所以「同步一份频道文档」不等于「同步了附件」。目前没有
同步机制，`uploads/` 与 `core.sqlite` 必须一起备份。已知且接受。

## ADR-051：模型看不见图片内容

**现象**：老大发一张截图，agent 回「我这侧读不了图的内容，只确认收到了」。

**原因**：附件在投递正文里只有一行占位（`[图片] 宽图.png`），`deliver` 没有把图片作为
视觉输入传给模型。pi-durable 的会话历史里放图片是可行的，但那要改 `runtime/` 的输入
组装，并考虑「一张 4MB 的图进每一轮上下文」的成本。

**决定**：先诚实——不假装能看图。占位行让模型知道「有个文件、叫什么、多大」，它应该说
「我看不到图里的内容，请用文字说一下要我做什么」。这条写进规矩与技能。

**升级路径**：等真正需要「看着截图改样式」时，在 `runtime/` 里把 `kind: "image"` 的
附件读成内容块塞进这一轮的输入，并且**只塞最近一轮**（不塞进历史，否则每轮都在付钱）。

## ADR-052：补历史只往前面插，不整列重建

**现象**：消息多起来以后，往上翻看历史，画面会跳一下；再多翻两轮，`document.querySelector`
按 `data-seq` 查到的是**另一条消息**。

**三个原因，都是实测出来的**：
1. `renderFlow` 的 `pinned` 在 `restore: false` 时写死 `true`。SSE 每来一条新消息都会走这条路，
   于是**正在上翻的人被拽回底部**（实测：滚到顶后发一条消息，`scrollTop` 从 0 跳到 1522）。
2. 补历史用 `[...earlier, ...current]` 直接拼，两次翻页有重叠时 DOM 里出现 20 个重复的
   `data-seq`。重复的行会让「按 seq 定位一条消息」这件事整体失效（高亮亮错行、动作条挂到
   另一条上）。
3. 补历史走的是整列重建（`renderFlow`），位置靠「离底部多远」这个差值找回来。可插在上面时
   离底距离必然会变，方向反了；而如果改用高度差，插入的行里有图片/附件/代码块时高度要等
   布局稳定才知道，实测差 300px（整屏内容往上跳了 10 行）。

**决定**：
- `pinned` 在 `restore: false` 时也取 `isPinned()`；`restore` 只决定要不要参考「上次离开这个
  频道时的位置」，不再决定「无脑钉底」。
- 补历史改成**只把新的行插到 `.feed` 最前面**，不重建整列；位置用锚点行（补之前视口最上面
  那条的 seq + 它的屏幕 y）按回原处。锚点是「同一条消息在同一个位置」，与插进去多少、插的是
  什么都无关。
- 合并在前端按 `seq` 去重 + 升序（`mergeMessages`），不指望「每次请求恰好不重叠」。
- 离开底部时浮出「回到最新」。**刻意不报「N 条新消息」**：增量推送、补历史、重放都会让前端
  自己数出来的条数失真，一个会算错的数字比没有数字更糟。要数字看顶栏的「N 件找你」。

**回归**：`test/ui/merge-messages.test.ts`（8 例）钉死「合并后 seq 唯一且升序」。
另外两条（上翻不被拽回、补历史后同一 seq 的行屏幕位置不变）没法用纯函数证明，
V2 也没有 UI e2e 工具了 —— 它们靠真浏览器 CDP 脚本验过，见 ADR-041 同款说明：
这类断言的价值在人工回归，不在 CI。

## ADR-053：提交之后不许再读文档代理 —— 一条消息回两遍的真因

**背景**：`say` 调用在频道里发出**两条一模一样**的消息。反复复现：每条「@知言 报时」都得到
两条「现在 10:35。」。sqlite 里会话 2 的条目序列是：

```
CALL  say {...}
tool-result <harness>[error] Cannot use a settled overlay</harness>
CALL  say {...}          ← 模型以为失败了，重发
tool-result 已发到「公司」#124
TEXT  在。
```

即**第一次调用写成功了，然后报错**。抓到的栈（`chord/dist/delta/tracker.js:361` → `:264` →
`src/core/channel/state.ts:220` → `src/core/channel/post.ts`）：

```
TypeError: Cannot use a settled overlay
    at nodeForTarget (chord/dist/delta/tracker.js:361:15)
    at recipientsOf (src/core/channel/state.ts:220:32)
```

**根因**：`postMessageUnlocked` 在 commit **之后**还在读 commit 事务里的东西 ——
`created = finalMessage` 是事务里的代理，`recipientsOf(channel, message)` 一读
`message.mentions` 就抛；`renderDigest(deps.state, slug)` 也会读整份快照。
chord 把「事务已结算」的读覆盖层判为不可用（`isSettledContext` = `overlayReleased` 或
`status ∈ consumed|aborted|stale`），而这个错**抛在写入之后**，于是「消息已进频道，工具报失败」。

**试过但无效的两条路**（记下来免得再走）：
- 把工具里取快照的 ctx 换成 `BACKGROUND_CONTEXT`（4 处替换）：仍然抛。说明不是工具的 ctx 过期。
- 提交之后重新 `snapshot(ChannelDoc, BACKGROUND_CONTEXT)` 取一份新的再读：**仍然抛**。

**决定**：把「提交之后还要用的东西」全部在提交**之前**抄成纯数据。

- 频道元信息：`channelMeta = { ...channel, members: [...], wakeOnAll: [...] }`，之后只用它。
- 新的那条消息：commit 结束前置换成 `JSON.parse(JSON.stringify(finalMessage))`（几百字节，
  和 5MB 的全量快照不是一个量级 —— `JSON.stringify(snapshot(ChannelDoc))` 实测 5,065,321 字节）。
- 未读摘要：`digests` 在提交前算好，`deliver` 收 `ReadonlyMap<string, string>` 而不是整份
  `state`。摘要本来就该是「这条消息之前」的样子，提前算既对又安全。

**回归**：没有能钉死它的单测 —— 这个错只在「真工具调用 + 真提交 + 提交后读」的组合下出现。
验证靠线上：连发两次「@知言 报时」，seq 140→141、142→143 各一条回复，临时栈日志零记录。
`test/core/serialize-commit.test.ts` 只覆盖「提交串行」这一半，别拿它当这条的证明。

## ADR-054：不上前端框架 —— 卡顿的病因是渲染策略，不是「没用 React」

**背景**：老大问「是不是前端要上框架了，有必要上 React 吗」，并说「切几个页面容易卡住」。

**查出来的三处真因**（都在渲染策略上，换框架一条都治不了）：

1. **每条 SSE 消息都整列重建**：`merge` 里无条件 `renderFlow({restore:false})` →
   `el.feed.replaceChildren()` + 把 60 条消息全部重新构造（每行一张 SVG 头像、正文再走一遍
   Markdown）。来一条消息重建一次全表，消息越快越卡。改成**只 append 新那一条**。
   顺带修掉一个隐藏 bug：重建会把正在流式写入的 `.md` 节点换掉，token 增量就找不到落点。
2. **org 推送成串**：每来一条 org 事件就 `loadChannels()` + `loadAttention()`（两次网络 +
   整条侧栏重建）。改成 400ms 合并。
3. **切一次频道重建三次侧栏**：改成只改 `aria-current`（`markCurrent()`）。

**决定**：不加框架、不加构建。前端保持「原生 ES module，无依赖，静态直出」。
理由：这个界面的状态是**一份快照 + 一个流**，没有需要框架来管的组件间状态同步；
真正的成本在「一次渲染多少 DOM」，那是手写更可控的地方。加 React 会引入构建步骤，
而本项目刻意没有构建（`ui/web/` 改完刷新就生效），换来的只是把 `replaceChildren` 换成
`key` + 虚拟 DOM —— 该整列重建的时候它一样整列重建。

**回归**：没有单测（DOM 性能测不出来）。判定标准写在 `docs/DESIGN.md` §10：
交付前用真浏览器跑一遍「连发 5 条消息 + 切 8 个频道」，主线程不出现 > 200ms 的长任务。

## ADR-055：侧栏一列平铺、两行

**背景**：老大列了四条：「左侧栏太乱，不要分组，直接平铺；名字后面跟状态；职位和项目不显示；
私聊点开后在头部显示；私聊头部的『2 人』根本不需要。」改完之后他又指出：
「左侧头像右边应该还是两行啊，你怎么变了。」

**决定**：

- **一列，无分组**。`GROUPS`（群组/成员两块）删掉，`.chan-head` 删掉，`#people` 人栏并入
  这一列 —— 人和频道混排，按最后活跃时间倒序。理由：分组是为了把「8 个人」和「5 个频道」
  分开，但平铺之后两者本来就有不同的头像（人脸 vs 群头像），分组标题只是重复。
- **每行两行文字**：第一行名字 + 状态（只有私聊行有状态），第二行最后一句。
  只留一行会变成「一堆名字 + 一堆时间」，扫不出哪个频道真的动了。
- 不显示职位、项目、成员数。私聊打开后，那个人的状态改到频道头上（`renderHead`），侧栏不重复。

**代价**：人和频道混在一起，找不到「只看人」的入口。接受 —— 人栏那 8 行在 13 行列表里
本来就占三分之一，再单开一块只是把同样的人画两遍。

## ADR-056：详情面板一次拉全，过程行归属「紧随其后的那句话」

### 背景
老大要的是 DS-BOT 那个位置的东西：私聊点右上角看**这个人**（职位、归属群组、预置提示词、
技能、记忆），群点开看**这个群**。另外两件事一起改：私聊头部只写「睡了」等于什么都没说；
过程行（想了 1s / 跑了一条命令）有时画在那个人的头像**上面** —— 因为 agent 先 think/tool、
后 say，而渲染是照着到达顺序画的。

### 决定一：`GET /api/people/:slug` 一次给全
一个路由返回人档案要的**所有**字段：`{slug,label,title,project,manager,managerLabel,body,
skills[],memory{exists,entries,digest},channels[]}`。不复用 `/api/org`（那里没有技能，而且
是全量名册），也不拆成三个接口。

- 技能走 `listSkills({workspace: dirname(agentsRoot), agents: agentsRoot}, slug)`。`CoreShell`
  没有 `workspace` 字段，工作区根就是 `dirname(agentsRoot)` —— 不要再为它加一个字段。
- 频道列表来自 `shell.channels()`。**频道文档里没有 `kind`**（V2 只在 view 层按 id 前缀推），
  所以这里也用前缀：`company` / `leadership` / `proj:` / `dm:`。
- slug 必须先存在于 `directory.slugToConversation` 且不是 `owner`。这一条同时干两件事：
  挡路径穿越，以及让不存在的人老实 404 而不是返回一个空档案。

### 决定一·五：从右边展开，不是弹窗
第一版做成了居中的模态框（遮罩压暗 18%、`place-items: center`、`el.frame.inert = true`）。
老大的原话是「要以右边展开的形式展现，不要弹窗」，改成：
- `.detail` 是 `position: fixed; inset: 0` 的**透明**层，`pointer-events: none` —— 底下的频道照常能点，
  `.detail-panel` 自己 `pointer-events: auto`。
- 面板 `width: min(420px, 100%)`、贴右、`padding-top: calc(var(--topbar) + env(safe-area-inset-top))`
  —— **从顶栏下面开始**，否则它会把「找你 / 团队 / 布局 / 主题」这几个开关自己挡住。
- 入场只走 `translateX(16px)` + 透明 → 不缩放；不设 `inert`（非模态），收起靠 document 的
  click 判「点在面板外且不是那个开关按钮」。
- 手机 ≤640px 铺满整屏（390px 的一条放下提示词太窄），并且**去掉 `.detail-doc` 的 260px 小滚动区**
  —— 整屏都是它时再套一层滚动就是「滚中滚」，手指没法操作。桌面那层仍限高，底部加一道渐隐
  （浮层滚动条在 macOS 上不动鼠标不出现，切断的行看着像排版坏了）。

### 决定二：界面不画后端没有的东西
`ui/web/js/detail.js` 只做「数据 → HTML」，开关和取数在 `app.js`。硬规矩写在文件头：
**没有的技能不画空标题**（写「还没有技能。他可以在干活时自己写一份」），没有记忆就没有
「打开记忆」按钮（点进去看空列表是白跑一趟），没有 title/project 就不画标签。
`test/ui/detail-panel.test.ts` 把这条钉住：空数组进来，断言页面里出现「还没有……」而不是
一个空 `<ul>`。

### 决定三：过程行属于它后面那句话
渲染顺序按「**谁说的话**」归块，不按到达顺序。`rows.js` 的 `buildStream` 用
`queueEvent`/`flushEvents`/`takeEvents` 缓冲：过程行先攒着，等同一个人的 `say` 到了再挂到
那句话**后面**；换人说话时把前一个人的过程行 flush 出来（它们没有对应的 say，就留在原地）。

增量路径（`buildOne`，一条消息一次渲染）没有那个缓冲上下文，所以在 `app.js` 的
`isAppend` 分支里补一层：过程行落地后进 `state.tailEvents`，等下一个非过程行到达时
**重新 `append` 一次**（`append` 已存在的节点是移动，不是复制），于是「想了 1s」跑到那句
话后面。整列重画时 `renderFlow` 把 `tailEvents` 清空，避免抓着一堆已经不在文档里的节点。

**代价**：DOM 顺序不再严格等于 seq 顺序（82 号 say 会排在 79–81 号过程行前面）。
`[data-seq]` 仍然是身份，`highlightSeq` / 上翻锚点 / 动作条都靠它，所以不影响定位。

### 决定四：头部副标题 = 岗位 · 项目 + 状态标签
私聊的 `renderHead` 副标题不再是「2 人」或光秃秃的「睡了」，而是 `岗位 · 项目` 加一个
1px 边框的胶囊状态。**只有文字那段可以省略**（`.pane-text` 带 ellipsis），状态标签
`flex: none` 永远完整 —— 实测过长时会把标签一起切掉（`前端开发（小恐龙）·di` 后面没字）。

### 决定五：「团队」搬到顶栏，右上角换成「详情」
团队是**全公司**的视角，和主题、布局是同一类东西（改的是整个界面），所以搬到 `.topbar`
并给一枚图标；`sheet-head` 原来那个位置留给详情（它作用于**当前这个频道**）。

### 补充：过程行收成一组
十几条 think/tool 全都平铺出来，等于把「他真正说的那句话」埋掉（老大的原话是「沟通内容
太多了，根本不像正常人之间沟通」）。所以 `wrapEvents()` 把一段连续干活收成一行
`沈舟 15 步过程 · 想 3 · 跑 8`，点开才看细节；只有一条时不收（收成「1 步过程」比直接写
「想了 1s」更难读）。`run` 的 stdout 会另存一条 `kind:"work"`，两条都数会变成「跑 6 · run 6」，
所以 `eventLabel()` 把 `run`/`bash` 统一记成「跑」。

## ADR-057：新消息只追加，旧消息比指纹再决定换不换那一行

**背景。** 老大的原话是「界面卡顿，切几个页面容易卡住」。实测（`/tmp/prof.mjs`，
`Page.addScriptToEvaluateOnNewDocument` 注入探针，跑一次真实任务，15 秒采样）：

| 指标 | 修之前 | 修之后（同一探针，30 秒） |
|---|---|---|
| `create` SSE 事件 | 1620 | 119 |
| `.feed.replaceChildren()` | 1616 | **0** |
| DOM 节点加了又删 | 51359 / 51356 | 4 / 0 |
| 长任务 | 8 个，共 5562ms | **0** |
| 最长一次卡顿 | **2691ms** | 0 |

两个原因各占一半，缺一个都不会这么惨。

**原因一：后端把「重推」当成了推送。** `pushChannel()` 每次提交都把最后 60 条消息
全部重发一遍（原注释写的是「最近 60 条足够」—— 对**首屏补齐**是对的，对增量是 60 倍放大）。
提交还被 debounce 120ms，所以一次运行里同一条消息会被重推几十次。
改成**每个 SSE 连接在每个频道上有一个游标**（`channelSeqs`，`RECENT_RESEND = 4`）：
刚连上的给全量 60 条，之后只给游标之后的，外加最后 4 条（占位气泡被填充时要能原地覆盖）。

**原因二：前端把「重推」当成了「新消息」。** `merge()` 里 `index >= 0` 就落到
`renderFlow({restore:false})` —— 整个频道 `replaceChildren()` 重建，每行一张 SVG 头像、
正文过一遍 Markdown。1616 次整列重建就是 2.7 秒的卡顿。

**决定。**
1. 服务端推「增量」不再推「尾巴」。
2. 前端对已有 seq 先算指纹 `messageSignature()`（seq / kind / status / at / 发送者 / replyTo /
   mentions / 附件 id / needsYou / 正文）。指纹相同 = 什么都没变 = 直接丢弃，连 `notePresence` 都不跑。
3. 指纹不同（占位填充、编辑）就 `row.replaceWith(buildOne(...))` **只换那一行**，
   不整列重画 —— 顺带修好一个隐性 bug：整列重画会把正在流式写入的 `.md` 节点换掉，
   后续 token 增量找不到落点。

**为什么不换框架。** React 治的是「状态到 DOM 的映射」，这里根本没有映射问题 ——
是「把没变的东西全量重画一遍」。上框架之后 `replaceChildren` 会变成全量 vdom diff，
64 行 × 每行一个 SVG 的 diff 一样会卡；而项目的前端是**无构建的原生 ES module**，
引入框架要加构建链、加依赖、加一层调试成本，换不来这几个数字。

**验收标准（写死，防回流）：** 连发 5 条消息 + 连切 10 个频道，`PerformanceObserver`
记录的长任务为 0。实测 10 次切换 0 个长任务、控制台 0 错误。

## ADR-058：`say` 拦内心独白，`say` 拦超长正文

**背景数字（线上 4804 条消息的统计）。** agent 的发言 46% 是英文（苏澄 96%、温言 92%、
周砚 58%），长度中位数 195 字而老大是 15 字（**13 倍**），最长一条 **21,568 字**。
老大的原话：「现在沟通的内容太多了，根本不像正常人之间沟通。」

规矩里从 ADR-038 起就写着「不用英文写内心独白（Let me… / Now I'll…）」，`rules.md`
也在提示词里 —— **该写还是写**。原因不复杂：规矩是建议，模型可以不听；而每一条 `say`
都会直接贴到老大眼前。所以这两条必须由代码拦。

**决定。**

1. **超过 1200 字直接拒**，把长度和上限一起回给模型：「频道里只放结论，把过程写进
   项目文件，再发一句结论加路径。」不是「存不下」（存储能存），是「不该在频道里说这么多」。
2. **内心独白直接拒**。判据两道一起过（`monologueOpener()`）：
   - 以第一人称计划开头（`let me` / `now i` / `i'll` / `i need to` / `okay,` …）；
   - **并且**英文字母占「英文字母 + 汉字」的 70% 以上（不看字符总数 —— 代码块里全是 ASCII，
     但那种正文以中文开头，第一道就过不了）。

   被拒的正文不落库，模型会拿到一条说明并重写。代价是多一次模型往返。

**为什么不做得更狠**（不用小模型判、不整条 `say` 翻译）：多一次 LLM 调用就是多一份延迟和
费用，而「开头是不是 Let me…」已经能覆盖绝大多数。误伤面很小 —— 中文汇报里夹
`docker compose up`、`SKILL.md`、报错原文都不会被打中，`test/core/monologue.test.ts`
四例专门钉住这四个边界。

## ADR-059：头像不用 `<mask>` 画眼睛，输出按「人 + 尺寸 + 状态」缓存

**背景。** 老大两次报「agent 在跑的时候页面卡死」。我在无头 Chrome 里量了 CPU profile、
长任务、帧间隔、服务端延迟、SSE 字节数，全都正常（最长帧 17ms、长任务 0、服务端最大 1.4ms）。
两边现象对不上的嫌疑落在一处：无头里 `prefers-reduced-motion` 被强制成 `reduce`，
`motion.css` 的 `av-bob` / `av-ponder` / `av-blink` 根本不跑；而真实浏览器里它们是
`animation: … infinite`。原来每张脸都是

```html
<svg><defs><mask id="avm123">…</mask></defs>
  <g class="av-b"><path class="av-plate"/><g mask="url(#avm123)">…</g></g></svg>
```

两个代价叠在一起：**①** 每张脸一份 `<defs><mask>`，一屏几十行就是几十份，而且 `id` 是自增的
（`avm1`、`avm2`…），同一张脸每次重画都是新 id，浏览器无法复用任何栅格化结果；
**②** `av-b` 上的 transform 动画每帧都要把蒙版重新栅格化。

**决定。** 眼睛改成直接画两块 `fill="var(--av-eye)"` 的圆角矩形，删掉全部 `<defs>`，
`avatarSvg()` 的输出按 `` `${slug}|${size}|${state}` `` 缓存成字符串。

**为什么视觉上一像素不差。** 蒙版的作用是「眼睛透出底下 `av-plate` 的颜色」，而 `av-plate`
的 fill 就是 `var(--av-eye)`；两个眼睛矩形（x 32–42.5 / 57.5–68，y 44.5–59.5）在三个外形里
都落在脸内部，不需要被外形裁剪。所以「先画脸再画两块 `--av-eye`」等价于「挖洞露出
`--av-eye`」。副作用是 `.av-plate` 这个类没有了 —— 已全仓 grep 确认没有别处引用。

**回归。** `test/ui/detail-panel.test.ts` 与浏览器实测：`svg.av mask` 计数 0、`defs` 计数 0；
截图对比眼睛位置、颜色、描边一致。

## ADR-060：连续的「接力到上限」告警只留一条；侧栏预览不取告警

**背景。** 线上一个私聊 197 条消息里 150 多条是 `接力到上限（3 次）…` 这条 note。
根因是 `post.ts` 每拦下一条 agent 消息就补一条 note —— 上限一旦触发，之后**每一条**都被拦，
于是告警被刷成了正文。这直接对应老大的抱怨「沟通的内容太多了，根本不像正常人之间沟通」。
同一时间侧栏预览显示的也是这条告警（预览取的是「最后一条消息」），于是整个频道看起来只剩错误。

**决定。**
1. `src/core/channel/post.ts`：只有「老大上次说话之后还没报过警」才补 note。
   判据不能写成「上一条是不是 note」—— 被拦的那条消息本身也会落库，上一条永远是它；
   也不能写成 `findLastIndex(from === OWNER)` —— note 自己就是 `from: OWNER`，
   它会把「老大刚说过话」误判成成立。所以找的是
   `item.from === OWNER && item.kind !== "note"`。
2. `src/core/shell/view.ts`：侧栏 `preview` 取 `findLast((item) => item.kind !== "note")`。

**回归。** `test/core/relay.test.ts` 的「连续被拦只留一条 note —— 否则频道里几百行
「接力到上限」」：第一次超限留 1 条 note，第二三次超限只加消息不加 note，note 总数保持 1。

## ADR-061：卡顿由浏览器自己记账，上报到 `workspace/logs/jank.jsonl`

**背景。** 「agent 在跑的时候页面卡死」复现不了：无头实测 55 秒 `replace 0`、`feedAppends 4`、
长任务 0、最慢帧 17ms；服务端 `/api/channels` 100 次采样最大 1.4ms；接口体积 1.2–5.8KB；
突发 40 条消息最慢帧 17ms。而老大那边是真卡。**继续在无头里猜是浪费老大的时间。**

**决定。** 让浏览器自己记：`ui/web/js/jank.js` 用 `PerformanceObserver({entryTypes:["longtask"]})`
加 rAF 帧间隔（`FRAME_GAP_MS = 240`、`TASK_MS = 200`），只记真卡的那几次，
带上「当时正在干什么」（`mark(label)` 由 `merge()` 和 `renderSidebar()` 埋点），
每 5 秒 `fetch("/api/diag", { keepalive: true })` 上报；服务端 `POST /api/diag`
追加到 `workspace/logs/jank.jsonl`。

**为什么值得留一个上报口子。** 这是唯一能拿到「老大真机上到底什么东西慢」的办法，
而且成本极低（只在卡的时候写、5 秒一次）。它也是唯一一个不画在界面上的接口 ——
消费者是 `jank.js`，不是视图，`check-boundaries.mjs` 的「路由必须有前端消费者」照样成立。

**自测。** 注入一次 500ms 主线程阻塞 → 6 秒后 `workspace/logs/jank.jsonl` 出现
`{"kind":"jank","entries":[{"why":"frame","ms":483,"doing":"idle","forMs":3394}]}`。

## ADR-062：「接力上限」在只有一个人的频道里不存在

**背景。** 老大问「接力到上限 3 次是什么意思」—— 因为他的私聊里躺着 150 多条这条告警。
追下去发现上限本身在私聊里是**错的**。

上限存在的唯一理由是 A 回 → 唤醒 B → B 回 → 又唤醒 A 的无限循环。而投递时收件人
一定会排除发件人自己（`recipientsOf` 的最后一步），所以「老大 + 一个 agent」的私聊里，
那个 agent 说完话之后**没有任何人**会被再叫醒 —— 循环根本起不来。计数却还在涨
（`botHopsSinceOwner` 数的是「老大上次说话之后 agent 说了几条」），于是 agent 汇报到第 4 条
就被堵嘴，频道里多出一行「这条只记下，没人被叫醒」。

**决定。** `relayLimit()` 在 `agents <= 1` 时返回 `Number.POSITIVE_INFINITY`；两个及以上
agent 仍是 `max(3, 3 × agents)`。`post.ts` 的 `capped = hops >= limit` 不需要改 ——
`Infinity` 天然永不触发。

**这不是放宽风控**：能产生循环的前提是「至少两个 agent 互相唤醒」。一个人孤零零说话的
频道里，每条消息都只花一次模型调用，且不会自己喂自己。

**回归。** `test/core/relay.test.ts`：新增「只有老大和一个 agent 时不设上限」；
原「至少 3」用例改成只验多 agent 的两档（6 / 9）。

## ADR-063：像同事发消息 —— 每轮附言 + `[PASS]` + 单人在场不许静音

**背景数字**（`/tmp/ws-audit/comm-behavior.md` 的行为审计）：agent 的 `say` 长度中位数
**195 字**，老大是 15 字（13 倍），最长一条 **21,568 字**；46% 的发言是英文自言自语
（苏澄 96%、温言 92%、周砚 58%）。对照 ds-bot（`/tmp/ds-research/f-brevity.md`）：
它一个字都不截断、不剥 markdown、不做「检测到小标题就判报告」——**短是生成时就短的**。

**ds-bot 的两个机制**（照抄的部分）：

1. **每轮贴在触发消息末尾的附言**（`groups.js:102` 的 `ROOM_REPLY`），不是系统提示词。
   静态规矩在长上下文里会被稀释，贴着生成点的那一句每轮重申一次。
2. **`[PASS]` 是合法输出**（`groups.js:81` 的 `isPass`，`:528-533` 记成 `passed`）。
   原注释点破了关键：**每轮必须产出一条消息，模型就会拿思维草稿去填空** ——
   英文独白、大量「收到」，本质都是填那个空。

**我们的三个不同**（不能照抄的部分）：

1. **我们一轮只有一个 `say` 槽位**（ds-bot 有「过程话立刻发 + 结果留到回合末」）。
   所以附言必须同时给出**长内容的合法去处**：「长只允许出现在被点名要的场合」——
   只写「要短」会得到**又短又偷工**。附言里因此保留了「说结果：谁、做了什么、卡在哪、下一步」。
2. **我们可能只叫醒一个人**（ds-bot 的发言位由 @／管理员分配，PASS 了还有下一位接）。
   单 agent 频道里 PASS 掉 = 老大什么都没收到 = **断线，不是安静**。
   所以 `[PASS]` 只在「这一轮还有别的 agent 被同一条消息叫醒」时成立；否则拒绝并要结果。
   判据不新增状态：读名册里的 `wakeOf`（投递成功时写入），再用 `recipientsOf`
   重算收件人 —— 与投递层同一个纯函数，不会两处口径不一致（`tools.ts` 的 `othersAwoken`）。
3. **空正文等于 `[PASS]`**。模型直接不调 `say` 本来就已经是「这一轮不说话」，
   两件事必须等价，否则它会被迫为「什么都不说」编一句话。

**决定**
- `src/core/channel/deliver.ts` 新增 `renderReplyRules({ woken, viewer, labelOf })`，
  由 `renderDelivery` 拼在正文末尾（纯函数、确定性，不破 ADR-005）。
- `src/core/channel/tools.ts` 新增 `isPass(text)`（空串 / `[PASS]` / `【pass】` / `（PASS）` / `pass.`）
  与 `othersAwoken(...)`；`say` 在解析落点**之前**拦一次。
- `seed/rules.md` 与 `workspace/rules.md` 各加两条（逐字相同的那两条）。

**回归**：`test/core/say-contract.test.ts` 新增 6 例（有同事时 PASS 不落库 / 只有自己被叫醒时
PASS 被拒且不落库 / 7 种写法算 PASS、4 种不算 / 附言在「一人」与「多人」两种措辞 /
投递正文里真的带上了这两句）。

**不做的**：不做小模型判定、不自动翻译、不事后清理 markdown、不把阈值抄成 20,000
（那个数字是为了「不丢内容」，不是为了「短」；我们的 `SAY_LIMIT = 1_200` 已经单独存在）。

## ADR-064：一轮只说一句结论（`step` / `result`）+ 未读摘要降级成背景

**背景**：ADR-063 只解决了「必须说话」和「贴着生成点提醒短」。剩下两个现象没治：
①告诉它「一两句」之后它靠**删内容**换短 —— 又短又偷工；②实测它有 39 条积压时，
把「未读摘要」当成任务，答了摘要里的旧问题，而刚投进来的那条没人回。

**ds-bot 的做法**（`turns.js:532`、`groups.js:889-909`）：一轮里分两种话 ——
过程话（`said`，带工具调用的文本，**立刻发、可以多次**）和结果（回合末**只交一次**）。
所以我们缺的不是「更短的提示」，是**多个短消息的合法出口**：只有一句的额度，它就必须把
结论压进那一条。

**决定**
1. `say` 新增 `step?: boolean`：`true` = 过程话，随时发、可以连发；不传 = 结论。
2. 新建 `src/core/channel/speech.ts`（`markSpoken` / `spokenResult` / `clearSpoken`）：
   进程内 `Map<conversationId, text>` 记「这一轮说过结果了」，第二次结果被拒并**把开头还给它看**，
   同时给出两条出路（改发 `step`，或等下一轮）。纯建议性质，重启清空只会松一点，不丢消息。
3. 「新一轮」的唯一入口是 `deliver()` —— 它 `clearSpoken()` 后再 `submit`。
   放在别处（比如按时间过期）会把「一轮」的定义变成猜测。
4. 未读摘要改成 `【背景：别的频道里还有 N 条没看】` + 「（这不是要你现在回的…先答上面那条。）」。
   变化只有一句措辞，但它是「模型把背景当任务」的直接原因。

**为什么不做「30 秒内连发的步骤合并成一条」**：ds-bot 需要它是因为它的步骤话来自
同一个回合的流式文本；我们的 `step` 是模型主动调的，每条都有独立意义，合并反而丢信息。
如果实测出现碎片化再补。

**回归**：`test/core/say-contract.test.ts` 新增 4 例（第二句结果被拒且不落库 / `step` 可连发且
之后结论仍能发 / 说过结论后仍可发过程话 / `clearSpoken` 后又可以说一句）；
`test/core/deliver.test.ts` 的摘要断言跟着改。

## ADR-065：过程话 30 秒内合并 + 同事的事在群里说

**背景**（两个实测现象）
1. 允许 `step` 连发之后，agent 把一个动作拆成「我先看下代码」「找到原因了」「正在改」
   三条。读起来像刷屏，更要紧的是**收件人被叫醒三次** —— 每次叫醒都是一整轮模型调用。
   ds-bot 的解法是 `ROOM_STEP_GAP_MS = 30_000`：同一个人 30 秒内的连续过程话算一段。
2. 员工↔员工的消息只占 1.2%，而「找个人问一句」没有出口 —— 私聊被（另一处）禁掉之后
   只剩群里喊。可提示词里没有任何一句告诉它**可以在群里 @ 同事**。

**决定**
1. `Message.step?: boolean` + `post.ts` 的 `mergeStep()`：同一个人、上一条也是过程话、
   30 秒内、不是占位、正文里没有 @ 别人 → 把正文用换行接在上一条后面（`seq` 不变、
   `at` 更新），**不新增消息、不重复投递**。
2. 三条不合并的边界：超 30 秒（新进展不该塞回旧消息）、有人被 @（`@` 的意思是「必须叫醒他」，
   并进已投递的消息他就永远收不到）、结论（`step` 不传，那是这一轮的话）。
3. `renderReplyRules` 增加一行（只在群/项目频道、且频道里除自己和老大还有别人时出现）：
   「同事的事就在这个频道说：要问 X、Y 就 @ 他，他会收到、也看得到上下文。不要为了找一个人
   去私聊 —— 同事之间的私聊系统不允许。」
4. `rules.md` 两条对齐：把「要动别人之前先问老大」收窄成「要**改别人**（招人、改身份、
   把活派给别的项目）之前先问」，并明说「同一个频道里的同事，只是问一句或同步进展就直接 @ 他，
   不用问」。不改的话两条规矩互相掐死：一条要求先问老大，另一条要求直接 @ 同事。

**为什么不把合并做在渲染层**：渲染层合并只省排版，不省唤醒 —— 而唤醒才是成本。
合并必须发生写入层，才能让「三段过程只打扰一次」成立。

**已知取舍**：合并后的消息 `seq` 不变，SSE 靠 `RECENT_RESEND = 4` 的回补窗口把更新推下去；
如果这条过程话已经被后续 4 条以上的消息盖住，浏览器这次收不到更新（刷新后正确）。
过程话密集到那个程度，读者本来也读不过来。

**回归**：`test/core/step-merge.test.ts`（6 例：合并 / 超时不合 / 带 @ 不合 / 不同人不合 /
结论不合 / 合并后不投递）；`test/core/say-contract.test.ts` 增加附言「同事的事在群里说」两例。

## ADR-066：半分钟算「一段」+ 老大问话让他前面的待办让路

**背景**
1. 后端已经把同一人的连续过程话并进上一条（ADR-065），但它只覆盖「上一条正好是同一个人的过程话」。中间夹了别人的一句、或者间隔超过 30 秒，屏幕上就又切开一块 —— 读起来像三个人在抢话。
2. 老大在别人忙的时候问一句，那句话说到底还是排在队尾：他要等对方手上的活干完。用户的原话是「一句话要等几分钟」。

**决定**
1. **视觉上再并一档**（`ui/web/js/rows.js` 的 `CONT_MS = 30_000`、`data-cont`）：
   同一个人、半分钟内相邻的几条 → 间距归零、时间戳只留第一个、老大的气泡把相邻圆角收平。
   和后端 `STEP_MERGE_MS` 是同一个数：后端合并「同一段过程话」，前端兜住**漏过来的**相邻几条。
   只改渲染，不动数据 —— 每条消息仍保留自己的 `data-seq`，复制/引用/定位照旧。
2. **插队只清排队项，绝不打断正在跑的那一轮**（`choresAheadOf` / `clearQueueAhead`）：
   老大说话时，把同一个会话里 `status: "queued"`（还没进 transcript）的待办撤掉（最多 5 条），
   让这条排到队头。撤掉的是**别的 agent 派给它的活**，那些消息还在频道里，下次被未读摘要
   叫醒时照样看得到；老大自己连说几句不让路（按顺序答）。
   `requestId` 加 `owner:` 标记，用来区分「谁排的」。

**试过并否决：打断正在跑的任务**（`harness.abortTask`）。
实测两次（`sleep 60` / `sleep 70` 期间插一句）：
- 打断确实生效（`tasks.abort_requested = 1`，工具也返回 `Tool run was aborted`）；
- 但**老大那句话本身被级联吞掉** —— 对方会话的 transcript 里连这条消息的条目都没有，
  老大看到的是彻底的没回应。先提交再打断、先打断再提交，两种顺序都试过，都吞。
- 丢他的消息比慢更坏。所以这条路封了，记进 `docs/CONCESSIONS.md`。

**已知代价**
- 被撤的待办不会自动重投，只靠「频道未读摘要」重新叫醒它。写在这里是为了以后
  有人问「为什么我派的活没回」时能直接定位。
- 正在跑长命令（`sleep 60`）时，老大的问题仍旧要等这条命令结束 —— 那是运行时的硬约束
  （abort 会把输入一起带走），不是本层的取舍。

**回归**：`test/core/queue-jump.test.ts`（7 例：同会话清、别的不动、`placed` 不动、
老大自己的不让路、自己这条不撤、最多 5 条、空表）。视觉合并靠真浏览器实测
（`data-cont="true"` 的相邻两条：间距 0、只有一个时间戳）。

## ADR-067：他答了但没说出来，替他发出去

**病根**
`say` 是 agent 唯一能把话送进频道的手段，而模型经常在最后一轮直接把结论写成正文就结束 ——
一次 `say` 都不调。实测（2026-10-29，会话 2）：transcript 里躺着
`sleep 45 跑完、耗时 45 秒…` 这段最终回答，可 `company` 频道里只有占位「开始处理…」。
老大看到的就是「问了没人理」，而系统认为一切正常。

**决定：事后补发，不改提示词**
新建 `src/core/shell/rescue.ts`。订阅会话提交，看到 `pi.assistant` 的正文就等 6 秒
（同一轮还会接着产出条目，早补等于抢话），然后判三件事：
1. 他还在这条任务里跑着（有 `placed` 提交）→ 让开，最多重试 10 次；
2. 这轮他在这条唤醒消息之后已经说过话 → 不补（`spokeAfterWake`，`note` 与他自己的
   处理中占位都不算「说过」）；
3. 有唤醒位 → 用 `postMessage` 替他说，`wake: false`（补发不该再触发一轮对话）。

**为什么必须在外层兜**
漏调工具是无法禁止的行为，只能在外面兜。放进 `deliver()` 不行 —— 那一层是「把消息
交给会话」，会话还没跑完，它不知道答案是什么。

**顺带修掉两个真 bug（都在写入口）**
1. **占位填错条**：`post.ts` 找待填的占位用的是 `findIndex`，于是填**最早**那条没被
   回过的「开始处理…」。实测补发时答案被塞进 `#26`，而频道里已经有 `#43` —— 屏幕上
   什么都不动。改成 `findLastIndex`（填最近的）。
2. **序号撞号**：`nextSeq` 落后于已有消息时（实测 `nextSeq["company"] = 19` 而频道里
   有 36 条），新消息拿到 `#20`，与旧消息同号。序列唯一的假设一塌，前端按 seq 去重、
   按 `[data-seq=N]` 定位、补历史按 seq 合并就全指向错的那条 —— 这正是「刷新后少了几句」
   的样子。写入口现在以消息本身为准：`highestSeq + 1`。

**回归**：`test/core/rescue.test.ts`（10 例：会补 / 说过就不补 / 没唤醒位不补 /
`note` 与占位不算说过 / 补发顶掉占位不新增一条 / `nextSeq` 落后时不自撞号 / 多条占位填最近的）。
线上实测：`[rescue] 知言 答在会话里但没说出来，已补发到 company（唤自 #43；落成 #44）`，
频道里 `#44 知言 现在 18:26:15。`。

## ADR-068：默认模型必须是清单里真有的，说不出来就回落并说清

**背景（实测，两次同一类）**。`workspace/settings.json` 里写着
`"defaultModel": "commandcode/auto/hy3"`，而 `providers` 里注册的 id 只有 `magpie`。
`setupModels()` 把这个字符串按第一个 `/` 拆成 `{provider:"commandcode", modelId:"auto/hy3"}`
原样返回，`assembleCore()` 再把它 `configure` 进每一个会话 —— 于是每次生成都在模型产字
之前就以 `no_model` 失败。

现场的三条证据：

```
tasks 5543  pi.generation  conv 2  terminal  startedAt→endedAt 相差 2ms
  outcome: {"status":"failed","error":{"message":"Model commandcode/auto/hy3 is not available",
            "detail":{"reason":"no_model"}}}
submissions 5542  "ch:owner:dm:owner-知言:192:知言"  status "unanswered"
entries   conv 2 最后一条是 user（#192），之后没有任何 assistant 条目
```

表现是**所有人都像在休息**：频道里只留下占位「开始处理…」，没有错误、没有回复、进程
0% CPU、`pi.live` 里没有任何 `run`。这和 ADR-0xx（`@CEO 不理我`）是同一类故障的第二次
发作 —— 上一次是 provider 改名（`commandcode` → `magpie`），这一次是 `defaultModel` 手改。

**决定**。`setupModels()` 在返回默认引用之前，拿注册好的清单核一遍（`models.getModel()`）：

- 命中 → 原样返回，不打日志；
- 没命中 → `console.warn("[core] … 指向不存在的模型 X/Y，改用 Z/W")` 并回落到清单里的
  第一个模型；
- 清单本身是空的 → 直接 `throw`，不拿空清单去启动（空清单启动等于全员静默死亡）。

三条入口（`settings.json`、`ANTHROPIC_API_KEY`、`OPENAI_API_KEY`）和本地网关兜底都走这个函数。
`settings.json` 本身也已改成 `magpie/auto/deepseek-v4.1-flash`，并把网关实际提供的
`auto/hy3` 加进清单（备用，不再是默认）。

**为什么不把错误也发声到频道里**：那是第二步（把 `unanswered` 的提交扫出来写一条
`kind:"note"`）。这一条先保证「配错了会自愈，日志里有话」，因为它是唯一让系统整体
失效、且界面上完全看不出异常的那种故障。

**回归**：`test/core/models.test.ts`（7 例）—— 坏 provider 回落并警告 / 坏模型名回落 /
对的引用不动也不警告 / 没写 defaultModel 用第一个 / 清单空则报错 / 清单空且引用坏也报错 /
`settings.json` 读不出来回落本地网关。

## ADR-069：他没答上来要留痕，系统留痕不进沉淀候选

**背景**。ADR-068 修好了一次「全员静默」的故障，但那件事真正的教训不是模型配错，而是
**配错之后界面上什么都没有**：频道里只剩一条占位「开始处理…」，进程 0% CPU，
`pi.live` 里没有 `run`。要靠人猜到「他们没在工作」，再靠翻 sqlite 的 `tasks.outcome`
才知道是 `no_model`。

投递本身「投了就走、不等回复」，这是对的（`deliver.ts` 头注释）。但**不等**不等于
**不知道**：`conversation.submit()` 返回的提交对象能等到结算，结算是 `unanswered`
就说明这一轮一个字都没产出，并且带着 `reason`（实测 `no_model` / `model_error`）。

**决定**。

1. `deliver()` 新增可选 `noteUnanswered`：提交之后在**后台**等它结算，只有 `unanswered`
   才回调。不 `await`（否则投递又变成等回复）、不抛（库关了不该影响别人）、
   只在底层真给了可等待提交时才做（测试替身没有 `.wait`，不能让留痕把投递拖成失败）。
2. 结算原因翻成人话写在 `src/core/channel/unanswered.ts` 的 `reasonText()`：
   `no_model` → 模型引用对不上；`model_error` → 调模型失败；`aborted` / `run_failed`
   各有说法；**没见过的原样贴出来** —— 编一句「未知错误」等于把唯一线索丢掉。
3. 频道里那一行：`#209 叫了 @知言，但他这一轮没答上来：model_error。`（`kind:"note"`，
   不唤醒、不计未读，和投递失败、接力到上限的留痕同一个语汇）。

**顺带修掉一个被它照出来的 bug**：`settleCandidates()` 原来把 `note` 也当候选。
于是「系统写了一条他没答上来」→ 沉淀扫描看见新消息 → 又叫负责人整理记忆 →
他没写 → 游标不推进 → 每轮再问一次。`botHopsSinceOwner` 的告警 note、投递失败的
note 同样会触发。现在 `settleCandidates()` 跳过 `kind === "note"`，
`confirmedBy()` 也只把候选消息的 seq 算进游标。

**为什么不轮询扫描**：`harness.inspect()` 只返回**还没结算**的提交
（`types.d.ts:656`「queued and placed submissions」），`unanswered` 是已结算状态，扫不到。

**回归**：`test/core/unanswered.test.ts`（9 例：原因翻译 3、留痕文案 1、后台等结算 5，
其中「底层没给可等待提交时什么都不做」是这次真踩到的：测试替身没有 `.wait`，
原来的写法让 `deliver` 抛错、目标被记成投递失败）；`test/core/project-memory.test.ts`
新增「系统留痕不是候选」。

## ADR-070 说过的话不再投影一次（「一次说两句」）

**现场**（2026-10-29，沈岸的私聊）：频道里连着两条 ——

```
247 chat 沈岸 | 在，老大，随时待命。
248 say  沈岸 | 已回老大：在，随时待命。
```

会话记录给出的顺序是：`toolResult「已发到「沈岸」#247」` → `assistant text「已回老大：在，随时待命。」`。
也就是说 247 是模型自己用 `say` 说的，248 是**投影管道**把他那句最终正文又落了一条。

**为什么不全是投影的错**：投影是「老大能看见员工说了什么」的唯一连线（`projector.ts` 头注释）。
模型没有调 `say` 的那一轮，正是靠它把答案送出来；`rescue.ts` 那层安全网也依赖它先不动手。
所以不能关掉投影，只能加一道「这句话是不是已经说过了」的判定。

**决定**：`projectionsToPost()` 挡两类正文，思考与工具卡片照常落。

1. **这一轮他已经用 `say` 说过了**（`spokenResult(convId) !== undefined`）。最终回答里那段正文
   往往是对刚做过的事的复述 —— 尤其「已回老大」「已发到频道」这种元陈述。`speech.ts` 的
   `spokenResult` 本来就是「本轮已说过」的记录，投递（下一轮开始）才清空，恰好等价于
   「这句话已经发过了」，不需要新的状态。
2. 刚在同一个频道说过同样的话（原有的 `alreadySaid`：正文相同或带同一个链接）。

**顺带改提示词**：`renderReplyRules()` 增一行「别复述：最终回答里不要写「已回老大」「已发到频道」
这类话」。判据在代码里兜底，但这句能减少一半发生概率 —— 实测这句话确实进了模型输入。

**为什么不做「同一轮第二句直接拒」**：那是 `say` 的护栏（ADR-063/064）已经做的事，管的是模型
主动发言；这里管的是**系统替他发**的那条，两者在不同层，混在一起会让「他到底说没说」变得
无法回答。

**回归**：`test/core/projector.test.ts` 新增 4 例（说过就不投影 / 没说过照常投影 /
刚说过同样的也不投影 / 只挡正文不挡过程卡片）。

## ADR-071 命令日志不进老大的私聊

**现场**：`ui/web` 的侧栏预览里，`dm:owner-林越` 显示的是
`$ cd /Users/kirer/projects/ai-company && sed -n 1,25p pack…`。查下去发现他那个私聊里
根本没有一句人话 —— 全是 `run` 记的命令行。

**为什么以前没拦住**：ADR-040 给投影管道加了闸（老大的私聊只留 `say`），但 `run` 的
`logWork()` 是**直接 `postMessage`** 写一条 `kind:"work"`，不经过投影。而 `personalId(slug)`
在老大那里恰好就是 `dm:owner-<slug>`，同一条频道。

**决定**：`shouldLogWork(channel)` —— 只有 `dm:` 前缀且成员里有老大时不写。其余（员工之间
的私聊、项目频道、公司群）照记。

**代价与补救**：老大在私聊里看不到命令行过程了。命令输出本来就在 `run` 的返回里给模型，
`read_channel` / `read_history` 也还查得到；真要复现一条命令，问一句即可，比翻几百行 `$ cd` 快。

**顺带修侧栏预览**（`previewOf` 上游）：预览优先取 `SPOKEN_KINDS`（chat/say/question/decision/report），
一层都没有才退回「最后一条非 note」。以前只排 `note`，于是 `work`/`tool` 当上了预览 —— 一列
频道看起来像全是机器输出。

**回归**：`test/core/work-log.test.ts` 4 例（老大私聊不记 / 员工私聊照记 / 项目频道照记 /
频道不存在不写）；`test/core/view.test.ts` 新增 3 例预览。

## ADR-072 「正在执行」的真实起点 + 接力上限按「说出口的话」算

**背景（老大两句话）**：
1. 「那个『执行了命令 67s』代表正在运行吗？」—— 它确实在跑，但那个 67s 会跳成 55s。
2. 「明明他们 at 的别人，跟我有什么关系。」（同一轮的误标，见 ADR-072 的兄弟条目
   `kind=decision` 自动补 owner，已一并修掉）

**为什么 67s 会跳成 55s**：`think`/`tool` 的 `at` 是**投影落库**时刻（`projector.ts` 写明
会话条目没有时间戳），比模型真正开始思考晚一个首包。而唯一能表示「正在跑」的
`processing` 占位——它的 `at` 本来是触发那条消息的时刻，却在第一条过程行落库时被**原地
填充**成投影时刻，`processing` 也一起置 false。于是「起点 = 第一条过程行 at」在首包之后才
成立：跑的时候按它算出的秒数包含了首包前的空白，填充那一刻起点前移，数字原地变小。

**决定一：给消息加可选 `startedAt`**（`Message.startedAt?: number`）。
只在创建 `processing` 占位时写入 `input.at`（= 触发那条消息到达的时刻），占位被填充时
`...placeholder` 自然沿用。`view.ts` 原样带出。界面起点 = `startedAt ?? 第一条过程行 at`
（`ui/web/js/rows.js` 的 `runStartAt()`）—— 取不到就退回旧行为，不报错、不猜。
不新增接口、不改任何现有字段语义（`at` 仍然是「这条消息落库的时刻」）。

**决定二：接力上限只数「说出口的话」**（`src/core/channel/state.ts` 的 `RELAY_KINDS`
= chat/say/question/decision/report）。`think`/`tool` 是过程投影，不叫醒任何人；把它们
算进接力，等于「干得多更容易被判失控」—— 一个 agent 跑 14 条命令就吃掉一整个额度。

**决定三：项目频道放宽到 6 倍**（`relayLimit()`：`proj:` 前缀 6 倍，其余 3 倍）。
实测 `proj:solo` 3 个 agent 按 9 条两次就撞线，拦掉的是「两个人来回对齐一句」，不是循环。
闲聊/公司频道保持 3 倍。

**为什么不干脆去掉上限**：A 回 → 唤醒 B → B 回 → 又唤醒 A 的循环是唯一真会烧钱失控的地方
（ADR-042 的原始理由没变）。放宽的是额度，不是取消护栏。

**回归**：`test/core/relay.test.ts` 新增「项目频道按 6 倍」「过程投影不算接力」两例；
`test/core/channel-state.test.ts` 新增「`startedAt` 原样落库；不传就不写这个键」一例
（「没有」和「0」是两件事：键不存在界面才会退回旧算法）。

## ADR-073 老板改称「老大」，`@owner` 显示成 `@老大`

**背景。** 老板的原话：「@owner 能否改成 @老大。以后称呼我为老大。」截图里员工一条消息正文第
一个词是 `@owner`，界面上是一串没人读的英文 slug —— 而它其实就是老板本人。

**决定。** 一个字面量不许再漏到界面上：

1. **展示标签**改成 `老大`（`view.ts` 的 `labelIn`、`assemble.ts` 的两处 `labelOf`、
   `agent/prompt.ts` 的 `actorLabel`、`shell/main.ts` 的 `ownerName`）。这五处是「老板」这个词
   进入界面的全部入口，其余地方（频道消息正文、rules.md）由它们带动。
2. **别名表加 `老大`**（`channel/alias.ts` 的 `OWNER_ALIASES`）。`@老大`、`@老板`、`@owner`
   都解析成 `owner`；前两个必须在表里，因为老消息正文已经写死了它们。
3. **界面统一画成 `@老大`**（`ui/web/js/rows.js` 的 `paintMentions`）：认识的三种叫法都收进正则，
   画出来一律是 `@老大`。历史数据里的 `@owner` 因此不用洗库。
4. **对模型说的话跟着改**：`rules.md`（`workspace/` 与 `seed/` 逐字节一致）第 10 条从
   「用 `@owner` 叫老板（`@老大` 也行）」改成「用 `@老大` 叫他（`@owner` 也认，但界面上显示的是
   `@老大`）」；`seed/skills/{工作规矩,记忆整理}/SKILL.md`、`seed/assistant/{立项,招人}/SKILL.md`、
   助理播种提示、`tools.ts` 的 `mention` 参数举例一并改。

**为什么不改 slug。** `owner` 是 6 张表里的外键、`dm:owner-*` 频道 id 的一部分、`localStorage`
与几十个测试的常量。改它等于重写数据；而它只是一个内部标识，界面不该被迫展示它。

5. **称呼写进身份，不只写进规矩**（老板追加的要求：「写进去」）。两处：
   - `agent/prompt.ts` 的 `orgSection` 加一行事实陈述 —— 「对老板的称呼：老大。正文里直接写「老大」，
     要叫他写 `@老大` —— 不要写 `@owner`。」放在组织那一段（和「你的上级是谁」并列），因为它和
     汇报线一样是**事实**；`rules.md` 是可删可改的工作约定，称呼不该跟着丢。
   - 三个人的 `workspace/agents/<slug>/identity.md` 正文改口，并在末尾加「## 怎么称呼老大」。
     改这一处是因为 identity 的正文原样进提示词，是他们自己读到的第一段话。

**没做的。** `paintMentions` 对「解析不出人」的 `@token` 也会上色（线上实测有一条 `@你的`
被画成了 mention）。这是既有行为、不是本次引入，且上色比裸文本更诚实地区分了「这是个 @」；
先留着。

**回归。** `test/core/mention-alias.test.ts` 新增「@老大 解析成 owner，@老板 也还认」；
`test/core/identity.test.ts` 新增「称呼写进组织这一段」；
`identity/rules-prompt/shell` 三处断言里的「老板」跟着改。真浏览器实测：侧栏与消息头显示
「老大」，正文里的 `@owner` 全部渲染成 `@老大`（`document.body.innerText.includes('@owner')`
为 `false`）。

## ADR-074 界面重做：骨架和配色整体对齐 DSH

**背景。** v2（ADR 里那套「取景框 + 白纸 + IBM Plex + 深松绿」）`inspect.mjs` 是 0 FAIL，
但老大看完只说了四个字：「很垃圾」。所以 0 FAIL 不等于好看 —— 那条检查器管的是**纪律**
（对比度、字号数量、有没有 emoji），不管**骨架**。而 v2 的骨架是错的那种：一张浮在页面上的
纸、一个横贯的顶栏、logo 挤在顶栏里，再加上给中文界面套的 webfont。

**做法：不去猜，去抄。** 把 DSH 桌面端（`deepseek-harness`）clone 下来读源码，抽出
布局 / 配色 / 字号 / 间距 / 圆角的字面值，一条一条落到我们的变量上。

**五条决定：**

1. **两栏到底**（侧栏 260 + 主列），logo 长在侧栏头顶，没有横贯顶栏。
   主列的标题行 56px + 0.5px 下边线。这是「像桌面应用」的第一性结构。
2. **正文用系统 UI 字体栈，不用 webfont。** DSH 用 `-apple-system, BlinkMacSystemFont,
   "Segoe UI", "PingFang SC"…`，所以在 macOS 上就是原生。v2 的 IBM Plex 反而把界面
   做成了「一个网页」。Montserrat 只留给 logo 那个 wordmark。
3. **配色照搬 DSH 的语义层**：一个蓝（`deepseek-500` 浅 / `deepseek-400` 深），
   三档面（侧栏 / 主区 / 输入卡），三档墨，三档线。v2 的深松绿整套废掉。
4. **几何照搬**：消息列 `min(100% - 32px, clamp(680px, 64%, 920px))`、气泡圆角 20 +
   padding 10/16、输入卡圆角 28 + 描边画在 `box-shadow` 里、发送键 34 满圆、`＋` 28 满圆、
   圆角 6 档（4/8/12/16/20/28）、**线宽默认 0.5px**。
5. **字号只剩两条主线**：14/24（正文）和 13/20（次级），其余都是 meta。

**为什么敢照搬。** 这些不是审美偏好，是**结构约束**：14/24 的行高决定「呼吸感」，
三档灰决定层次读不读得出来，0.5px 决定发丝线还是表格线。抄错这些，再多细节也救不回来。

**没做的（都记着）。**

- **TurnNavigator**（右侧那排 2px 刻度轨）：我们一条对话的消息数还很少，先不做。
- **`corner-shape: superellipse`**：只有新 Chromium/Safari 支持，退化后就是普通圆角，不影响。
- **`inspect.mjs` 的 `font-count` 会报 1 FAIL**（390px 下 3 个字体族：系统栈 + SF Mono +
  Montserrat）。这是**故意**的：DSH 也是三个。检查器的规则是给「一套页面一个字体」准备的，
  桌面应用有 wordmark 是常态。这条 FAIL 记在这里，不当作欠债。
- `plex-*.woff2` 五个文件留在 `ui/web/fonts/` 但已无人引用，可随时删。

## ADR-075 侧栏可以收起成 56px 的图标条

**背景。** DSH 的侧栏能收到 56px（图标条），我们不能 —— 一屏宽 1440 时，260px 的侧栏吃掉
18% 的宽度，而老板经常要同时看两条消息的正文。

**决定。**

1. **收起 = 换 `--sidebar`，不是藏起来。** `.frame[data-side="rail"] { --sidebar: 56px }`，
   宽度、隐藏哪些列、行变成 36×36 方块，全部由这一个属性派生；JS 只写属性，不写尺寸。
   尺寸只有一个家（CSS），改一处就够。
2. **收起不是「变小」，是换信息密度。** 名字 / 预览 / 相对时间全收起来 —— 56px 里塞两行中文
   只会挤出半行字。未读从数字退化成 7px 的点：数字放不下，但「有东西」这件事不能丢。
3. **名字进 `title`。** 收起后光看一堆脸分不清谁是谁；`title` 同时喂鼠标悬停和读屏的
   无障碍名字，比自绘 tooltip 便宜且不会漏。
4. **状态存 `localStorage["ai-company.side"]`。** 收起是「我现在想多看点正文」的临时姿态，
   但重启后再点一次的代价比记住它大。
5. **手机上不提供。** 手机侧栏是整屏的一个区域（`body[data-pane]` 切换），没有可收的列。

**没做的。** 拖拽调宽（DSH 支持 264–420）：我们的侧栏内容只有两行文字，宽度没有实际收益，
先不做。

**回归。** `test/ui/side-rail.test.ts`（6 例）钉住：宽度 56、由 `data-side` 驱动、收起后藏三样、
36×36 方块 + 点状未读、手机上不提供、本地存储 + `title` 兜底。

## ADR-076 右栏是第三列，不是浮层

**背景。** 「详情」原来是从右边展开的浮层（`position: fixed`，420px，盖住纸面）。
老板要的东西变成两样：详情 **+** 工作区文件（DSH 右边那一栏）。两个都塞进浮层就只能叠罗汉。

**决定。**

1. **它是 `.frame` 的第三列**，宽度 `--rightbar` 0 ↔ 360，跟着一起过渡。
   浮层可以盖住别人，但**推不开**别人 —— 而这一栏的用途是「一边读文件一边写消息」，
   盖住正文等于每次都手动关一下。
2. **两帧打开**：先 `hidden=false`，下一帧改 `data-right="open"`。同一帧改两样，
   浏览器会直接跳到终态，动画不存在（这是 grid 列宽过渡的硬约束，不是风格问题）。
3. **列 300ms、内容 240ms 带 60ms 延迟**，同一条 `cubic-bezier(0.4, 0, 0.2, 1)`：
   先让列让开、字后进来，否则内容会在半宽里被挤着重排一遍 —— 那看起来像「闪」。
4. **收起等滑完再 `hidden`**（300ms，`prefers-reduced-motion` 时为 0）。直接隐藏
   等于把动画剪掉，右边会「啪」地弹一下。
5. **换频道不收起，只换内容。** 右栏现在属于布局，收起来会让中列宽度跳一下；
   而「详情」讲的就是当前这个频道，跟着换是正确的。
6. **`--rightbar: 0px` 必须有定义。** `grid-template-columns` 里 `var()` 解析失败会让
   **整条声明作废**，三列塌成一列（症状：侧栏和中栏叠在一起）。这条是踩过的坑。

**文件页的数据来自新接口 `GET /api/files?path=`**，只读、路径校验在工作区根之内、
二进制只报大小、超 200KB 不传。前端不做 `..` 判断 —— 同一件事有两处判断就会有两套答案。

**没做的。** 拖拽调宽、多文件对照、在右栏里编辑（写操作一律走 agent，不给界面开写口子）。

**回归。** `test/ui/right-panel.test.ts`（8 例）：三列 + `--rightbar` 有 0 定义、
落在第三列且不是 fixed、`hidden` 不占位、两条动画的时长与延迟、tab 下划线 scaleX、
关闭等 300ms、文件页不拼路径。

## ADR-077 右侧栏：一个入口、一个关闭、能往下钻也能退回来

**背景。** 右栏上线后老板连问四件事：为什么有两个关闭按钮、点某个成员读不到档案、
进了某个人的档案怎么回来、详情和文件能不能合成一个按钮。四条都是「同一件事有两份实现」
的产物，不是样式问题。

**决定。**

1. **一个入口。** 顶栏只留「详情」按钮；详情与文件是同一栏里的两个 tab。
   两个按钮长得几乎一样，点错的结果是「我想看文件，怎么弹出人名」。
2. **一个关闭。** ✕ 只在栏顶那条 bar 上（它是这一列的控件）。内容里原来那个 ✕ 删掉：
   同一个动作在一屏出现两次，人会先怀疑「这两个是不是不一样」。
3. **能往下钻也能退回来。** 点成员换成那个人的档案，栏顶出现「‹ 返回」；栈底永远是当前
   频道，退到底不画返回。换频道时栈重置 —— 那一栏讲的就是这个频道。
4. **老大那一行不可点。** 他没有「档案」页（`GET /api/people/owner` 是 404）。做成按钮的
   结果就是老板点一下收到「没有这个人」。同理，读不到档案时**保持原样**再 toast：
   把整块内容换成一行错误，等于点错一下就把刚才那个项目详情弄丢了。
5. **`identity.md` 开头与自己同名的 `# 标题` 剥掉**（只在完全一致时）。面板顶上已经写着名字，
   同一屏出现两遍像渲染错了。
6. **设置弹窗重做。** 选项改成「图标在上、名字在下、右上角勾」的卡片，选中态是
   `--accent-wash` + 46% 强调色描边，每段下面一行说明。布局是「看起来怎么样」的事，
   一行胶囊加个对勾没有说服力。

**为什么不把「文件」做成独立按钮。** 它和「详情」共享同一个容器、同一条动画、同一个
Esc 语义；拆成两个按钮就要处理「同时开着算谁的」，而收益只是少点一次 tab。

**回归。** `test/ui/right-panel.test.ts`（8 例）继续守列/动画/路径；`test/ui/detail-panel.test.ts`
守「档案里的东西全部来自后端」。这两条行为靠真浏览器验（已验：✕ 仅 1 个、老大不可点、
进人后返回可见、返回后回到频道、设置 400px / 5 个选项各有图标）。

## ADR-078 前端模块的具名导入必须被静态检查

**背景。** `ui/web/` 没有构建步骤，浏览器直接按 ES module 链接。2026-10-30 白了一次屏：
成员改了 `app.js`（`import { markGroupDone } from "./rows.js"`）和 `rows.js`，只补了一边。
浏览器在**链接阶段**就抛 `Uncaught SyntaxError: The requested module './rows.js' does not
provide an export named 'markGroupDone'` —— 整页一个功能都点不开。

**为什么现有检查都漏了。** `tsc --noEmit` 不覆盖 `ui/web/*.js`（不在 tsconfig 的 include 里）；
单测也覆盖不到，因为没有哪条测试会去 import「出错的组合」；`check-boundaries` 管的是模块
方向，不管名字。只有真浏览器会炸，而人不会每改一行都开浏览器。

**决定。** 新增 `test/ui/imports.test.ts`：扫 `ui/web/js/*.js` 里所有
`import { … } from "./x.js"`，逐个核对 `x.js` 确实导出了那个名字（`export function|const|
let|class` + `export { … }`），错了就列出 `调用方 → 目标：没有导出 X`。
已验证它抓得住：把 `rows.js` 的 `export function markGroupDone` 改成非导出，这条立刻失败。

**代价。** 一个 2 例的文件、~100 行、跑 114ms。它替代不了浏览器验收，但能拦住
「改了两个文件、只补了一边」这一类把整个前端变成白屏的错。

**同时落地的功能改动（成员做的，我补的那半边）。** 跑完的过程组不再显示「名字 已完成，
用时 X 秒」，组头只剩一个展开箭头；定格由 `rows.js` 新导出 `markGroupDone(group, endAt)`
负责（只改那一个节点，不重建 —— 重建会吃掉老板正开着的展开状态）；底部活动行跑完立刻收掉，
不再停 4 秒显示「已完成」。

## ADR-079：前端换成 React + TypeScript + Vite（取代「无构建」的约定）

**背景。** 旧前端是 `ui/web/` 下 11295 行手写 JS + CSS，靠字符串拼 DOM。老板的原话是
「前端小毛病太多了，主要是消息展示的各种情况」「很有重构前端的必要了，尽量使用成熟的框架」。

**病根不是「没框架」。** 复盘那批毛病，几乎全部来自同一个渲染策略：

- 每条 SSE 消息到达就把整列 `replaceChildren` 重建（1316 次/15 秒，最长一帧卡 2.7 秒）；
- 过程行「该排在哪句话下面」靠事后搬 DOM 节点；
- 「现在展开着没有」「滚动到哪」这类视图状态散在闭包和 `dataset.*` 里，两边不同步。

所以引入框架的价值不是「多一个库」，而是把「状态 → 视图」变成单向的：视图状态写进
React state，行模型由纯函数算出来，DOM 不再被手工搬来搬去。

**决定。**
1. 源码搬到 `ui/app/`（React 18 + TypeScript strict + Vite 6），构建产物写回 `ui/web/` ——
   服务端的 `serveStatic` 一直是「发 `ui/web`」，它不需要知道有构建这回事。
2. `vite.config.ts` 用 `emptyOutDir: false`：清空会在构建出错时把 `index.html` 一起删掉，
   那时连白屏都看不到，只剩 404。
3. **消息流的关键规则抽成纯函数** `ui/app/src/stream/model.ts` 的 `buildRows()`：谁跟谁算一段、
   过程行归谁、时间分隔插哪儿、占位怎么死，全部在这里算，可以单测（`test/ui/stream-model.test.ts`）。
   `Stream.tsx` 只负责把它画出来。
4. `check` 脚本加一道 `tsc -p ui/app/tsconfig.json`；`check-boundaries` 的「路由必须有消费者」
   改成扫 `ui/app/src`（原来是扫已删除的 `ui/web/js`）。
5. 样式沿用已经认可的 DSH 观感（`ui/app/src/styles/*.css`，类名不变），只补 React 需要的少数结构。

**代价。** 仓库第一次有了构建步骤：改完界面必须 `npm run ui:build`，忘了就是「改了没生效」。
这一点必须写进 AGENTS.md 的固定动作里，否则下一个人会踩。同时 `test/ui/` 里那些
「读源码文本正则匹配」的测试失去意义，改成测纯函数或直接删。

**顺带作废 ADR-078 的那条测试。** `test/ui/imports.test.ts` 是为了在没有编译步骤时防
「导出名字对不上」而写的，现在 `tsc -p ui/app` + Vite 构建在任何一次 `npm run check` 里都会
报同一类错，那个文件已删除。

**没做的。** 不引入状态库（Redux/Zustand/Jotai）—— 一个 `useSyncExternalStore` 的 40 行 store
够用；不引入 UI 组件库 —— 观感是手写的，组件库会把它拉回「生成式仪表盘」。

## ADR-080：五个词定死——我、助理、团队、agents、团队管理员

**背景。** 同一件事在仓库里有好几套名字：真人叫「老板」「老大」「上级」「owner」；项目既是
一个聊天频道又是一个档案目录；「项目负责人」和「老板」在代码里都叫 `owner`（`ChannelState.owner`
与 `READMEFront.owner` 在同一个函数里含义相反）。频道还按前缀分成 `dm:` / `proj:` / `all`
三套，每套一套规则。

**决定。** 组织只有五个概念，代码与文档按这张表对齐：

| 概念 | 内部标识 | 界面上叫 |
|---|---|---|
| 真人（唯一的用户） | `owner` / `OWNER_SLUG` / `dm:owner-*` **保持不变** | 我 |
| 直接向我汇报的 agent | `manager: owner`（已有字段） | 助理（默认「知言」） |
| 有档案的一组人和一个目标 | `team:<slug>` / `teams/<slug>/` / `src/core/team/` | 团队 |
| 团队成员（含助理） | `agents/<slug>/` | agents / 同事 |
| 团队负责人 | README 的 `lead:` / `ChannelState.lead` | 团队管理员 |

1. **内部 `owner` 保留**，不做数据迁移；只改给人看的文字。代价是提示词里会出现
   「我是上级」这种歧义，所以在系统提示词首行加一句定义：**提示词里的「我」指用户本人**，
   agent 称呼用户时用「你」。
2. **项目 → 团队** 全改：目录、频道前缀（`proj:` → `team:`）、`identity.md` 的 `project:`
   字段、工具名（`list_projects` → `list_teams` 等）、`scope: "project"` → `"team"`。
   这是一次带数据迁移的改名，脚本见 `scripts/rename-teams.ts`（默认 dry-run）。
3. **项目负责人 → 团队管理员**：README 头字段 `owner:` 改成 `lead:`，
   `ChannelState.owner/ownerLabel` 改成 `lead/leadLabel`。**不能机械替换**：`ownership`、
   `ownerless` 是 pi-durable 的 API，`projection` 是「投影」，都不是这个意思。

**为什么团队不是一个新实体。** 团队 = 一个有档案的群聊。没有 `README.md` 的群就是一个
拉起来问一句的群，不需要登记、不需要成员表、不需要负责人。这样「建团队」和「拉个群」是
同一个动作，少一套状态机。

**代价。** 磁盘上已有 `proj:solo`(214 条)、`proj:ai-drama`(15 条) 与 6 个 `dm:owner-*`(579 条)，
不迁移就是孤儿消息、员工被 `syncTeamChannel` 踢出群。迁移脚本必须先备份、可 dry-run、
可重入。

## ADR-081：删掉「过程剧场」——投影、占位、步骤合并、草稿流

**背景。** 为了让界面「看得见 agent 在干活」，仓库里长出了四层东西：把 think/tool 事件
投影成消息写进个人频道（`shell/projector.ts` + `startTranscriptSink`）、发消息时先占位
（pending/processing，10 分钟 TTL）、把同一轮的多个 tool 合并成 step（`STEP_MERGE_MS`）、
以及从 `subscribeCommits` 里偷 say 参数当「正在说」（`runtime/drafts.ts`）。它们共用一套
索引、一个反向注入的 hook（`setChannelStreamHook`）、一条 SSE `draft` 事件和约 250 行状态机，
而 ADR-040 的数据是：私聊 30 分钟 76–197 条，回复率 1%。问题不是「看不见思考」。

**决定。** 全部删除，不留开关：
- `shell/projector.ts`、`backfillTranscripts`、`startTranscriptSink`；
- 占位消息与 `expireStalePlaceholders`、`PLACEHOLDER_TTL_MS`；
- step 合并与 `STEP_MERGE_MS`；
- `runtime/drafts.ts`、SSE `draft` 事件、「正在说」界面；
- 生成 `think` / `tool` / `work` 消息的路径。历史库里已有的这些 `kind` 仍然要能读出来
  （按普通行显示或忽略），不做数据清洗。

**以后要「正在输入」怎么办。** 用 `harness.inspect()` 的会话忙闲在读取时派生，不落库、
不进消息表、不发 SSE 事件。界面可以有，数据模型里没有。

**代价。** 删掉后界面在 agent 干活期间是静的，只能看到最终的 `say`。这是有意的：先保证
「消息 = 说过的话」，恢复可见性再作为纯读取层的功能加回来。

## ADR-082：四层，依赖只能朝一个方向

**背景。** `shell/` 曾经同时是 HTTP 传输、业务编排、前端契约和组合根。`serve.ts` 1305 行，
每条路由的 handler 里直接写业务；`view.ts`（界面投影）长在外壳里；`ui/app/src/api/types.ts`
是 DTO 的手抄镜像，改后端字段界面不会报错。ADR-016 要求「不画后端没有的东西」，但没有机制
保证界面看到的就是后端愿意承诺的。

**决定。** 内核分四层，依赖方向单向：

```
interface  →  app  →  domain
     ↘         ↓
       view（纯投影，谁都能用，自己不依赖任何人）
shell = 装配层，唯一可以同时 import 全部
```

| 层 | 目录 | 规则 |
|---|---|---|
| domain | `agent/` `channel/` `team/` `runtime/` | 不 import 其它三层；只有 `runtime/` 能碰 pi-durable |
| app | `app/` | 用例：发消息、开私聊、开团队、招人、读数；不 import `node:http`，不写 HTTP 状态码 |
| view | `view/` | 纯函数，零 IO、零 `node:*`；`view/dto.ts` 是界面契约的唯一权威 |
| interface | `interface/http/` | 唯一能 `import node:http` 的地方；handler 只做「解析 → 调 app → 序列化」，≤30 行 |
| shell | `shell/` | `assemble.ts` / `main.ts` / `serve.ts`，只做装配与启动 |

`scripts/check-boundaries.mjs` 机械检查这五条，违反即失败（和 ADR-002 的三条边界同一机制）。

**为什么 view 不依赖 domain 的类型。** 如果 DTO 直接引用 `ChannelState`，改内核字段就会
悄悄改掉界面契约。DTO 自带结构，投影函数显式挑字段，界面 type-only 引用 DTO。

**代价。** 多了一层转发，一个路由要跨三个文件才能读完。这是有意的：读 `interface/http/routes.ts`
能看到「有哪些接口」，读 `app/` 能看到「系统能做什么」，读 `view/` 能看到「界面被承诺了什么」。

## ADR-083：把 pi 已经给的三个机制接上，不再自己绕

**背景。** `runtime/open.ts` 只给底座传了 models/registry/settings，三处能力一直空着：

1. **失败是静音的。** pi 的 crash-loop guard 第 5 次重启后会把任务 park 成 `blocked:
   restart_limit` —— 既不 pending 也不 terminal，对我们就是「这个人突然不干活了」，日志里
   什么都没有。
2. **compaction 永不触发。** `models.ts` 写 `contextWindow ?? 1_000_000`，阈值 983616；
   真实 200k 模型永远到不了，最后是 provider overflow 报错。等于把底座最贵的一个机制关掉了。
3. **提示词整段 `tag:false`**，打穿前缀缓存（ADR-005 / C-003）：每轮重新计费整段 system。

**决定。**

- **接 `onReport`。** 报告落 `workspace/logs/runtime.jsonl`（单条 4KB、单文件 5MB 轮转，
  与 `logs/jank.jsonl` 同一套写法）；最近一条非良性报告经 `GET /api/diag` 的 `lastReport`
  露出来。`task_outdated` 视为良性（每次启动都会出现，不能当事故）。
- **真实 `contextWindow`。** 先用 pi-ai 的模型目录取值；取不到回落 **128k**（保守：宁可
  早压缩，也不要等 provider 报错）。compaction 显式配：reserve 15%、keepRecent 10%
  （底 8192、封顶阈值一半）、background 5%，按 `provider/model` 出 overrides。
- **提示词分段。** 稳定段 `who → rules → position → team → tools → memory → skills →
  directory`，每段一个 section key（`tag:false`，因为 tag 会多出字节）；内容没变的段不发
  新版本。渲染结果与旧实现**逐字节相同**（黄金测试 `test/core/prompt-segments.test.ts`）。

**代价与边界。** 底座没有「某段失效」的钩子，只有按 key 的最小 patch，所以新增段或调序会
触发一次性整块重写。`telemetry` 不接：它要求 `pi-telemetry` 的 `TelemetryContext`，那是
传递依赖、不在 dependencies 里，自写适配器的成本高于收益。以上三条写进 `CONCESSIONS.md`
的条目可标「已处理」。

## ADR-084：工具 17 → 11，一个动词一件事

**背景。** 17 个工具每轮都进提示词；其中 5 组是同一件事换个动词
（`list_skills`/`read_skill`/`write_skill`、`list_teams`/`read_team`、
`read_channel`、`read_history`/`recall`、`read_file`/`write_file`），模型要在近义名字里
选，选错的代价是一轮对话。`org` 返回的东西提示词里已经有一份。

**决定。** 收敛成 11 个，合并的工具用 `action` 枚举，不用多个布尔参数：

| 工具 | 吸收 |
|---|---|
| `say` | — |
| `chats` | `read_channel`（`list` 列会话、`read` 读消息） |
| `read_history` | `recall`（`scope: channel｜memory`） |
| `remember` | — |
| `teams` | `list_teams` + `read_team` |
| `write_team` | — |
| `skills` | `list_skills` + `read_skill` + `write_skill` |
| `hire` | — |
| `me` | `update_identity`（`show` 顺带返回自己的身份/团队/上级） |
| `run` | — |
| `file` | `read_file` + `write_file` |
| 删除 | `org` |

**为什么不用「一个万能工具」。** 工具的 description 是模型唯一的说明书。合并到「同一件事
的几种做法」是收敛；合并到「读写删查都走一个入口」是把选择成本转成参数猜测成本。`say`
尤其不合并：它是唯一有硬拦（长度、英文独白、私聊权限）的工具，值得独立。

**验收。** 工具清单仍由注册表实拍（不写死名字）；`say` 的选频道/叫醒/硬拦行为不变；
`live` 12/12。

## ADR-085：瘦身是删代码，不是加防御——审计出的 4 个 bug 与「过防御」清理

**背景**：四层与工具收敛落地后，代码仍然偏多（`src/core` 10340 行、前端死 CSS 801 行）。
五个只读 agent 逐符号审了一遍（报告在 `workspace/notes/code-audit*.md`），结论是三类：
死代码、重复实现、过防御。同一轮里还查出 4 个真 bug —— 说明「代码多」不只是难读，
它会让同一条规则存在两个实现，然后只有其中一个被修。

**决策**：
1. 删死代码与重复实现，不为了「以后可能要用」保留。新增三处唯一实现：
   `agent/frontmatter.ts`（YAML 头）、`oneline.ts`（折行截断）、`runtime/io.ts`
   （`readTextOrUndefined` / `createSerialGate`）；`channel/state.ts` 的 `upsertChannel`
   成为「有则并成员、无则建」的唯一实现。
2. 过防御该减的减：SSE 的按连接游标合成一份共享游标（字节合同用
   `test/core/hub-stream.test.ts` 钉死）、`open.ts` 的翻页/sqlite 样板合一、
   `main.ts` 换 `node:util` 的 `parseArgs`。
3. 修 4 个 bug：`chats` 的 read 改走 `markRead`（游标夹取）；`ownerSpeak` 每次重新读名册
   合成 labels（原来用装配期那份，新人的显示名永远缺）；identity / SKILL / 团队 README
   三条写盘补 `redact`；前端设置面板的 `aria-pressed` 改 `aria-checked`、代码块复制改用
   事件委托（正文是 `dangerouslySetInnerHTML`，React 事件接不到里面的按钮）。
4. `needsOwner()` 删除（ADR-037 的关键词嗅探在更早就已移除，函数只剩恒 false 的空壳）：
   「要你拍板」的判据现在只有一处 —— `say` 在两种情形把 `owner` 加进 `mentions`：
   正文显式 @我，或 `kind=decision` 且没点别人。ADR-037 的「两处判据故意不同」因此作废：
   投递侧与「找你」列表现在是同一个判据。

**不做的**：`reconcileZombieTasks` 的单事务顺序、`serialize.ts` 的进程级串行、
`models.ts` 的四级回落、`rescue.ts` 的三个阈值 —— 这些是踩过坑换来的，不是防御。
`tools.ts` 里 7 处 `typeof slug !== "string"` 也不收：收成回调要重排 7 个工具体，
净行数为 0，diff 却覆盖全部工具。

**验收**：`npm run check` 绿、59 文件 511 例、`ui:build` 成功、`live` 两轮 12/12。

## ADR-086：唤醒只有一条路；沉淀那一轮的正文也外置

**背景**：这一刀修的是同一个形状的两个实例——**同一条规矩存在两个实现，只有一个被修**。

1. **唤醒有两条路。** `post()` 那条有全套兜底（合并排队项、记 wake、没产出留痕、贴回话段），
   而 `team/settle.ts` 直接 `conversation.submit()`：裸提示词，三样都没有。于是「叫醒」在两处
   行为不同；settle 那条出问题时频道里一片空白，症状和「模型不肯干」一模一样（live 11/12
   排查了很久才分清）。
2. **提示词外置漏了第三条路。** 第一刀只覆盖了 system 8 段和 delivery 2 段，沉淀那一轮的正文
   还是 `team/memory.ts` 里的硬编码散文，而且带着 V2 工具语法（`skills(action=read)`、
   `remember(scope=team)`、`say` 时传 `channel:`）。它只说「按技能整理」，可技能正文**不在**
   那一轮的上下文里（常驻的只有名字和一句描述），模型既没判据、也没被要求去读技能 ——
   判断「这批不值得记」是很自然的结果。

**决策**：

1. **`channel/wake.ts` 收口**：`wake()` 是唯一的唤醒入口，把合并排队项、记 wake、一轮一句的
   重置、提交、没产出留痕全收进来。正文用 `bodyOf(merged, busy)` 回调给 —— 「把 N 条并成了
   这一条」要先合并才知道条数，所以不能传拼好的字符串。`post()` 与 `settle` 都走它。
2. **沉淀正文外置**到 `seed/prompt/95-settle.md`（`use: delivery`，段名 `settle`，插槽
   `{{team}}` / `{{pending}}` / `{{candidates}}`）。`renderSettlePrompt(template, team,
   candidates)` 只做排版。**模板缺了就不问**（warn + 游标不推进），不退回硬编码散文 ——
   退回去等于让「缺模板」永远发现不了。
3. **插槽叫 `{{pending}}`，不叫 `{{count}}`**：`{{count}}` 在 `20-position.md` 里已经是
   「全公司 agent 数」。一个名字两个意思，就是两个家。
4. **判据写进正文，且要可判断**：decision 类必须记（拍板、定方向、改验收标准，漏记下一个人
   会照旧结论干活）；report 类看有没有超出当前任务；纯过程话、客套、复述命令输出不记；
   拿不准就问「下一个人不知道这条，会不会做错」。

**不做的**：

- 不改游标语义（ADR-033）：问完只记 `waiting`，记忆文件 mtime 变了才推进。
- 不把判据写成代码。判据是给模型看的，人和 agent 都要能改 —— 所以它是 md，不是 if。
- 不在 `assembleCore` 里为「读不到模板」加兜底文案：生产入口 `main.ts` 播种后直接断言
  system 模板非空，读不到就抛。**单段缺失不抛**（`skip-empty` 就是为合法编辑准备的）。

**验收**：`npm run check`（现在含 `scripts/`）、`npm run prompt:check`（8 段 system +
3 段 delivery、未知插槽 0）绿；`test/` 里 4 条断言随这一刀改成从真模板读；`live` 跑两次
12/12 —— 上一次 11/12 的根因就是沉淀那一轮没有判据，这一次红灯必须自己说清是哪一类
（没提交 / 排着没跑 / unanswered / done 但 memory 没变 / 记录丢了）。

**验收结果（同日补记）**：`check`（含 `scripts/`）绿、`581/581`、`prompt:check` 绿、
`live` 12/12，且 `[rescue]` 从 6~7 次降到 **0 次** —— 模型真的调了 `say`，不再是「答在会话里
靠 rescue 补发」；沉淀那一轮记对了内容（`owner 定了自测团队的验收标准：能跑通 core:live 全部
12 项`）。

补记一条**代价**：`{{tool:xxx}}` 在 delivery 段没有注册表可查，改成 `toolSlots()` 按后缀
自解释（`{{tool:say}}` → `say`），所以**名字写错不会报错**，会原样出现在正文里。这是有意的
取舍：宁可让错名一眼看得见，也不渲染成「（未设置）」把话截断。名字对不对由 seed 侧检查兜
（`test/` 里把 `{{tool:*}}` 的名字和真工具名对一遍）。
