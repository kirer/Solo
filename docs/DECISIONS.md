## ADR-001：底层运行时库只允许在 `src/runtime` 内导入

**日期**：2026-10-24
**状态**：生效

**背景**：`@earendil-works/pi-durable` 的 README 第一行标注 experimental，且 1.1 → 1.4 每个 minor 版本都带破坏性变更（删过 `TaskRuntime.sleep()`、改过 `Storage.commit()` 签名、把 `ToolExecutionResult.content` 改成 `output`、把 `checkpointWhen` 改成必填）。

**决策**：只有 `src/runtime/` 可以导入 `@earendil-works/pi-durable`、`@earendil-works/pi-ai`、`@earendil-works/chord`。业务层（`src/company`）与界面层（`src/tui`）必须通过 `src/runtime` 暴露的接口使用它们。

`@earendil-works/pi-tui` 例外：它是界面渲染库，不是运行时，界面层可直接使用。

**执行**：`npm run check:boundaries` 静态检查，违规即失败。该检查已并入 `npm run check`。

**理由**：升级时改动集中在一个目录，而不是散落全仓库。这是应对 experimental 依赖的唯一可扩展做法。

## ADR-002：锁定精确版本，不用 `^`

**日期**：2026-10-24
**状态**：生效

**决策**：`package.json` 里四个 `@earendil-works/*` 依赖全部写精确版本（当前 `1.4.0`），不加 `^` 或 `~`。

**理由**：同上，minor 版本会破坏 API。自动升级会让构建在无代码改动的情况下失败。

**升级流程**（强制）：

1. 备份存储文件（SQLite 的 schema 迁移不可回退）
2. 改版本号 → `npm install`
3. 跑 `npm run check && npm test`（契约测试会覆盖规格里的每条行为）
4. 只有全绿才允许启动

## ADR-003：成本只从用量文档取，禁止按历史消息求和

**日期**：2026-10-24
**状态**：生效

**背景**：分叉会话的可见历史包含父会话的消息，但它的用量文档从零开始计。按历史消息求和会重复计账——实测虚高：分支真实 19 tokens，求和得 26。

**决策**：

- 汇总成本（项目 / 角色 / 全公司）**只能**读会话的用量文档
- 单条消息的用量只用于「这条花了多少」的展示，**不得**参与任何跨会话求和
- 代码里禁止出现 `entries().filter(kind === "pi.assistant").reduce(usage)` 这类写法

**执行**：`test/unit/cost.test.ts` 含反例断言（按消息求和必须不等于真实值），使错误写法无法通过测试。

## ADR-004：员工的能力包不含任何管理工具

**日期**：2026-10-24
**状态**：生效

**决策**：项目员工的能力包只含执行类工具（读写文件、执行命令、搜索）。招聘、派活、立项、创建会话、向上越级这些工具**只装在**管理层与项目负责人的能力包里。

**理由**：只靠提示词说「你不能越级」不可靠——模型可能编造。工具不存在则物理上无法执行。实测：员工生效工具集合为空，管理层为 `["hire"]`。

**不采用的做法**：用钩子在工具调用时拦截越级。作为第二道防线可以保留（用于预算、危险操作），但不能作为主要机制——它依赖每个调用点都记得装钩子。

## ADR-005：员工的归属必须是后台任务

**日期**：2026-10-24
**状态**：生效

**决策**：项目员工会话的归属是一个 `background: true` 的后台任务，而不是普通任务或前台子会话。

**理由**：老板中断某个管理层会话时，该管理层的下属员工**不能**被一起中断——员工的工作必须能跨上级的一次对话存活。实测：老板中断 CEO 后，员工仍正常答完。

**副作用**：员工不会被上级的空闲等待阻塞，所以「等员工干完」必须显式等待任务，不能依赖上级空闲。

## ADR-006：派活的请求标识必须由业务语义推导

**日期**：2026-10-24
**状态**：生效

**决策**：投递消息与派活使用的请求标识必须由稳定输入推导（例如「派活任务标识 + 员工标识」），**不得**随机生成或使用时间戳。

**理由**：崩溃恢复是「至少一次」语义。重开后重复投递依靠请求标识去重——标识不稳定就会重复派活、重复计费、重复执行。

**执行**：`src/runtime/ids.ts` 提供统一的标识生成函数，业务层只调用它，不自己拼字符串。

## ADR-007：角色职责描述必须是纯函数

**日期**：2026-10-24
**状态**：生效

**决策**：角色的职责描述（系统提示片段）渲染时**不得**包含时间戳、随机值、或任何每次调用都变化的内容。

**理由**：底层只在内容真正变化时才追加系统消息增量，以保住模型提供方的提示词缓存。内容每次都变会导致每轮请求都击穿缓存——缓存读取便宜约 10 倍、缓存写入贵约 1.25 倍，成本可能翻几倍。

**执行**：代码评审检查；成本监控里关注缓存读取占比是否异常偏低。

## ADR-008：界面由订阅驱动，不轮询

**日期**：2026-10-24
**状态**：生效

**决策**：界面附着到会话时先取一次当前状态，此后由变更订阅推送。不实现定时轮询。

**理由**：底层保证「只有已提交状态可观察」，订阅返回的每一帧都是一致快照，界面无需做乐观更新或冲突合并。多客户端（将来加图形界面）可以复用同一套订阅。

**约束**：

- 切换会话必须显式停止旧订阅，否则资源泄漏
- 慢消费者会丢中间帧（底层最多缓存 100 帧后降级为整帧快照），所以界面只能假设「收到最新状态」，不能假设「收到每一帧」
- 迟到附着直接呈现当前状态，不重放历史事件

## ADR-009：新建会话必须显式指定能力包

**日期**：2026-10-24
**状态**：生效

**背景**：实现组织模型时发现一个真实的安全漏洞——底层库的默认行为是「会话选中全部已注册能力包」。因此如果招聘员工时只写 `extensions: { remove: [...] }` 或干脆不写，员工会拿到 CHRO 的 `staff_hire`、CPO 的 `project_create` 等管理工具，等于可以自己招人、自己立项、自己越级。

这个漏洞不会报错，测试不覆盖就发现不了——员工看起来一切正常，直到它真的开始自己招人。

**决策**：任何新建会话（员工、项目负责人、临时分支）都必须显式给出 `extensions: [该角色应有的能力包数组]`，不得依赖默认选择。

**执行**：`test/e2e/org.test.ts` 断言「员工生效工具集合为空数组」，使漏配直接失败。

**注意**：`tx.createConversation()` 只接受 `ownership`，不能在同一调用里给 `agent`。必须用 `configure(tx, conversation.id, { extensions })` 在同一次提交内完成配置，否则会有一个短暂的窗口期，员工按默认选择运行。

## ADR-010：管理层的能力按岗位裁剪，工具缺失即无权限

**日期**：2026-10-24
**状态**：生效

**决策**：`roles.ts` 里每个岗位声明 `capabilityNames`，装配时映射成实际工具。岗位没声明的工具不装。例如 CFO 只声明 `budget_check`/`cost_report`，就不会有 `staff_hire`。

**理由**：与 ADR-004 同源——权限靠「工具不存在」而不是「提示词说不要」。这也让「同一岗位不同授权级别」成为配置问题：把 `decide` 从某岗位的 `capabilityNames` 里去掉，它就只剩 `escalate`，物理上无法自行拍板（对应 escalation 规格的「未授予决策能力的管理层」）。

**执行**：`test/e2e/org.test.ts` 断言 CFO 无 `staff_hire`、CHRO 有。

## ADR-011：项目显示名与目录标识分离

**日期**：2026-10-24
**状态**：生效

**决策**：项目有两个标识字段——`name`（显示名，任意语言）与 `slug`（目录标识，必须是小写拉丁字母/数字/连字符）。`createProject` 接受显式 `slug`；不传时从 `name` 推导，但 `name` 含非拉丁字符时会报错并提示补 slug。

**背景**：曾考虑「中文名自动生成哈希 slug」与「直接用中文目录名」。前者目录名不可读（`tank-battle-2f8a`），后者路径含非 ASCII 字符会让部分工具链出问题（shell 转义、git 输出、日志编码）。老板确认采用「强制英文 slug」。

**后果**：CPO 立项时必须同时给出英文 slug。`project_create` 工具的参数说明里已写明这一点，模型会在立项时生成合理的 slug。

**执行**：`test/e2e/workspace.test.ts` 断言「中文显示名 + 英文 slug」的组合可用，且「纯中文名无 slug」报错信息包含「英文 slug」字样。

## ADR-012：派活标识必须每次派活唯一，不能只按员工推导

**日期**：2026-10-24
**状态**：生效

**背景**：实现派活时踩到一个真实陷阱。最初用 `${project}/${employee}` 作为派活标识推导请求标识，结果**第二次派活拿回了第一次的结果**——因为底层按请求标识幂等去重，同一个标识永远返回同一个提交。

这个行为在崩溃恢复场景下是**正确的**（重开后重复投递不该让员工重复干活，见 ADR-006），但在「给同一员工派第二件事」场景下是**灾难性的**：第二件事根本没送出去，派活方却拿到了上一次的答复，看起来一切正常。

**决策**：派活标识必须每次派活唯一。优先级：

1. 调用方显式提供（推荐：用升级/派活任务的任务标识，天然唯一且稳定）
2. 未提供时，退化为 `${project}/${employee}/${序号}`，序号取该员工会话里已投递的用户输入条数

**为什么用「已投递条数」做序号**：它由已提交状态推导，崩溃重开后能重建出同一个序号——所以「重试同一次派活」仍然幂等，「派下一次」则拿到新序号。如果用随机数或时间戳，崩溃重开后会重复派活。

**执行**：`test/e2e/delegation.test.ts` 覆盖「连续两次派活各自独立」与「忙碌时 reject」两条路径。

**教训**：请求标识的语义是「这件事的身份」，不是「这个人的身份」。凡是「同一对象可以发生多次」的场景，标识里必须带事件序号或事件 ID。

## ADR-013：升级链的层级状态必须存进检查点，待决项必须按层级精确定位

**日期**：2026-10-24
**状态**：生效

**背景**：实现升级链时踩到两个 bug，都属于「看起来对但语义错」。

**bug 1：读答复时不区分层级。** 最初 `readOutcome` 只按升级标识查「最近一条已答复的待决项」。结果：CTO 说「我拍不了」→ 升级到 CEO → CEO 阶段醒来读答复，读到了 **CTO 那条**，于是把 CTO 的「拍不了」当成 CEO 的决定，流程直接结束在 CEO 层，老板根本没被问到。

修法：待决项同时以 `(升级标识, 层级)` 为键，每层只读自己那一层。

**bug 2：路径靠推导而不是存储。** 最初想从审计记录反推「走过哪些层级」。但审计是异步追加的，且在升级过程中会被并发写入干扰。修法：把 `path` 数组放进任务检查点状态，每次跃迁时 `[...state.path, 下一层]`。

**决策**：

1. 升级任务的检查点状态里必须包含 `path: string[]`，记录已走过的层级。
2. 待决问题的定位键必须是 `(escalationKey, level)` 二元组，不能用单一键。
3. 等待老板的阶段用 `sleepUntil` 轮询，不占执行名额；轮询间隔是常量 `POLL_MS`。

**执行**：`test/e2e/escalation.test.ts` 的「升级到 CEO 后不再回到管理层」与「完整路径可从结果读出」两条用例直接覆盖这两个 bug。

## ADR-014：员工能力包名必须唯一，按角色分配工具

**日期**：2026-10-24
**状态**：生效

**背景**：真实跑流程时发现员工「能对话但干不了活」——所有员工的工具集合是空的。排查发现两个叠加的 bug：

1. **能力包名冲突**：所有员工共用 `role-employee` 一个名字。底层按名字存会话的能力包选择，后招聘的员工覆盖了前面的定义，导致先招的人拿不到工具。
2. **统一工具覆盖按角色分配**：启动时给所有员工传了同一套工具，CHRO 招聘时又用统一值覆盖，角色差异被抹平。

**决策**：

- 员工能力包名必须唯一：`role-employee:<project>/<name>`
- 员工工具按角色分配（`staff-tools.ts`）：开发有 `read/write/edit/bash`，产品/设计只有 `read/write/edit`，运营只有 `read`，未知角色最保守只给 `read`
- 启动时自愈：已存在但没有工具的员工会话会被重建能力包并重设

**教训**：底层「按名字解析」的设计意味着**任何按角色区分的能力包都必须让名字带上实例标识**。同理适用于未来的插件、技能包。

## ADR-015：标识生成必须支持 Unicode

**日期**：2026-10-24
**状态**：生效

**背景**：CTO 给员工派活全部失败，报错 `无法从"林越"生成标识片段`。根因是 `slug()` 只允许 ASCII，把中文名过滤成空串后抛错。

员工叫「林越」是完全合法的（而且模型自发给员工起了中文名，体验更好），不该因为它不是 ASCII 就失败。

**决策**：

- 标识字符集放宽到 `\p{L}\p{N}`（含中文），只过滤真正危险的符号
- 全符号输入兜底为稳定哈希（同输入同输出），保证 ADR-006 的幂等性
- **目录标识（project slug）仍严格限制 ASCII**——这是路径安全问题，与内部标识不同

**区分原则**：内部去重标识可以用 Unicode；落到文件系统的路径必须 ASCII（ADR-011）。

## ADR-016：生产模型清单不能含测试模型

**日期**：2026-10-24
**状态**：生效

**背景**：CHRO 给员工分配模型时选中了 `faux-1`（测试用的假模型），导致员工运行报 `no_model`。根因是 `DEFAULT_MODEL_CATALOG` 里塞了测试模型，CHRO 看到它「零成本」就优先选了。

**决策**：

- `DEFAULT_MODEL_CATALOG` 为空。生产清单由 `setupModels()` 提供，测试清单由 `test/support.ts` 的 `TEST_MODEL_CATALOG` 提供，两者不混
- 招聘时校验模型是否在公司清单内，不在则报错并列出可用项
- 清单为空且未给默认模型时，`bootstrapCompany` 直接报错而不是静默用一个猜测值

**教训**：任何「看起来更省钱」的默认值都会被模型优先选中。测试替身绝不能出现在生产的可选项里。

## ADR-017：角色之间需要显式的依赖顺序

**日期**：2026-10-24
**状态**：生效

**背景**：CEO 同时给 CPO 和 CHRO 派活，两个岗位并发执行。CHRO 先跑完，查项目清单时 CPO 还没建好项目，于是 CHRO 正确地停下来等——但之后没有人重新驱动它，整个流程卡死。

**决策**：

- `delegate_to_role` 返回目标岗位的**回复摘要**，让调用方能据此判断下一步
- 所有角色的通用准则里写明典型依赖顺序：立项（CPO 建项目拿 slug）→ 招人（CHRO 用真实 slug）→ 派活（项目负责人）
- `project_create` 幂等：同名项目已存在则复用，不重复建

**仍然存在的局限**：这依赖模型遵守提示词里的顺序约定。彻底的解法是引入显式的流程编排（工作流引擎），留给后续变更。

## ADR-018：渲染必须用自定义整屏组件

**日期**：2026-10-24
**状态**：生效

**背景**：三栏界面在真实终端里分隔线错位。排查发现 `pi-tui` 的 `Text` 组件默认带左右各 1 列 padding，**且会按宽度自动换行**——把已经精确排版好的三栏画面重新折行。

**决策**：用 `src/tui/screen.ts` 的 `Screen` 组件替代，它只负责按行输出与截断，不折行、不加 padding。宽度计算完全由 `renderLayout` 负责。

**教训**：给自己的布局引擎写渲染层时，不要复用会「自作聪明」重排内容的组件。

## ADR-019：网页界面用 SSE 而不是 WebSocket

**日期**：2026-10-24
**状态**：生效

**决策**：服务端推送用 Server-Sent Events，老板的操作走普通 POST。

**理由**：

- 推送是单向的（服务端 → 浏览器），SSE 足够
- 浏览器原生支持断线重连（`EventSource` 自带 `retry`），不用自己写心跳与重连
- 零依赖，不需要 ws 库
- 组织快照用一个全局订阅 + 250ms 防抖重建，多个标签页共享同一份数据，不会把数据库读爆
- 会话流按客户端各自 `watch()`，切换会话即停止，避免泄漏

**代价**：中文文本通过 SSE 传输时，一个连接最多占用浏览器 6 个并发连接中的一个。同时开三个以上标签页看不同会话会碰上限。缓解：会话流合并 150ms 内的多次提交，实际连接数远小于提交数。

## ADR-020：项目卡翻转用 JS 控制容器高度

**日期**：2026-10-24
**状态**：生效

**背景**：项目卡正反面叠放（`backface-visibility: hidden`），翻转时容器高度会跳变——因为背面（负责人 + 员工列表）通常比正面高，如果容器高度跟着内容走，没翻转的卡也会被撑高。

**尝试过但不行**：

- 让容器高度 `auto`：正反面都是 `position: absolute`，容器塌成 0
- 只设 `min-height`：翻转后仍会跳，因为没有过渡起点

**决策**：`sizeProjects()` 先量出两面的自然高度存进 `data-h-front` / `data-h-back`，翻转时把容器高度从当前值改到目标值，靠 CSS `transition: height` 平滑过渡。

**注意**：`sizeProjects()` 会被面板开合触发（宽度变化会导致重新换行），所以它必须按「当前朝向」设置高度，不能一律设回正面高度。

## ADR-021：网页界面的数据只走一个流接口

**日期**：2026-10-24
**状态**：生效

**决策**：界面需要的一切都由 `/api/stream/org`（组织快照）与 `/api/stream/feed/:id`（会话流）两个 SSE 端点提供，不做细粒度的增量补丁。

**理由**：

- 每帧都是完整快照，前端不需要维护 diff 逻辑，也不会因为丢帧导致状态错乱
- 组织规模是一位老板 + 七个高管 + 若干项目，全量快照只有几十 KB
- 帧率由提交频率决定，不是定时轮询——空闲时零流量

**代价**：会话变很长时 feed 会变大。缓解：只取最近 400 条条目，更早的历史不推。

## ADR-022：终止与删除分两步，删除必须经老板确认

**日期**：2026-10-24
**状态**：生效

**背景**：老板要能「跟 CEO 说一句就停掉项目」。一开始我做了界面上的停止按钮，但老板明确不需要——他要的是对话式的两步操作：

1. 说「终止 X 项目」→ 项目停下
2. CEO 问「要不要彻底删除」→ 老板同意才删

**决策**：

- **第一步 `project_terminate`**：中断项目负责人与全部员工正在跑的活（穿透后台归属边界）、项目状态改为 `terminated`、员工归档、该项目挂着的待办自动关闭。**数据不删，产物文件保留。** 这一步可逆（可以重新启动项目）。
- **第二步 `project_delete`**：只有在项目已经是 `terminated`、且老板在对话里明确同意后才允许。删除项目索引、员工名册、磁盘上的工作空间目录。
- CEO 的职责描述里写死：终止之后**必须问**老板要不要删除，老板没说删就到此为止。`project_terminate` 的返回值里直接带着该问的那句话。

**为什么不在 UI 上做删除按钮**：删除是不可逆的破坏性操作，放在对话框里由 CEO 复述后果、老板确认，比一个按钮更难误触。也让「谁在什么时候决定了删除」自然留在对话记录里。

**为什么强制两步**：`project_delete` 会校验 `status === "terminated"`。一句话不能把正在跑的项目连根拔掉——必须先看到「已终止」的状态，再确认删除。

## ADR-023：删除文件前必须校验路径

**日期**：2026-10-24
**状态**：生效

**背景**：`project_delete` 要做 `rm -rf`，而目标路径来自数据库里的 `project.workspace`。测试时踩到：数据库是旧的，路径指向别处，结果删掉的是另一个目录（幸好那个目录本来就是要删的）。

这是真实的破坏性风险：数据库被改错、项目被手动搬走、或者从别的机器同步过来的库，都可能让 `rm -rf` 指向不该删的地方。

**决策**：删除前做两道校验，任一不通过就**不删文件**并明确报告：

1. 解析后的绝对路径必须落在公司记录的工作空间根目录之下
2. 路径的最后一段必须等于项目 slug

为此在 `CompanyDoc` 里新增 `workspaceRoot` 字段，bootstrap 时写入。

**执行**：`test/e2e/terminate.test.ts` 的「路径不在工作空间根下时拒绝删文件」用例直接覆盖——造一个指向根目录之外的路径，断言删除被拒且目录内容完好。

**教训**：任何来自持久化数据的路径进入 `rm -rf` 之前，都必须重新校验，不能信任写入时的正确性。

## ADR-024：忙碌时发出的消息必须显示「已排队」，并允许插队

**日期**：2026-10-24
**状态**：生效

**背景**：老板在 CEO 正忙时发了一句「终止 Web浏览器 MVP 项目」，界面上**完全没有反应**——没有回复、没有提示、项目也没停。老板以为消息没发出去。

排查发现：消息确实发出去了，但被排进了队列（`pi.inbox`，mode `followUp`），要等当前这一轮 run 答完才会被处理。而 CEO 当时正卡在 `delegate_to_role` 里等 CHRO，这个等待可能长达几分钟。加上界面从来不渲染队列，所以看起来就是「石沉大海」。

**决策**：

1. **渲染排队消息**：`/api/feed` 带上 `queued` 数组，界面用虚线框显示「已排队 · 本轮工具结束后处理」，并给出这条消息的原文。
2. **默认改成 `steer`**：老板的话不该排最后。`steer` 在本轮工具结束后插入，比 `followUp`（整轮答完才处理）早得多。
3. **提供「立即处理」**：点它走 `/api/interrupt`——先 `abort()` 中断当前运行，再把队列里的消息补回去。这样急事能立刻生效，又不必在界面上常驻一个「停止按钮」。
4. **乐观回显**：点击发送后立刻把消息显示成「已排队」，不等下一次 SSE 推送。
5. **排队消息要区分来源**：`feed.queued` 带 `origin: "owner" | "agent"`。别的 agent 派来的任务（`app.delegate` 条目）显示「由 X 派来，本轮结束后自动处理」，**不给「立即处理」按钮**——那不是老板的话，重投会替 agent 发言。

**为什么不默认打断**：老板的补充说明很多时候不需要中断当前工作，直接打断可能白费一轮产出。默认排队 + 显式插队，比默认打断更可预期。

**注意（2026-10-24 修正）**：旧实现里 `abort()` 会丢队列，而且会**无限等会话 idle**——如果当前工具永远不返回（跨会话同步转交死锁），HTTP 请求就永远挂着，界面一直「处理中…」。现在：

- abort 最多等 5 秒，超时也先把消息排进去；
- abort 之前先记下队列，abort 之后把「点的那条 + 其它排队消息」重新投递，不再吞消息；
- 转交工具改为可被 abort 的 context 取消，并在同步转交前做环检测 + 目标忙碌快速失败（见 ADR-025）。

**教训**：任何「异步排队」的交互都必须让排队状态可见，否则用户无法区分「没发出去」和「在排队」；并且任何等待都必须有上限。

## ADR-025：同步转交必须有环检测和忙碌快速失败

**日期**：2026-10-24
**状态**：生效

**背景**：真实跑 dino-runner 时，CEO → CTO → 项目负责人 → 又转交回 CTO，三个会话互相 `await`。所有工具卡显示「运行中 / 等待输出…」，参数还因为实时文档不存参数而显示「（无参数）」；点「立即处理」也没反应（abort 要等 idle，而这个环永远不 idle）。

**决策**：

1. **环检测**：进程内维护 `waiter -> awaited` 等待图（`src/company/delegation-guard.ts`）。同步转交前检查目标是否直接/间接在等自己，有环就拒绝并给模型明确指令（先回复对方，或走 escalate）。
2. **忙碌快速失败**：目标会话还有未结束任务或排队消息时，`delegate_to_role` / `delegate_to_leader` 直接返回「正在忙，本次未执行」，不排队等待。
3. **可中断等待**：把工具调用的 `Context` 一路传到 `submission.wait(context)`，老板 abort 时 waiter 立即取消，abort 得以完成。
4. **转交来源入档**：转交写成 `app.delegate` 条目，队列和会话流都能显示「谁派给谁」，不再伪装成老板的 `pi.user`。

**为什么不直接改成全异步**：异步派活需要一套回调/任务状态机，改动面比环检测大；先堵住死锁和无限等待，保留同步语义（模型能拿到结果再决定下一步）。后续如果要做真正的并行协作，再引入任务化派活。

**教训**：同步 `await` 另一个自主 agent 是死锁制造机；只要有 A→B 的等待，就必须假设 B 会反向等待 A。

## ADR-026：指令无条件受理，决策按汇报线路由，等待必须有默认值与期限

**日期**：2026-10-25
**状态**：生效（三步全部落地，验收测试全绿，2026-10-25）
**替代**：ADR-025 决策 2 里「上级的指令也一并拒收」的部分；ADR-024 决策 2/3/4 里「老板消息默认排队 + 点『立即处理』才受理」的部分（仅限老板通道，agent 来源不变）

**背景**：老板提了两条硬要求。

1. **他发出的每条指令都必须被无条件受理。** 他是这家公司的老板，指令到达即生效；管理层对下属同理。不许出现「正在忙，本次转交未执行」这类抗命。
2. **他不要在界面上再看到「已排队 / 立即处理 / 插入」这类需要他二次点击的提示。** 他发的每一条消息，都必须有回应。

现状与这两条直接冲突：

- `/api/message` 默认 `whenBusy: "steer"`（`src/server/http.ts`）——老板的话排在本轮工具结束之后，急了才点「立即处理」；
- `delegateToRole` / `delegateToLeader` 先查忙碌再拒收（`src/company/org.ts`），是明文抗命；
- 排队消息要老板点一下才被受理（ADR-024 决策 3）——把「要不要现在听」这个决定，推回给人，而且是在信息最少的时候问；
- 派活是 `await submission.wait()`，被打断时没有挂起状态，半成品直接作废，所以「先放下」等于「弄丢了」。

**决策**：

### 1. 两类决策，两个主人

下属被打断时，其实有两个不同的问题，归属不同人：

| 决策 | 内容 | 归谁 | 理由 |
|---|---|---|---|
| **时机** | 新指令何时生效：立刻停 / 等这一步 / 等这一轮 | **新指令的下达人** | 只有他知道自己急不急 |
| **处置** | 被打断的旧工作：放弃 / 暂搁 / 恢复条件 | **被打断工作的下达人** | 谁派的活谁负责，别人不能替他砍 |

同一人时一次答完。不同人时——下属**立刻执行**新指令，同时把处置问题抛给旧工作的下达人，并抄送新下达人。

这条区分是全部设计的支点：CTO 可以决定「你先停下帮我」，但不能替项目负责人砍掉它的任务。真实公司也如此——你能让别的部门的人先帮你，不能取消他们部门的项目。

### 2. 权限矩阵：按「领域 + 阈值 + 汇报线」授权，不按「重要性」

「重要性」是主观的，模型会用它给自己授权。所以授权只来自结构，与 ADR-004 / ADR-010 同源：**有 `decide` 工具才有权，没有就物理上拍不了。**

| 层级 | 能定 | 超出就往上路由 |
|---|---|---|
| 老板 | 立项 / 砍项目 / 预算上限 / 对外承诺 / 组织架构 | —（终点） |
| 管理层（CTO/CFO/CPO/COO/CMO/CHRO） | 本领域本阈值内：技术选型、预算内支出、需求优先级、预算内招聘 | 超阈值 → CEO → 老板 |
| 项目负责人 | 本项目内：排期、任务拆分、员工间调配、退回不合格产出 | 跨项目人手 → CHRO；预算 → CFO |
| 员工 | **不拍任何板**，只能执行 + 结构化提问 + 建议 | 一律 escalate |

推论：老板待办里应该只剩「立项 / 砍项目 / 超预算 / 对外」。管理层能答的问题还堆在老板那儿，说明路由没做，不是他们不该有权。

**「链上上级」的判定**：只有员工 `manager` 链上的上级，指令才是无条件受理的。旁系上级（CFO 找开发要数据）必须走该员工的 line manager 或 escalate——否则「无条件」等于「谁都能命令我」，权责反而崩。

### 3. 时机不做问询，做政策

「要不要等手头做完」不值得事后问：下属要先复述自己在干什么，再让人判断，多一次往返还丢信息。改成**指令自带档位，发送时一次选定**：

| 档位 | 语义 | 落到底层 |
|---|---|---|
| `now`（**默认**） | 立刻停，丢当前轮 | `abort()` + 投递 |
| `step` | 等当前工具调用结束再并入 | `whenBusy: "steer"` |
| `turn` | 等本轮生成答完再处理 | `whenBusy: "followUp"` |

**唯一例外不征求，只通知**：档位是 `now` 但正处在不可中断的原子操作（写文件 / 提交 / 外部副作用）时，下属回一句「正在提交，最多 30 秒后切换」，然后自己切。这不是征求同意，是告知——30 秒内撕坏文件对公司没有任何好处，而延迟有硬上限。

**「这活重要不重要」这个问题从此不存在。** 不需要谁判断自己的活重不重要：档位由下令人给，例外触发条件是客观的（是否处于原子操作）。

### 4. 处置必须问，但默认只能是可逆的一侧

处置必须问——「放弃」不可逆，不能让执行者替派活人决定。提问必须是**结构化的、带事实、带推荐**，不能开放：

```
被打断的工作：<项目> / <任务>
进度：第 3 步 / 共 5 步，已完成 2 次工具调用，已耗 12k token
选项：① 暂搁（推荐）② 永久放弃
若暂搁：需要恢复条件（默认 30 分钟后提醒下达人）
```

**恢复条件是必填项**，不是可选项。没有恢复条件的「暂搁」不是暂停，是让工作无声烂掉——它占着人、占着上下文、占着记忆，却不产出，比直接砍掉代价更高。

### 5. 超时表

**任何「等回答」的状态都必须带默认值和期限**——因为「等你答」本身违反第 1 条决策。超时不是兜底，是协议的一部分。

| 待决项 | 默认值 | 期限 | 到期行为 |
|---|---|---|---|
| 处置：放弃 vs 暂搁 | **暂搁**（唯一可逆的选项） | 5 分钟 | 按暂搁执行；问题留在待办，事后可改 |
| 恢复条件 | 30 分钟后提醒下达人 | — | 到期提醒；无恢复条件的暂搁必须挂提醒 |
| 时机 `now` 遇原子操作 | 最多等 30 秒 | 30s | 硬切 |
| 决策路由（管理层答不了） | 上一级接手 | 按 ADR-013 的检查点逐级 | 停在该级，不丢上下文 |

三条原则：**默认值必须可逆；默认值可被事后推翻；默认值的选择必须写进留痕**（否则事后分不清「机器决定了」和「人决定了」）。

### 6. 冲突与路由

| 情况 | 处理 |
|---|---|
| 两个上级同时下令 | 汇报线上更高者胜；同级 → 共同上级；期间旧工作一律暂搁（安全侧） |
| 旁系上级越级下令 | 不直接生效，走 line manager 或 escalate |
| 底层死锁（A 等 B 等 A） | 保留 ADR-025 的环检测，拒绝并让模型改走 escalate |
| 老板穿透指挥（跳过中间层） | **允许，但必须抄送直属上级**，否则负责人以为员工在干 A、其实在干 B |

### 7. 每条消息必须有回应（界面契约的硬要求）

三道保证，缺一不可：

1. **回执不经过模型**：HTTP 受理成功即写一条 `app.receipt` 条目，界面立刻显示「收到 · 正在停下第 3 步」。这条是系统写的，模型失败也必须有。
2. **终局必须有一条**：每条消息最终要么有一条 `pi.assistant` 答复，要么有一条 `alert`（模型失败 / 超时 / 被更高层指令覆盖）。**不允许静默结束。**
3. **老板通道永不排队**：连续多条消息合并进同一轮上下文，按发送顺序处理，不产生「排队」这个状态。

推论（界面必须改）：

- 删掉老板通道的「已排队 · 本轮工具结束后处理」虚线框，删掉「立即处理」按钮（ADR-024 决策 1/3/4 对老板通道作废）；
- agent 来源的排队提示保留，仍不给按钮（ADR-024 决策 5 不变——重投会替 agent 发言）；
- 界面不再出现任何「插入」措辞。

**为什么不再保留「点一下才打断」**：把「要不要现在听」推给人，等于在最没信息的时候让他做决定，而他已经明说了要什么。正确的权威模型是——**受理无条件、停手有界、代价可见**。

### 8. 留痕

每条指令记四样：`timing`（档位）、`disposition`（处置与恢复条件）、`覆盖了什么`（覆盖的任务、作废的步骤数、token）、`实际用了哪个默认值`。

不是为了追责。是为了让「模型判断错了」和「老板改主意了」可区分——否则复盘时两者都表现为「任务没完成」，系统的自我改进无从下手。

**落地（三步，互不阻塞）**：

1. **不许抗命**：链上上级的指令一律受理 + 立刻抢占；去掉 `delegateToRole` / `delegateToLeader` 的忙碌拒收；`/api/message` 对老板通道默认 `now`。这一步消掉最直接的痛点。
2. **处置与恢复**：被打断时机械写 checkpoint（从工具结果与 trail 推导，不花 token）+ 处置待办 + 默认暂搁 + 恢复条件提醒。这一步让「先放下」不变成「弄丢了」。
3. **决策路由**：把 `awaitingOwner` 泛化成 `awaitingDecision`（带 decision owner），接入权限矩阵，让该管理层拍的自己拍掉。

第 3 步才是「不用什么都由老板决定」的落地，但它必须最后做——前两步没做，路由过去的决策也执行不了。

**验收（可写成测试）**：

- `test/e2e/owner-gate.test.ts` 扩：CEO 正忙时发消息，必须在回执时限内产生 `app.receipt`，且最终必有一条 `assistant` 或 `alert`；
- 终局扫描：对话结束后，未获答复的老板消息数必须为 0；
- `test/e2e/delegation.test.ts` 扩：链上上级派活时**不得**返回「正在忙」；
- 界面：老板通道的 `feed.queued` 中 `origin === "owner"` 结构上不可能出现（`npm run ui:check` 断言）。

**教训**：把「机器不够快」翻译成「让用户点一下」，是把复杂度转嫁给用户。正确做法是把「受理」和「执行」在协议上分开——受理必须瞬时且不设条件，执行可以在最近的干净断点开始；两者都不该需要用户二次确认。而任何需要人决定的待决项，都必须自带可逆的默认值和期限，否则「等一个人」就会变成「整个公司停摆」。

**落地记录（2026-10-25）**：

- 第 1 步：`/api/message` 老板通道默认 `now`，派活/转交去掉忙碌拒收（`adr-026-obedience.test.ts`、`owner-gate.test.ts`）。
- 第 2 步：`src/company/disposition.ts`（零 token 推导 checkpoint、处置待办、5 分钟期限、默认暂搁、**恢复条件到点提醒下达人**）；读时兜底 + 看门狗双驱动（`disposition.test.ts`）。
- 第 3 步：`src/company/decision-routing.ts`（权限矩阵纯函数）+ `startEscalation` 唯一路由入口 + `PendingItem.decisionOwner`；`awaitingOwner` 泛化为 `awaitingDecision`；`escalate` 自动从员工记录/项目索引补 `project`，项目内事项真的落到负责人（`decision-routing.test.ts`）。
- 界面：老板通道不再有排队与「立即处理」；决策人不是老板时显示「待 X 拍板」（`chat.js`）。
- 已知残留：`feed.queued` 的 agent 来源提示保留（ADR-024 决策 5 不变）；「事后改处置」目前走 `answer_pending` / `/api/answer` 同 key 重答，界面暂不渲染「已按默认暂搁」的卡片。

## ADR-027：项目负责人用字符串引用，权限靠能力包，终止换只读包

**日期**：2026-10-25
**状态**：生效

**背景**：`ops-defect-loop` 暴露的问题——员工名册里的 `manager` 只能是七个管理层岗位，项目负责人（许砚舟）无法被引用；负责人拿不到执行工具、接不了员工上报；项目状态从立项起一直停在 `planning`。

**决策**：

1. `StaffEntry.manager` 的类型是 `ManagementRole | \`leader:<slug>\``，**持久化仍是字符串标量**。不新建「负责人实体」：`project.leader` + `leaderName` 已经是稳定身份，缺的只是可引用性。
2. 权限继续等于「能力包里的工具」：负责人能力包加 `read/write/edit/bash` 与 `pending_list`/`answer_pending`；员工能力包加 `escalate`；不引入权限矩阵。
3. 终止项目时把负责人的能力包换成 `role-leader-readonly`（启动修复也按项目状态选包），让「终止后没权限」成为结构事实。
4. 状态推进只接受显式边（`planning→active`、`active↔paused`、`active/paused→done`），同状态幂等，`terminated` 仍走两步终止流程。

**为什么不用对象**：升级链把层级原样存进待决文档并用 `===` 比较。对象经 JSON 落盘/恢复后引用必然不等，升级任务会永远等不到答复（表现为 30s 超时而不是报错）；同一对象进 `ROLE_LABELS[...]` 得到 `undefined`，进 `ROLE_LABELS[x] ?? x.toUpperCase()` 直接 TypeError。字符串方案不动升级状态机、不升 `CompanyDoc` 版本（升版本必须写 `migrate`，否则底层启动即抛「requires migration」）。

**为什么是 `leader:<slug>` 而不是 `leader:<conversationId>`**：负责人换人时员工引用自动跟随，不需要迁移员工记录；项目删除后解析失败，回落 CEO 并告警。

**代价**：每个展示点都必须走 `managerLabelOf`，不能再直接查 `ROLE_LABELS`；跨项目负责人由 `isValidManagerRef` 在写库前拒绝。

**已知残留（不在本决策内解决）**：`bash` 没有沙箱，项目目录在主仓 worktree 内，负责人拿到 bash 等于能写整仓。收紧需要路径围栏，且会破坏运维项目跨目录读 `workspace/company.sqlite` 的现有用法，留待单独设计。

**补充（同日）**：上线后负责人被问「能不能改代码/重启」时，凭旧记忆与旧台账答「不能」，实际工具都在。根因是工具在会话中途变化，而模型没有自查手段。因此加了两件事：①`my_capabilities` 工具返回**当前会话真实**的工具清单与工作目录；②`org_tree` / `staff_list` 显示每个成员的工具名；③通用准则与负责人职责里写死「回答能不能之前先自查或实测，不得引用旧台账」。可用性不靠提示词保证，但至少让「事实」可被当场查到。

## ADR-028：通信与工作分离，`deliver()` 是唯一的跨 agent 原语

**日期**：2026-10-26
**状态**：生效
**替代**：ADR-025 全部（同步转交）；`company/delegation.ts` 的职责

**背景**：旧实现把「通信」做成了「同步函数调用」：

```
delegate_to_role → cto.submit(...) → await submission.wait(180s) → readAssistantText(cto)
```

这一行 `await` 同时造成五个症状（老板逐条报过）：

1. CEO 派活后阻塞（派 3 个活卡 9 分钟）
2. 做完不上报（上报只在「同步等待成功返回」这条路径上写）
3. 员工不问上级（问一次要等对方整轮，成本高 → 倾向自己猜）
4. 员工之间无法通信（通信绑在 `delegate` 上，而派活有层级校验）
5. 没有真正的「任务」（看板从「谁在忙」推导，那是运行时状态）

**决策**：

1. **`deliver()` 投递后立刻返回，不等待回复**。回复通过频道异步回来。
2. **通信与工作分离**：`Channel` 是通信容器，`Task` 是工作容器，两者不共用一条路径。
3. **派活 = 建任务 + 发频道消息 + 投递**，不再同步等待。
4. 保留 `submission.wait()` 只用于**圆桌**这类确实需要收齐多方意见的场景（它有硬上限）。

**代价**：异步之后「没人兜底」成为新风险 → 必须靠看门狗（见 ADR-031）。

**执行**：`test/e2e/channels-deliver.test.ts` 断言「连发 3 条 < 3 秒」。

## ADR-029：频道集中存储，广播存储 + 定向唤醒

**日期**：2026-10-26
**状态**：生效

**背景**：老板要「公司大群包含所有员工」+「项目群」+「个人工作记录」+「随时私聊」。

**决策**：

1. **一个 session 级文档装全部频道**（`ChannelDoc`）。一条公司群消息只存一份，
   而不是往 15 个会话里各写一份（那样存储与已读状态都无法维护）。
2. **广播存储 ≠ 广播唤醒**。唤醒规则是纯函数 `recipientsOf()`：
   - 有 @ → 唤醒被 @ 的人
   - 老板发言无 @ → 唤醒频道 owner（公司群/领导层 → CEO，项目群 → 负责人）
   - agent 发言无 @ → **不唤醒任何人**（只进频道）
   - `wakeOnAll` 的成员（负责人对自己项目群）→ 也唤醒
3. **没被唤醒的人不会错过**：下次因任何原因醒来，输入前缀带未读摘要。
4. **每频道只保留最近 800 条**。聊天是流水，不是档案；要留档的结论进 `AuditDoc` / `TaskDoc`。
5. **已读用 `lastReadSeq` + `readBy` 推导**，不单独存未读数（避免两个真相源）。

**性能坑（实测）**：`tx.doc()` 返回可写 overlay，按**路径**生成 delta。
最初用「清空所有键 + `Object.assign` 整个 state」写回，导致每追加一条消息
都把整个 `ChannelDoc`（21 频道、几百条消息、实测 130KB）当成一次 delta 写盘。
改为只赋值 `doc.channels[id]` 后，delta 只含那一个频道。

**代价**：群消息不进每个人的 context，模型必须会用 `read_channel` 拉历史。

## ADR-030：任务必须有验收标准，看板只读 TaskDoc

**日期**：2026-10-26
**状态**：生效

**背景**：老板明确「真真算得上任务的才能上看板」。

**决策**：`task_create` 强制三条校验，任一不满足就拒绝并给出可操作提示：

1. `acceptance` 非空（有验收标准）
2. `assignee` 是唯一一个人（不是「团队」）
3. `project` 非空

不满足时返回的报错必须**告诉调用方该怎么做**（「请改用 `ask`」），
因为模型看到可操作提示才会改行为。

**看板只读 `TaskDoc`**，不再从「谁在忙」推导卡片——那是运行时状态，不是任务。

**状态机只接受显式边**（`todo → doing → review/done`，`blocked → doing`），
拒绝 `todo → done` 这种没有过程的完成。

**代价**：模型随口说「你去看一下 X」不算任务、不上看板。这是有意的——
那种指派是聊天，应该用 `ask`。

## ADR-031：完成上报由系统写，不经模型

**日期**：2026-10-26
**状态**：生效

**背景**：老板报「任务做完经常不上报给 CEO」。根因是上报是 `delegate()` 内部
顺带写的，只在「同步等待成功返回」这条路径上发生；超时 / abort / 换路径 → 根本不会写。

**决策**：

1. **`transitionTask()` 是唯一的状态迁移入口**。三个触发点（模型调 `task_update`、
   看门狗、项目终止）都只能走它。
2. 状态落到 `done` / `blocked` / `review` 时，**它自己**写一条 `report` 到频道
   并 `deliver` 给 `assignedBy`。调用方不需要记得。
3. 看门狗补三项检查：`escalate-question`（@ 的问题 10 分钟没回 → 升级）、
   `nudge-task`（任务卡住 → 提醒）、`resurface`（老板消息无回应 → 告警）。

**为什么不做成钩子**：钩子依赖每个调用点都装；`transitionTask` 是**唯一入口**，
结构上不存在「绕过去」的路径。

## ADR-032：能力目录声明式 + 延迟工具 + tool_search

## ADR-033：老板级待办只能由 CEO 递

**日期**：2026-10-26
**状态**：生效

**背景**：老板明确：

> 需要我（老板）拍板确认的事情，只能 CEO 给我。其他问题，他们自己找上级决定，
> 如果上级决定不了，上级再交给他的上级。直到我。

**发现的两个真实 bug**：

1. **`ask-manager` 的 `escalate` 直接跳 `ask-ceo`**，跳过中间层。
   一个项目负责人能定的排期问题被一路推到 CEO，CEO 再推给老板。
   这正是「老板待办堆满别人的活」的成因之一。
2. **`path` 出现两个连续的 `ceo`**：`ask-manager` 在「直属就是 CEO」时
   先写了一次 `ceo`，`ask-ceo` 结束时又写一次——`path` 里写了却没真问过。

**决策**：

1. **逐级上升，不许跳级**。`domain/membership.ts` 的 `nextLevelUp()`
   沿 `manager` 链找上一级：`员工 → 负责人 → 管理层 → CEO → 老板`。
2. **只有 CEO 能进 `ask-owner`**。`domain/routing.ts` 的 `canReachOwner()`
   是唯一判定口径，只有两个合法入口：
   - `initial()` 的 `startAtOwner: true`（**发起人必须是 CEO**，按身份反查，不信任入参）
   - `ask-ceo` 阶段的 `escalate: true`（CEO 复核后决定）
3. **非 CEO 声明 `company-level` 也不直达老板**：先落 `ask-ceo` 让 CEO 复核。
4. `path` 只在「真的问过某一级」时追加，不再伪造。

**测试**：`test/e2e/owner-only-from-ceo.test.ts`（11 条）锁住：
逐级上升、非 CEO 进不了老板层、CEO 复核后才能递、`path` 无重复层级。

**代价**：一个本该老板快速拍板的小问题，现在要走完整条链。这是有意的——
链上的每一级都必须先做出「我能不能定」的判断，否则层级就形同虚设。

## ADR-034：投递回执——`deliver()` 不许假装「投递成功＝已读」

**日期**：2026-10-27
**状态**：生效

**背景**（圆桌裁决 B4，本轮最严重的缺陷）：

`deliver()` 只做 `conversation.submit(...)` 再 `delivered.push(target)`，**从不看
settlement**。而 `watchdog.ts` 的队列扫描只认 `status === "queued"`——`unanswered`
是 settled 状态，压根不在扫描集合里。结果是：发给某人的消息可以静默死亡，
发现时间 = 无限。

生产库实测：`submissions` 里 `done 402` / **`unanswered 69`**（`reason=no_model`），
其中项目负责人（会话 89）**50 条**、CEO 11 条、13 号 6 条。只有两个**同步**调用方
（`delegation.ts`、`roundtable.ts`）检查了 `unanswered`，**异步的频道投递路径一个都没检查**。

**决策**：

1. **`deliver()` 返回三态** `DeliverOutcome { delivered, failed, unanswered }`。
   类型层强制：调用方不能再假设「delivered 就是成功」。
2. **`deliver()` 仍然不等待**，所以它返回的 `unanswered` **恒为空数组**。
   这不是偷懒，是分层：判定「被结算成 unanswered」需要回头看 submission，
   而「回头看」只能异步。理由写在 `deliver.ts` 头注释里。
3. **判定归看门狗**。消息上落 `deliveredTo: {conversationId, submissionId}[]`
   （追加式，同一目标的最后一条才是当前有效 submission），
   看门狗每轮巡检（`WATCHDOG_DEFAULTS.redeliverMs = 30_000`）用
   `harness.submission(id).status()` 反查，命中 `unanswered` 就**重投**：
   `requestId` 加 `:rN` 后缀（`admitSubmission` 同 requestId 会直接返回原
   submission，甚至把 unanswered 报成 done——不换 key 的重投是假的）。
4. **重投上限复用 `maxAttempts`（2）**，耗尽后**只告一次** `giveUp` 告警，
   之后彻底沉默（`WatchdogState.deliveryGaveUp` 记住已经宣告过的那些）。
   无限重投只是把「静默死亡」换成「每 30 秒一次的噪声」。
5. **`ActorView.unanswered`** 把这件事暴露给老板：`company/watchdog.ts` 的
   `unansweredDeliveryCounts()` 算好计数，`server/org-view.ts` 只消费
   （`src/server` 不许直接读 doc token）。

**为什么不放在 `deliver()` 里等**：`deliver()` 不等待是硬约束一（ADR-028）——
一次投递要等模型跑完，一条消息就能把老板的输入卡住几分钟。
「不等」和「知道结果」是两件事，前者靠 `deliver()`，后者靠回执 + 看门狗。

**代价**：发现延迟 = 一轮巡检（30 秒）而不是瞬时；`no_model` 这类**永久性**
失败重试 2 次仍然失败（模型没配就是没配），回执的价值是**让它可见并告警**，
不是让它自愈。真正的修复仍需人配模型。

**测试**：`test/e2e/delivery-receipt.test.ts`（4 条）锁住：`deliveredTo` 落库并能反查、
unanswered 触发重投并写 `app.alert`、重投上限后只告一次。
