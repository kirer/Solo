# 架构决策记录（ADR）

记录**不可轻易更改**的工程约定。要改一条，追加新条目说明为什么，不要直接改旧条目。

> 这些决策只对当前代码（`src/core/` + `ui/web/`）成立。第一代核心（`src/company` +
> `src/domain` + `src/server` + `src/tui`）连同它那 41 条 ADR 一起在 V2 删除了 ——
> 当时的推理仍在 git 历史里（`main` 分支）。

## ADR-001：底层运行时库只允许在 `src/core/runtime` 内导入

**状态**：生效

**背景**：`@earendil-works/pi-durable` 标注 experimental，1.1 → 1.4 每个 minor 都带破坏性
变更（删过 `TaskRuntime.sleep()`、改过 `Storage.commit()` 签名、把
`ToolExecutionResult.content` 改成 `output`、把 `checkpointWhen` 改成必填）。

**决策**：只有 `src/core/runtime/` 可以 import `@earendil-works/pi-durable` /
`pi-ai` / `chord`。其余所有代码通过它暴露的接口使用。

**执行**：`npm run check:boundaries`（已并入 `npm run check`）静态检查，违规即失败。

**理由**：升级时改动集中在一个目录。这是应对 experimental 依赖的唯一可扩展做法。

## ADR-003：组织是文件，不是代码

**状态**：生效

**背景**：第一代把组织写进代码 —— 七个管理层岗位是枚举、每个岗位的提示词是模板字符串、
能力是工具名数组、待办/任务/成本/升级链各有自己的文档。改一个岗位要改代码，改一句提示词
要重新部署。

**决策**：一个人 = `agents/<slug>/` 一个文件夹，里面只有 `identity.md`（必需）、
`memory.md`、`skills/`。没有岗位枚举，没有第五个 YAML 字段。组织架构是把所有人的
`manager` 连起来得到的树，断链/成环都只是「这条线断了」，不崩。

**理由**：改组织应当和改一个句子一样便宜。而且「谁是技术负责人」是**某个人写下的判断**，
不是代码常量 —— 让它可以被组织自己改写，组织才能演化。

## ADR-004：公共事实是渲染出来的，不是写下来的

**状态**：生效

**背景**：第一代把组织架构存进每个 agent 的身份文档。CEO 重组架构后没人去改旧文档，
agent 会按三周前的架构认真工作，**而你看不出来它错了** —— 这是最贵的一类失效：静默、
持续、看起来正常。

**决策**：

- **公共事实**（组织架构、项目成员、名册）→ 一份权威来源，每次请求**渲染**进提示词。
- **私有身份**（我怎么理解自己的职责、我的工作方式）→ 各人自己的 `identity.md`，
  **写**下来。

`renderAgentPrompt()` 的「你在组织里的位置」一段全部由 `identity.md` 的 `manager` 与
`project` 现场推导，一个字都不存进身份文档。

## ADR-005：提示词必须确定性，否则打穿 prompt cache

**状态**：生效

**决策**：`renderAgentPrompt()` 同输入必逐字节同输出。不许注入时间戳、不许用
`Object.keys()` 的顺序碰运气、排序规则写死（人按 slug 排序、技能按名字排序）。

**理由**：cacheRead 比普通输入便宜一个数量级，cacheWrite 更贵。一段会抖的提示词会让
每次请求都全额付费；而且抖动往往不可见（少一个空格也算）。

## ADR-006：能力拉平，不分层

**状态**：生效

**背景**：第一代按岗位发工具包 —— 「员工不能越级」靠少给工具实现，「管理层」有
`delegate_to_role` 而员工没有。结果是同一件事在两处实现，纪律靠工具缺失来保证。

**决策**：工具只有一套，人人都有。`registeredTools(registry)` 从注册表实拍，
**不读任何清单文件**。「你能做什么」写进 `identity.md` 的正文与技能里。

**代价**：`bash` 这类能力一旦装上就是人人可用（含读写别人的记忆）。这是**已知且被接受**
的 —— 隔离靠目录归谁的约定，不靠沙箱。

---

## ADR-007：能力是代码，技能是文档

**状态**：生效

**决策**：

- 一个**能力**（tool）= 一个 TS 函数，注册在 `src/core/channel/tools.ts`。
- 一门**技能** = `skills/<名字>/SKILL.md`，正文是 markdown。

想教 agent「怎么做一件事」，写技能，不要写工具。只有「需要机器真的动手」（发消息、写
文件、跑命令）才配一个工具。

**理由**：能力是**编译期**的东西，技能是**运行期**的东西。落地一道工序应该不重启进程。
`identity.md` 里写「你可以执行命令」造不出工具 —— 让 agent 自己写代码然后执行，等于把
机器交出去。

---

## ADR-008：每条消息只有一条投递路径，且发送方不等回复

**状态**：生效

**背景**：第一代为长跑攒了一整套投递设施：回执、看门狗、重投、同步派活 + 异步派活两条
路径、`whenBusy` 的多档语义。其中「投递成功 ≠ 已读」那条（ADR-034）是对的，但为了它
写的 400 行回执机器大半没被读过。

**决策**：`deliver()` 是唯一的跨 agent 原语。它 `submit` 一次 `input` 事件，
`whenBusy: "steer"`，**不等待回复**。发送方拿到的是 `{delivered, failed, skipped}`，
不是对方的答案。要答案就 `say`（带 `mention`）然后等对方在下一条消息里说。

**代价**：没有「确认对方读到了」。实测依据：468 条 `done` 的提交里只有 11 条回执带了
`deliveredTo` —— 那套机器基本没被用上。

## ADR-009：唤醒是在频道里点名，不是派任务

**状态**：生效

**决策**：`recipientsOf()` 四条规则 —— ①显式 `@` 且是频道成员；②老板发言且没 `@` 任何人
→ 第一个非老板成员；③`wakeOnAll` 成员；④减去发件人自己。

**引用回复等于 @ 作者**（`appendMessage` 里把被引用者并进 mentions，自己除外）。

**理由**：「@」是**唤醒**（把消息推到他的下一次请求），不是「指派任务」。私聊 = 两人的
房间。没被唤醒的人不会错过 —— 下次因任何原因醒来时，输入前缀带未读摘要。

## ADR-010：频道集中存储，一条消息只存一份

**状态**：生效

**决策**：一个 session 级文档（`core.channels`）装全部频道。一条公司群消息只存一份，
而不是往 15 个会话里各写一份。

**性能坑（实测）**：`tx.doc()` 返回可写 overlay，按**路径**生成 delta。最初用「清空所有
键 + `Object.assign` 整个 state」写回，导致每追加一条消息都把整个文档（21 频道、几百条
消息、130KB）当一次 delta 写盘。改为只赋值 `doc.messages[id]` 后，delta 只含那个频道。

**注意**：`tx.doc()` 读到的是**副本**。对取回的数组 `push()` 不产生任何 op ——
必须整体替换那个键（`doc.messages[id] = [...list, message]`）。踩过一次，症状是消息写进去
了又没了。

## ADR-011：`dm:` 频道统一为一类

**状态**：取代旧版（`personal` / `direct` 分两类）

**决策**：所有 `dm:` 频道统一为一类。个人频道（`dm:owner-<slug>`）= 与老板的私聊，
也是工作台：执行记录落在这里，老板插话就是在找他对话。不需要区分「个人频道」和
「私聊」—— 收件人规则、未读、渲染完全一样。

## ADR-012：项目负责人是 `README.md` 的字段，频道成员是它的投影

**状态**：生效

**决策**：负责人的真相在 `projects/<slug>/README.md` 的 `owner`。项目频道的成员是这份
文档的投影（老板 + 负责人 + 所有 `project:` 指向它的人）。改负责人 → 立刻重投影。

**理由**：如果项目频道自己存一份成员表，它就会与项目文档漂 —— 漂了之后员工在项目频道
里 @ 不到刚任命的负责人，而没人知道为什么。

## ADR-013：记忆沉淀用单游标，问完即推进

**状态**：取代 ADR-013 旧版（双游标 + 定时补漏）

**背景**：旧版用两个游标（`awaiting` + `cursors`）+ 5 分钟定时补漏。问题：
①定时器删了之后 `awaiting` 的「别重复打扰」功能反而成了「永远不推进」——
负责人说「没有」时游标不动，下次再问一遍，体验差。②双游标逻辑复杂，维护成本高。

**决策**：单游标 `cursors[项目]` = 已处理到第几条 seq。`settleProject` 问完
一批后即推进到这批最后一条的 seq —— 不等 `remember(scope=project)` 落盘。负责人
说「没有需要沉淀的」也算处理过，不会重复打扰。`remember(scope=project)` 落盘后
`confirmedBy()` 做兜底推进。

**代价**：负责人没回话时这批 decision 不会被重复问。但消息仍在频道里，负责人
下次醒来读项目频道能看到未读 —— 信息不丢，只是不会自动再催一遍。

## ADR-014：形状用代码判，语义用模型判

**状态**：生效

**决策**：

- 代码只判**形状**：这条消息落在 `proj:<slug>` 频道、`kind` 是 `decision` / `report`、
  是否已读、谁能收到。
- 语义（「这句话是不是真的结论」「值不值得写进项目记忆」）交给模型：`settle` 把候选
  发过去，写不写、写什么由它决定。

**理由**：代码判得准形状，判不准语义。第一代写过一个自动摘要器 —— 它最终变成一堆
正则和阈值，然后在语义边界上错得毫无规律。

## ADR-015：唤醒记录必须在 `submit` **之前**落盘

**状态**：生效

**背景**：`deliver()` 在投递成功后记下「他是在哪个频道被叫的」。实测发现老板在公司频道
问话，对方在**个人频道**回答。

**根因两处**：①`ownerSpeak`（老板说话那条路径）漏传了 `rememberWake`；②记 wake 的时机在
`submit` **之后** —— 提交一入队对方就可能已经跑起来，此刻 wake 还没落盘。

**决策**：wake 先写，再 `submit`。任何新增的「发起对话」路径都必须走同一个记录点。

**回归测试**：`test/core/shell-e2e.test.ts` 的「老板在哪个频道叫醒某人，就记下那个频道」。

## ADR-016：界面只画后端真的有的东西

**状态**：生效

**决策**：没有待办就不画待办卡，没有 trace 就不留占位块。宁可空着。

**理由**：第一代为了填满布局画了一堆恒空的块 —— 看的人分不清是「没有」还是「坏了」。
第一代的 `ViewOrg` 带 `projects` / `pending` / `costs` / `links` / `ceoQueue` 五个字段，
**一个消费者都没有**。

**推论**：`src/core/shell/view.ts` 的每个字段都必须有前端消费者。`check-boundaries.mjs`
的第三条规则就是据此写的：`serve.ts` 的每条路由都要在 `ui/web/js` 里被请求到，唯一的
白名单是 `/api/org`（Docker 健康检查用）。

## ADR-017：一个区域整体替换，不做增量 patch

**状态**：生效

**决策**：渲染用 `replaceChildren(fragment)`，不维护 diff。

**理由**：一个频道几百条消息时这比 diff 更快，也更难写错。第一代的增量渲染是「消息不停
往上跳」「已读点错位」这些 bug 的共同来源。

**配套**：`[hidden]` 必须真的藏住（`ui/web/css/app.css` 里有 `display: none !important`）
—— 类选择器里的 `display: flex` 会顶掉浏览器默认的 `[hidden]`。

## ADR-018：界面数据只走一个快照流

**状态**：生效

**决策**：组织快照由 `/api/stream/org`（SSE）推送，老板的操作走普通 POST。**不做细粒度
增量补丁，不轮询。**

**理由**：每帧都是完整快照，前端不需要维护 diff 逻辑，也不会因为丢帧状态错乱。组织规模
是一位老板 + 十几个 agent，全量快照只有几十 KB。帧率由提交频率决定 —— 空闲时零流量。

**实现细节**：任何文档提交都会触发一次推送，但**去抖 120ms**（一次提交可能连带几次改动），
空闲时每 15s 一个 `: ping` 心跳。浏览器断线重连靠 `EventSource` 自带机制（服务端给
`retry: 1500`）。

## ADR-019：标识生成必须支持 Unicode

**状态**：生效

**背景**：第一代 CTO 给员工派活全部失败，报 `无法从"林越"生成标识片段` —— `slug()` 只允许
ASCII，把中文名过滤成空串后抛错。而模型自发给员工起中文名（体验更好），这是常态。

**决策**：`slugify()` 字符集为 `\p{L}\p{N}`（含中文），只过滤真正危险的符号；重名加 `-2`。

**注意区分**：内部标识可以用 Unicode；**落到文件系统的路径**必须经 `slugify`（它会把
`/`、`..` 之类的字符过滤掉）。

## ADR-020：生产模型清单不能含测试模型

**状态**：生效

**背景**：第一代 CHRO 给员工选模型时选中了 `faux-1`（测试假模型，因为它「零成本」），
导致员工运行报 `no_model`。

**决策**：生产清单由 `setupModels()` 提供；测试清单由测试自己造，两者不混。

**教训**：任何「看起来更省钱」的默认值都会被模型优先选中。

## ADR-021：模型引用按**第一个**斜杠拆

**状态**：生效

**背景**：2026-10-27，整个公司发不出话，所有 `pi.generation` 任务失败于
`Model commandcode/auto/deepseek-v4.1-flash is not available`。三个因叠在一起：

1. 设置里的「内置模型覆盖项」被当成纯自定义模型又追加一遍 → catalog 里同 id 两条 →
   `resolveModelOption` 判 `ambiguous` → 默认模型回落成 `no_model`；
2. 覆盖项改了名，与内置 id 对不上；
3. 所有会话持久化的 `model` 是旧 id。

**决策**：

- `resolveModelOption()` 按 **`indexOf("/")`** 拆成 `provider/modelId` —— 不能用
  `lastIndexOf`，因为 `modelId` 自身含斜杠（`auto/deepseek-v4.1-flash`）。
- 同 id 多条时**宁可报 `ambiguous` 也不猜**，但代码不能造出同 id 两条。
- 内置模型的「覆盖 / 改名 / 删除」机制整个拆掉 —— 它只服务于已删除的设置页，
  而它正是上述事故的成因机器。

## ADR-022：删除文件前必须校验路径

**状态**：生效

**背景**：项目删除要做 `rm -rf`，目标路径来自持久化数据。踩到过：库是旧的、路径指向
别处，于是删掉了另一个目录。

**决策**：任何来自持久化数据的路径进入 `rm -rf` 之前重新校验 —— 解析后的绝对路径必须
落在预期的根目录之下，且最后一段必须等于预期标识。任一不通过就不删文件并明确报告。

**教训**：不能信任写入时的正确性。

## ADR-023：能删的都删

**状态**：生效

**决策**：没有消费者的文件、导出、路由、CSS 规则、配置项，一律删掉，不「留着以后可能
有用」。

**理由**：留着的死代码会骗人 —— 下一个人会以为「这里有业务概念」，然后照着它写新代码。
第一代攒了 `tasks` / `pending` / `costs` / `links` / `ceoQueue` 这类从没人读的字段，
以及 1952 行的 `ui/js/channels.js`。

**执行**：`check-boundaries.mjs` 的「每条路由都要有前端消费者」就是这条的机械化。

## ADR-024：项目频道含统筹链；老板只与知言私聊，公司频道预留

**状态**：生效

**背景**：第一版项目频道的成员 = 老板 + 负责人 + 所有 `project:` 指向它的人。问题：
① 负责人的上级（知言，统筹者）不在项目频道里，于是「知言在项目频道给负责人派活、负责人
向知言汇报」落不下，统筹者只能绕到别处；② 老板一开始误在公司频道下达任务，而公司频道的
语义是「预留、暂不承载任务消息」。

**决策**：

1. 项目频道成员 = 老板 + 项目负责人 + 负责人的整条汇报线（向上到老板，含统筹者）+ 所有
   `project:` 指向它的人。`syncProjectChannel`（`src/core/shell/assemble.ts`）按事实重算后
   **整体替换**成员表，不用「只加不删」——否则改名/重建后旧 slug 残留在成员表里，界面上
   显示成一个连不上会话的幽灵成员（`gunanyan` 踩过）。
2. 老板下达任务、知言回复老板，一律走**与知言的私聊**（`dm:owner-知言`），不进公司频道。
   公司频道（#公司）预留，目前不应有任何任务/汇报消息。这条规矩写进知言的 `identity.md`
   与 `立项` 技能，下一条消息就生效（不改代码）。
3. 项目里的日常协作（派活、汇报、验收）发生在**项目频道**：知言作为负责人的上级也在项目
   频道里；只有「知言定不了、需要老板拍板或交付给老板」才回到与老板的私聊。

**理由**：组织是文件，不是代码（ADR-003）。「谁和谁在项目频道协作」该由事实（负责人 +
它的汇报线 + 项目成员）推出，而不是写死；「老板↔知言走私聊」是沟通纪律，写进身份与技能
即可，不需要新工具或新字段。

**与 ADR-012 的关系**：沿用「项目负责人是 `README.md` 的 `owner`、频道成员是它的投影」
这一条，只是把投影扩到「负责人的整条汇报线」，并明确成员表用精确重算替换而非累加。

## ADR-025：启动时把强杀留下的半截任务树一次结算，不尝试恢复

**状态**：生效

**背景**：`Harness.open` 会加载所有非终态任务并尝试恢复。进程被 `kill -9` 时，一棵任务树
可能停在半截（父任务 `waiting`、子任务 `running`、还有 `placed` 的输入 submission）。恢复
时调度器重放这些任务，但它们背后的模型/工具调用已随进程消失，于是抛
`Task N invocation has ended`；这是异步未处理拒绝，直接崩进程，且库一直脏，下次照样崩。

**决策**：`openCore` 在 `Harness.open` 之后、`assembleCore` 之前调用
`reconcileZombieTasks()`：

1. **一次 commit** 把所有非终态任务结算成 `terminal`
   （`outcome: {status:"orphaned", reason:"restart"}`）。必须一次做完：只结算父任务会被
   级联把子任务改回 `pending`，仍然重放、仍然崩。terminal 状态要剥掉 `checkpoint`/`memos`。
2. 未结输入：`queued` 用 `abortSubmission` 撤销（连 inbox 项一起清）；`placed` 的 entry
   已在会话里、却没有活着的任务会回答它，就地 `settleSubmission` 为
   `unanswered`/`restart`，否则每次启动都会重复出现。
3. 自愈失败只打日志，不挡启动。

**理由**：强杀后的半截调用**无法**恢复——恢复需要重放一个已经不存在的模型/工具调用。
把它结算成 orphaned 是唯一符合持久化语义的终态。走 Harness 自己的 `commit`/`settleSubmission`，
与调度器共用连接和事务，避免外部 SQLite 连接被页缓存覆盖的竞态（实测旧方案无效）。

**代价**：强杀时正在跑的一轮工作会丢失，需要重新发起。这比进程起不来好。

## ADR-026：会话记录投影必须用 BACKGROUND_CONTEXT，不能用提交回调带来的任务上下文

**状态**：生效

**背景**：`startTranscriptSink()` 用 `harness.subscribeCommits()` 把 `pi.assistant` 条目投影进
个人频道。提交回调的第二个参数是**刚写完这次提交的那个任务的 context**。任务一结束，
调度器就会 abort 它，于是投影里紧接着的读游标/写消息会抛
`Task N invocation has ended`。这个监听是 fire-and-forget（`void sink(...)`），异常成为
**未处理的 Promise 拒绝**，直接崩进程；而且最后一条 assistant 文案（往往正是给老板的
交付结论）永远投影不进去 —— 症状就是「个人频道只有工具调用，没有最后那句话」。

**决策**：

1. 投影订阅一律在 `BACKGROUND_CONTEXT` 里跑，并给 `void` 的 Promise 加 `.catch` 打日志。
2. `projectEntry` 投影正文前做一次「刚说过」去重：同一人、同一频道、5 分钟内，正文相同
   或带同一个链接，就跳过这条 `say` 投影（思考与工具卡片照常显示）。
3. `hire` 的 `manager` 必须是名册里已有的 slug（含 `owner`），否则拒绝并列出可选值；
   不传仍是「你自己」。防止模型把「知言」写成 `zhiyan`，把整条汇报线弄断。

**理由**：投影是机械投影，不该继承任何一次具体任务的取消信号；「说过的话不再投影」是
显示层去重，不是业务规则。上级 slug 写错是事实错误，工具拒收比事后修组织图便宜。

## ADR-027：往频道里加一条消息必须是「单元素追加」，且频道文档必须定期压基线

**状态**：生效

**背景**：线上库 `core.sqlite` 长到 64 MB，其中 `core.channels` 一个文档的增量历史占
60.7 MB（971 条 delta），而它当时的真实状态只有 0.7 MB —— **85 倍放大，且随消息数平方增长**。

根因不是「存了什么」，是「怎么写下去的」。文档层用增量描述变化，而
`state.messages[id] = [...历史, 新消息]` 在它看来是**替换整个数组**，于是一条 300 字的
消息要重写该频道的全部历史。实测对比（`test/core/channel-write.test.ts`）：

| 写法 | 40 条消息累计 |
|---|---|
| 整值替换 `[...list, msg]` | 223,762 字节 |
| 原地 `list.push(msg)` | 约 4 万字节（≈ 消息本身） |

**决策**：

1. 写消息只走 `postMessage()`，它拿 `doc.messages[id]` 这个**文档代理给出的数组**直接
   `push` 一个元素。`appendMessage()` 返回的新 state 只用来算，不写回文档。
2. `push` 必须作用在代理对象上。`doc.messages[id] ??= []` 之后再 push 本地变量不算数 ——
   那不是代理，提交时不会产生任何 op，消息静默消失。
3. `ChannelDoc.checkpointWhen` 除了「单频道 ≥ 256 条」之外，**必须**在
   `info.deltasSinceBase >= 64` 时也压基线。
4. 不许把大块文本塞进单条消息：`run` 的输出落进频道前剪到约 3,000 字（头 1/4 + 尾 3/4），
   回给模型的剪到 8,000 字。

**理由**：这个文档是 `scope: "session"`，存储层写基线时会把该文档的旧 revision 全删
（`isCurrentOnly` 为真）。也就是说**压基线是这里唯一的回收机制** —— 不压，历史只增不减。
早先只按「消息条数 ≥ 256」判断，而实际最多 189 条，所以一次都没触发，库里只有一条
70 字节的初始基线，其余全是增量。

**代价**：压基线时把整份状态写一次（0.7 MB 纪律内），换来确定的空间上限与 O(1) 重放。

**注意**：这条决定的是「写下去多大」，不是「存几份」。过程记录仍然是双份（见 ADR-028）。

## ADR-028：会话记录投影必须**落库**，不做读时拼接

**状态**：生效

**背景**：曾经考虑过让个人频道的 think/tool 卡片在读接口里临时拼接（`entries` 里已经有
内容，为什么还要在频道里存一份？）。

**决策**：投影结果照旧写成频道消息。

**理由**：会话条目**没有时间戳**——存储层的 `entries` 表只有 `id`、`conversation_id`、
`head`、`commit_seq`、`record`，`EntryRecord` 类型里也没有 `at`。读时拼接无法回答
「这句思考插在哪两条消息之间」，只能把一整轮的过程堆在时间线末尾。落地时刻就是它发生
过的时刻，这是唯一的排序依据。

**代价**：同一条思考在 `entries`（模型当初看到/说过什么，续跑要用）与频道消息（老板什么
时候看到的，时间线要用）各存一份。两份都只按条数线性增长，且各自回答不同的问题。

## ADR-029：`write_file` / `read_file` 的路径围栏与静态服务保持一致

**状态**：生效

**背景**：`tools.ts` 早先直接 `join(workspaceRoot, path)`，`../../agents/别人/identity.md`
可以读写任何人的文件夹；而静态文件服务那边是有越界判断的。同一个仓库两套规则。

**决策**：工具侧也拦：`resolveInWorkspace()` 解析后必须落在工作区根之内，否则返回
「路径在工作区之外」，不抛异常。

**理由**：agent 有 `run`（shell），恶意拦不住 —— 这里拦的是**写错**。路径穿越几乎总是
「它对层级搞错了」，静默写到别人文件夹里比报错难查得多。两处规则一致，读代码的人也不用
猜「这里到底拦不拦」。

## ADR-030：`scanTasks` 必须翻页，一次启动自愈要看完整状态集

**状态**：生效

**背景**：`reconcileZombieTasks()` 早先对每个非终态状态只调用一次
`tx.scanTasks({ status }, 256, undefined)`，只要第一页。

**决策**：`while` 循环跟随 `page.next`，直到拿完该状态的全部任务。

**理由**：僵尸任务超过 256 条时，剩下的一次都清不掉 —— 每次启动都要重建现场、再崩一次。
自愈这种「只在事故时运行」的代码最容易写漏分页，因为正常路径上永远只有 0 条。
