# 架构决策记录（ADR）

记录**不可轻易更改**的工程约定。要改一条，追加新条目说明为什么，不要直接改旧条目；
觉得旧条错了，就新增一条「取代 ADR-0xx」。

> **编号从 ADR-001 重新开始（2026-10-31）。**
> 之前的 101 条记录已删除 —— 需要溯源时看 git 历史（`git log -- docs/DECISIONS.md`）。
> 导航文档（`AGENTS.md`、`docs/*.md`）里的引用已一并清掉；代码注释与测试里残留的
> `ADR-0xx` 是那个时期的标记，**不再指向当前任何条目**，判断行为以代码、`docs/` 正文与
> `seed/` 内容为准。下一条新决策才叫 ADR-001。

## 怎么写一条

一条决策只回答一个问题：**为什么这件事不能轻易改**。

固定五段：

- **背景**：之前的做法是什么，哪里不行（最好带上实测数字或踩过的症状）。
- **决策**：现在只有哪一种做法。
- **执行**：哪条测试 / 哪个检查守着它（没有就写「无」）。
- **取舍**：放弃了什么，为什么值得。
- **验收**：改完之后跑什么、看什么。

不写施工流水与文件清单（那些在 `docs/CODE.md`），也不写「以后可能怎样」的猜测。

## ADR-001 轨迹从会话条目派生，不落库

- **背景**：V3 把 `think` / `tool` / `work` 的过程投影从频道里删掉了 —— 它们混在人的对话里，
  机器留痕被读成「他说了这句话」。删干净之后，agent 干活的几分钟界面上是静的：
  跑了什么命令、改了哪个文件、为什么失败，只能事后翻日志。CONCESSIONS C-007 也记过：
  草稿和 token 流都不可靠，删了。
- **决策**：轨迹**只读派生**，不新增表、不写频道、不发草稿。一轮 = 会话里那条
  `kind: "core.channel"`（`data` 带 `channelId` / `seq`）到下一条 `core.channel` 之间的全部条目；
  助手消息里的 `thinking` / `text` / `toolCall` 与工具结果本来就在会话里。
  新接口 `GET /api/channels/:id/trace` 读它，SSE `trace` 只推节流后的快照。
- **执行**：切轮与摘要写成纯函数（服务端切轮、前端排版，同一套判据各一份），单测守
  「摘要文案、连续 think 合并、`[PASS]` 不画、截断」；`check-boundaries.mjs` 要求新路由
  在前端有消费者。
- **取舍**：读一次要扫会话条目（单轮上限 200 步、64 KB）；进程重启或会话回收后，历史轨迹
  可能读不到（返回 `null`，界面不画）。换来的是频道里永远只有人说的话 —— 机器做过什么，
  在另一个维度里看。
- **验收**：真模型跑一轮，轨迹里的命令/文件与频道里的结论对得上；刷新后同一条轨迹仍在；
  `workspace/core.sqlite` 不因轨迹变大。

## ADR-002 前端保持 React 18 + Vite，桌面端后置成壳

- **背景**：参考实现（deepseek-harness）是 `apps/web`（Vite + React）+ `apps/desktop`（Electron 壳），
  客户端逻辑收在共享的 client 层。我们已经有 React 18 + Vite + 手写 CSS，换栈的收益为零。
- **决策**：不换框架、不引组件库、不引 Tailwind。平台差异只经过 `ui/app/src/platform.ts`
  （storage / openExternal / copy）。桌面端以后用 Electron 加载同一个本地服务，不重写界面。
- **执行**：不引平台抽象层（一开始写的 `platform.ts` 没落地 —— 为两个调用写一层壳，
  比直接调更绕）。`localStorage` 只出现在 `state/store.ts`（界面开关与轨迹展开状态），
  剪贴板走 `lib/format.ts` 的 `copyText`；这两处是以后套壳时唯一要看的文件。
- **取舍**：放弃「一次做成跨端组件库」；换来改造面小、样式完全可控、六档字号不被工具类打散。
- **验收**：`grep -r "localStorage" ui/app/src` 只命中 `state/store.ts` 与 `stream/RunBlock.tsx`；
  `npm run ui:build` 的产物能被 Electron 直接加载。

## ADR-003 轨迹接口拆成「窗口摘要」与「单轮全文」

- **背景**：ADR-001 写的是 `GET /api/channels/:id/trace?seq=`，一次返回一轮的完整步骤。
  实现时发现两个问题：① 一条消息可以叫醒多个人，`seq` 不唯一；② 消息流首屏有十几轮，
  每轮八步，全带会把一次读放大到几百 KB。
- **决策**：拆成两条 —— `GET /api/channels/:id/turns?from&to` 返回窗口内每一轮的**折叠版**
  （`stepCount` + `summary`，不带 `steps`）；`GET /api/channels/:id/turn?seq&slug` 返回
  一轮的完整步骤。SSE `trace` 推正在跑的那几轮的瘦身版（每步输出 ≤ 2 KB）。
  这是 ADR-001 的接口细化，**不改变「不落库」那条**。
- **取舍**：折叠态与展开态是两种形状，前端要认 `steps === undefined` 是「还没拉」而不是
  「没有过程」；换来首屏读小、展开只拉一次。
- **验收**：`npm test` 的 `test/core/trace.test.ts`；真模型跑一轮时，折叠行有摘要、点开有步骤。

## ADR-004 每个成员一条私聊；过程在私聊里看，群聊只留结论

- **背景**：ADR-001 把轨迹派生出来之后，轨迹块挂在**群聊消息下面**。真跑起来的结果是
  群聊被过程淹了：一个团队频道里连着几十条「在想 / 跑了 N 条命令」，人说的话要找半天。
  同时私聊是「我开的时候才存在」的（`ensureDm` 明确不存在），所以 agent 的工作过程没有
  一个属于「他」的地方 —— 它属于**频道**，不属于人。
- **决策**：装配 / 招人时给每个成员幂等地建一条 `dm:<我, 他>`（`ensureOwnerDm`）；
  群聊**不再画轨迹块**；私聊是工作记录页，按时间合排「私聊消息 + 这个人在所有频道里的轮次」
  （`GET /api/people/:slug/turns`，SSE 在私聊里推他的跨频道轮次）。
  私聊仍然是两个人的房间：agent 不能私下找另一个人，也没有「个人频道」。
- **执行**：`test/core/assemble.test.ts` 守「新人一出现就有私聊」；`test/ui/stream-model.test.ts`
  守群聊不画轨迹、工作行按时间插、跨频道键不撞；`scripts/core-live.ts` 的「新人」阶段
  检查私聊成员恰为 `{owner, 他}`。
- **取舍**：侧栏频道数随人数线性增长；每个成员多一条空频道。换来的是「这个人干了什么」
  只有一个入口，群聊回到对话本身。
- **验收**：真模型跑一轮团队任务，团队频道只有结论；点开那个人的私聊能看到他在团队频道里
  的那几轮；`npm run live` 两次 16/16。

## ADR-005 团队管理员必须是名册里的真实成员，写 README 时拒绝

> **已被 ADR-058 取代**（2026-11）：没有 `lead`，团队里没有负责人这一层。

- **背景**：建团队时助理直接把自己写进 `lead`，团队频道于是把助理当管理员：他既是统筹者，
  又是被叫醒干活的人，派活与验收混成一个人。技能里写了「不能是你自己」，但技能是建议，
  模型照样写过。
- **决策**：`file` 写 `teams/<slug>/README.md` 之前校验 `lead`（`team/doc.ts` 的
  `leadProblem`）：必须有；必须是 `agents/` 里真实存在的 slug；不能是直接向 owner 汇报的
  助理。不通过直接拒绝、不落盘、不 `syncTeam`，错误文案告诉模型「先招一个团队管理员」。
  流程本身写进技能「建立团队」：第 1 步招人，第 2 步写 README。
- **执行**：`test/core/team.test.ts` 守三条判据；`test/core/tools-actions.test.ts` 守
  「拒绝时不落盘」「合法 lead 照常写」；`scripts/scenario-live.ts` 的 `build-team` 场景
  检查 `lead` 在名册里且不是助理。
- **取舍**：合法的「助理兼管理员」配置被禁掉了；老工作区里没有 `lead` 的 README 下一次
  被 `file` 写入会失败。换来的是团队频道「谁负责」这件事不再靠模型自觉。
- **验收**：让助理建团队，它先 `hire` 一个管理员再写 README；直接写 `lead: 自己` 被拒绝。

## ADR-006 说话不进过程：`say` 不画成步骤

- **背景**：工作记录里的步骤树把 `say` 也画成了一行（「说了一句」/「在 #小恐龙 说了一句」），
  点开是那句话的原文。可那句话本身就是频道里的消息，私聊里就排在这块工作记录旁边 ——
  同一段话出现两遍，而且「说出来」被算进了「做了几步」。
- **决策**：`buildTurn` 不再把 `say`（工具调用或纯正文）收进 `steps`；`stepCount` 与摘要
  随之只数「做的事」。只说了话、没做事的一轮不画 work 壳（`buildWorkRows` 跳过
  `stepCount === 0`）。话在它落到的那个频道里看；工作记录只答「他做了什么」。
- **执行**：`test/core/trace.test.ts` 守「say 与正文都不进步骤」；`test/ui/stream-model.test.ts`
  守「空轮不画壳」；`docs/WEB-API.md` 的 `ViewStep.kind` 去掉 `say`。
- **取舍**：私聊的工作记录里不再显示「他在别的频道说了什么」，要去那个频道看。
  换来的是「消息」和「过程」两种东西彻底分开，不再重复。
- **验收**：真模型跑一轮，私聊里一句话只有一条消息气泡，工作记录里只有思考与工具调用。

## ADR-007 头像换成服务端画好的插画（DiceBear `micah`）

- **背景**：原来的头像是前端手绘的几何脸 —— 三族外形 × 六色底，两种眼睛。它能稳定区分
  「谁是谁」，但一屏排下来全是同一个意思：一个身体加两个点。中文名首字区分度本来就低
  （「林越」「林墨」都是「林」），读人只能靠旁边的名字。
- **决策**：头像改由服务端生成插画（`@dicebear/core` + `@dicebear/collection` 的 `micah`），
  `GET /api/avatar/:seed?size=` 直接吐 SVG；前端只拼 `<img class="av" src="…">`（
  `ui/app/src/lib/avatar.ts`）。种子是 **slug**，取景固定（`scale 170` / `translateY 18`），
  底色 6 支淡彩按 slug 挑；同一张脸永远同一张，长缓存一周。
- **执行**：`src/core/app/avatar.ts` 是唯一的画法（纯函数）；路由在
  `interface/http/routes.ts`；`test/core/avatar.test.ts` 守「同 seed 同字节」「尺寸夹在 16–256」
  「ETag 跟着 seed 与尺寸变」。
- **取舍**：多了一个依赖（约 1 MB 的图形数据，只装在服务端，不进 bundle）；头像从「一行
  内联 SVG」变成「一次 HTTP 请求」（`<img>` 有浏览器缓存，一屏几十张也只是一批）。
  换来的是扫视时真的能认人 —— 发型、肤色、表情、眼镜都在变。
- **已知代价**：插画是 `<img>`，CSS 进不去内部结构，所以「眨眼」这个动效没了，三态改成
  整张脸的歪头 / 点头 / 回弹（§6.5、§6.4）。画风如果要换，老缓存最多留一周（`max-age` 不是
  `immutable`）。

## ADR-008 删掉输入卡上方的活动条

- **背景**：私聊里输入卡上方有一条 32px 的活动条（「● 苏禾 在做活 10s ›」），每轮开跑时
  从 0 高度展开、跑完收起。可它显示的是**过程**，而过程已经在私聊的工作记录里一行一行
  排着了；一条跟着每一轮冒出又消失的横条，正好落在最需要安静打字的输入区上方。
  群聊那条在 3606b48 已经去掉，私聊这条一直留着。
- **决策**：`ui/app/src/composer/ActivityBar.tsx` 连同渲染与样式一起删掉；`store` 的
  `activity` 映射也删掉（头像的忙态仍由 `presence` 从 `/api/org` 的 `people[].activity`
  派生，接口字段不动）。
- **取舍**：想知道某人在跑什么，要去私聊的工作记录里看那一轮（他开跑时那一块本来就会
  长出来）。不再有「一眼看到他此刻在跑什么」的入口。
- **验收**：私聊输入卡上方不再出现任何运动中的东西；`/api/org` 的 `activity` 仍然驱动
  头像的 working 态。

## ADR-009 「需要你」只认显式 @我；团队指令必须发在团队频道

- **背景**：一次真实运行里，知言私聊 43 条消息中有 13 条被标成「需要你」。拆开看，6 条是
  它把本该发给团队的指令写进了和我的私聊（正文 @ 的是沈舟、林越，可他们不在这个私聊里），
  团队频道查不到这几条；另外 7 条里只有约 4 条真在等我回话。放大噪音的是旧规则：
  `kind=decision` 且「没明确点本频道成员」时自动把我补进收件人 —— 助理几乎每条公告都打
  decision，而它在私聊里 @ 的团队成员都不是私聊成员，「没点别人」必然成立。
- **决策**：两处一起改。① `say` 只在**正文显式 @我**时把 `owner` 加进 `mentions`；
  `decision` 标签只是分类，不再替我找人。② 私聊的投递附言从「只回这里，别去群里说」
  改成「回答我只回这里；要指挥团队，就回团队频道说一句」——旧文案正是在教它把全团队的
  指令压在私聊里。
- **取舍**：助理拍板后要我看，必须自己写 `@我`，不然这条不会进「找你」。这个代价换掉的
  是：每条通告都变成待办，真正的提问被 13 条噪音埋住。技能「工作规矩」里那条
  「带 decision 标签、又没点别人时系统会把我算进收件人」同步改掉。
- **验收**：`say-contract.test.ts` 守「decision 不补 owner」「私聊附言指向团队频道」；
  真跑一轮：助理在私聊里汇报、在团队频道里派活，私聊里只有显式 @我 的消息挂「需要你」。

## ADR-010 审计走 pi-durable 的钩子，只读不改

- **背景**：排查「他为什么忽然不说话 / 这一轮为什么这么慢」时，手里只有频道消息和
  `logs/runtime.jsonl`（底座报错）。**工具调用、耗时、token、模型停止原因**一个都没有 ——
  C-009 记的就是这件事。而底座 1.4 的扩展本来就有 `hooks` 字段（`hook(ToolTask, …)` /
  `hook(GenerationTask, …)`），我们一个都没装过（`grep hook(` 零命中）：`core-tools` 只带了
  `tools`，身份扩展只带了 `sections`。
- **决策**：新增 `app/audit.ts`，两个钩子挂在 `core-tools` 扩展上（它是每个会话都选的扩展，
  装一次 = 全都在审）：
  - `beforeTool` / `afterTool` → 一行：谁、哪个工具、成没成、耗时；
  - `afterResponse` → 一行：谁、模型、停止原因、耗时、输入 / 输出 / 缓存 token、成本。

  落 `workspace/logs/tools.jsonl`，5MB 轮转一代（与 `jank.jsonl` / `runtime.jsonl` 同一套
  `appendJsonLine`）。钩子**只读不改**：不改参数、不拦调用、不改结果；写失败就丢这一行。
- **为什么不是写在工具里**：工具只看得见自己跑成功的那一次。失败的、被拦下的、底座自己
  生成的错误结果，工具里一个字都留不下 —— 而那正是要查的时候。
- **为什么不做另外三件事**：
  - **拦截**（密钥 / 路径越界 / 建团队权限）留在工具里：那里有 `workspaceRoot` 和名册，
    `HookApi` 拿不到，硬搬过去等于把校验拆成两处。
  - **自动重试**：`beforeTool` 在调用之前，重试不了；`afterTool` 只能替换结果，替换出来的
    还是同一次执行。要重试得在工具内部做。
  - **超时看门狗**：钩子没有「请求进行中」的时刻可以等，超时归底座的重试策略。
- **取舍**：每次调用 / 每次回复多一次 `appendFile`（不 await，失败丢弃）；日志会一直长，
  靠 5MB 轮转封顶。审计只在本机、只给排障看，**不进任何接口**。
- **验收**：`test/core/audit.test.ts` 钉行的形状（谁 / 工具 / ok / ms；没走过 `beforeTool`
  就不写 `ms`、认不出人就不写 `who`）；真跑一轮看 `logs/tools.jsonl` 里 `tool` 与 `model`
  两类行都在。

## ADR-011 `say` 的 channel 认频道名，不认就落回私聊

- **背景**：真实运行里，知言在私聊里被我叫醒，想给团队派活，写下「@温言 用户在 Wechat-B 上
  已经扫码登录成功…」。这条落在**私聊**：团队频道 88 条消息里它只发过 2 条，而私聊 60 条里
  它发了 40 条；它还回我「团队那边已经收到并指派了温言」，因为 `say` 确实返回了「已发到
  「知言」#55」。根因不是它不肯发，是**手上没有可写的东西**：提示词里只给频道标题
  （`群「QQ农场」`），`say.channel` 要的却是 `team:qq-farm`。省略 channel 就落回唤醒频道，
  也就是私聊。投递附言写了「在这里说的话只有我看得见」，它照发 —— 文案治不了这个。
- **决策**：`defaultChannel` 的显式频道先按 id 找，找不到再按**标题全等**在「我所在的频道」
  里找；重名直接报错并列 id；都没有就报错并列出我在的频道（id + 标题）。提示词只动两处：
  `80-reply.md` 的「频道参数省略即可」加三个字变成「**回话时**省略频道参数即可」；
  `84-dm.md` 的「回团队频道说一句」改成「用 `say` 把 `channel` 写成那个团队频道的名字」。
  换频道这件事**只在私聊那一句里说**，不进通用回话规则（见下）。
- **为什么不是硬拦**：最早想的是「正文 @ 了不在本频道的人就拒绝」。那治的是「没做到」，
  但这次是「做不到」—— 它想发，没地方发。先补能力，再谈纪律。
- **为什么不做模糊匹配**：`mentions.ts` 早就定过这条（别名只认精确匹配，拼音 / 职位 /
  `@老板` 一律丢弃）。频道名同理：只认标题全等，且只在我自己的频道里找；重名报错让人选，
  不猜。
- **取舍**：频道标题不是唯一键，两个团队同名时必须写 id（错误信息里给了）。工具参数说明
  从「频道 id」变成「频道 id 或频道名」，多一个概念，但换来「回团队频道说一句」第一次
  成为一句能执行的话。
- **踩过的坑（同一次改动里）**：第一版把「要发到**别的**频道，把名字写进 `channel`」写进了
  通用的 `80-reply.md`。真跑一遍掉到 13/16：成员乙被我在全员频道叫醒，除了照规矩报给团队
  管理员，还额外往全员频道贴了一条「@我 这个我定不了」—— 那句话被当成通用建议，鼓励它
  往别的频道多贴一份。改成只在私聊附言里说换频道，连跑两次 16/16。通用回话规则里
  **不要**出现「别的频道」这种话。
- **验收**：`say-contract.test.ts` 守三件事 —— 有唤醒记录在私聊时，写频道名照样落到团队
  频道；重名报错且不落盘；名字写错时把「你在：…」连 id 一起给出来。

## ADR-012 技能加一层「团队」：`teams/<团队>/skills/`

- **背景**：技能原来只有全员层（`skills/`）和个人层（`agents/<slug>/skills/`）。团队频道
  的技能栏因此是空态，界面上写着「团队没有技能目录」。可事实是团队确实会攒自己的做法
  （这个团队的发布流程、这个客户的验收口径），写在 README 里既不像手艺也不进提示词的
  技能段，成员根本读不到。
- **决策**：加第三层 `teams/<团队>/skills/<名字>/SKILL.md`，`SkillScope = "all" | "team" |
  "personal"`。合并方向是**下层覆盖上层**：全员 → 团队 → 个人，一个人看到的是三层并集，
  同名只留最靠下的那份，提示词里标「全员通用 / 团队共用 / 你自己写的」，被盖住的那份带
  `overrides`。
- **为什么是团队而不是「每个频道」**：团队是磁盘上的一个文件夹，也是提示词里已经存在的
  边界（`30-team.md`）；频道是投影，私聊频道还会随人消失。把技能挂在团队上，技能的
  归属和「谁能看见」都跟组织一致。
- **为什么写入口还是 `file` 工具**：早先的 `skills(action=write)` 已经删了（它只是
  「往固定路径写 md」的包装）。团队技能就是一个文件路径，`file` 写
  `teams/<团队>/skills/<名字>/SKILL.md` 即可，不新开工具、不新开 `scope` 参数。
- **取舍**：一个人同时只在**一个**团队里（`identity.md` 的 `team` 只有一个值），所以
  「看得见哪一层的团队技能」不需要额外配置；哪天要跨团队共享，这里得再加一条规则。
  团队技能不进 `seed/`（出厂内容只有全员层），开团队时团队自己写。
- **验收**：`skills.test.ts` 的「技能：团队层」三条（团队内可见 / 覆盖方向 / 别队看不见）、
  `team-profile.test.ts` 的档案字段；界面在团队频道的「技能」栏列出这一层。

## ADR-013 后台命令：跑完自己回来

- **背景**：`run` 只有两条路。前台等它跑完（最长 300 秒），或者以 `&` / `nohup` 脱手
  （立即返回 PID，**永远没有回音**）。跑一次完整测试、一次构建、一段长脚本，前者会卡死
  一轮，后者等于把它扔进黑洞：跑完了没人知道，跑挂了更没人知道。
- **决策**：`run` 加 `background: true`。起跑时就把「结果回哪个频道」定下来（用
  `defaultChannel`，此刻的唤醒记录才对），立刻返回；跑完由 `channel/jobs.ts` 把结果作为
  一条 `note` 发回那个频道，并用 `wakeTo` 叫醒起跑的人。最多跑 30 分钟，到点整组杀掉。
  起跑前在 `logs/run/<id>.json` 留一条记录，跑完删掉；服务启动时 `app/runs.ts` 扫一遍，
  活着的杀掉、死掉的照实留一句。
- **为什么不用 `&` 代替**：这是两种意图。「起个服务，别管我」和「这条慢命令跑完告诉我」
  混成一个参数，前者就会在 30 分钟后被当成超时杀掉。
- **为什么结果从「我」发、而且是 `note`**：它是系统产出，不是哪个 agent 说的话；`note`
  不计未读、默认不叫醒任何人 —— 所以 `post.ts` 加了 `wakeTo`：显式给收件人时才叫醒。
  收件人是「谁起的这条命令」，不重新解析正文里的 `@`。
- **取舍**：结果只回起跑的那个频道，不广播；回给模型的只有输出尾巴（8000 字），全文在
  `logs/run/<id>.log` 里，路径写在消息里。进程崩了只能告诉你「它断了」，不会自动重跑 ——
  重跑是起跑那个人的决定。记录里只有 pid：pid 被系统复用时清扫会误杀一个无关进程
  （很少见）；要更稳得连进程启动时间一起记，现在没做。
- **验收**：`run-jobs.test.ts` 五条（跑完回调 / 超时杀掉 / 起不来也回话 / 重启清扫 /
  `note` 默认不叫醒、`wakeTo` 才叫醒）。

## ADR-014 群聊里的字数上限比私聊紧

- **背景**：一条 `say` 统一 1200 字。线上见过 21,568 字的一条 —— 那不是说话，是把整个
  思考过程倒进频道。可 1200 对群聊还是太宽：一群人都在看的频道，长段落没人读完。
- **决策**：群聊 600 字，私聊 1200 字（`guards.ts` 的 `sayLimitOf`）。超了不落库，回一句
  「太长了」并告诉它把过程写进团队文件、只发结论加路径。
- **取舍**：硬拦会让它重写一次（多花一轮）。但把 700 字的结论倒进群里，花的是所有人的
  注意力，而且没有人读。
- **验收**：`say-contract.test.ts` 的「群聊里的上限比私聊更紧」与「超长正文不落库」。

## ADR-015 我不 @ 人时，接话的是「接我上一句话的那个人」

> **部分被 ADR-058 取代**（2026-11）：团队频道里没人被 @ 时接话的是**助理**（`wakeOnAll`），不再看负责人。

- **背景**：收件人的兜底一直是「我不 @ 任何人 → 成员表里第一个非我的成员」。团队频道里
  那个第一个通常是团队管理员，于是我在跟成员乙聊到一半、下一句忘了 @，话就掉给了管理员 ——
  他知道个大概，却没有那件事的上下文；真正在办的人反而没被叫醒。
- **决策**：兜底优先给**我上一句话之后第一个接话的人**（`rules.ts` 的 `speakerBefore`），
  他只在这个频道里、且不是我时才生效；我还没说过话、或紧接着是我自己说的，就退回原来的
  「第一个成员」。系统留痕（`kind: "note"`）不算接话 —— 那是机器写的。
- **为什么不是「紧挨着的上一条」**：团队频道每轮结束会落一条沉淀报告，作者是团队管理员，
  它正好挡在成员的回话和我的下一句之间。按紧挨着算，真实服务里实测过「我在跟乙说话，
  下一句没 @ 就掉给了甲」；按「第一个接话的人」算才对得上人。
- **为什么不是 dsh 那种「订阅」**：他们放开的是「多个 Worker 订阅同一个 Thread，事件同时
  直通给所有人」，代价是群里几个人同时开口。我们一个频道默认只有一个人接话，这条改动只是
  把「谁」从固定变成「刚在说的那个」，不增加同时说话的人数。
- **取舍**：投递正文里「这条会叫醒：X」必须和实际名单一致，所以 `renderDelivery` 改成吃
  投递层算好的 `woken`，不再自己推一遍（两处各推一次就会说叫醒甲、实际叫醒乙）。
- **验收**：`mention-alias.test.ts` 的「我在跟谁说话（ADR-015）」五条（先接话的人 /
  中间夹一条沉淀报告也不改判 / `note` 不算接话 / 我还没说话就退回第一个 / 接话的人不在
  这个频道就不算），外加真实服务里两个人跑一遍：`delivered` 里第一个是我在跟的人。

## ADR-016 看门狗先做循环，不做人

- **背景**：底座报上来的异常（任务被挂起、会话失败、迁移失败）只写进 `logs/runtime.jsonl`，
  只有打开 `GET /api/diag` 才看得见。线上真的出过「人还在、频道还在，但那个人此后不会再有
  输出」—— 这件事在界面上和「他今天没活」长得一模一样。
- **决策**：不做成一个 agent，只做一个订阅者（`app/watch.ts`）：`diag.onAbnormal` 一有
  异常报告，就在全员频道留一条 `note`（`底座报告：…`），10 分钟最多一条。`serve.ts` 启动
  时 `start()`，关服务时 `stop()`。
- **为什么不是人**：要看的都是机械判据（报告的类型和原文），代码本来就看得见，不需要模型
  判断。做成人的代价是每次醒来都烧 token，而它 99% 的时候只会说「一切正常」—— 那正是最该
  省掉的那种消息。等真碰上「看见了但不知道要不要动」的情况，再升级成人。
- **为什么是订阅不是轮询**：`lastReport()` 只留最新一条，两次轮询之间来的报告会被覆盖掉。
  异常本来就少，推给订阅者比让它们排队等着被读便宜。
- **取舍**：只通报、不自动救（`docs/CORE.md` §12 的自觉取舍）。通报失败只写 stderr ——
  看门狗自己出事不该再制造一次事故。
- **验收**：`watch.test.ts` 三条（异常变一句话 / 窗口内只报一条 / stop 之后不再写频道）。

## ADR-017 运行状态按秒补推，前端不再「每条消息重连」

- **背景**：界面上的两处状态一直是滞后的（我报的具体样子）：一轮已经「完成」了，进度行还
  挂着「正在执行」；已经回过话了，还写着「没回话」；人在跑，头像不亮圈；右栏的头像同样
  不动。查下来是两件事叠在一起：
  1. 推送只由**文档提交**触发，而「在跑 / 在想」写在会话的 live 文档里 —— 模型思考的
     那几十秒根本不落盘，状态变了也不会有人去推；
  2. 前端 `useChannelStream` 的依赖里有 `lastSeq`：每来一条消息就 `close()` 掉连接重连。
     而同一批 flush 里 `create` 和 `trace` 是前后脚写的 —— 消息一到就重连，紧跟着的
     `trace` 帧（「完成」就是它推的）正好被丢掉。
- **决策**：
  - 服务端：**一次提交之后的两分钟里，每秒补推一跳**（`sse.ts` 的 `wakePulse` /
    `pulseNow`），`org` 与 `trace` 都按指纹去重，没变就不发；真在跑（`activity` 或
    `running`）就每跳重置预算，长活不会断。闲下来自己停。
  - 前端：`useChannelStream` **只在切频道时重连**，`since` 在连上的那一刻读一次。
- **为什么触发点是提交和连接、不是「此刻忙不忙」**：一轮是「消息提交 → 模型开想」，提交
  那一刻 `activity` 还没写进去。等忙态出现再开表，第一跳可能已经是几十秒后 —— 补推就
  正好错过要补的那一段。
- **为什么不做成长连接上的状态心跳/WebSocket**：本地一个人用，一秒读一次快照的代价远小于
  再引一套通道；而且两分钟自动停，闲着的页面一次盘都不读。
- **验收**：`hub-stream.test.ts` 补两条（第二个浏览器接进来也拿得到首屏 / 内容没变不重推）；
  真服务上跑一轮带 `sleep` 的 `run`，肉眼看到「正在执行 → ✓ 完成」和头像圈自己切换。

## ADR-018 插件：文件夹 + 四个动作 + 两个插槽，不做 Cordis

- **背景**：加一个工具、一条接口、一块界面，过去都要改代码 + `npm run ui:build`。
  研究者（我）看上了 DeepSeek Harness 的插件体系：一切皆插件、上下文即服务仓、`inject`
  声明依赖、注册即可逆副作用、前端 bundle 由服务端拼成 boot 图注入页面。
- **决策**：只借它的**形状**，不搬它的运行时。
  - 插件 = `workspace/plugins/<slug>/` 一个文件夹（`plugin.md` 清单 + `plugin.ts` + `client.js`），
    和 agent / team / skill 同构；
  - 后端只给四个动作：加工具、追加一段提示词、加一条 JSON 路由、听消息。每个动作只落一个数组，
    由 `shell/assemble.ts` 并进去；
  - 前端只声明两个插槽（`sidebar.footer` / `rightPanel.tab`），插件入口是一个原生 ESM，
    页面启动时按 `/api/plugins` 逐个 `import`，`apply(ui)` 里注册组件。**装插件不重建界面**。
- **为什么不搬 Cordis**：它的价值在「几千行内核 + 服务定位器 + 五种事件派发 + 可逆副作用
  树」，收益是任意替换模型适配器 / agent loop / 会话日志。Solo 现在不需要替换这些 —— 需要的是
  「给组织加能力」。搬进来等于让每个插件作者先学一套框架，和「代码只做机械的事」相反。
- **为什么前端不用 boot 图 + lazy-CJS**：dsh 那样做是因为它要 HMR、要跨包共享模块身份、
  要一次装几十个包。Solo 的插件数量是几个，一个 ESM 文件 + 原生 `import` 就够；
  React 由宿主递给 `apply`，不需要模块表。
- **没有沙箱**：插件在进程内、页面内执行，等于本机全权限。信任来自「它是我自己（或者 agent）
  写进工作区的」，所以文档里必须写清「不要装别人给的插件」。dsh 同样没有客户端沙箱。
- **第一版不做**：热重载、插件管理界面、权限与市场、按 agent 分发工具（现在人人都有）。
- **取舍**：插件改完要重启进程（后端）或刷新页面（前端）；一个插件的提示词段对所有人生效。
- **验收**：`plugin.test.ts`（清单 / 隔离 / 四个动作 / 装配进注册表）、`ui/plugin.test.ts`
  （插槽排序与去重）；真服务上看到左栏一行、右栏一个页签，且 `clock` 工具能被模型调用。

## ADR-019 装插件 = 搬一个已经写好的文件夹，不是起个名字建空壳

- **背景**：ADR-018 把「插件管理界面」列为第一版不做。做出来时先按最省事的方式做成了
  「输入名字 → 建一个只有 `plugin.md` 的空目录」。这是错的：插件的能力全在它自己的
  `plugin.ts` / `client.js` 里，空壳装进去**什么都不做** —— 那不是安装，是占位，
  界面上会多出一行「装了但没功能」的东西，比没有这个按钮更糟。
- **决策**：安装的输入是**一个文件夹**（界面用 `<input type="file" webkitdirectory>` 选，
  每个文件 base64 传给 `POST /api/plugins`）；宿主先校验、再一次落盘：
  1. 名字合法且没有重名（不覆盖别人的插件）；
  2. 每个文件的相对路径都在插件目录里面（`../`、绝对路径、反斜杠一律拒绝）；
  3. 根上有 `plugin.md` —— 没有清单的东西不是插件。
  任一条不满足就**一个文件都不写**。装完之后列表里显示它**真的**带来了什么
  （`brings`：工具名 / 有没有提示词段 / 接口条数 / 听不听消息），还没进进程的写
  「还没加载 · 重启服务后生效」。
- **为什么是这个形状**：这就是 dsh 的 `inspect → install → 再启用` 顺序
  （`/tmp/dsh` 的 guided-plugin-installation 笔记），只是它从包管理器 / git 拿，
  Solo 没有包管理器，从磁盘上拿 —— 语义一样：**先看清它是什么，再让它生效**。
  顺带否掉「空壳后再手写代码」这条：手写代码直接写工作区里的文件夹就行，不需要界面代劳。
- **不做的**：市场、远程地址安装、依赖解析、签名校验。装进来的代码仍然是本机全权限
  （ADR-018 的「没有沙箱」不变）。
- **取舍**：一次只能装一个文件夹；大文件夹受 8 MB 请求体上限（插件里有二进制资源时要留意）。
- **验收**：`plugin.test.ts` 的「装 / 卸」四条（正常安装含二进制、缺清单不落盘、
  越界与重名拒绝、删除整目录）；真服务上选 `seed/plugins/示范` 装成一个新 slug，
  列表出现那一行并带着「工具 clock · 一段提示词」，再删掉。

## ADR-020 前端插槽铺满界面，取代 ADR-018 的「只声明两个插槽」

- **背景**：ADR-018 为了少画东西，前端只开了 `sidebar.footer` 与 `rightPanel.tab` 两个插槽。
  实际用起来这不叫「能改界面」—— 想在输入框旁边显示点东西、想在顶栏加一个按钮、想给设置
  加一节，都做不到，只能改 Solo 自己的代码再 `npm run ui:build`，插件层等于白做。
- **决策**：把界面上**说得清的缺口**都声明成插槽（11 个：`sidebar.header` / `sidebar.list.before` /
  `sidebar.footer` / `topbar.actions` / `stream.top` / `stream.bottom` / `composer.actions` /
  `rightPanel.tab` / `rightPanel.bottom` / `settings.section` / `overlays`，位置表在 DESIGN §2.8），
  每个宿主里画一个 `<Slot name>`。同时把界面状态递给插件：`ui.store`（快照 + 动作）与
  `ui.useStore`（宿主那个订阅钩子）—— 没有它，插槽里的东西只能是一块死文字。
- **为什么不是「让插件贴 DOM」**：那样插件要猜 Solo 的类名，Solo 改一次样式就悄悄坏掉一片插件；
  插槽是**契约**：名字在 TS 里、宿主位置在文档表里、`test/ui/plugin.test.ts` 查每个 `SlotName`
  都有一处宿主。加一个插槽的成本是「登记一个名字 + 画一个 `<Slot>`」，仍然比让插件猜便宜。
- **仍然不做**：插件往插槽里传 props（格子组件不收参数，自己用 `ui.useStore` 读状态）；
  运行时增删插槽；多个插件之间的组件复用。插槽**启动时填一次**，改插件 = 刷新页面。
- **取舍**：横排插槽（顶栏 / 输入框）里的东西要自己负责尺寸，宿主不替它画框 —— 会在那一行里
  撑开或挤歪。这是「不画后端没有的东西」的同一条：宿主不知道插件想长什么样。
- **验收**：`test/ui/plugin.test.ts`（每个 `SlotName` 都有宿主）；真页面上装一个把格子撒进
  多个插槽的插件，刷新即见，删掉即消失。

## ADR-021 模型管理是插件，不是内核功能

- **背景**：模型配置（`workspace/settings.json` 的 providers / defaultModel）一直是手改文件，
  没有界面；照着 dsh 的「设置 → 模型」做一个表单是很自然的下一步。问题是它该长在内核里，
  还是长成插件。
- **决策**：写成出厂插件 `seed/plugins/模型管理/`，界面挂在 `settings.section` 插槽上，
  后端用插件自己的三条 JSON 路由（`/api/p/models`、`/api/p/models/probe`）读写那个文件。
  内核只知道 `settings.json` 的格式，一行都不为界面改。
- **为什么**：模型配置是「一个文件 + 一层表单」，没有业务语义，也没有别的模块依赖它 ——
  正好是插件的形状。写在内核里会让 `interface/http` 多三条只为一块表单存在的路由，
  而选项还会跟着 provider 生态一直长（拉模型、测连通、按团队分配）。
- **安全边界照旧**：插件在进程内跑，`apiKey` 只写不读 —— `GET` 只回尾号（`keyHint`），
  密钥留空表示沿用已存的那一份。写文件用「临时文件 + rename」，校验不过一个字节都不写：
  这份文件写坏了等于全员不回话（`docs/DEPLOY.md` §3 记过一次）。
- **不改运行中的模型**：模型在进程启动时装配（`setupModels`），插件只写文件，界面上明写
  「重启服务后生效」。要做热切换得先让运行时支持换 provider，那是另一件事。
- **取舍**：界面上的「现在生效的是…」是按环境变量与文件镜像出来的提示，不读运行时真值；
  保存后用环境变量兜底的那一份要重新填一次密钥（密钥不会从环境变量带进文件）。
- **验收**：`test/core/model-manager-plugin.test.ts`（读 / 写 / 密钥打码与沿用 / 五类非法提交
  不落盘 / 坏文件不炸）；真页面上「获取可用模型」打到本地网关，列出它的模型清单。

## ADR-022 删掉的出厂插件不再被 seed 复原

- **背景**：`seedPlugins` 原来的判据是「工作区里有没有同名目录」，缺了就从 `seed/plugins/` 补一份。
  于是界面上的「删除」只在这次进程里生效：删掉模型管理、重启服务，它又回来了 —— 和按钮上
  写的那句「连同它的代码一起删掉，找不回来」直接矛盾。实测复现。
- **决策**：`.seed-manifest.json` 加一条 `plugins`（出厂插件里**见过**的目录名）。见过的插件
  之后不再碰：盘上有 = 我留着 / 改过；盘上没了 = 我删的。两种都不该再补。新一版 seed 里
  新增的插件没有记录，照旧会补进来 —— 「升级能拿到新东西」和「删掉的不复活」都成立。
- **代价**：老工作区第一次跑这一版时，以前删过的出厂插件会补回来一次（没有历史可查）。
  之后就不会了。
- **验收**：`test/core/seed-plugins.test.ts`（第一次补、第二次不写、删了两次启动都不回来）；
  真服务器上删掉模型管理后重启：插件清单里没有它、`/api/p/models` 404、`settings.json` 原样、
  agent 照常回话。
 
## ADR-023 没配模型就是没模型，不悄悄兜底

- **背景**：`setupModels` 的第 4 条原来是「什么都没配 → 用本地网关 `127.0.0.1:3425`」。
  于是从零起一个服务，界面一切正常、agent 会答话，用的却是一只用户没选过、也没被告知
  存在的模型。本机没有那个网关时它同样「一切正常」，只是谁都不回话，而原因在代码里，
  界面上看不出来。
- **决策**：删掉这一条。优先级变成 `settings.json` → `ANTHROPIC_API_KEY` →
  `OPENAI_API_KEY` → **没有模型**（空注册表、`defaultModel: undefined`）。这时服务照常启动、
  界面照常可用，启动日志写一行「还没有配置模型：设置 → 模型，或写 workspace/settings.json」，
  设置里的「模型」一节写「还没有配置模型」并提供「加一份本地网关」的入口。
- **为什么**：替人做的决定必须看得见。一只来源不明的兜底模型比不响更糟 —— 它让人以为
  「已经配好了」，等到回答质量不对时也找不到该改哪里。本地网关仍然是**最方便**的选择，
  只是现在由用户显式写进 `settings.json`（一次，或点一下插件里的按钮）。
- **连带**：会话不再保证带模型，第一次生成以 `no_model` 失败（不是悄悄换一只顶上）。
  `npm run live` / `live:scenarios` 自己往临时工作区写本地网关配置（`scripts/live-support.ts`
  的 `setupLiveModels`），所以 `COMMANDCODE_*` 从此只对脚本有意义。
- **代价**：老用户升级后如果一直靠兜底，重启会发现没人回话 —— 启动日志和设置页各有一句
  明说，照着填一次即可。
- **验收**：`test/core/models.test.ts`（无 settings / 坏 settings 都是 `defaultModel: undefined`、
  注册表为空）；`test/core/model-switch.test.ts`（providers 删空后老会话的模型引用解析不到，
  而不是回落）；真服务器上删掉全部 provider 重启：界面可用、设置页写着「还没有配置模型」。

## ADR-024 给某个人换模型：当场生效，记在 settings.json 的 agentModels

- **背景**：ADR-021 写的是「不改运行中的模型」——模型在进程启动时装配，插件只写文件，
  保存后要重启。那时只有一个全局默认模型，够用。现在要的是「某个人换一只模型」，而重启
  一次换一个人完全不成立；底座本来就支持逐会话 `configure({model})`。
- **决策**：新增 `POST /api/people/:slug/model`（`src/core/app/people.ts` 的 `setPersonModel`）：
  1. 先确认这只模型在装配好的注册表里，否则 400（写一个解析不到的引用 = 那个人此后每轮
     `no_model`，界面上只留「他这一轮没答上来」）；
  2. 当场 `conversation.configure({model})`，不用重启；
  3. 同时写进 `workspace/settings.json` 的 `agentModels`（slug → `provider/modelId`，
     原子写），装配时 `modelFor(slug)` 用它压过 `defaultModel`。
  空串 = 跟默认，删掉这条记录。
- **为什么落盘**：只改会话的话，下次启动 `applyModel` 会把所有人对齐回默认 —— 界面上看起来
  就是「设置自己变回去了」。落盘是唯一能让「我设的」和「默认的」分开的地方。
- **为什么记在 settings.json 而不是新文件**：模型配置已经在那里（`providers` / `defaultModel`），
  多一个 `agentModels` 是同一件事的第二维；新文件等于两份模型事实。插件保存时原样保留不认识的键，
  两边不会互相抹掉。
- **边界**：全局 `defaultModel` / `providers` 仍然要重启（ADR-021 那条不变）；这里只放宽到
  「一个人」这一级。指向已删 provider 的 `agentModels` 记录在装配时被丢掉（按默认走），
  不让人静默 `no_model`。
- **验收**：`test/core/person-model.test.ts`（当场生效、写进 settings.json、重启后装配认、
  空串回默认并删记录、没有的模型与没有斜杠的写法 400 且会话不动）。

## ADR-025 改 settings.json 不用重启：就地重装注册表

- **取代**：ADR-021 的「提供商在进程启动时装配、改了要重启」与 ADR-024 末段「全局
  `defaultModel` / `providers` 仍然要重启」。那两条的前提是「注册表是启动时建死的」，
  而底座（pi-ai）的 `MutableModels` 本来就支持 `setProvider` / `clearProviders` 原地 upsert，
  harness 拿的是**同一个对象** —— 前提不成立。
- **背景**：在设置里加完提供商，详情面板仍然写着「还没有配置模型」，模型下拉是空的。
  人被送回设置页白改一遍（实测被这么问过一次）。这不是文案问题，是「改了不生效」。
- **决策**：`runtime/models.ts` 新增 `syncModels(models, file)`：读 `settings.json`，
  **先装进一份临时注册表**，装得上才 `clearProviders` + 逐个 `setProvider` 到运行中的那份；
  返回装完之后的 `defaultModel` 与 `agentModels`。装不上（文件里没有 providers / 配置坏到
  算不出默认模型）返回 `undefined`，旧的那份原样留着 —— 跑着的服务不能被一份坏配置换掉全部模型。
- **什么时候重装**：不挂文件监听。`shell/assemble.ts` 的 `refreshModels()` 读一次 mtime，
  变了才重装；它挂在三处「要读模型」的地方 —— `openOne`（开会话前）、`GET /api/models`
  （`app/models.ts` 的 `list`）、`POST /api/people/:slug/model`（校验之前）。没有轮询，
  也不用给插件 API 加东西：设置页保存完，界面下一次拉清单就装好了。
- **默认模型换了怎么办**：`CoreServices.defaultModel` 改成 getter（读的是当下那份），
  重装后把**没有 `agentModels` 记录的人**重新 `applyModel` 一次；单独指定过的人不动。
  删掉的提供商同理：挂着它的人回到默认，而不是静默 `no_model`。
- **代价**：压缩策略（`compactionSettings`）仍按启动时的模型表算，新加的模型用全局兜底
  （128k 窗口）—— 估小了只是多压几次，不会压坏。真要按新模型窗口压，重启一次即可。
- **验收**：`test/core/person-model.test.ts`「改 settings.json 不用重启」两条（加一只模型
  下一次读清单就在、当场能换上；删掉一家提供商后它消失、挂着它的人回到默认）。

## ADR-026 插件热重装：改文件不用重启进程

- **取代**：ADR-018 / ADR-019 里「第一版不做热插拔，开关 / 装 / 卸都要重启」那一段。
- **背景**：插件的能力是**进程里注册出来的**（工具进注册表、提示词段进身份扩展、接口进路由表、
  监听进 `afterPost`）。第一版把这四处都在装配时拼死，于是「装上了」和「装上了但没生效」长得
  一模一样，只能靠重启区分。实际用起来：每改一次 `plugin.ts` 就得重启一次服务。
- **决策**：`shell/assemble.ts` 新增 `reloadPlugins()`，整份重装而不是增量改：
  1. 重新 `loadPlugins`（`plugin/load.ts` 的 import 带 `?v=<mtime>`，否则读到的是 import 缓存
     里那份旧代码 —— 重装看起来「没反应」就是栽在这里）；
  2. 工具：按同名 `registry.install(buildToolsExtension())` 原地换掉 `core-tools`
     （底座 `install` 的语义就是「同名替换」；会话按扩展名解析，下一次生成就看得见）；
  3. 提示词：插件段是装的时候拍下来的快照，所以要重装每个人的身份扩展；
  4. 接口与消息钩子：本来就在用时取 —— `coreRoutes` 的 `*rest` 兜底里每次请求现查
     `app.plugins.routes()`，`afterPost` 拿的是 `() => plugins.messages`。
- **什么时候重装**：两个入口。界面上开关 / 装 / 卸（`app/plugins.ts` 三个用例，写完文件就调）；
  进程外面动 `plugins/` 目录（手写文件、`git checkout`）靠 `runtime/io.ts` 的 `watchDirAt`
  递归监听 + 200ms 防抖（一次保存常常连着好几个事件，装到一半还读不到文件）。
  监听不上（目录不存在、平台不支持）只是不自动装，服务照起。
- **代价**：重装是**同步做完才返回**的，安装一个插件会让那一次 HTTP 请求慢一点；
  正在生成的那一轮拿的是旧快照，下一轮才是新的。**前端 `client.js` 仍要刷新页面**
  —— 浏览器里那份代码已经跑起来了，换代码只能重新加载（服务不用重启）。
- **验收**：`test/core/plugin-reload.test.ts`（打开开关后工具进注册表、接口当场能打到、提示词
  里有那一段；改了 `plugin.js` 再重装读到的是新代码，不是 import 缓存里那份）。

## ADR-027 自建更新源 = 一个只读静态目录，服务端不改写清单

- **背景**：桌面端要自己发更新（不走 GitHub Releases）。`electron-updater` 的 `generic`
  provider 只要一份 `latest*.yml` 清单和它点名的安装包；清单里的 `files[].url` 是相对路径时，
  客户端会以清单地址为基准拼出绝对地址（`newUrlFromBase`）。所以「改写 URL 成绝对地址」这一步
  在服务端是多余的 —— DeepSeek Harness 那套要改写，是因为它先 `?` 后再把产物搬去另一个前缀，
  Solo 不需要。
- **决策**：`scripts/update-server.ts` 就是一个 `node:http` 只读静态服务，零依赖：
  清单 `no-cache`、产物 `immutable`、目录外 404、根路径列出目录内容。
  没有上传接口、没有鉴权、没有库、没有版本淘汰。发布 = 把 electron-builder 的产物放进目录。
- **为什么不做「更新后台」该有的那些东西**：客户端还没接上，任何一步都是猜。等真的发过一个
  版本、真的回滚过一次，再按缺什么补什么（上传接口 / 鉴权 / 淘汰）。
- **纪律**（写进 [DEPLOY](DEPLOY.md) §9）：二进制先传、清单最后传；旧产物永不删，回滚 = 换回旧清单。
- **验收**：`test/desktop/update-server.test.ts`（清单不缓存、产物长缓存、根路径可列、
  `../` 与 `%2e%2e%2f` 都 404）。

## ADR-028 桌面端是一个 Electron 壳，后端作为子进程跑同一份源码

- **背景**：ADR-002 早就定了「Electron 加载同一个本地服务，不重写界面」，但没定三件事：
  后端怎么随包、数据放哪、升级走哪。
- **决策**：
  1. **壳只管进程边界**：`desktop/src/` 起一个子进程（`process.execPath` + `ELECTRON_RUN_AS_NODE=1`）、
     开窗口、加载 `http://127.0.0.1:<port>/?shell=desktop`。它**不 import `src/core/` 一个文件**
     （`scripts/check-boundaries.mjs` 第 7 条机械化检查），端口靠后端已有的
     `[core] http://127.0.0.1:<port>/` 那一行认（`desktop/src/ready-line.ts`）。
  2. **后端不打包、不 transpile**：Electron 自带的 Node 24 已经稳定支持类型擦除、内置 `node:sqlite`，
     所以 `src/**/*.ts` 原样随包发布；`ui/web` 与 `seed/` 一起放进去，`import.meta.url` 向上找
     它们的相对深度一像素没变 —— 后端零改动。
  3. **不用 asar**：播种技能走 `fs.cp(目录, …, {recursive:true})`，而 asar 的 fs 垫片只支持拷文件，
     拷目录直接 NOT_FOUND。摊在 `Resources/app` 里一样能跑，排障还更好看。
  4. **端口先试 7788，被占再退 0**：`localStorage`（主题、布局）按 origin 存，端口每次变等于偏好每次丢。
  5. **数据在 `userData/workspace`**，不认仓库里的 `workspace/`（那是真实数据）。开发态连 userData
     都放临时目录，跑坏了删掉即可。
  6. **升级**：`electron-updater` + 自建源（ADR-027），`autoDownload=false`、`autoInstallOnAppQuit=false`、
     `allowDowngrade=false`；下载与安装各要一次明确点击；安装前先停后端（它占着 sqlite，还在跑后台命令）。
  7. **标题栏藏进界面里**：macOS `hiddenInset` + `trafficLightPosition`，界面用 `?shell=desktop`
     给侧栏 logo 行让出 40px 并装好拖拽把手（`ui/app/src/styles/shell.css` 末尾那一段）。
     Windows 保持系统标题栏 —— 覆盖式按钮要配合右内边距，先不冒险。
- **未签名的 macOS 构建装不了更新**：Squirrel.Mac 换包前核对新旧 `.app` 的签名身份，没有
  Developer ID 必然失败。所以壳会先探测签名（`codesign -dv`）：没签名就只提示「去下载页」，
  不让「重启安装」点下去变成应用直接消失。Windows 不受影响。
- **取舍**：整包约 390 MB（生产依赖都在里面），换来「用户机器上不需要 node/npm」和「dev 与打包
  走同一条 spawn 路径」。真要瘦身，再按 `files` 排除用不到的依赖。
- **验收**：`npm run desktop:dev` 出窗口；`npm run desktop:pack` 后 `release/mac-arm64/Solo.app`
  能起、能播种、能说话；`SOLO_UPDATE_URL=http://127.0.0.1:8899/` 指向假 feed 时日志出现
  `[update] 有新版本 …`。`test/desktop/ready-line.test.ts` 守就绪行与更新源地址的判据。

## ADR-029 更新走「自签清单 + zip 替换」，不用 Squirrel / NSIS（取代 ADR-028 第 6 条与「未签名装不了更新」那段）

- **背景**：ADR-028 选了 `electron-updater`。它在 macOS 上落到 Squirrel.Mac，换包前要求新旧
  `.app` 是同一个 Developer ID 身份 —— 未签名（或无证书的开发机）必然停在「不能自动安装」。
  实测：2.0.1 下载成功、sha512 校验通过，最后一步被系统拒掉。GitHub 上大量开源桌面应用能自动
  更新，靠的不是 Apple 签名，而是**应用自己的更新器**（Sparkle 用 Ed25519、Tauri 用 minisign）。
- **决策**：两个平台走同一条路线，`electron-updater` 从依赖里移除。
  1. feed 里放每平台一份 JSON 清单（`latest-mac.json` / `latest-win.json`）+ 同名 `.sig`；
     签名是 Ed25519，**私钥只在发布机**（`~/.solo-update-key.pem`），公钥编进应用
     （`desktop/src/update-key.ts`，`npm run update:key` 生成）。
  2. 应用先验清单签名，再比版本（只比数字段），再下载 zip；下完核对清单里的 sha512。
  3. 安装由**进程外的脚本**做：等应用退出 → 解包 → 把旧包挪开、新包换进去（失败挪回来）→ 重新打开。
     macOS 是 `sh` + `ditto`；Windows 是 PowerShell `Expand-Archive` + `robocopy /MIR`。
  4. 更新源地址在 `desktop/src/feed.ts` 的 `DEFAULT_FEED_URL`，运行时可用 `SOLO_UPDATE_URL` 覆盖；
     只认 https 或本机 http（同 ADR-028）。
- **为什么可行**：更新包由应用自己下载，不带浏览器下载才有的 quarantine 标记；替换由外部脚本做，
  不经过任何系统签名比对。安全边界从「Apple 信任这个二进制」换成「这份清单是发布密钥签的」——
  这正是 Sparkle / Tauri 的做法。
- **取舍**：替换逻辑自己维护（换到一半失败要能回滚）；Windows 上的 zip 替换没有安装包，
  快捷方式仍由首次安装的 NSIS 建立，更新只覆盖程序目录。**Windows 这条在本机没有实机验证过**，
  首次验证时要盯 `robocopy` 与重启。
- **验收**：`npm test` 里的 `test/desktop/manifest.test.ts` 守验签、改字、换钥、版本比较与平台取包；
  端到端是「2.0.0 应用 → feed 上 2.0.1 → 点立即重启安装 → 应用以 2.0.1 重新打开」。

## ADR-030 两个根：应用私有的东西和我的组织分开放，旧 `workspace/` 不迁移

- **背景**：以前所有东西都在一个 `workspace/` 里：助理身份、提示词、内置插件、`core.sqlite`、
  `settings.json`，和成员 / 团队 / 技能 / `rules.md` 挤在一起。后果是三件真事：换机器时
  想只带走「我的组织」，但数据库和插件也一起走了；备份 / 清空「组织」时得小心绕开数据库；
  成员也没有自己的工作目录，`run` 的默认 cwd 是整个工作区。
- **决策**：两个根，各管一摊，路径只在 `src/core/layout.ts` 里拼：
  - **应用私有根**（桌面端是 `app.getPath("userData")`，命令行默认 `./.solo-app`，可用
    `--app-root` 指）放：`assistant/`（助理身份与技能）、`prompt/`（提示词模板）、
    `plugins/`（内置插件）、`settings.json`、`core.sqlite`、`uploads/`、`logs/`、`secrets.json`。
  - **用户根**（默认 `~/.solo`，可用 `--user-root` 指）放：`members/`、`teams/`、`skills/`、
    `rules.md`。
  - 旧的 `workspace/` **不读不写不搬**：新根从空开始，旧文件留在磁盘上。
- **执行**：`test/core/roots.test.ts` 按「文件落在哪」逐项钉死；`test/core/layout.test.ts` 守拼路径；
  `scripts/check-boundaries.mjs` 把 `layout.ts` 放进「根原语」组（不许 import 上层）。
- **取舍**：没有迁移脚本 —— 旧数据和新的组织目录不是同一批文件，自动搬一半比不搬更糟。
  代价是升级后要重新招人 / 建团队；值得，因为两个根本来就不该纠缠。
- **验收**：`npm start -- --app-root /tmp/solo-app --user-root /tmp/solo-user` 之后两个目录里
  的东西互不串；桌面端打包后 `~/.solo` 与 userData 各就各位。

## ADR-031 出厂内容按 hash 同步：我改过的永远不动（正式记下这条原本只在代码注释里的约定）

- **背景**：`rules.md` 和全员技能以前只在一个空的工作区里拷一次，于是「先给结论」这类修正
  永远进不了已经在跑的组织（实测同一份技能 5766 vs 4729 字节）。改成每次启动都同步又会让
  手改过的内容被覆盖。
- **决策**：播种时记一份 `.seed-manifest.json`（每份文件上次播下去的 hash）。下次启动：
  hash 没变 = 我没改过，升到新版；hash 变了 = 我改过，原样留着；我删掉的出厂插件不再补
  （ADR-022）。身份文件仍然只在空的时候写一次 —— 那些属于那个人自己。
- **执行**：`test/core/seed-sync.test.ts`、`test/core/seed-plugins.test.ts`。
- **取舍**：hash 只认内容，不认来源；同一份内容被别处按字节重写一次也会当成「没改过」。
- **验收**：改一次 `seed/skills/工作规矩/SKILL.md` 后重启，跑着的工作区跟着变；手动改过的
  文件不被覆盖。

## ADR-032 `agents/` 改名 `members/`，每个成员、每个团队都有自己的工作目录

- **背景**：目录叫 `agents/` 是把实现方式当成了组织名词；计划 3 也要求「每个人有自己的
  工作目录」，否则 `run` 的默认 cwd 是整个工作区，两个人的产出会互相覆盖。
- **决策**：
  - 用户根下是 `members/<slug>/`（原来是 `agents/`），助理在应用根的 `assistant/<slug>/`；
    扫描时两个根都看，助理在前。
  - 每个成员建出来时就带自己的 `workspace/`；团队建出来时带 `teams/<slug>/workspace/`。
  - **「待在自己的工作目录里」写在提示词里**（`seed/prompt/70-directory.md` 的 `{{self.dir}}`），
    不在代码里拦：`run` 的默认 cwd 是调用者自己的 `workspace/`，越界仍然可以显式指定。
- **执行**：`test/core/roots.test.ts`（旧 `agents/` 不出现）、`seed-contract`（助理在
  `assistant/`、`identity.md` 路径写法）、`test/core/skills.test.ts`（个人层跟着身份目录走）。
- **取舍**：改名会让旧工作区「没人」。按 ADR-030 本来就不迁移，这不额外增加代价。
- **验收**：招一个人 → 用户根出现 `members/<slug>/` 与 `workspace/`，没有 `agents/`。

## ADR-033 生命周期并入 `hire`：招人 / 让人走 / 看模型；解散团队是改 README 的 `status`

- **背景**：核心工具固定七个（ADR-084 的前身约定），每加一个同义工具，模型选错的概率就涨。
  而「让人走」「解散团队」在真实使用里和「招人」是同一件事的三个动作。团队解散也没有
  工具可写：团队的真相在 `README.md`。
- **决策**：
  - `hire` 有 `action = create（默认）/ fire / models`。`fire` **只移不删**：目录移到
    `members/.retired/<slug>-<时间>/`，从频道与名册里摘掉，和我的私聊归档；拒绝开除助理、
    我、团队管理员（先交出 `lead`）、手下还有人的（先改派）。
  - `action=models` 列出「现在配好的模型」，招人时按角色选（协调 / 汇总用便宜的，复杂开发用强的），
    写进 `settings.json` 的 `agentModels`，当场生效（ADR-024）。
  - **解散团队不写新工具**：`file` 把 `teams/<slug>/README.md` 的 `status` 改成 `archived`，
    `syncTeamChannel` 把频道归档（列表里消失，历史还在），取消归档就写回 `active`。
- **执行**：`test/core/tools-actions.test.ts`（hire 三个动作、拒绝 lead、`.retired/`）、
  `test/core/settle-e2e.test.ts`（README 存在才建频道、归档与取消归档）。
- **取舍**：开除没有二次确认 —— 但目录只是移走，界面上要做确认按钮。团队「解散」不删目录，
  记忆和技能都还在。
- **验收**：私聊里说「让沈舟走」「解散 alpha」→ 侧栏与右栏当场更新，历史仍可读。

## ADR-034 组织推送的指纹包含**频道投影**（标题 / 成员 / 唤醒表 / 归档），不含未读与预览

- **背景**：界面靠 `org` 事件触发列表刷新。以前指纹只看名册：解散团队、往团队里加人、
  改标题都不会推一次，右栏就停在旧样子上（实测「助理说解散了，右栏还写着那个团队」）。
  把未读 / 预览也塞进去，则每来一条消息都推一次全量组织。
- **决策**：`orgSignature` = 名册行 + 频道结构行（id / title / archived / 排序后的成员与
  wakeOnAll）。有快照的 `flush` 顺带算频道指纹，补推只算名册（频道变化一定伴随一次提交，
  提交一定走 `flush`）。
- **执行**：`test/core/sse-*`（编码）、界面 `store.refreshLists` 的对账：频道没了 / 归档 →
  关掉当前频道；标题或成员数变了 → 重拉一次详情。
- **取舍**：频道指纹的字符串比较每次都是全量 O(频道数)；频道很少，值这个钱。
- **验收**：在私聊里让助理解散团队，不刷新页面，右栏与侧栏当场消失。

## ADR-035 「要我选」是一条带 `options` 的普通消息，不另开路由

- **背景**：界面需要「选项卡片」，而任何新路由都得多一条接口、多一个前端消费者，还得考虑
  历史里怎么存。
- **决策**：消息多一个可选字段 `options`（2–6 个，不重复）。`say` 带 `options` 时 kind 固定成
  `choice` 并自动 @我。**我的回答不新增接口**：普通消息 + `replyTo = choice.seq`，正文就是选项
  文字（或「跳过」/ 我自己写的）。输入框收到「最后一条带选项、之后我没说过话」的消息时，
  换成选项卡（radio + 其他 + 跳过 / 提交）。
- **执行**：`test/ui/choice.test.ts`（`pendingChoice`）、`test/core/say-contract.test.ts`
  （2–6 个、去重、kind=choice、自动 @我）。
- **取舍**：选项不是机器可枚举的枚举值，模型可能给出语义重叠的选项；约束写在工具描述里。
- **验收**：让人在私聊里问你「先做哪个」并给你两个选项，输入框出现选项卡，点一个就发出带引用的回答。

## ADR-036 插件能问「这个频道的工作区在哪」，但**路径守卫在插件里**

- **背景**：文件树 / 预览是频道级的（私聊 → 那个人的 `workspace/`，团队频道 → 团队的），
  插件拿不到频道数据；把整份频道文档塞给插件又会把「越界」责任推给内核。
- **决策**：`PluginApi` 增加 `scope(channelId)`：返回 `{kind, title, root, label}` 或 `undefined`
  （全员频道没有工作区）。内核只回答「根目录是哪一个字符串」；解析、前缀检查、`realpath`
  二次检查、软链接拒绝、大小 / 条目 / 深度上限，全部在插件里做完。出厂插件
  `seed/plugins/文件树/` 是第一个消费者：`/api/p/files/tree` 与 `/api/p/files/preview`。
- **执行**：插件自己的守卫没有单测（插件是数据，不进内核测试）；内核侧由 `plugin.test.ts`
  守装载与开关。
- **取舍**：插件可以拿根目录做任何事 —— 这就是 ADR-018 的边界：插件是可信任的本地代码。
- **验收**：分别打开一个私聊与一个团队频道，文件页签看到的是两个不同的工作区；路径里带
  `../` 或指向外面的软链接会被拒绝。

## ADR-037 附件预览：服务端按**真实 mime** 决定内联，HTML 永远是 `text/plain`

- **背景**：以前只有图片能点开（灯箱），其余附件只能下载。要能「点开看一眼」就得决定
  哪些类型可以内联 —— 而文件名是用户起的，不可信。
- **决策**：`GET /api/uploads/:id?preview=1`：图片 / PDF / `text/*` 内联；`text/html` 一律
  降成 `text/plain; charset=utf-8`；其余照旧 `attachment` 下载。前端按**响应头**决定画
  `<img>` / `<iframe>` / `<pre>`，不看扩展名。
- **执行**：`test/core/uploads.test.ts`（内联策略与 disposition）。
- **取舍**：预览是「看一眼」，不是编辑器；PDF 用 iframe，没有页码控制。
- **验收**：上传一个 `.md`、一个 `.html`、一张图，点开分别是文本、源码、图片；`.html` 不会执行脚本。

## ADR-038 文件树是出厂插件，不是内核的「文件管理」

- **背景**：需求要「频道级文件树 + 预览」。内核已经有 `file` 工具（agent 读写），界面却
  没有任何看产出的地方。
- **决策**：做成出厂插件 `seed/plugins/文件树/`（ADR-036 的第一个消费者），走 `rightPanel.tab`
  插槽；内核只提供 `scope`。原来的「示范」插件里的右栏「插件」页签删掉 —— 插件总览在
  「设置 → 插件」，一个只列清单的页签是死页签。
- **执行**：`test/ui/plugin.test.ts`（插槽表与宿主绘制点）、`plugin.test.ts`（清单与装载）。
- **取舍**：预览不做 markdown 渲染（原文更可信），也不做写操作。
- **验收**：右栏出现「文件」页签，私聊里看到那个人的 `workspace/`，团队频道里看到团队的。

## ADR-039 模型看得见的话都在 md 里，代码只留键名与机械规则

- **背景**：工具的描述、参数说明、拒绝与回话、投递头、附件说明，以前全是 TS 里的中文字面量。
  改一句「PASS 什么时候合法」要动 `say.ts` 并重跑五个测试文件；同一件事还在 `rules.md`、
  技能、工具描述里各写一遍，改一处漏两处；`prompt:check` 也管不到代码里的这些句子。
- **决策**：新增文案目录 `seed/text/*.md`（`## key` 分节，节体可多行、可带 `{{插槽}}`），
  启动时只补缺失地播种进 `<appRoot>/text/`；`md/catalog.ts` 读成 `TextCatalog`，装配时
  放进 `CoreToolDeps.text` / `ChannelWiring.text` / `AgentPaths.text` / `CoreServices.text`。
  代码里只留键名、数字、正则和条件。键缺失返回空串（工具不能因为一句话没配就坏掉），
  缺失由 `prompt:check` 直接报出来。
- **执行**：`test/core/no-hardcoded-text.test.ts`（点名的模块里没有中文字符串字面量）、
  `scripts/prompt-check.ts` 的文案段（键存在、插槽可填、确定性）、
  `test/core/seed-contract.test.ts` 的 `ONE_HOME`。
- **取舍**：工具描述在**装配时**定型，所以改 `text/tools.md` 要重启（和插件一致），
  不像 `prompt/*.md` 改完下一条消息就生效。投递/附件文案同样在装配时读入 —— 别假装热更新。
- **验收**：改一句拒绝话术后重启，模型收到的是新句子；删掉一节后 `prompt:check` 报出缺的键名。

## ADR-040 两个根的绝对路径进提示词；`hire` 点明「团队还没有 README」

- **背景**：2026-11-02 实测。助理要建 `xiaokonglong` 团队，把 `teams/xiaokonglong/README.md`
  和产物写进了 `<appRoot>/teams/`。原因是 `run` 的默认 cwd 在 `<appRoot>/assistant/<slug>/workspace`，
  向上两级就是应用根，而 `file` 按路径第一段分流 —— 同一个相对路径 `teams/…`，在两边落到
  不同的地方。团队频道是 README 的投影，于是团队根本不存在；`say` 到不存在的频道失败只回给
  模型自己，界面上什么都看不见，它在两个根之间猜了二十多步。
- **决策**：`70-directory.md` 写明两个根、`file` 的分流规则，并给出**绝对路径**
  （`{{root.user}}` / `{{root.app}}`）；`run` 只说「没有组织含义」。`hire` 带 `team`
  而那个团队还没有 README 时**不拦**（`建立团队` 技能的顺序就是先招人、再写 README），
  但在回话里点明「团队频道还不存在、要用 `file` 写 README」。
- **执行**：`agent/sections.ts` 的 `slotsFor` 填两个绝对路径；`scripts/prompt-fixture.ts`
  样例值；`test/core/identity.test.ts` 的确定性用例改成**同一个根**渲染两遍；
  `test/core/tools-actions.test.ts` 的 hire 用例。
- **取舍**：提示词不再与安装位置无关 —— 同一份模板在不同根下渲染出的字节不同。prompt cache
  按安装计，不受影响；「同一份输入逐字节相同」仍然成立。
- **验收**：拿一个空根起服务，让它建团队，写的是 `<userRoot>/teams/…`；`hire` 到一个
  不存在的团队时，回话里带「还没有 README」。

## ADR-041 日志跟着用户根走（`<userRoot>/logs/`）

- **背景**：日志原来在应用根（`<appRoot>/logs/`）。排查时它总是要和组织数据对照着看 ——
  「这条审计行是谁调的」「这个后台命令是谁起的、当时在哪个频道」，这些答案都在 `~/.solo`
  里。两个根分开之后，日志留在应用根意味着换机器只带走组织、带走不了一次现场的留痕。
- **决策**：`Layout.logsRoot = <userRoot>/logs`。审计（`tools.jsonl`）、诊断（`jank.jsonl` /
  `runtime.jsonl`）、后台命令（`run/`）、桌面壳的后端日志（`core.log`）都落这儿。
  其它安装物（库、上传、密钥、配置、提示词、文案、插件、助理）仍在应用根。
- **执行**：`layout.ts` 一处改；`app/diag.ts` / `app/audit.ts` 的构造参数从 `workspaceRoot`
  改成 `logsRoot`（避免在调用点再拼一次 `logs`）；`desktop/src/main.ts` 的 `logFile`；
  `test/core/layout.test.ts` / `roots.test.ts` / `diag.test.ts` / `audit.test.ts`。
- **取舍**：用户根的体积会随日志增长。四份日志都是「单文件 5MB、轮转一代」，后台命令记录跑完
  就删，所以增长有界；真要备份组织时把 `logs/` 排除即可。
- **验收**：起服务后 `~/.solo/logs/` 出现 `tools.jsonl`，`<appRoot>/logs/` 不再新生。

## ADR-042 新进团队频道的人自己报到；团队管理员只做管理

> **部分被 ADR-058 取代**（2026-11）：报到保留；「团队管理员」不存在了，团队频道成员 = 我 + 助理 + 团队成员。

- **背景**：2026-11-02 实测。助理建完团队，按技能在团队频道里发一条欢迎并 `@` 所有人，
  请他们自我介绍 —— 频道的第一句话永远是助理的，成员只是被叫到才说话；而「管理员」在
  实测里被写成「开发负责人」，一个人既统筹又交付，没人盯着整体。
- **决策**：
  1. **报到由系统叫醒、成员自己说**。`syncTeamChannel` 返回这次新进频道的成员
     （不含我和直接向我汇报的助理），`shell/assemble.ts` 的 `syncTeamAndAnnounce` 用一条
     `note`（`membership.joined`）叫醒他们；助理不发言、不替他们介绍。
     只有**运行时**的重投影（`hire` / 写团队 README / `services.syncTeam`）会叫：
     启动时的 `joinTeamChannel` 不叫，否则每次重启都让全体成员白烧一轮。
     招人是个例外：`openAgent` 会顺手把人加进频道，等重投影时「新进的」已经算没了，
     所以 `hire` 自己点名（`CoreToolDeps.announceJoin`），团队还没有 README 时不叫。
  2. **团队管理员是纯管理岗**。`建立团队` 与 `招人` 技能改口径：管理员只做拆解、派活、
     验收、盯进度，不亲自写代码、不做设计；`manager` 是助理；执行成员 `manager` 是管理员。
  3. **角色语义仍只在 md 里**：代码不认识「管理员」这个词，只知道 `lead` 与 `manager`。
- **执行**：`channel/membership.ts` 的返回值；`shell/assemble.ts` 的 `syncTeamAndAnnounce` / `announceJoin`
  与 `ownerSpeak` 的 `wakeTo`；`channel/tools/hire.ts` 的招人分支（`CoreServices.postAs` 同步加这个可选字段）；
  `seed/text/channel.md` 的 `membership.joined`；`seed/assistant/skills/建立团队|招人`；
  `test/core/membership.test.ts`。
- **取舍**：成员被叫醒是**并发**的，报到的先后不固定。要顺序就得排队叫醒，代价是团队
  一建好要等 N 轮；报到的价值在「每个人说了一句」，不在顺序。
- **验收**：起服务建一个新团队，团队频道的第一句话来自管理员或成员；再重启一次，
  没有人被重新叫醒。

## ADR-043 五层平级：`app` / `view` / `interface` / `shell` 搬出 `src/core/`

- **背景**：分层重构后 `src/core/` 里同时装着内核（agent / team / channel / md / runtime / 原语）
  和它的四个上层（app / view / interface / shell）。于是「core」有两个意思：文档里说
  「内核不得 import 上层」，而代码路径写着 `src/core/app/…` —— 上层看起来也是内核的一部分。
  界面的 `ui/app/src/api/types.ts` 再导出 `src/core/view/dto.ts`，也读成「界面依赖内核」。
- **决策**：四个上层搬到 `src/` 下与 `core/` 平级。`src/core` 从此只表示 domain（业务事实）。
  `src/` 的五个目录与依赖方向一一对应：`core`（domain）、`app`（用例）、`view`（契约）、
  `interface`（传输）、`shell`（装配）。分层、依赖方向、边界规则一条没变，变的只是路径。
- **执行**：`git mv` 四个目录；`src/app/*` 与 `src/shell/*` 对域内的 import 改成 `../core/…`；
  `scripts/check-boundaries.mjs` 的 `CHECKED_DIRS` 扩成六项（新目录也要受「只有 runtime 能
  import 底层库」约束），`LAYER_RULES` 的 `dirs` 与 `ROUTE_FILE` 换新路径，桌面壳的禁止项
  从 `src/core/` 扩成 `src/(core|app|view|interface|shell)/`；`package.json` / `Dockerfile` /
  `desktop/src/backend.ts` 的入口改为 `src/shell/main.ts`；`.claude/skills/code-flowmap` 的路径表。
- **历史条目**：ADR-001 起的旧条目里出现的 `src/core/app/…` 等路径是当时的事实，按「只追加
  不改旧条目」的规矩保留；读它们时按本条的映射换算。
- **验收**：`npm run check`（边界 8 组、29 条路由）、`npm test`（80 文件 777 例）、
  `npm run prompt:check` 全绿；`npm run live` 连跑两次 16/16；服务从 `src/shell/main.ts` 起。

## ADR-044 重启打断的那一轮，装配完把人叫回来接着做

- **背景**：2026-11-02 实测。团队「小恐龙」验收通过、林越正要把「断网重开」那条口径
  转给知言时进程重启，那一轮被底座结算成 `orphaned`，之后**没有任何人再动**：频道里
  最后一条是验收结论，看上去像「事情做完了」。`reconcileZombieTasks` 只负责把半截任务
  清干净（否则调度器会崩），它不知道频道，也没有人补那一步。
- **决策**：启动自愈顺手报出「谁的这一轮断了」（有 `pi.live.run` 的会话），装配层在
  **他当时干活的那个频道**留一句 `note`（`turn.interrupted`）并用 `wakeTo` 把他叫醒。
  只有进程死时确实在跑的会话才算 —— 正常重启一个人都不叫。
  唤醒记录（`agent/roster.ts` 的 `wake`）给出「当时在哪个频道、接着哪条」；
  没有记录就不猜，宁可不叫。
- **执行**：`runtime/open.ts` 的 `reconcileZombieTasks` 返回值与 `CoreRuntime.interrupted`；
  `shell/assemble.ts` 的 `resumeInterrupted`（装配最后一步，频道和私聊都已建好之后）；
  `shell/main.ts` 把 `runtime.interrupted` 传进装配；文案 `seed/text/channel.md` 的
  `turn.interrupted`；`test/core/resume.test.ts`。
- **取舍**：被打断的人重启后会多跑一轮（每人一次），这是要的代价 —— 不跑就是整条线停摆。
  中断的那一轮里已经做过的工具调用不会重放，模型从频道历史里接着判断，可能重做一小段。
  另外 `text/` 是「只补不改」播种的，升级时新键不会自动进老工作区，需要手工补
  （这是既有缺口，不在本条范围内）。
- **验收**：跑到一半杀掉进程再起，频道里出现「服务重启，X 在 #N 之后的那一轮被打断了」，
  被叫的人接着那条往下做；正常重启（没有半截 `run`）不产生任何新消息。

## ADR-045 文案升级落到「键」上：缺文件整份拷，有文件只追加新键

- **背景**：`seed/text/*.md` 一直是「文件在就不动」，本意是保护我手改过的措辞。代价是
  **新增的键永远进不了已经在跑的工作区**：工具描述、拒绝话术取不到键就是空串，模型看不见
  任何约束，而服务起得来、测试全绿，只有行为慢慢变差。实测踩过两次（`membership.joined`、
  `turn.interrupted`），两次都是手工去补 `.solo-app/text/`。
- **决策**：判据从「文件」降到「键」。文件不存在 → 整份拷；文件已存在 → 只把出厂文案里
  **它还没有的键**追加到末尾，已有的键一个字不动（手改的措辞仍然归我）。
  改已有键的措辞依旧不传播 —— 那是「只补不改」的本意，改文案的人自己改工作区那一份。
- **执行**：`md/catalog.ts` 的 `appendMissingKeys`（纯函数）；`shell/seed.ts` 的 `seedTextFiles`
  改用它；`test/core/catalog-merge.test.ts`（追加、幂等、已有键不动）。
- **取舍**：工作区文件会随着版本追加变长，删除的键也不会被清掉（无害）。顺序按 seed 文件里的
  顺序追加，不重排已有内容 —— 重排会让 diff 看不出真正改了什么。
- **验收**：老工作区里删掉一个键再启动，它被补回文件末尾；改过措辞的键保持原样。

## ADR-046 过程属于人：聊天只留消息，运行态是 `live` 占位 + 按人的任务面板（取代 ADR-004 的「过程在私聊看」、DESIGN §8.2 ④ 的「不做任务面板」）

- **背景**：ADR-004 把「过程」安置在私聊里——每一轮在消息流里插一个 `work` 块（折叠两行、
  可展开步骤树），群聊什么都不画。两头都不对：
  1. 读对话时被「N 步 / 6 秒 / 跑了两条命令」的壳打断。私聊是**一个人和一个人的对话**，
     它同时也是这个人的工作记录页，于是对话永远读不干净；过程属于人，却被塞进房间的时间线。
  2. 群聊里有人正在干活时屏幕上什么都没有 —— 只有头像光圈在动，看不出他在做什么，也看不出
     他会不会回话。ADR-008 删掉活动条之后，「此刻在跑什么」在界面上没有任何入口。
  3. 想看「刚才那句话他到底做了什么」得去私聊翻，而他可能根本没在那个私聊里说过话。
- **决策**：
  - **聊天流里只有消息**，加一条**派生**的 `live` 行：某个人在这个频道被叫醒、还没回话时，
    占位显示「最新一步 · 第 N/M 步 · 耗时」；`replySeq` 出现就消失，真实回复顶上来。
  - **过程的家是一个按人的任务面板**：顶栏「任务」按钮（带在跑人数），从右侧盖在聊天上滑出。
    一块 = 一轮，块头是「哪个频道 + 哪句话触发的」（`ViewTurn.trigger`），下面是步数 / 耗时 /
    状态 / 确定性摘要，展开是步骤树（复用现有 `RunBlock` / `StepRow` / `StepDetail`）。
  - 私聊不再画 `work` 块；`buildWorkRows` 与从没人读的 `state.turns` 一起删掉。
- **为什么不建任务表**：一轮就是一次唤醒，步骤就是会话条目（ADR-001 仍然成立）。面板只是
  换个维度重新排一次的视图；一旦落库就会出现「任务」与「条目」两份真相。
- **它不恢复什么**：没有 `draft` / token 流（C-007 依然成立）。`live` 行报的是「做到哪一步」，
  不是「将要说什么」；也不知道模型下一步会干什么——只报已经发生的。
- **执行**：`src/view/dto.ts` 的 `ViewTurn.trigger`；`app/read.ts` 的 `turnsOf` 投影它、
  `readPersonTurns` 支持 `limit`；`ui/app/src/stream/model.ts` 的 `buildRows` 产出 `live` 行；
  `ui/app/src/stream/LiveRow.tsx`；`ui/app/src/panels/TasksPanel.tsx`；`state/store.ts` 的
  `runs: Map<slug, Turn[]>`（群聊与私聊同一张表）。
- **取舍**：占位与真回复之间有一个极短的双写窗口，纯函数按「同一个人在这条触发消息之后
  已经说过话」提前收；面板在看的人还在跑时每 2 秒重拉一次列表（只在面板打开时），
  沿用 ADR-017 的判断，不新开通道。
- **验收**：群里派活 → 占位立刻出现并随步骤更新；点开面板，块头就是那句话；回话后占位消失、
  不留第二份；刷新后聊天里干净、面板里那一轮还在；私聊不再有 `N 步` 的壳。

## ADR-047 系统留痕不进聊天流：`note` 不画，只有后台命令那条折成一行（收紧 ADR-046 的「聊天只留消息」）

- **背景**：ADR-042 的报到、`unanswered` 的「没答上来」、看门狗通报、团队记忆沉淀的
  「记了什么」都落成 `note`，界面上是灰字 + 左侧竖线。ADR-046 把过程搬走之后，这些灰字
  反而成了聊天流里最显眼的噪音：一屏对话里插五六条，读起来像日志，而不是「谁对谁说了什么」。
  实测（2026-11-02，小恐龙团队刚建好）头七条消息里有四条是留痕，其中两条还是同一句话。
- **决策**：`ui/app/src/stream/model.ts` 的 `buildRows` 不把 `note` 变成行；
  **唯一例外**是后台命令跑完的留痕（`noteOf: "run"`）—— 它折成一行、点开才是输出。
- **数据不动**：留痕仍然照常落库、照常出现在 `chats(action=read)` 与 SSE 里，
  只是这一屏不画。要查「他到底答没答」走 `chats` 或任务面板。
- **代价**：`unanswered` 的「没答上来」在聊天里看不见了。0 步、没回话的一轮在任务面板里
  也不占块（ADR-046 的实现取舍），所以那一轮现在**没有界面入口**——这是明确接受的：
  宁可漏一条「他没答」，也不让每个频道都被灰字填满。
- **执行**：`ui/app/src/stream/model.ts`（过滤 + 注释）、`test/ui/stream-model.test.ts`
  （留痕不画、`noteOf: "run"` 照旧成行）、`docs/DESIGN.md` §2.1 / §2.5、`docs/CORE.md` §9。

## ADR-048 唤醒分轻重：轻的撤不掉重的（团队记忆沉淀不许挤掉投递）

> **已被 ADR-058 取代**（2026-11）：自动沉淀删了，`WakePriority` 也一并删了 —— 队列只做「同一会话只留一个未开始项」。

- **背景**：合并唤醒（`channel/queue.ts` 的 `coalesceQueue`）撤掉同一个会话里「还没开始」
  的排队项，一个会话最多留一个未开始的唤醒。沉淀走的是同一条 `wake()`、也开了
  `coalesce: true`，于是它能撤掉**任何**排队项，包括真正要人干活的那条投递。
  实测（2026-11-02，小恐龙团队刚建好）：周野的 `ch:team:xiaokonglong:{3,4,5}:周野`
  三条投递唤醒全部 `aborted`，最后一次只剩 `settle:xiaokonglong:5` 跑完 ——
  他醒来只整理了两条记忆，频道里三个人的话一句没答，团队从此不动。
- **决策**：给唤醒分轻重（`queue.ts` 的 `WakePriority`：`work` / `bookkeeping`），
  `queuedAhead` / `coalesceQueue` 多一个 `incoming` 参数，规则只有一条 ——
  **轻的撤不掉重的**。轻重由 `requestId` 前缀判（`priorityOf`）：`settle:` 是记账，
  其余都是干活。所以沉淀只能撤掉另一个沉淀；反过来投递能撤沉淀 —— 他马上要读整个频道了，
  沉淀可以等下一批。
- **为什么不给每条唤醒单独传轻重**：`requestId` 本来就是「谁叫的、为什么叫」的身份，
  再存一个字段只会多一处能对不上的地方。以后加看门狗通报、插件通知，按轻重进这张表即可。
- **代价**：沉淀的排队项可能比别的唤醒多活一轮；它本来就有 `waiting` + 游标兜底，
  重复问一次不会丢东西。
- **执行**：`src/core/channel/queue.ts`（`WakePriority` / `priorityOf` / `RANK`）、
  `src/core/channel/wake.ts`（按 `requestId` 判好传给 `coalesceQueue`）、
  `src/core/channel/post.ts` / `dispatch.ts` / `src/core/team/settle.ts`（签名透传）、
  `src/shell/assemble.ts`、`test/core/queue-jump.test.ts`、`docs/CORE.md` §8。

## ADR-049 收尾补发按「最后一段是不是复述」判，不按「说过话没有」

- **背景**：ADR-099 的收尾在结算后把最终正文补进频道，判据是「这条唤醒之后他说过话没有」。
  太粗：他说完一句话又接着干活，最后那段是**新结论**，也会被当成「已经说过了」吞掉。
  实测（2026-11-02，小恐龙团队）：陈默被叫醒只是报个到，顺手把整个游戏写完了，
  最终正文写着「index.html 已落地……等 @李岚 验收」，频道里只有他开头那句自我介绍 ——
  验收的人什么都不知道，任务链断在这里。
- **决策**：加一个结构判据 `saidLast`（`channel/turn/finish.ts`）：从答案条目往前翻，
  这一轮**最后一个工具调用**是不是 `say`。是 → 最终正文就是那句话换了个说法，不补；
  不是（跑了命令、写了文件）→ 他说完之后又干了活，最后那段照补。
- **为什么不按文本相似度**：模型复述时经常改措辞（实测那条沉淀的留痕和最终正文就不一样），
  按字面比对会漏；「最后一个动作是什么」是确定的，不需要阈值。
- **代价**：`say` 之后又干活、最后再复述同一句的，会多发一条。这类收尾本来就该少；
  宁可多一条，也不吞结论。
- **执行**：`src/core/channel/turn/finish.ts`（`saidLast` + `turnTarget` 的 `restated`）、
  `test/core/turn.test.ts`、`docs/CORE.md` §4。

## ADR-050 一个人可以有多条会话：会话键从「人」变成「人 + 用途」

> **已被 ADR-058 取代**（2026-11）：额外会话唯一的来源是 `<管理员>#settle:<团队>`，它跟着自动沉淀一起删了。会话键就是 slug。

- **背景**：名册是「slug → 一条会话」（`DirectoryState.slugToConversation`），投递、插话、
  团队记忆沉淀全部进这一条。于是同一份上下文被两类工作轮流占用：管理员正在读频道、拆活，
  沉淀的唤醒排进来；ADR-048 只解决了「谁撤掉谁」，没解决「它们本来就该分开」。
  记账那一轮醒来要重读整个频道，占满一轮的上下文和注意力，和「答人」这件事没有任何共享。
  DeepSeek 的 `dsh-superagent-prototype` 用的是另一个单位：一个 agent 身份 + **每个工单
  一条执行会话**（`worker-<ticketId>`），会话只是执行器，状态在工单上，路由器会话只持有摘要。
- **决策**：会话的键从「人」扩成「人 + 用途」。
  - 键的形状：`<slug>`（主会话，兼容旧数据）或 `<slug>#<用途>`（额外会话）。
  - `conversationToSlug` 仍然映射回**人**：工具靠它认「我是谁」，身份、记忆、技能、
    模型都还是同一个人，只有对话历史分开。
  - 额外会话**懒创建**：`conversationOf(key)` 找不到就开一条，和 DSH 的 `sessions.ensure`
    同一个形状。开出来的会话仍然装同一个人的身份扩展和工具包。
  - 第一步（本次）：团队记忆沉淀用 `<管理员>#settle:<团队>`，不再和投递抢同一条会话。
- **三步走**：
  1. **会话键**（本次）：名册多一张 `sessions` 表；`conversationOf` / `rememberWake` /
     `wakeOf` 按会话键走。
  2. **记账独立**（本次）：沉淀走管理员自己的第二条会话。它和投递并行，互不排队；
     `wake` 记录按会话 id 存（本来就如此），`say` 的默认频道天然正确。
  3. **任务会话**（未做，落地时另开 ADR）：把唤醒记录里的 `task` 提升成 taskId，
     一个任务一条 `<slug>#task:<id>`，投递按「线程 → 任务」的订阅表决定进哪条。
     这一步需要先有「这条消息属于哪个任务」的判据，没有更便宜的解法 ——
     DSH 用的是线程归属 + worker 自己判断 + handback，不是 @ 规则。
- **为什么不做 DSH 的全套**：每个任务一个工作区在 Solo 里没必要 —— 产出本来就在团队
  workspace，隔离在对话层就够。路由器/执行器分离 Solo 也已经有：助理和团队管理员就是
  路由层，`team/settle.ts` 才是那个不该和路由共用会话的「执行器」。
- **代价**：多一条会话就多一份上下文缓存，token 会涨；目前只有每个团队管理员一条，
  量可控。界面按 slug 聚合的地方不受影响 —— 额外会话不进 UI 列表，也不进频道成员。
- **执行**：`src/core/agent/roster.ts`（`sessions` 表 / `personOf` / `sessionKeyOf`）、
  `src/core/channel/wiring.ts`、`src/core/channel/wake.ts`（`WakeInput.session`）、

  `test/core/directory-persist.test.ts`、`test/core/settle-e2e.test.ts`、`docs/CORE.md` §1 / §8。

## ADR-051 收尾补发是一条真发言：要叫醒人，而且同一条答案只补一次

- **背景**：ADR-049 的收尾把模型写在正文里的结论补进频道，用的是 `postMessage(...,
  { wake: false })`。两件事同时炸了（实测 2026-11-02，小恐龙团队）：
  1. **不叫醒人**：沈舟的交付结论写着「@周岚 请验收；@许知远 地址到了」，补发进频道后
     周岚、许知远一个都没醒 —— 结论落进一个没人看的房间，团队从此不动。
     他的正文里没有 `say`（最后一个动作是 `run`），所以整轮只有这一条补发。
  2. **重复**：同一条答案会被**多条提交**各结算一次 —— 周岚的报到唤醒与沈舟的自我介绍唤醒
     都结算到条目 189；沈舟的投递唤醒与「后台命令跑完」唤醒都结算到条目 230。收尾因此跑了
     两遍，频道里并排两条一模一样的话（#11/#12、#15/#16，相隔 1 毫秒）。
- **决策**：
  - 补发去掉 `wake: false`，按正常发言投递（`@` 谁就叫醒谁；团队频道的 `wakeOnAll`
    照旧）。安静的一轮（团队记忆沉淀）不受影响：它的 `kind` 是 `note`，`note` 本来就不叫人。
  - 补发前比对：**这个人在这个频道里已经有一模一样的一句，就不再补**。判据是正文完全相同，
    不是「说过话没有」—— 后者正是 ADR-049 要绕开的那个粗判据。
- **为什么不按「提交 id」去重**：结算给的是条目 id，而两条提交拿到的是**同一个**条目 id，
  按条目去重会把第二条整条丢掉 —— 但它可能带着另一条唤醒的 `reply`/`task`。
  按「频道里已有同一句」判，既能挡住重复，又不动投递语义。
- **并发也要挡**：两条提交会在**同一毫秒**结算，两次收尾并发跑，都快照到「频道里还没有这句」，
  于是照样发两遍（实测 2026-11-02 周楠 #15/#16、苏黎 #17/#18）。所以整个收尾串在一个
  **进程级**串行闸门里（`createSerialGate`）：后一次才看得见前一次。闸门不能放在收尾器里 ——
  装配会接两次线（主装配 + 插件热重装），每个收尾器一份等于没串。
- **代价**：模型在一轮里真的想连说两遍一模一样的话时，第二遍会被吞掉。收尾补发是兜底路径，
  不是 `say`，这个代价可以接受。
- **执行**：`src/core/channel/turn/finish.ts`（`duplicate` 判据 + 去掉 `wake: false`）、
  `test/core/turn.test.ts`（「同一条答案被两条提交各结算一次，只补一次」/「补发会叫醒被 @ 的人」）、
  `docs/CORE.md` §4、`AGENTS.md` §3.3 的「插话回哪儿 / 一轮答完自动补发」一行。

## ADR-052 收尾不按字数吞话：短回答照补

- **背景**：收尾（ADR-049 / ADR-051）曾经有一条「正文不足 6 个字不补」的判据，本意是挡住
  `好的`、`收到` 这类残句。实测（2026-11-02，`auto/hy3` 跑 `npm run live`）它把正常回话吞了：
  我问「@助理 你在吗？用一句话回答」，他答「在。」—— 两句话都在会话里，频道里却一个字没有，

- **代价**：模型在「只需要应一声」的轮次里会把 `好的。` 也发进频道。比起叫了没人理，
  这更接近真实同事的行为。
- **执行**：`src/core/channel/turn/finish.ts`（去掉 `TURN_MIN_CHARS`，跳过时留一行日志）、

## ADR-053 派活：md 里的策略 + 确定性闸门 + 会留下来的工单（移植 dsh-superagent）

> **已被 ADR-060 取代**（2026-11）：整套工单 / 派活删掉了 —— 没有消费端。
> （第 2、4、5 条里的「规矩」曾先被 ADR-059 取代，现在连 `policy.md` 一起没了。）

- **背景**：V3 里「谁该干什么」全靠每轮现拼的提示词和人的临场判断。没有一张地方记得住
  「这件事是谁派的、按什么授权做的、做到哪一步」。一句话说完就散在消息流里，隔天要它接着做，
  只能靠翻聊天记录猜。dsh-superagent 的原型把这件事拆得很干净：Trigger → Eval →
  Mandate → Ticket → Report → Attention，授权是显式的、工单是活的、阶段是算出来的。
- **决策**：
  1. **只搬概念，不搬存储。** Source / Thread 就是频道（同一条消息流，不记两处）；
     Trigger 由消息派生（`triggerOf`），不落盘；Assignment 就是「这个人的会话被叫醒」。
  2. **判据写在 `<userRoot>/policy.md`。** 模式（`off` / `observe` / `auto`）、谁能明着派、
     谁不 @ 也能派、以及一组规矩。这份文件同时被两处读：提示词（`{{policy}}`）和闸门。
     改字存盘就生效，不需要重新部署 —— 这是「语义写在文档里」的延续。
  3. **闸门是纯函数，模型不能绕。** `gateOf` 只认事实：是不是人说的、有没有点名、是不是
     既有工单的追问、在不在名单里。`work(action=open)` 在工具里再跑一遍闸门，所以模型
     「觉得自己可以」不算授权。
  4. **工单落盘，阶段是算出来的。** `Ticket` 记授权（策略版本 + 命中的规矩 + 派活的人）、
     汇报、卡住时的问题；`stageOf` 照 dsh 的阶段表实现（ended → answer → review →
     blocked/failed → queued → idle → working），界面、工具返回、模型自述用同一份。
  5. **授权会失效。** 重试之前先 `mandateHolds`：规矩被删掉、策略改过，就停下来重新请示。
- **代价**：多了一份要维护的 md（`policy.md`），多了一个工具（8 个）。工单多了要清理，
  所以判断留痕只留 200 条、工单按增量文档压基线。
- **执行**：`src/core/work/`（`types` / `policy` / `gate` / `ticket` / `stage`）、
  `src/core/channel/tools/work.ts`、`seed/policy.md`、`seed/text/work.md`、
  `seed/prompt/89-work.md`（插槽 `{{policy}}`）、`test/core/work.test.ts`。

## ADR-055 立单在代码里，推进在模型里，收工在收尾里（补 ADR-053）

> **已被 ADR-060 取代**（2026-11）：`intakeAll` / `closeUntouched` / `bodyNotes` 全部删除。

- **背景**：ADR-053 把工单交给模型自己 `open`。真模型跑了二十几轮，**它一次都没开**——
  改提示词段、改工具描述、在投递正文里加一句、改策略措辞都不动。但它会用**已经存在的**
  工单（正文告诉它「你手上是 T1」，它就 `report`）。结论：**「要不要有这张单」是判据，不是
  创作**，判据已经有了（`gateOf`），不该再指望模型复述一遍。
- **决策**：
  1. **接活由代码做。** 一条消息叫醒某个人时，`intakeAll` 先跑一遍闸门；闸门接受就落一张
     工单，并把一句「这一轮属于工单 T{{id}}」拼在投递正文末尾（`work.wake.line`）。
     模型只负责推进：`report` / `ask` / `stop`。
  2. **追问不另开。** 同一频道、同一派活人、同一执行人、没点名的后续消息，沿用那张没结的
     单（`followUpIn`）。否则一句话一张单，频道变账本。
  3. **一轮结束自动收工。** 这一轮一个字都没报过的单，收尾时按 `dropped` 关掉
     （`closeUntouched`）；报过 progress 的留着。这样 `list` 才不是一天就废。
  4. **`open` 留着。** 模型自己另起一件要动手的活时仍然需要它，闸门照旧拦。
  5. **结束的单子有上界。** 每句话都会立一张，所以 `openTicket` 收尾时只留最近 200 张
     结束的（`MAX_TICKETS`）；**没结束的一张都不丢** —— 那是「他手上还有活」的唯一凭据。
- **代价**：每轮多一次工单文档快照 + 一次可能提交；判据（`gateOf`）从此在**投递路径**上，
  不只是工具里 —— 改 `policy.md` 会影响谁被立单，这一条写进了 `docs/CORE.md` §14。
- **实测（写正文那一句该怎么写）**：正文末尾那句的分量比想象的大，它会被当成「这一轮还要做什么」。
  - 写「做完先 report ready……再回话」→ 模型 report 完就收工，**不在频道里回话**了
    （`[turn]` 从 1–3 次涨到 10 次，走结算补发）；
  - 写「先在频道回话，再 report」→ 回话有了，但真正的活（写文件调工具）被跳过（live 掉到 14/16）；
  - 只写「这件事记在工单 T1「…」上」→ 回话正常，**但它基本不 report 了**，单子靠收尾按 `dropped` 关。
  结论：**一句话只能承载一件事**，而「把结论说出来」永远优先于记账。所以正文只陈述事实，
  记账靠工具描述和 `89-work.md`；模型报不报都行，单子的生命周期是机械的。
- **执行**：`src/core/work/intake.ts`（`intakeAll` / `closeUntouched`）、
  `channel/post.ts`（`policyFile` + 正文补一句）、`channel/dispatch.ts`（`bodyNotes`）、
  `channel/turn/finish.ts`（收尾收工）、`seed/text/work.md` 的 `work.wake.line`、
  `seed/prompt/89-work.md`、`test/core/work-intake.test.ts`。

> **已被 ADR-058 / ADR-059 取代**（2026-11）：没有「上级」这一层，拍不了板直接 `@我`；

## ADR-058 扁平组织：没有上级，也没有团队负责人

- **背景**：V3 的组织是一棵树 —— `identity.md` 的 `manager:` 连成汇报线，团队 README 的
  `lead:` 指定负责人，团队频道按「负责人 + 他往上的整条链 + 助理」投影成员、谁说话都叫醒他，
  团队记忆再靠一个叫「负责人」的影子会话（`<slug>#settle:<团队>`）自动沉淀。三套东西互相咬合，
  代码里长出一批只服务这套层级的机制：`reportsOf` / `chainUp` / `managerOf`、`leadProblem`、
  `team/settle.ts`（273 行）+ `SettleDoc` + 游标、`WakePriority` / `priorityOf`、额外会话。
  **用户判定这套层级是多余的**：团队本来就是「一个频道 + 一份 README（目标/验收/成员）+ 一份记忆」，
  里面不需要一个负责人；人只需要两种位置。
- **决策**：组织只有两种位置，且都是**文件夹事实**：
  1. **助理** = 身份目录在 `<appRoot>/assistant/` 下的那个人（`layout.isAssistantDir` /
     `assistantsOf`）。它不是谁的上级，只是「谁在直接跟我说话」这个事实。
  2. **成员** = `members/<slug>/` 里的人，用一个 `team:` 字段说明在哪个团队。
  - `identity.md` 的 YAML 头只剩 3 个字段（`name` / `title` / `team`），`manager` 消失；
    团队 README 没有 `lead`；`ViewChannel` / `ViewActor` 的 `lead` / `manager` 字段一并删掉，界面只画「助理」。
  - 团队频道成员 = `[我, ...助理, ...团队成员]`（平铺，去重）；**`wakeOnAll = 助理`**：
    没人被 @ 时由助理接话。这是原来「谁说话都叫醒负责人」的等价替代 —— 不设的话成员说「做完了」
    不 @ 人就没人接，会退回成轮询（实测过）。接话人是助理，不是负责人。
  - 拍不了板就**直接 @我**，中间没有一层转话的；组织变动（招人 / 开除 / 建团队 / 改别人身份）

## ADR-060 没有消费者的概念不上内核：删掉工单 / 派活

- **背景**：ADR-053 / ADR-055 把 dsh-superagent 的域模型（Trigger → Eval → Mandate →
  Ticket → Report → Stage）搬进了内核：自动立单、工单号进投递正文、七个动作的 `work` 工具、
  阶段表、200 条判断留痕。做完之后回头看，这套东西**没有任何读它的人**：
  - `WorkDoc` 只在 `core/work/` 自己的三个文件里读写；
  - `ticket` 在 `app` / `view` / `interface` / `shell` / `ui` / `scripts` 里 **0 次命中**：
    没有接口、没有界面、没有一条 live 或场景测试碰它；
  - 它唯一可见的产物是投递正文末尾那句「这一轮记在 T3 上」，外加一个模型可能调的工具。
  dsh 里这套模型的消费端是任务面板；我们搬了生产端，没搬消费端。结果是 **~1750 行只写不读的账本**。
- **决策**：整条删除。
  1. 删 `src/core/work/`（`types` / `policy` / `gate` / `ticket` / `stage` / `intake` / `index`）、
     `channel/tools/work.ts`、`seed/policy.md`、`seed/prompt/89-work.md`、`seed/text/work.md`；
  2. 拆掉接线：`post.ts`（`intakeNotes` / `policyFile`）、`dispatch.ts`（`bodyNotes`）、
     `turn/finish.ts`（`closeUntouched`）、`tools/context.ts`、`channel/wiring.ts`、
     `agent/sections.ts`（`{{policy}}` 插槽）、`layout.ts`（`policyFile`）、`shell/seed.ts`
     （`seedPolicy`）；
  3. 工具 8 → 7，系统提示词段 10 → 9，系统提示词正文 1837 → 1465 字符。
- **原则**（写进 `docs/CORE.md`）：**每一块代码要么被界面读、要么被模型读、要么被测试钉住
  行为。只写不读的账本不是能力，是负债。** 另外：**一个概念不要在两处各有一套生命周期** ——
  一条消息原来的生命周期是「落库 → 叫醒 → 回话」，工单又造了第二套，两套之间没有消费者。
- **为什么可以删而不伤行为**：闸门只决定「立不立单」，而单子没人读，所以它今天不改变任何

  「要拍板、要东西、要改范围，用 `ask` 停下来问人」在兜着。修法不是把那段搬回来，而是把
  规矩写成机制：`rules.md` 的拍板那条改成「**在正文里 `@我`**……光写『你』叫不醒我」。
  改完两次 live 都是 13/13（收尾 0/7、0/7）。
- **执行**：`src/core/work/`（删）、`src/core/channel/tools/work.ts`（删）、

## ADR-061 消息只有两种 kind；出厂不再带「示范」插件

- **背景**：写入侧会产出 7 种 `kind`（`chat` / `say` / `question` / `choice` / `decision` /
  `report` / `note`），Web 接口还允许客户端传任意值。但**行为上只区分两种**：`note` 与
  非 `note`。`say` 工具的 `kind` 参数只有 `decision` / `report`，没有任何读者；`question` /
  `choice` 由代码写、也没人读（是否在等我选，判的是 `options`）；前端的 `SAY_KINDS` 只是
  「不是 note」的另一种写法；`rules.ts` 还在判一个已经跟着工单删掉的 `work`。文档说
  「按 kind 决定显示」，界面上这几种画法完全一样 —— 这是 ADR-060 那条判据的又一个实例：
  **没有消费者的概念不上内核**。
- **决策**：
  1. 写入侧只允许两种：`chat`（默认）与 `note`（系统留痕）。`say` 去掉 `kind` 参数；
     收尾补发不再打 `say`；`POST /api/channels/:id/messages` 不再收 `kind`；`write` /
     `post` / `ownerSpeak` 的类型收成 `readonly kind?: "note"` —— 想加第三种，编译就不过。
  2. 读侧只有 `channel/types.ts` 的 `spokenKind()` 一个判据：`note` 与旧版本的过程行
     （`think` / `tool` / `work` / `step`）不算发言。`messageView` 在这里把旧 kind 归一成
     `chat` / `note`，DTO 类型收成 `"chat" | "note"`；界面不再认识旧 kind（删 `SAY_KINDS`、
     `LEGACY_PROCESS_KINDS`），未读、侧栏预览、「找你」共用同一个判据。
  3. 删除 `seed/plugins/示范/`：它默认装上并生效，给每个 agent 多一个 `clock` 工具、
     每轮提示词多一句、侧栏与输入框各多一块 UI，自己的清单里写着「没有实际用途」。
     插件的契约在 `src/core/plugin/api.ts` 与 `docs/WEB-API.md` §13.4，不需要一个常驻样板。
     现网 `<appRoot>/plugins/示范/` 是用户数据，不删。
- **为什么可以删而不伤行为**：唯一被读的区分是「算不算人说的话」；旧数据在投影层归一，
  不改库、不迁移。带选项的消息叫醒我靠的是 `options` 自动进 `mentions`，与 kind 无关。
  `clock` 的能力与 `run` 重叠（`date`），去掉后工具表与提示词各少一条。
- **代价**：旧数据里的 `choice` 消息以前不进聊天流（只画在输入框上方的选项卡里），归一后
  作为普通气泡留在记录里 —— 问题本来就该留在记录里，这是修正。只有过程行的旧频道，
  侧栏预览从「最后一条机器输出」变成空 —— 机器输出不是人话。
- **执行**：`src/core/channel/{types,rules,write,post}.ts`、`channel/tools/say.ts`、

## ADR-063 任意组群；团队频道由助理在后台分发；`@` 只用来请求回复

- **背景**：ADR-058 把组织拍平之后，唤醒只剩「谁被 @」「`wakeOnAll` 里的谁」两条机制。
  这留下三个缺口：
  1. 只有团队（有 README 的群）和私聊，没有「临时拉几个人说件事」的地方；
  2. 团队频道里 `wakeOnAll = 助理`：助理每条都醒，但**其他人不会**。助理看完了却没有
     把手里的消息交给相关的人的办法，团队频道里因此有一半消息没人接；
  3. `@` 同时承担「提到」和「要你回」两种意思，模型于是给每个名字都加 `@`，投递名单
     被无关的人撑大，一轮里多醒好几个人。
- **决策**：
  1. **任意组群**：频道 id `group:<slug>`，任何成员都能建（`chats action=create`；
     我走 `POST /api/channels`）。建群的人自动在群里，至少两个人，成员必须真实存在，
     同名不建第二份。群**没有** README、记忆、负责人：它就是「这些人一起说话」的房间。
     `wakeOnAll = members` —— 群里每个人都被新消息叫醒，自己判断要不要接（`[PASS]`）。
     人走了之后只剩一个成员的群自动归档（跟私聊同一条清理规则）。
  2. **团队频道的后台分发**：`wakeOnAll` 仍是助理。助理读完新消息，用新工具 `route`
     把那条交给相关的人：`deliverExisting` 复用普通投递（不写第二条消息、频道里不出现
     「转交」），收件人看到原文，正文多一句「X 让你看这条」。同时写一条
     `kind: "note", noteOf: "route"` 的隐藏留痕：它是「这一轮已经把消息交出去了」的凭据，
     收尾据此不再补发（`saidLast` 认 `route`），界面不画（ADR-047）。已经被 `@` 的人
     不会重复叫（投递时他就收到了）；我、助理自己、不在频道里的人都不能转。
  3. **`@` 只用来请求回复**：要对方回话才 `@`，只是提到名字就直接写名字。机制不动
     （`parseMentions` / `recipientsOf` 照旧），改的是 `rules.md`、助理身份与工作规矩技能
     里的说法 —— 这是「语义写在文档里」的那一半。
  4. **界面**：侧栏品牌行加一个「＋」→ 拉群浮层（群名 + 成员多选）；建完直接进那个群。
     会话列表的形态仍由后端 `kind`（`dm` / 群聊）给，前端不自己判。
- **代价**：
  - 团队频道里助理是唯一的入口：它漏转一条，那条就没人处理（没有兜底唤醒）。
    这是「助理负责阅读每一条」的必然代价；`route` 的留痕让漏转可审计。
  - 群越大，每条消息唤醒的人越多，token 成本按人数线性增长；群是临时协作，不是常态。
  - `route` 在频道里不可见：人看到的是「某人突然开始说这件事」，不知道是谁让他看的；
    收件人自己的投递正文里有那一句，别人看不到。
- **执行**：`src/core/channel/{types,membership,post,dispatch,delivery}.ts`、
  `channel/tools/{route.ts,chats.ts,hire.ts,index.ts}`、`channel/turn/finish.ts`、
  `src/app/chat.ts`、`src/interface/http/routes.ts`、`ui/app/src/{sidebar/Sidebar.tsx,
  panels/Overlays.tsx,state/store.ts,api/client.ts,styles/shell.css}`、
  `seed/{rules.md,assistant/identity.md,skills/工作规矩/SKILL.md,text/{tools,channel}.md}`、
  `test/core/{membership,route,tools-actions,turn}.test.ts`。

## ADR-064 插件读审计日志算 token：只给 `logsRoot` 一个根，账在插件里

- **背景**：Token / 成本 / 缓存命中率只有一份来源 —— 审计钩子写的
  `<userRoot>/logs/tools.jsonl`（ADR-010 / ADR-041）。插件拿到的 `workspace` 是**应用根**，
  够不到用户根；而「按调用算账」不该长进内核：内核不画界面，也没有别的模块依赖这份账。
- **决策**：`PluginApi` 增加 `logsRoot`（`<userRoot>/logs` 的绝对路径），装配层传
  `layout.logsRoot`。和 ADR-036 的 `scope` 同一个口径：**核心只给根**，读哪份文件、
  怎么容错（坏行跳过、旧行没有 `write` 当 0）、按本地日切天、什么算「计费 Token」，
  全在插件里做完。出厂插件 `seed/plugins/Token统计/` 是第一个消费者：
  `GET /api/p/tokens?days=7|30|0` 返回总量、每日、8 周热力图、按人 / 按模型的分组。
- **取舍**：插件因此能读整个日志目录（包括诊断与后台命令的日志）。这就是 ADR-018 的边界：
  插件是可信任的本地代码；给它一个根，比给它一条专用接口更省，也更符合「语义写在插件里」。
  审计日志是 5MB 封顶、只轮转一代的**排障账**，不是数据库 —— 面板里的「全部」也只是
  这两份装得下的部分。
- **执行**：`src/core/plugin/{api,load}.ts`、`src/shell/assemble.ts`、`src/app/audit.ts`

## ADR-065 一键重置：删两个根里的数据，保留模型配置，退出让壳重开

- **背景**：试坏一套组织之后只能手删 `~/.solo` 和 `Application Support/solo`，
  删错一个目录（比如把 `settings.json` 一起带走）应用就再也说不出话。需要设置里
  一个明确的「回到刚装好」入口。
- **决策**：
  1. **删什么**：用户根（`~/.solo`）整个删；应用根只删内核自己的东西 ——
     `assistant/`、`prompt/`、`text/`、`plugins/`、`uploads/`、`core.sqlite*`、
     `.seed-manifest.json`。桌面壳的 Chromium 缓存也在应用根里，绝不能整目录删。
  2. **留什么**：`settings.json` 与 `.secrets.json`。重置是清数据，不是把应用
     打成不能说话的空壳；模型配置是配置，不是历史。已装插件不保留，出厂插件
     下次启动按 `seed/` 装回来。
  3. **怎么做**：`POST /api/reset` 只认 `{ confirm: true }`；handler 先回 200，
     再把「该重置了」交给 `shell/main.ts`。删除必须在库关掉之后（开着删不掉
     `core.sqlite`），顺序是：停 watcher → 关服务 → 关壳 → 关库 → `wipeAll` →
     以退出码 75 退出。
  4. **怎么回来**：桌面壳（`desktop/src/backend.ts`）监听后端子进程退出，
     收到 75 就 `app.relaunch()`；壳与内核之间仍然只有进程边界这一条线，
     两边各写一个常量，不 import。网页版没有壳，退出后手动再起一次。
- **取舍**：不做进程内重启（关库再开、换端口、重建全部单例），那条路要在
  `main.ts` 里维护一个可重启的装配循环，且 `port: 0` 时会换 origin、打断
  localStorage 与 SSE。退出重开还顺带清掉内存里的插件、模型与定时器，
  更接近「刚装好」这个语义。
- **执行**：`src/app/reset.ts`、`src/app/index.ts`、`src/interface/http/routes.ts`
  的 `POST /api/reset`、`src/shell/serve.ts` 的 `onReset`、`src/shell/main.ts` 的
  `resetAll`、`desktop/src/backend.ts` 的 `onExit`、`desktop/src/main.ts` 的
  `restart`、`ui/app/src/panels/SettingsPage.tsx` 的 `DataSection`。
- **验收**：设置 → 数据 → 重置所有数据，确认浮层列出删 / 留；确认后应用自动重开，
  成员、团队、频道、聊天记录全空，模型配置还在，出厂插件和助理已回来。
  `test/core/reset.test.ts` 钉住「删什么、留什么、没确认不让重置」。

## ADR-066 装完带前端的插件：问一句再重开，复用退出码 75

- **背景**：插件后端在装完就热装（ADR-026），工具、提示词、接口立刻能用；但前端
  `client.js` 只在页面启动时 `import` 一次，插槽也是启动时填一次。于是「装好了却看不见」
  不是没装上，是界面那一半还没重新加载。用户需要知道这一点，并且自己决定什么时候打断当前工作。
- **决策**：
  1. 装成功且 `GET/POST /api/plugins` 返回的插件带 `client: true` 时，插件页起一个确认浮层
     「「X」已经装好了」；`client` 缺失的纯后端插件不弹 —— 它已经能用了，没必要打断轮次。
  2. 浮层两个出口：「稍后」只关浮层，插件保持已装；「立即重启」在桌面壳里请求
     `POST /api/restart`（只认 `{ confirm: true }`），后端回 200 后关服务、关壳、关库，
     以退出码 75 退出，壳 `app.relaunch()`。网页版没有壳，按钮写「刷新页面」，
     `location.reload()` 重新走 `bootPlugins`。
  3. 重启不删任何文件，和重置共用退出码 75；桌面壳不区分两者，都只做 `restart()`。
- **取舍**：不做进程内热加载前端（要清旧插槽、旧 `<style>`、动态 `import` 缓存，还要处理
  「注册到一半」的中间态）；整份重开还顺带清掉内存里的定时器与会话，和「刚装好」一致。
  代价是正在跑的轮次会断，重启后按 ADR-044 接着做。也不做「装完自动重启」—— 安装可能发生在
  正在回答的时候，必须让人选。
- **执行**：`src/interface/http/routes.ts` 的 `POST /api/restart`、`src/shell/serve.ts` 的
  `onRestart`、`src/shell/main.ts` 的 `restartApp`（与 `resetAll` 共用 `stopCore`）、
  `ui/app/src/panels/PluginsPage.tsx` 的安装回调、`ui/app/src/panels/Overlays.tsx` 的
  `RestartSheet`、`ui/app/src/state/store.ts` 的 `restartOpen`、`ui/app/src/api/client.ts` 的
  `restartApp`；桌面壳仍是 `desktop/src/main.ts` 的 `restart`。
- **验收**：装一个带 `client.js` 的插件 → 退出确认浮层写明生效范围 → 「立即重启」后应用重开、
  插件入口出现；「稍后」后插件仍在清单里，下次启动出现。纯后端插件装完不弹浮层。
  `test/core/reset.test.ts` 钉住「没确认不让重启、确认后才交给启动层」。

## ADR-067 用 GitHub Actions 打包，GitHub Releases 当更新源

- **背景**：打包一直靠发布机上一台 Mac 手动跑 `desktop:dist:mac` / `desktop:dist:win`，
  再把产物、清单与签名搬进自建静态目录（ADR-027 / ADR-029）。Windows 包本来就是交叉编出来的，
  再维护一台「发布机」没有必要；而 GitHub Releases 天然带 https、带版本化资产、带「最新版本」
  的固定地址，正好是 `latest/download/` 能直接喂给现有客户端的那一种。
- **决策**：
  1. `.github/workflows/release.yml` 由 `v*` 标签（或手动运行）触发：先跑 `npm run check` +
     `npm test`，再并行打 macOS arm64（dmg + zip）与 Windows x64（NSIS + zip）。
  2. 发布任务从仓库 secret `SOLO_UPDATE_KEY` 取 Ed25519 私钥，用现有
     `scripts/update-manifest.ts` 签 `latest-mac.json` / `latest-win.json`；先建 **draft**
     release，二进制传完最后才传清单与 `.sig`，最后才正式发布。已经正式发布过的标签拒绝覆盖。
  3. `desktop/src/feed.ts` 的 `DEFAULT_FEED_URL` 指向
     `https://github.com/kirer/Solo/releases/latest/download/`；`SOLO_UPDATE_URL` 仍可覆盖，
     本机 http feed 仍可用于验证升级。
- **取舍**：私钥从「只存在发布机」变成「发布机 + GitHub secret」；换钥匙仍然等于老客户端再也
  升级不了，所以两处都要备份。仓库必须公开，未登录的客户端才能直接读 Releases；要私有就回到
  自建 feed（脚本保留）。`latest/download` 只指向最新**正式**版，回滚只能发一个版本号更高的
  回滚版本，或者用 `SOLO_UPDATE_URL` 指回旧 feed。
- **执行**：`.github/workflows/release.yml`、`desktop/src/feed.ts`、`docs/DEPLOY.md` §9–10。
- **验收**：`git push origin v2.0.8` → Actions 全绿 → Release 里有 dmg / 两个 zip / exe /
  四份清单文件（两份 JSON + 两份 `.sig`）；装 2.0.7 的桌面端「检查更新」能看到 2.0.8。

## ADR-068 桌面包瘦身：只带用得到的语言、源码映射与 provider

- **背景**：2.0.7 的 Windows 包解包 478 MB、zip 164 MB；macOS `.app` 410 MB。拆开看，
  Electron 本体（`Solo.exe` / dll / pak / `icudtl.dat`）约 326 MB，是地板的；其余大头不是业务
  代码，而是 55 个 Electron 语言包 48 MB、`*.map` 24 MB、以及随 `pi-ai` 进来的 Google /
  Bedrock SDK 链 29 MB。Solo 只支持 `openai-responses` / `anthropic` / `openai` 三种 API，
  后两家的 SDK 运行时根本走不到；`react` / `react-dom` 也已经被 Vite 打进 `ui/web`。
- **决策**：
  1. `electronLanguages` 只留 `en-US` / `zh-CN` / `zh-TW`，原生菜单和对话框够用。
  2. `files` 排除 `**/*.map`、`openai/src`、`@anthropic-ai/sdk/src` —— 运行时走 dist，
     `exports` 不指向 `src`；source map 只影响线上排错，仓库里仍保留。
  3. 排除 Google（`@google/genai`、`protobufjs`、`web-streams-polyfill`、`google-auth-library`、
     `gaxios`、`node-fetch`、`fetch-blob`）与 Bedrock（`@aws-sdk`、`@smithy`）的 SDK 链。
     `providers/all` 仍会 import 这两个 provider 模块，但它们的 API 是
     `lazyApi(() => import(...))`（`google-generative-ai.lazy.js` / `bedrock-converse-stream.lazy.js`），
     不调用就不会加载 SDK；Solo 的 `APIS` 表也没有它们。
  4. 排除 `@earendil-works/pi-codemode`、`quickjs-wasi`、`@silvia-odwyer/photon`：Solo 只 import
     `pi-durable` 根和 `storage/sqlite/node`，没有 import `codemode` / `images` 子路径。
  5. `react` / `react-dom` 从 `dependencies` 移到 `devDependencies`：界面构建需要，运行时不需要。
  6. `compression: maximum`：构建慢几分钟，换压缩包小几个百分点。
- **取舍**：以后要正式支持 Gemini / Bedrock，必须把对应 SDK 从排除项里放回来，否则选中它们会在
  生成时 `module not found`。排除 source map 后，生产环境的 JS 堆栈看不到源码行；要排错就用
  仓库里的同一版本重新构建。Electron 本体、`dxcompiler.dll`、`vk_swiftshader.dll`、`ffmpeg.dll`
  和 `LICENSES.chromium.html` 一律不动：前三个影响 GPU / 媒体兜底，最后一个是法律要求。
- **执行**：`electron-builder.yml` 的 `files` / `electronLanguages` / `compression`；
  `package.json` 与 `package-lock.json` 的 `react` / `react-dom` 位置。
- **验收**（2.0.7 实测）：`Resources/app` 35 MB（原 104 MB），`node_modules` 33 MB（原 101 MB），
  `locales` 只剩 `en-US.pak` / `zh-CN.pak` / `zh-TW.pak`；macOS `.app` 296 MB（原 410 MB），
  dmg 106 MB（原 139 MB），zip 116 MB（原 139 MB）；Windows 解包 362 MB（原 478 MB），
  zip 141 MB（原 164 MB），NSIS 安装包 112 MB（原 130 MB）。瘦身后的打包后端能启动、
  `/` 返回界面、`/api/org` 与 `/api/models` 正常，`npm run live` 13/13。

## ADR-069 Windows 的菜单搬进自绘标题带（取代 ADR-028 第 7 条的 Windows 那半）

- **背景**：ADR-028 第 7 条让 Windows 保留系统标题栏，理由是覆盖式窗口按钮需要界面给右边留内边距。

## ADR-070 Windows 更新安装：先握手、用 tar 解包、替换前后核对版本

- **背景**：2.0.9 → 2.0.10 在 Windows 上真实失败：更新包下载完、点「立即重启安装」后应用退出，
  十分钟没有重新打开；手动再启动仍是 2.0.9。2.0.9 的安装脚本用 `Expand-Archive` +
  `robocopy /MIR`，只在失败时写日志；主进程不等安装器确认就退出，用户也无法知道是解包慢、
  文件被占还是脚本根本没起来。`docs/DEPLOY.md` 早就写着「Windows 的 zip 替换没有实机验证过」，
  这次是第一次真机验收。
- **决策**：
  1. **先握手再退出**：安装脚本启动后的第一件事是写 `<zip 目录>/installer-<uuid>.ready`。
     `scheduleInstall` 等这个文件（10 秒超时）才返回；主进程随后才停后端并 `app.quit()`。
     安装器没起来（被杀软拦、PowerShell 起不来、job 对象限制）会弹「更新安装器没起来」，
     应用不退出，而不是无声消失。
  2. **用系统自带的 `tar.exe` 解包**（`%SystemRoot%\System32\tar.exe`），它比 PowerShell 5.1
     的 `Expand-Archive` 快一个数量级；没有 `tar.exe` 才退回 `Expand-Archive`。
  3. **等所有同路径的 `Solo.exe`**：先等主进程 90 秒，再按进程名 + 可执行文件路径等后端 /
     后台命令 30 秒；仍不走就强制结束。只等主进程 PID 不够 —— 后端也是同一个 exe，文件没解锁
     时 `robocopy` 会失败，旧版本又被打开，表现和「点了没反应」一样。
  4. **替换前后都核对版本**：解包后读 `resources/app/package.json`，必须是清单里的新版本；
     `robocopy` 之后再读安装目录的同一文件，不是新版本就抛错。失败时只有安装目录仍是完整的
     旧版本才自动打开旧程序；半套文件不启动。日志从第一行开始写 `%TEMP%\solo-update.log`
     （等待 / 解包 / robocopy 退出码 / 提权 / 版本 / 启动），不再只在 catch 里写。
  5. **这条修复只对 2.0.11 起的客户端生效**：2.0.9 / 2.0.10 的安装器还是旧代码，必须手动装一次
     2.0.11 的 `.exe`；之后的更新才走新脚本。
- **取舍**：`tar.exe` 从 Windows 10 1803 起才有（Electron 本身也只支持 Windows 10+），更老的系统
  会退回慢路径。强制结束同路径进程会打断正在跑的后台命令 —— 更新对话框已经写明「正在跑的事会中断」。
  `robocopy /MIR` 仍不是原子替换：如果它在复制中途失败，可能留下混合文件；版本核对能拦住
  「旧版本静默重开」，但不能替代备份，失败时按提示手动安装。日志里会包含本机路径，只落在
  `%TEMP%`，不上传。
- **执行**：`desktop/src/install.ts` 的 `windowsInstallScript` / `scheduleInstall`、
  `desktop/src/updates.ts` 的安装分支、`test/desktop/install.test.ts`；
  `docs/DEPLOY.md` §10。
- **验收**：单测覆盖 ready 文件、tar 优先级、解包 / 替换后的版本核对、旧版本才自动重开；
  Windows 手工从 2.0.11 升 2.0.12：点安装后应用退出、新版本自动打开，`%TEMP%\solo-update.log`
  能看到 `tar 解包` → `robocopy 退出码 1` → `安装完成`；失败时能看到 `Solo 更新失败` 弹窗。

## ADR-071 pi-durable 1.4.0 → 1.5.0 直升：schema 门面 + 报告适配 + 不急着用新能力

- **背景**：`@earendil-works/pi-durable` 1.5.0（2026-11-02）是一个破坏性 minor：工具参数
  schema 改由 `@earendil-works/pi-schema` 校验，`pi-ai` 根不再转发 TypeBox 的 `Type`；
  `onReport` 从一个错误对象改成一整条带 `kind` 的 `Report`；`subscribeCommits()` 换成
  `observeCommits()`；`task_parked` / `session_failed` 改叫 `task_interrupted` /
  `storage_failed`，连续重启超限不再 park 等 `retryTask`，而是结束任务并报告。我们的
  8 个工具文件里的 46 处 `Type.*`、报告落盘、SSE 提交订阅都踩在破口上。这次直接在当前分支升级（不开
  分支），先弄清变更与可用新能力。
- **决策**：
  1. **四个包一起锁 `1.5.0`**（`pi-durable` / `pi-ai` / `chord` / `pi-schema`，无 `^`）。
  2. **`Type.*` 门面留在 `src/core/runtime/index.ts`**：把 `Object/String/Number/Boolean/
     Array/Optional` 六个名字映射到 pi-schema 的 `obj/str/num/bool/arr/opt`。工具定义与
     插件 API（`api.Type`）一行不改；`pi-schema` 仍然只有防腐层能 import。`obj` 默认闭合
     （多传参数会被拒），正是工具参数要的语义。
  3. **报告只在一个地方翻译**：`toRuntimeReport(report)` 把 `Report` 摊平成 `RuntimeReport`
     （`type` = `report.kind`，错误正文 / 堆栈 / 任务 / `reason` / `callback` / `restarts`）。
     `app/diag.ts` 的文案表跟着换成九个新 `kind`。上层仍然只认自己的形状，不 import 底座类型。
  4. **SSE 订阅改成同步观察者**：`harness.observeCommits({ advance, end })`，`detach()` 取消；
     120ms 去抖和按频道推增量都不变。观察者在新版里晚一个微任务、只拿**已落盘**的提交，
     对 120ms 的 UI 推送没有影响。
  5. **不为了「有新能力」而改行为**。1.5.0 的 `maxTurns`、`continue`、`runFailure`、
     `readOnly`、`whenIdle: "reject"`（与已有的 `whenBusy: "steer"` 合成一次 admission）、
     `beforeProviderRequest`、`afterRun`、`ConversationTranscript` 都先记在案，等有具体需求
     再接：`maxTurns` 会截断合法长活，没有 continue 入口时会把活停住；`continue` 要先有
     「重试这一轮」的产品入口；`readOnly` 只在多进程看同一份库时才有意义，而底座本来就不
     支持多进程同写。`wake` 从 1.4.0 起就用 `whenBusy: "steer"`，不需要重接。
  6. **`pi.live` 的空闲判据继续用 `run !== undefined`**：新版失败后会保留 `runFailure`，
     不能再拿「文档是不是空对象」判空闲；我们的自愈也继续删 `run`（`runFailure` 留着无害）。
- **取舍**：门面只映射我们用到的六个构造器 —— 将来工具需要 `union` / 枚举 / 嵌套开放对象，
  要在防腐层补，而不是让工具文件直接 import `pi-schema`（那会破边界）。1.5.0 的组提交、
  无存储读、进度延迟落盘能显著降低存储往返，但我们的 `serializedHarness` 本来就串行化
  同进程写入，收益会小一些；进度最多晚 1 秒落盘，SSE 的 1 秒补推已经覆盖这个窗口。
  升级后工具参数由 pi-schema 校验（错误话术与 TypeBox 不同），必须用真模型跑两遍
  `live`，单测看不见模型是否还会正确调工具。
- **执行**：`package.json` / `package-lock.json`、`src/core/runtime/index.ts`（schema 门面）、
  `src/core/runtime/open.ts`（`toRuntimeReport` / `safeReport`）、`src/interface/http/sse.ts`
  （`observeCommits`）、`src/app/diag.ts`（报告文案）、`scripts/check-boundaries.mjs`
  （`RUNTIME_ONLY` 加 `pi-schema`）、`test/core/diag.test.ts`；
  文档同步 `AGENTS.md` §1–2、`docs/DEPLOY.md` §7、`docs/WEB-API.md` §13.2、`docs/CORE.md` §11、
  `docs/research/02-pi-durable.md` 的升级注记。
- **验收**：`npm run check`、`npm test`（89 文件 / 821 例）、`npm run prompt:check` 全绿；
  `npm run live` 连跑两次都 13/13；用真实数据副本启动，`pi.live` 自动迁到 version 3，
  `/api/org`、频道详情正常。

## ADR-072 失败可见：`runFailure` 单独投影，不塞进 `activity`，也不把留痕画进聊天

- **背景**：1.5.0 在 `pi.live.runFailure` 里留下「这一轮为什么没答上来」（`reason` + `detail`），
  但 Solo 只在频道里写一条系统留痕；而 ADR-047 又规定系统留痕不进聊天流。结果是：模型
  配错、网关 502、工具轮数超限这些真失败，界面上和「他还没说话」长得一模一样。1.5.0 新增的
  `interrupted` / `restart_limit` / `nothing_to_answer` / `turn_limit` / `faulted` / `orphaned` /
  `reset` 也都没有文案，只会把原始英文原因贴出来。
- **决策**：
  1. **失败是人的状态，不是「正在做」的一种**。`ViewActivity` 仍然只有 `thinking` / `working`；
     `ViewActor` 新增独立的 `lastFailure?: { reason, detail?, text }`。`text` 由服务端按
     `text/channel.md` 翻好，界面直接画，不在两份地方各写一套原因表。
  2. **不把 `failed` 塞进 `activity`**：`sse.ts` 的 1 秒补推用「有人 `activity`」当还有活，
     失败会一直留在 `runFailure` 里直到下一轮开始；塞进去会让补推永不停止。`orgSignature`
     把 `lastFailure` 拼进指纹，失败出现 / 消失仍能实时推给界面。
  3. **只有 `run === undefined` 时才读 `runFailure`**：`afterFailedRun: "continue"` 启动的
     下一轮可能在同一份 `pi.live` 里还带着上一次失败，那时以「在跑」为准。
  4. **`detail` 压成一行、截 200 字**进频道留痕；完整错误仍在 `logs/runtime.jsonl` 与会话条目里。
     新增的原因键覆盖 1.5.0 的全部 `RunFailureReason`，外加 Solo 自己的 `run_failed` / `restart`。
  5. **`nothing_to_answer` 不留痕**：上下文本来就以一条回答结尾，continue 没东西可答，不是
     「他掉了链子」。和 `aborted`（被合并唤醒撤掉）同等对待。
  6. **`task_interrupted` 按 `reason` 分文案**：`restart_limit` 是「连续重启超限，已结束」，
     `interrupted` 是「任务被重启打断，已结束」；两者都带上 `restarts`。旧文案把单次崩溃
     也说成「连续超限」，会把人带到错误的排查方向。
- **取舍**：失败卡放在「后台任务」第二屏的人名旁与详情顶部，不放进聊天流，也不新增路由 ——
  这正是 ADR-047 的延续；代价是不打开第二屏时只能看到人名旁一个 5px 红点。失败卡只显示
  最近一轮，历史失败仍在每一轮的 `ViewTurn.status = "failed"` 里。
- **执行**：`src/core/channel/unanswered.ts`（原因表 / `detail` 裁剪 / `watchSettled`）、
  `src/core/channel/dispatch.ts`（`WakeNote.detail`、`nothing_to_answer` 过滤）、
  `src/core/channel/post.ts`（留痕透传）、`seed/text/channel.md`（原因文案）、
  `src/app/diag.ts`（`reportLabel` + `restarts`）、`src/app/read.ts`（`liveMaps` / `liveOf`）、
  `src/view/dto.ts`（`ViewLastFailure`）、`src/interface/http/sse.ts`（组织指纹）、
  `ui/app/src/panels/TasksPanel.tsx` + `styles/tasks.css`（红点 / 失败卡）。
- **验收**：`test/core/unanswered.test.ts`、`test/core/wake.test.ts`、`test/core/diag.test.ts`；
  `npm run check`、`npm test`、`npm run ui:build`；真机看一次失败卡（无模型或网关错误）。

## ADR-073 最大限度依赖 1.5.0：先删掉自己写的并发保证（取代 ADR-071 决策 5）

- **背景**：ADR-071 升级到 1.5.0 时采取的立场是「不为了有新能力而改行为」，于是底座已经
  提供的排序、恢复、失败结算仍然由 Solo 自己再保证一遍。最典型的是
  `runtime/serialize.ts` 的 `serializedHarness`：它把同一进程里**所有** `harness.commit`
  串行化，起因是 1.4.x 的文档代理按读集覆盖，不排队会互相吃掉（真实事故是一条 `say`
  报 `Cannot use a settled overlay`，但消息其实已经写进去，模型重试后频道里出现两条一样的话）。
  1.5.0 的 group commit 已经把「同一份文档 / 同一个键的 commit」排进同一个 job 队列，
  不同文档可以并行；再包一层全局串行只会把并行度重新压回 1。
- **决策**：
  1. **底座已经保证的事，Solo 不再保证**。`openCore` 直接使用 `DurableHarness.open` 返回的
     句柄；删除 `serializedHarness` 与 `test/core/serialize-commit.test.ts`。
  2. **并发底线改由裸 harness 测试守**：`test/core/commit-concurrency.test.ts` 不经过投递层，
     直接并发调用 `appendToChannel` / `rememberWake`，断言同一文档 30 个并发追加一条不少、
     seq 连续、前一个 commit 在事务里等待时后一个会排队（而不是撞覆盖层），以及频道与名册
     两份文档并行写时各自完整。
  3. **保留 `post.ts` 的串行闸**：它保护的不是 commit，而是 commit **之前**对频道元数据、
     摘要、收件人的 `snapshot` 读与队列合并。group commit 只管提交，不管提交外的「读—算—提交」
     竞态；等这段读搬进事务（`submit(tx)` 那一阶段）再单独评估，不在这一条里顺手删。
  4. **保留 `finish.ts` 的 `repostGate`**：它防的是同一轮里宿主与模型各补发一次，与存储层
     的并发无关。
  5. **后续阶段按同一原则逐条接**：`continue` 取代假输入、`submit(tx)` 原子唤醒、
     `afterRun` durable 收尾、`maxTurns` 都要有自己的验收门（单测 + 两次 `live` + 场景），
     不一次性全开。
- **取舍**：group commit 的收益是不同文档的 write 可以并行，同文档仍然串行；所以延迟不会
  变差，吞吐只在「多人同时写不同文档」时变好。真正的风险是此后有人依赖「全局串行」这个
  不存在的保证 —— 所以边界写在测试里，而不是写在注释里。
- **执行**：`src/core/runtime/open.ts`（去掉包装）、删除 `src/core/runtime/serialize.ts` 与
  `test/core/serialize-commit.test.ts`、新增 `test/core/commit-concurrency.test.ts`；
  文档同步 `docs/CODE.md` 文件表、`docs/CONCESSIONS.md` C-010、`AGENTS.md` §3.3。
- **验收**：`npm run check`、`npm test`、`npm run prompt:check`；并发用例连续跑多次不抖；
  真模型路径（`live` 两次 + `live:scenarios --rounds=1 --smoke`）无重复消息。

## ADR-074 重启打断的那一轮由底座重放，Solo 只清理悬空标记

- **背景**：1.4.x 的 `reconcileZombieTasks` 在启动时把所有非终态任务一并结算成失败，再用
  一条「接着做」的假输入把会话叫醒。1.5.0 的调度器在 open 时自己把 `running` 翻回 `pending`、
  `restarts + 1`，`resume()` 之后按 checkpoint 继续；被崩溃切断的一次请求按一次失败重试计，
  超过 `settings.restartLimit` 才以 `restart_limit` / `interrupted` 结束。再来一遍 Solo 的
  强杀不仅多余，还会把底座本来能续跑的一轮直接判死。
- **决策**：
  1. **启动不结算任务**：`runtime/open.ts` 的 `inspectStartup` 只做底座不做的三件事 ——
     报出「有 generation 任务的 `restarts > 0`」的会话、清掉 `run` 指向一个**不存在**的任务
     的悬空标记（连同 `generation` / `tools` / `nestedTools`，把该轮的输入结算为
     `unanswered/restart` 并放回队列）、找出没人取的 queued submission。
     仍然存在的任务一律不动：`afterRun` 正在跑的那一轮也是非终态，误杀会让收尾永远不来。
  2. **留痕不叫醒**：装配层对被打断的会话只写一条 `turn.interrupted` note，然后
     `harness.resume()`。重放由底座做，Solo 不再提交任何「继续」输入。
  3. **真崩溃守门**：`test/fixtures/crash-child.ts` 在子进程里起一个会挂起的任务，
     父进程 `SIGKILL` 后重开，断言任务回到 `pending`、`restarts >= 1`，`resume()` 后跑完
     （`test/core/crash-replay.test.ts`）。
- **取舍**：重放是 at-least-once —— 崩溃前已经发生的工具副作用可能再做一次（写文件、发消息）。
  Solo 的工具本来就按「幂等键 / 至少一次」设计，这一条把代价写明，不假装 exactly-once。
  重放还会再花一次模型调用的 token；收益是「服务重启后活还在」，这是用户真正要的。
- **执行**：`src/core/runtime/open.ts`（`inspectStartup`）、`src/shell/assemble.ts`
  （`noteInterrupted` + `harness.resume()`）、`src/shell/main.ts` 传参；文案
  `seed/text/channel.md` 的 `turn.interrupted`；测试 `test/core/{resume,reconcile,crash-replay}.test.ts`。
- **验收**：`npm run check`、`npm test`、`npm run prompt:check`、`npm run live` 两次 13/13。

## ADR-075 「继续这一轮」用 `continue`，不自动重试

- **背景**：模型失败（`model_error`）、服务重启（`interrupted`）之后，频道里只有一条 note，
  人看不到「还能不能接着做」，也没有入口。旧恢复路径用一条假用户输入叫醒，模型会把那句
  假话当成新任务来答。
- **决策**：
  1. **启动恢复用 `continue`**：`inspectStartup` 找出的 backlog（queued submission 没有
     对应 run / 正在跑的生成）在 `harness.resume()` 之后逐个
     `conversation.submit({ type: "continue" })`。不再伪造用户消息；`nothing_to_answer`
     或 `ConversationBusy` 就放弃这一次（消息仍在频道，下一轮会看到未读摘要）。
  2. **手动继续是一个用例，不是一条通用「重跑」**：`POST /api/people/:slug/continue`
     （`src/app/people.ts` 的 `continuePerson`）只对一个人的主会话提交 `continue`。
     界面的失败卡给「继续这一轮」，`no_model` / `nothing_to_answer` 不显示 —— 前者要人去改
     配置，后者本来就没有可答的东西，点了只会再失败一次。
  3. **不打开 `afterFailedRun: "continue"`**：失败后自动重试会在配置坏掉时刷屏；是否接着做
     由人决定。等有明确需要再单独评估。
- **取舍**：按钮只能续跑「上下文还在」的失败；进程重启后上下文仍在盘上，所以它也覆盖重启。
  它不能修模型配置、不能补回已被合并唤醒撤掉的输入 —— 文案不承诺这些。
- **执行**：`src/core/runtime/open.ts`（`backlog`）、`src/shell/assemble.ts`（提交 continue）、
  `src/app/people.ts`、`src/interface/http/routes.ts`、`ui/app/src/api/client.ts`、
  `ui/app/src/panels/TasksPanel.tsx`（失败卡）；文档 `docs/WEB-API.md` §10.4、
  `docs/DESIGN.md` §8、`docs/CORE.md` §4。
- **验收**：`test/core/resume.test.ts`（backlog → continue）、`test/core/read*.test.ts`；
  `npm run check`、`npm test`、`npm run ui:build`；`npm run live` 两次。

## ADR-076 记 wake 与入队同一个 commit

- **背景**：投递原来先单独提交一次名册（记「他被谁在哪个频道叫醒」），再提交输入。两次
  commit 之间会话可能已经开跑：它查不到 wake，只能退到「我最早的那个频道」（往往是私聊），
  于是问在群里、答在私聊。注释里一直写着「先记 wake、再提交」，但那只是把窗口缩小，没有关掉。
- **决策**：
  1. 1.5.0 的 `Conversation.submit(tx, draft)` 允许在调用方的 commit 里准入。投递走
     `conversation.commit(async (tx) => { rememberWakeTx(tx, …); return conversation.submit(tx, draft); })`：
     名册的 wake 与排队项要么一起落盘，要么一起没有。
  2. **先写文档、再准入**：准入是这次 commit 的第一次表写，之后同一事务不能再读表
     （`ReadAfterWrite`）；名册写只碰文档，放在前面是唯一合法顺序。
  3. **句柄在 commit 之后取回**：事务形式只返回 `SubmissionId`，收尾等待用
     `harness.submission(id, context)` 重新拿 `Submission`。取不回来时投递仍算成功（已经在盘上），
     只少这一轮的收尾监听，并写 stderr。
  4. **保留退路**：没有接上 `wakeTogether` 的调用方（测试替身、旧路径）仍走
     「先 `rememberWake`、再 `submit`」；生产装配只有 `wiring.ts` 一处接线。
- **取舍**：每次投递多一次 `submission()` 查询；换掉的是一个真实出现过的错频道回答。
  多收件人仍是每人一个 commit（一次 commit 只能一次准入），group commit 会把它们批量落盘。
- **执行**：`src/core/agent/roster.ts`（`rememberWakeTx`）、`src/core/channel/wiring.ts`
  （`wakeTogether`）、`src/core/channel/dispatch.ts`（`wake`）、`src/core/channel/post.ts`、
  `src/core/channel/turn/finish.ts`（补发也叫醒，同样走原子路径）、
  `src/core/channel/tools/context.ts`、`src/shell/assemble.ts`。
- **验收**：`test/core/wake.test.ts`（同 commit、抛错两个都不落、退路顺序）、
  `test/core/directory-persist.test.ts`（真 harness 上 wake 仍在）、`npm run live` 两次。

## ADR-077 答完写回频道做成 durable task（`afterRun`），删掉宿主的结算回调收尾

- **背景**：模型经常在最后一个回合把结论写进正文、一次 `say` 都不调，所以「答完替他说」
  是频道里能不能看到结论的最后一跳。旧实现挂在 `watchSettled` 的 `done` 回调上：答案提交
  与回调执行之间、回调执行与消息落盘之间各有一个窗口，进程在这两个窗口里死掉，结论就
  永远留在会话条目里 —— 而重启恢复只重放 generation，不会重放宿主的一段 `Promise` 回调。
- **决策**：
  1. **收尾改成 durable task**：`src/core/channel/turn/report.ts` 用 `defineTask` 定义
     `core.turn-report`，输入只有三样：`slug`、这一轮的 `RunSummary.answer`、唤醒记录。
     任务唯一的行为是调现有的 `finishTurn`（判据、`[PASS]` 过滤、同文去重、补发叫醒都不变）。
  2. **接在 `afterRun` 上**：钩子从名册反查「这条会话是谁、最后被谁在哪个频道叫醒」，返回
     `runEndTask(task, input)`。任务与钩子挂在 `core-tools` 这个**每个会话都已选中**的扩展上
     —— 新钩子不需要给老会话补选扩展，也不需要新建扩展名。任务本身按名字进注册表，
     `assembleCore` 重启后 `resume()` 时能重新解析到同一份定义。
  3. **删掉宿主补发**：`dispatch.ts` 的结算回调只留「没答上来」留痕；`finishTurn` 从
     `DeliverOptions` / `PostDeps` 里移除，`post.ts`、`tools/context.ts`、`assemble.ts` 不再
     往下传。收尾只有一个触发点，避免双发。
  4. **幂等靠同文判据，不靠 exactly-once**：任务在「消息已落盘、终态没提交」时被重放，
     `finishOnce` 会看到频道里已有同一句而跳过。底座保证的是至少一次，收尾自己保证不重复。
  5. **行为边界**：钩子只在**答完**（`answer` / `terminate`）时触发，失败与中止不触发；
     没有唤醒记录的 run（手动 `continue`、子会话）不收尾。名册里最后一条 wake 是这一轮
     该回的地方 —— 和旧路径相比，`continue` 产生的答案现在也会写回最后说话的地方，
     这是「答完就写回频道」的本来含义。
  6. **收尾不算「还在干活」**：`liveConversations` 跳过两类活任务 —— `core.turn-report`
     本身，以及「只等收尾任务」的 `waiting` 生成。答完之后底座会让 generation 停在
     `waiting`，等 `afterRun` 的子任务跑完才结束；这一段里模型已经收手了，只是账还没记完。
     不跳过的话，紧随其后的消息会被写成「这是插话，不是新任务」，模型只答一句就收手，
     工具活整个丢掉（实测 2026-11-05：三次 `live` 里丢了 2–3 项）。
- **取舍**：收尾任务让 generation 多挂几毫秒，但投递判据把这一段排除在外，所以新输入
  不会因此被当成插话；换来的是任何时刻被杀都能补上结论。任务记录会随轮次增长，由底座的
  `pruneTerminalTasks`（3 天）回收。
- **执行**：`src/core/channel/turn/report.ts`（任务 + 钩子 + 输入投影）、
  `src/core/channel/turn/finish.ts`（`FinishTurnInfo` 只要 `EntryReader`，`TaskRuntime` 也满足）、
  `src/core/runtime/index.ts`（转发 `runEndTask` / `Task` / `RunSummary`）、
  `src/shell/assemble.ts`（`core-tools` 的 `tasks` / `hooks`）、

  （`TURN_REPORT_TASK`）、`src/core/channel/tools/context.ts`。

## ADR-078 消息生命周期收进 `src/core/flow`：主线只有 `publish` / `forward`

- **背景**：「一条消息落盘之后谁被叫醒」原来散在三个文件里 —— `channel/post.ts` 的
  `postMessageUnlocked` 又落盘又定规则（`note` 不叫人、没 `@` 时接上一说话人、`wakeTo`
  覆盖），`channel/dispatch.ts` 的 `deliver` / `wake` 又把扇出、合并队列、写 wake、`submit`
  揉在一起；读代码的人看不到一条消息从落盘到入队的完整顺序。`afterPost` 也不对称：
  `say` / `ownerSpeak` 调，补发与后台命令的回执不调，和「每条消息都通知插件」的承诺不符。
- **决策**：
  1. **建 `src/core/flow/`（domain 的新兄弟目录）**，对外只暴露 `createFlow(ports)` 的
     `publish` / `forward`。`publish` 的固定顺序是：闸内「读快照 → 落盘 → 算事实
     （`lastSpeaker` / `defaultTargets`）→ 策略链 → 校验（去重，滤掉我 / 发件人 / 非成员）
     → 逐人扇出」，闸外 `afterPublish`（抛错只 warn，不影响这条消息）。`forward` 只读、
     校验、扇出，不写第二条消息。
  2. **策略优先级固定**：`wake: false` / `note` 无 `wakeTo` 不叫 → `wakeTo` → 策略链
     （第一个返回决定的生效，抛错跳过）→ `facts.defaultTargets`。策略只能**提议**，谁真的
     被叫仍由 `validate` 决定。
  3. **`channel/dispatch.ts` 并入 `flow/runner.ts`**（`deliver` / `wake` / 结算回调原样搬家）；
     `channel/post.ts` 降为旧入口的薄壳：把 `PostDeps` 拼成 `createFlow(...)` 再转调。
     落盘、频道规则、投递正文排版仍留在 `channel/`。
  4. **`afterPublish` 覆盖每条公开消息**：`say`、我说话、补发、后台命令的回执都调用一次；
     `route` 的隐藏留痕（`store.note`）不算 publish，不通知插件。这是有意的行为变化：
     插件第一次真正看到补发与后台回执。
  5. **暂缓项写在这里，免得下一阶段忘掉**：进程级串行闸仍以 `channel/post.ts` 的模块单例
     作默认值（Phase 4 挪进装配注入）；结算后是否补发仍由 `channel/turn/finish.ts` 判断
     （Phase 2 搬进 `flow/settle.ts`）；插件 `flow` 动作（Phase 3）。
- **取舍**：多了一层端口（`MessageStore` / `Router` / `TurnRunner` / `PublishHooks` /
  `FlowGates`），但每个端口都有默认实现、现有测试或已知的未来消费者，不是第二套生命周期
  —— `Message` / `WakeRecord` / `Submission` 仍是唯一事实，`flow` 不建账本（ADR-060 的教训）。
  代价是调用方要多传一个 `gate`，以及 `post.ts` 与 `flow` 之间有一次薄壳跳转。
- **执行**：`src/core/flow/{index,types,ports,publish,forward,runner,policies,validate,store}.ts`、
  `src/core/flow/defaults/router.ts`、`src/core/channel/{post,wiring}.ts`、
  `src/core/channel/turn/finish.ts`、`src/core/channel/tools/{context,say}.ts`、
  `src/shell/assemble.ts`、`src/app/types.ts`、`scripts/check-boundaries.mjs`（域加 `flow`、
  接口层禁直接 import `flow`）。
- **验收**：`test/core/flow-publish.test.ts`（分支：默认规则 / `note` / `wake:false` /
  `wakeTo` / 越界过滤 / 钩子错误隔离 / 频道被删）、`flow-order.test.ts`（闸内读—写—扇出、
  闸外钩子；`forward` 不写不钩）、`flow-invariants.test.ts`（校验）、`flow-policy.test.ts`
  （first-defined-wins、`drop`、回退）；`npm run check`、`npm test`（97 文件 / 860 例）、
  `npm run prompt:check`、`npm run live` 两次 13/13（`[turn]` 各 1 次）。

## ADR-079 结算收尾收进 `flow.settle`：一个入口、两条来源，判断与机械分家

- **背景**：ADR-078 把「消息落盘后叫醒谁」收进了 `core/flow`，但「一轮结束之后怎么办」
  仍分两条路：`done` 走 durable `afterRun → core.turn-report → finishOnce`，`unanswered`
  走投递时挂的 `watchSettled → appendNote`；判断（取正文 / `saidLast` / `turnTarget` /
  同文判据）与读答案、补发、日志混在 238 行的 `channel/turn/finish.ts` 里，找「答完发生
  了什么」的人通常只看到其中一条。ADR-078 的暂缓项 5 说这一阶段搬进 `flow/settle.ts`，
  这里兑现。
- **决策**：
  1. **`flow.settle(event)` 是结算的唯一入口**，`Settlement` 只有两种：
     `{kind:"done", slug, answer, wake, entries}` 与 `{kind:"unanswered", channelId, text}`。
     `done`：持 `repost` 闸 → 读当前频道快照 → 取答案条目 → 问 `Settler` → 要补就调一次
     `publish`（补发是正常发言：算人、叫醒、钩子、名册都走同一条主线）。`unanswered`：
     只 `store.note` 一行留痕，**不进闸** —— 它不和补发抢。
  2. **判断搬进 `flow/defaults/settle.ts`**（`finalTextOf` / `spokeAfterWake` /
     `answerEntry` / `saidLast` / `turnTarget` / `defaultSettler()`），逻辑逐字搬家，不重写。
     默认收尾的四条「不补」理由显式化成 `SettleDecision.reason`：`no-entry` / `pass` /
     `no-target` / `not-member`（含同文去重判为 `duplicate`）。
  3. **`channel/turn/finish.ts` 降为薄壳**：保留 `createTurnFinisher` 这个名字（`wiring.ts`
     与测试按它接线），内部把 `TurnDeps` 拼成 `createFlow(...)` 再取 `flow.settle`。
     纯函数从 `flow/defaults/settle.ts` 转出，命名不变。
  4. **两把进程级闸收进 `flow/gates.ts`**：`publish`（ADR-073）与 `repost`（ADR-069 /
     原 `finish.ts` 的模块单例）由 `sharedGates()` 提供一份，`channel/post.ts` 与收尾薄壳
     共用。`settle` 持 `repost` 后再调 `publish`（再取 `publish`），**锁序固定为
     `repost → publish`，反方向不存在**，写在 `flow/settle.ts` 头注释里。
  5. **`MessageStore` 增加 `snapshot()`**：flow 只造一次也要读当前盘面；`postMessage` 的
     调用方给了快照就直接用，保留原来的快路径。
- **取舍**：`channel/` 里多了一条 `finish.ts → flow` 的引用（domain 组内部的单向依赖，
  `check-boundaries` 允许）；`flow` 与 `settle` 互相需要，`createFlow` 用一个中转解开，
  真正调用时两边都已装好。没有引入新状态：`Message` / `WakeRecord` / `Submission` 仍是
  唯一事实。
- **执行**：`src/core/flow/{settle,index}.ts`、`src/core/flow/defaults/settle.ts`、
  `src/core/flow/gates.ts`、`src/core/flow/{types,ports,store,publish,forward}.ts`、
  `src/core/flow/runner.ts`（`noteUnanswered` 改调 `settle`）、
  `src/core/channel/turn/{finish,index}.ts`、`src/core/channel/post.ts`；
  文档 `docs/CORE.md` §4、`docs/CODE.md` §1–§3、`docs/CONCESSIONS.md` C-010、`AGENTS.md`。
- **验收**：`test/core/flow-settle.test.ts`（补发 / 同文不补 / `[PASS]` 与空正文不补 /
  找不到答案条目 / `unanswered` 只留痕且不进闸）；`turn-report` / `crash-turn-report` /

## ADR-080 插件第五个动作 `flow`：策略可替换，执行仍归 core

- **背景**：ADR-018 把插件限定为四个动作（工具 / 提示词 / 路由 / 听消息），ADR-078 又把
  消息生命周期收进 `core/flow`，于是「消息该叫醒谁」和「答完要不要补发」成了插件碰不到的
  内核。实际使用里这两处恰恰最需要按组织习惯调整（比如团队频道按关键词分给某个人、给结论
  统一加前缀）。但 `scripts/check-boundaries.mjs` 不允许插件层 import `core/flow/` —— 这条
  边界是对的：插件不该拿到 `Context` / `Harness` / `Conversation`，也不该自己写盘、入队。
- **决策**：
  1. **新增第五个动作 `api.flow({kind:"router"|"settle", run(facts)})`**，和其余四个动作一样
     只往一个数组里 push（`PluginSinks.flow`）；`PluginHost.flow` 暴露给装配层，
     `PluginSummary.brings.policies` 数给界面看。
  2. **策略形状放在 `channel/types.ts`**（`RouteFacts` / `RouteDecision` / `SettleFacts` /
     `SettleDecision` / `FlowPolicy`），`flow/types.ts` 只做转出。插件层允许 import
     `channel/types.ts`、不许 import `flow/`，这样策略的契约归领域原语，编排仍留在 flow。
  3. **策略只拿只读事实，只能提议**：`router` 返回 `targets` / `drop` 或 `undefined`；
     `settle` 返回 `repost` / `silent` 或 `undefined`。拿不到运行时对象，不能写频道、不能
     入队。提议一律经过 core 校验：频道在不在、他是不是成员、正文空不空（补发时），
     其余（成员过滤、去重、owner / self、落盘、唤醒、闸门）仍在 `flow` 里做。
  4. **组合顺序固定**：`router` 策略排在 `defaultRouter()` 之前，按注册顺序问，第一个给出
     决定的生效（`policyRouter`）；`settle` 是**替换**而不是链，最后注册的那条生效，弃权
     或抛错回退 `defaultSettler()`（`policySettler`）。理由：默认收尾已经是一个完整判断，
     多条替换串起来没有明确语义；需要叠加时可以自己组合后注册一条。
  5. **热替换靠活引用**：装配层传 `() => plugins.flow`，`reloadPlugins` 只替换 `plugins`
     变量，下一次 `publish` / `settle` 自动读到新数组。没有额外的注册 / 注销协议，也不
     需要重启。在途的一轮已经捕获了计划，不受影响。
  6. **三条发消息的路都要看得见策略**：`ChannelWiring.policies` 一路传到工具 `say` / `run`
     的 `postDeps`、`ownerSpeak` 自己的 `PostDeps`、以及 `turn/finish.ts` 的收尾器；
     装配层的主接线与 `ownerSpeak` 各传一份。漏掉其中一条，插件就只对部分消息生效。
- **取舍**：插件 API 从四个动作变成五个，`channel/types.ts` 多了一组面向插件的形状（它本来
  就是频道的数据契约，不算新的层）；`settle` 不做策略链，表达力比 router 弱，但避免了
  「谁覆盖谁」的歧义。策略抛错只 warn 并回退，不把一条坏策略升级成投递失败。
- **执行**：`src/core/channel/types.ts`（策略形状）、`src/core/flow/{types,policies,settle}.ts`、
  `src/core/plugin/{api,load,index}.ts`、`src/core/channel/{wiring,post}.ts`、
  `src/core/channel/turn/finish.ts`、`src/core/channel/tools/context.ts`、
  `src/shell/assemble.ts`（`policies` 活引用 + `ownerSpeak`）、`src/view/dto.ts` 与
  `ui/app/src/panels/PluginsPage.tsx`（`brings.policies`）；
  文档 `docs/CORE.md` §13、`docs/CODE.md` §2–§3、`docs/WEB-API.md` §13.4、`AGENTS.md`。
- **验收**：`test/core/flow-policy.test.ts`（router 先注册先问 / 抛错跳过 / settle 无策略回退 /
  最后注册生效 / 抛错回退）；`plugin.test.ts`（五个动作、`brings.policies`）；
  `plugin-reload.test.ts`（重装后下一次发布立刻换规则）；`settle` 的 core 校验留在
  `flow-settle.test.ts`；`npm run check`、`npm test`（98 文件 / 871 例）、
  `npm run prompt:check`、`npm run live` 两次 13/13。

## ADR-081 装配拆成 `shell/wire`，全应用只有一个投递门面

- **背景**：ADR-078 把消息生命周期收进 `core/flow`、ADR-080 让插件能替换分发与收尾策略，
  但装配层还留着一份平行接线：`shell/assemble.ts` 820 行里混着开会话、装插件、名册落盘、
  模型切换与团队留痕；我说话走 `ownerSpeak`，它每次自己 `wireChannel(...)` 再拼一份
  `PostDeps`。后果是 ADR-080 第 6 条写的「三条发消息的路都要看得见策略」只能靠人记 ——
  漏接一条，插件就只对部分消息生效。另外 `deliver` / `wake` / `finishTurn` 上带
  `BACKGROUND_CONTEXT` 默认值，调用方在哪个事务里调用是隐式的。
- **决策**：
  1. **`shell/assemble.ts` 只做组合与顺序**，具体接线拆到 `shell/wire/` 七份：
     `plugins`（装 / 重装 / 听消息 / 策略活引用）、`conversations`（扫文件夹、开会话、
     进频道、写名册）、`identities`（提示词段）、`models`（模型切换）、`directory`
     （名册落盘）、`teams`（报到 / 重启留痕）、`speak`（我开口）。
  2. **投递门面只有一份**：`wireChannel` 造出的 `ChannelWiring.flow` 同时交给工具
     （`say` / `route` / `run`）、宿主发言（`speak`）、团队留痕（`teams`）与收尾
     （`finishTurn`）。谁都不再自己拼 `PostDeps`；插件钩子与策略因此对每条公开消息生效。
  3. **`ChannelFlow.publish` 收本次调用的频道快照**（`publish(state, input, ctx)`）：
     工具先读、门面再交给 flow。提交之后再读同一份覆盖层会报
     `Cannot use a settled overlay`，所以快照必须由调用方在提交前读好。
  4. **`Context` 显式传递**：`deliver`（现 `fanOut`）/ `wake`（现 `enqueue`）/
     `finishTurn` 去掉默认值；谁在什么事务里调用，由调用方写出来。内部只有「没答上来」
     的留痕仍用 `BACKGROUND_CONTEXT`（那是 durable task 自己的后台结算）。
  5. **关库只由运行时负责**：`shell.close()` 幂等，`main.ts` 不再先关壳再关运行时；
     加一条断言测试锁住「关两次只关一次库」。
- **取舍**：`wire/` 是 `shell/` 里的新目录，不是新分层（shell 本来就是唯一可 import 全部的
  装配层）；`flowOf` 每次调用现造一个薄对象（没有隐藏状态，也避免把快照钉在闭包里）；
  两把串行闸仍是进程级（ADR-073 / ADR-078），只是从模块单例变成装配注入。内部改名
  `deliver → fanOut`、`wake → enqueue`、`deliveryPrompt → deliveryText`，落盘与接口不变。
- **执行**：`src/shell/assemble.ts`、`src/shell/wire/{plugins,conversations,identities,models,directory,teams,speak}.ts`、
  `src/core/channel/post.ts`（`createChannelFlow`）、`src/core/channel/wiring.ts`（`flow`）、
  `src/core/channel/tools/{context,say,route,run}.ts`、`src/core/channel/turn/finish.ts`、
  `src/core/flow/{runner,types}.ts`、`src/shell/main.ts`；
  文档 `docs/CODE.md` §1.1 / §2、`AGENTS.md` §2 / §3.3。
- **验收**：`test/core/assemble.test.ts`（关两次只关一次库）；`npm run check`、`npm test`
  （98 文件 / 872 例）、`npm run prompt:check`；临时根目录启动冒烟；Phase 5 收尾时
  `npm run live` 两次 13/13 与 `live:scenarios -- --rounds=1 --smoke`。

## ADR-082 文档收进 `core/documents`：基础 + 各自的实现

- **背景**：`src/core/agent`、`src/core/team`、`src/core/md` 三个包读起来别扭：它们处理的

  提示词模板 / 文案目录），却被拆成三个平级目录。`md/doc.ts` 已经是「一份 markdown 文档」
  的公共基础，但它的实现（人、团队、技能、规矩）住在另外两个包里；`agent/` 还混进了
  名册（会话 id 与唤醒记录）和密钥脱敏（跨层安全网）—— 这两样都不是任何人的档案。
- **决策**：
  1. **一个包，两侧**：`src/core/documents/` 下分 `base/`（机械的文档与文本操作，零业务：
     `doc` / `slots` / `template` / `catalog` / `memory` / `memory-store` / `oneline`）与实现
     （`member/` 一个人的身份、记忆、日志；`team/` 一个团队的 README 与记忆；
     `skills.ts` / `rules.ts` / `prompt.ts`）。实现依赖基础，基础不认识实现。
  2. **`prompt.ts` 放包根**：它是唯一同时 import `member/` 与 `team/` 的文件；放进
     `member/` 会留下 `member → team` 这条边，「两份并列实现」就不成立了。
  3. **`base/memory-store.ts` 只收机械部分**：一条串行链上的「读全文 → 交给 build → 写回」。
     去重、标题格式（个人同日合并 / 团队永远新开）、校验失败是返回还是抛错，仍留在各自
     实现里 —— 两种记忆共用格式，但不共用判断。`base/memory.ts` 只增加对应的纯函数
     （`alreadyRecorded` / `appendNewSection` / `appendOrExtendLastSection`）。
  4. **名册归 `channel/roster.ts`**：它记的是 slug ↔ 会话 id 与唤醒记录，真相是文件夹，
     属于消息系统；这样也去掉了 `documents → channel` 的反向依赖。
  5. **密钥归 `src/core/secrets.ts`**：渲染出口的跨层安全网，与 `fsx` / `naming` / `layout`
     同级，不属于任何人的档案。
  6. **边界规则 8 组变 9 组**：域（`documents|channel|flow|runtime`）/ **文档基础**
     （不许 import 任何实现与上层）/ **文档实现**（不许 import channel / flow / plugin）/
     plugin / 根原语（加入 `secrets.ts`）/ view / app / desktop / interface。插件只许用
     `documents/base/`（负向前瞻 `/documents/(?!base/)`），不给通用 allowlist —— 那会误伤
     `node:*`、`./api.ts`、`channel/types.ts` 与 `runtime/*`。
- **取舍**：不引入泛型 `DocKind<T>` 框架，也不把记忆 store 做成一组开关 —— 团队的标题回退、
  技能的三层覆盖、人的多根扫描正是业务本身，塞进配置只会变成一堆开关。对外导出、函数签名、
  落盘格式与提示词文案**一律不变**；只改文件位置、相对 import 与文档。历史 ADR 里的旧路径
  不重写（它们记录的是当时的事实）。
- **执行**：`src/core/documents/**`（原 `core/md/*`、`core/agent/{identity,memory,journal,skills,rules,sections}.ts`、
  `core/team/{doc,memory}.ts` 迁入并改名 `slots` / `template` / `prompt`）、
  `src/core/channel/roster.ts`、`src/core/secrets.ts`、`scripts/check-boundaries.mjs`（9 组）；
  文档 `AGENTS.md` §1–§3、`docs/CODE.md` §1–§3、`docs/CORE.md` §2 / §7 / §10、
  `docs/WEB-API.md` §12、`docs/README.md`。
- **验收**：`npm run check`（tsc + 9 组边界）、`npm test`（98 文件 / 872 例）、
  `npm run prompt:check`、`npm run live` 两次 13/13；不改界面，不跑 `ui:build`。

## ADR-083 `settings.json` 只有一个写入口，坏文件绝不覆盖

- **背景**：模型装配、给某个人换模型、出厂「模型管理」插件都各自读改写这份文件。旧写法
  在 JSON 解析失败时把它当成「空配置」，然后整份重写 —— 一个手滑的逗号就能把全部提供商
  和模型抹掉，而且没有任何报错。这份文件是**用户配置**，不是可以随时重建的缓存。
- **决策**：
  1. `src/core/runtime/settings.ts` 是唯一读写口：`readSettingsFile` / `updateSettingsFile` /
     `setAgentModel`。所有调用方（`runtime/models.ts`、`shell/wire/models.ts`、`app/people.ts`）
     都经它，不再自己 `readFileSync` + `writeFileSync`。
  2. **区分「没有」和「坏了」**：文件不存在 = `undefined`（首次启动，可以写新文件）；
     存在但读不懂 = `SettingsFileError`，必须把这句话交给用户。绝不能当空配置继续。
  3. 写回是「读 → 只改 change 动过的键 → 临时文件 + rename」。不认识的键原样保留
     （前向兼容），写到一半崩掉不会留下半份 JSON。
- **取舍**：坏文件会让启动或切模型**失败**，而不是带着空配置跑起来。这是有意的：静默丢掉
  用户配置比一次看得见的错误糟得多。同步 IO 保留 —— 这两个调用点都在同步上下文里，文件很小。
- **执行**：`src/core/runtime/settings.ts`、`runtime/models.ts`、`shell/wire/models.ts`、
  `app/people.ts`；`docs/CODE.md` §1 的 `node:fs` 例外表加入 `settings.ts`。
- **验收**：`test/core/{models,model-switch,model-manager-plugin}.test.ts`（坏文件不覆盖、
  未知键保留、原子写）。

## ADR-084 出厂内容共用一本 hash 账本

- **背景**：技能有 `.seed-manifest.json` 按 hash 判「用户改过没有」，但提示词模板与
  `rules.md` 是「只补不改」—— 出厂修正永远进不来：`seed/rules.md` 改一句，已经在跑的
  工作区一辈子看不到。三个地方各写各的规矩，判据也不一样。
- **决策**：提示词模板、规矩、技能**共用一本账**（`<appRoot>/.seed-manifest.json`，按文件
  内容 hash）：
  1. 目标不存在 → 拷过去，记账；
  2. 当前内容 hash == 账本记的 → 没改过，升到新版并记账；
  3. 当前 hash != 账本记的 → 用户改过，**原样保留**并 warn；
  4. 老工作区没有账本 → 用 `src/shell/seed-legacy.ts` 的历史 hash 集合判一次；命中 =
     旧版出厂内容，可以升级。新版本不再往集合里加（账本会记住基线），等不再支持从这些
     版本升级时整个文件删掉。
- **例外**：`seed/text/*.md` 仍按**键**只追加（文案是「一个键一句话」，用户改过的句子归他，
  新键要能进老工作区）—— 它和整文件升级是两件事，不并进账本。
- **取舍**：用户改过又改回与某个历史版本逐字节相同的内容，会被当成「没改过」升级。
  无法区分，接受；账本只在真有变化时写盘，启动是幂等的。
- **执行**：`src/shell/seed.ts` 的 `syncSeedFiles` / `syncSkillTree` / `SEED_MANIFEST_FILE`、
  `src/shell/seed-legacy.ts`；`test/core/seed-sync.test.ts`。

## ADR-085 旧形状靠迁移，读取处不留兼容分支

- **背景**：为了读老数据，读取路径上堆了一串兼容分支：`spokenKind` 维护「哪些旧 kind 算
  发言」、`recipientsOf` 拿空名册再解析一次字面 `@我`、`parseWake` 兼容平铺的唤醒记录、
  `headerOf` 同时认 `project:` 与 `team:`。每个读的人都要记住整段历史；漏一处就是静默
  错投（字面 token 落库、频道里「叫了谁」是错的），而且没人看得出。
- **决策**：
  1. **库里的文档**升 version 写 `migrate`：`ChannelDoc` v2 的 `migrateMessages` 把旧 kind
     归一成 `chat` / `note`、把字面 `@我` / `我` 归一成 `owner`；`DirectoryDoc` v2 的
     `migrateWakes` 把平铺的唤醒记录拆成 `{reply, task}`。第一次读到旧版本时自动归好。
  2. **磁盘上的文件**在启动时一次性改写：`src/shell/migrate.ts` 的 `migrateWorkspace` 把身份
     头的 `project:` 改成 `team:`（已有 `team` 就删掉 `project` 行），正文与其它字段逐字节
     不动，重复跑不再改。顺序固定在「迁移 → 播种 → 装配」之前。
  3. **规矩**：加字段就升 version + 写 `migrate`；改文件形状就写启动迁移。**不要在读取处
     加「两种形状都认」的分支** —— 那等于让每个读者重新学一遍历史。
- **取舍**：迁移是一次性的、不可逆的写盘（文件）或首次读取开销（文档）。换来的是所有读的
  代码只认一种形状；老数据的语义在迁移里集中定义一次，测试也只钉那一处。
- **执行**：`channel/types.ts` 的 `migrateMessages`、`channel/roster.ts` 的 `migrateWakes`、
  `channel/turn/record.ts` 的 `parseWake`（只认新形状）、`shell/migrate.ts`、`shell/main.ts`；
  `test/core/{mention-alias,directory-persist,migrate,view}.test.ts`。

## ADR-086 名册只有一个真相：落盘那份

- **背景**：旧实现读名册时把内存里的映射「并」到盘上再回写。后果有两个：开除一个人只删了
  盘上的条目，下一次读又把他从内存并回去（重启后频道和私聊全回来）；新建会话只写内存，
  中间任何一次「整份名册写回旧值」都会让映射永久丢失（顾南雁丢过一次，22 条历史留在孤儿
  会话里）。
- **决策**：`DirectoryDoc` 是唯一真相，内存 `directory` 只是镜像：
  1. 写：先提交文档（逐字段比较，只写变化过的顶层字段，路径式更新），提交成功后再把结果
     抄进内存；
  2. 读：从文档抄一遍（`now`），**不再合并内存**；
  3. 启动 / `rescan` 只合并 `labels`（显示名），不合并会话映射；
  4. `openAgent` 建完会话立刻 `bind` 落盘（`hire` 不走 `rescan`，不立刻写就会丢）。
- **取舍**：每次读多一次文档快照（底座里就是内存表，代价可忽略）；换来「删掉的不会复活、
  新加的不会丢」这两条能单测钉死的不变量。
- **执行**：`src/shell/wire/directory.ts` 的 `save` / `now` / `merge` / `bind`、
  `channel/roster.ts`；`test/core/directory-persist.test.ts`。

## ADR-087 收尾是 durable 任务，补发按答案条目去重

- **背景**：宿主侧在结算回调里直接调 `finishTurn`，有两个窗口会在重启时丢结论：答案提交了、
  回调还没跑；回调跑了、消息还没落盘。模型没调 `say` 时正文只存在会话条目里，丢了就是丢了。
  另一头，同一条答案会被多条提交各结算一次，并发时都照到「频道里还没有这句」，于是同一句
  发两遍（实测 2026-11-02 #15/#16、#17/#18）。
- **决策**：
  1. 收尾做成 durable task：`core.turn-report`（`channel/turn/report.ts`），由 `afterRun`
     钩子写成这一轮 generation 的子任务；进程重启后 `resume()` 接着跑完。
  2. 任务终态如实记录：补发成功 = `completed`（带答案条目 id 的收据）；补发失败 = `failed`；
     被 Stop / 关库打断 = `aborted`。**不能一律报 completed**，否则「补没补上」永远查不出来。
  3. `flow.settle` 的 `done` 分支持进程级 `repost` 闸包住「读答案 → 判重 → 补发」；判据是
     `sourceEntry`（答案条目 id），不是正文 —— 两个人真说了同一句「在。」不该互相吞掉。
  4. 补发就是一次正常 `publish`：落盘、算人、扇出、钩子全走主线，且必须带名册
     （`@我` 落成 `owner`，不能存字面 token）。
- **取舍**：每一轮多一件账务任务（`channel/bookkeeping.ts` 登记，不算「在干活」）；换来
  重启不丢结论、重放不双发。
- **执行**：`channel/turn/report.ts`、`flow/settle.ts`、`flow/defaults/settle.ts`、
  `channel/queue.ts`；`test/core/{turn-report,turn-report-e2e,crash-turn-report,flow-settle}.test.ts`。

## ADR-088 写完之后的重投影失败要回到调用方

- **背景**：`file` 写身份 / 团队说明、`hire` 招人之后都要重投影频道。旧写法把这些后续
  动作的失败只写进 console：模型收到「写好了」，频道里却还是旧成员 —— 界面上看不出异常，
  下一次 @ 才发现人不在。
- **决策**：
  1. 工具结果带 warnings：`file.write.sync-failed` / `file.write.team-sync-failed` /
     `hire.create.announce-failed`。写盘本身成功了，所以**不回滚**，但模型必须知道后半段
     没成，能在同一轮里补救或告诉我。
  2. 装配依赖收紧：`hire` 不再单独收一个 `ensureDm` —— 开会话、建私聊、进全员 / 团队频道
     统一由 `openAgent` 一次做完，不存在「人建好了、频道还没接上」的半成品路径。
  3. 装配层建**一份** `diag`，底座报告、插件、策略错误都写进同一条线（见 ADR-091）。
- **取舍**：模型会多看到一行失败说明；换掉的是「保存成功但状态是旧的」这种无声错误。
- **执行**：`channel/tools/file.ts`、`channel/tools/hire.ts`、`shell/assemble.ts`、
  `seed/text/tools.md`；`test/core/tools-actions.test.ts`。

## ADR-089 插件工具不覆盖核心工具，监听失败只丢自己

- **背景**：插件工具与核心工具进同一个注册表。同名时旧行为是后者覆盖前者 —— 一个插件
  注册 `say` 就等于把说话换成了别人写的函数，模型完全看不出来。插件的听消息钩子用
  `Promise.allSettled` 并发跑，抛错被吞掉，没人知道它坏了。
- **决策**：
  1. `loadPlugins` 收 `reservedTools`（核心的 8 个名字）；一个插件的工具名**先全部核一遍，
     全过才登记**：与核心重名、与先装的插件重名、同一插件内重复，都让**整个插件不装**，
     错误进插件列表。装一半的插件不占名字、不进注册表。
  2. 听消息的每个 listener 在装载时包一层：抛错只记这个插件的一条错误（走 `onError` →
     装配层的 `report` → 诊断），别的插件照跑，投递不回滚。
  3. `flow` 的策略形状只在 `channel/types.ts` 定义一次，`flow/types.ts` / `flow/ports.ts`
     只转出 —— 插件层能拿到，领域里没有第二份定义。
- **取舍**：插件作者必须给工具名加前缀；一个坏插件在插件页里显示为「没装上」，而不是
  静默半工作。
- **执行**：`core/plugin/load.ts`、`shell/wire/plugins.ts`、`flow/ports.ts`、`flow/types.ts`；
  `test/core/{plugin,token-plugin}.test.ts`。

## ADR-090 频道 id 收敛到一处，助理判定按路径分量

- **背景**：`id.startsWith("team:")` + `slice` 散在业务代码里，前缀一改就得全仓库找，漏一处

## ADR-091 策略 / 监听失败进诊断，账务任务自己登记

- **背景**：插件策略抛错、听消息抛错都只有 console；界面上「他就是不回话」和「他回话时
  策略炸了」看起来一模一样。队列判断「他还在干活」时写死跳过 `core.turn-report`，
  新增一类收尾 / 摘要任务就要回来改队列。
- **决策**：
  1. `FlowPorts.report` 是运行中出错的唯一出口（形状由 core 描述，接到哪里由装配层定）；

     失败都走这条线。

     `docs/CONCESSIONS.md`），所以登记放在我们这一层。
- **取舍**：只通报不自动重试 —— 策略坏了应该被人看见并修，而不是被系统悄悄绕过。
- **执行**：`flow/ports.ts`、`flow/policies.ts`、`plugin/load.ts`、`shell/wire/plugins.ts`、

## ADR-092 技能带 `sourcePath`，工具自己登记轨迹展示

- **背景**：`readSkill` 拿到技能名后要按三层顺序重新猜它从哪一层读出来；轨迹投影里有一大段
  `switch (工具名)`，加一个工具就要回来改投影，插件工具只能画成裸名字。提示词装配里还留着
  一个已经没人用的 `count` 插槽的兼容读取。
- **决策**：
  1. `listSkills` 的每一项带 `sourcePath`（它到底从哪一层读出来的），`readSkill` 直接用，
     不再按名字重猜层。
  2. 工具在注册时用 `traced(tool, trace)` 声明自己那一行（`channel/tools/presentation.ts`）；
     `app/trace.ts` 只按名字查表，不认识具体工具。没声明过的（插件工具）退回「原名 + 通用
     行」——不认识不等于不该画。
  3. `count` 插槽保留填充：出厂模板已经不用它，但账本会保留用户改过的旧
     `prompt/20-position.md`（ADR-084），那些模板里的 `{{count}}` 不能渲染成「（未设置）」。
- **取舍**：领域里的 `TraceKind` 必须能赋给契约层的 `ViewStep["kind"]`，由 `app/trace.ts`
  的赋值处替这条兜底（领域不能 import 契约层）；多一种界面不认识的种类就编不过。
- **执行**：`documents/skills.ts`、`channel/tools/presentation.ts`、`channel/tools/index.ts`、
  `app/trace.ts`、`app/read.ts`、`documents/prompt.ts`；`test/core/{skills,trace}.test.ts`。

## ADR-093 明确取代：正文去重改为答案条目判重，旧形状只靠迁移

- **背景**：ADR-051 的「补发前比对正文」与 ADR-061 的「投影层归一、不改库不迁移」都已被
  后来的实现取代（ADR-087 / ADR-085），但旧条目没有标注，读者按旧 ADR 改回去会和 core 的
  不变量打架。
- **决策**：
  1. **ADR-087 取代 ADR-051 的去重判据**：补发前比对的是答案条目 id（`sourceEntry`），
     不是正文。ADR-051 里「为什么不按提交 id 去重」那一段不再成立。
  2. **ADR-085 取代 ADR-061**：旧形状（消息 kind、字面 `@我`、平铺 wake、身份头 `project:`）
     一律在迁移里一次性归一，读取处不留兼容分支。
- **取舍**：旧 ADR 保留原文（只追加、不改历史）；以本条为准。
