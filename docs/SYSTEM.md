# 系统逻辑

这份文档回答一个问题：**「一人公司」跑起来的时候，究竟发生了什么。**
不涉及代码，只看角色、数据、消息怎么流动。

要改代码看 [CODE](CODE.md)。

---

## 0. 一句话

> 一群**长期活着的 AI 会话**，在一个**共享的数据库**里，通过**频道**说话、通过**任务**干活、通过**升级链**做决定。进程重启后它们还在，说过的话还在，没做完的事接着做。

三个词定义这个系统：

| 词 | 意思 | 不是什么 |
|---|---|---|
| **会话** | 一个 AI 的「永久身份」，有 id、有历史、有工具、有工作目录 | 不是一次对话。它跨重启、跨天、跨压缩，一直存在 |
| **频道** | 消息的容器，类似群聊 | 不是双向连接。写进去是广播，谁被唤醒由规则算 |
| **任务** | 一件有验收标准的工作，有状态机 | 不是 prompt。它会被持久化，崩了能继续 |

## 1. 组织：谁是谁

```
老板（人类，conversationId = 0，没有独立的 AI 会话）
  └─ CEO            ← 老板与它之间的会话是「根会话」
      ├─ CTO   CFO   CPO   COO   CMO   CHRO        （6 个管理层）
      └─ 项目 A
          ├─ 负责人（项目经理）
          │   ├─ 员工：开发 / 测试 / 设计 …
          └─ 项目 B …（结构相同）
```

**全部都是**「会话 + 一个能力包 + 一段职责提示词」。
CEO 与员工在底层没有任何形态差异——只有三样东西不同：

1. **提示词**（你是谁、向谁汇报、什么不许做）
2. **工具集**（能调哪些函数）
3. **归属**（员工的会话挂在一个后台任务上，见 §7）

层级在系统里体现为三件事：

| 层级体现在 | 具体是什么 | 在哪 |
|---|---|---|
| **谁能派任务给谁** | 只能从上到下。横向协作要 `ask_role`（通信不限方向） | `canAssign` |
| **谁能看见哪些频道** | 老板看全部；管理层看公司群+领导层+自己项目；员工看自己项目群 | `canView` |
| **问题往上走的路** | 员工 → 负责人 → 对应管理层 → CEO → 老板，不许跳级 | 升级链 |

**注意**：`ask` / `ask_role` 是**不限方向**的——员工可以问 CEO，CEO 也可以问员工。
限制只加在「派活」（`assign_task`）和「谁有权拍板」（决策路由）上。

## 2. 一次典型的一天

```
1. 老板在网页上给 CEO 发一句：「做个抽奖活动页」
      ↓ 消息进 CEO 的会话，CEO 醒来
2. CEO 判断：这要立项。调 project_create → CPO 建项目、建目录、建项目群
3. CEO 派任务给 CPO：assign_task（带验收标准）→ 立刻返回，不等
4. CPO 找 CHRO：ask_role「这个项目要 1 开发 1 测试」
5. CHRO：staff_hire ×2 → 两个员工会话诞生，锚在后台任务上
6. CPO 把活拆了派给负责人 → 负责人再派给员工
7. 员工干活（能读写文件、跑命令），做完了 task_update（**必须带证据**）
      ↓ 系统自动把这个状态写进项目群，不用模型自己汇报
8. 负责人验收 → 有问题就退回（review → todo），没问题就 done
9. 员工遇到拍不了的问题：escalate → 变成一条「待决问题」，
   躺在负责人的队列里休眠（不占执行名额、可跨天）
10. 负责人答了（answer_pending）→ 升级任务醒来，继续
11. 老板随时能点开任何人的会话、看它此刻在想什么、在调什么工具
```

关键点：**除了第 1 步和最后一步，全程没有人等待。**
`assign_task` 派完就返回，`deliver()` 投完就返回，答案通过频道异步回来。
这不是优化，是硬约束——同步等待成环会把整机挂死（真实事故，见 §9）。

## 3. 数据：存在哪、长什么样

全部数据在一个 SQLite 文件里：`workspace/company.sqlite`。

**没有第二份真相**。内存里的一切都是这份库的投影。备份这一个文件就是备份整个公司。

里面有两类东西：

### 3.1 会话自己的历史（底层管，本项目不碰）

每个会话有自己的消息流、思考、工具调用、token 用量、队列。
`node_modules/@earendil-works/pi-durable` 负责它的持久化与压缩。

### 3.2 公司的业务文档（本项目定义，10 个）

| 文档 | 装什么 | 为什么单独存 |
|---|---|---|
| `app.company` | 公司名、7 个岗位的会话 id、项目清单、员工名册、模型清单 | 组织关系是全局的 |
| `app.profile` | 每个会话在组织里的位置（岗位/项目/工作目录） | 会话自己的小档案 |
| `app.channels` | **全部频道和消息**（一个文档装所有频道） | 一条公司群消息只存一份 |
| `app.tasks` | 全部任务与状态 | 看板只读它 |
| `app.pending` | 待决问题（按层级的队列） | 升级链的状态 |
| `app.audit` | 谁在什么时候做了什么决定 | 留痕、可追责 |
| `app.trail` | 沟通图（谁跟谁说过话） | 界面上那张关系网 |
| `app.budget` | 预算与告警 | CFO 用 |
| `app.memory` | 分层经验记忆（员工 / 项目 / 公司三层，按 `level + owner` 分区） | 经验要跨会话、跨任务复用，但不是流水账 |

设计要点（每一条都是踩过的坑）：

- **频道集中存一个文档**：如果按会话各存一份「我看到的消息」，15 个人就有 15 份副本，已读位置无法维护。
- **文档靠 delta 重放恢复，不是定期存快照**。写操作进日志，崩溃后重放。所以「提交」`commit(tx => {...})` 是一等公民——一次提交要么整体生效，要么整体不生效。
- **每个频道只留最近 800 条**。聊天是流水，不是档案；要留档的结论进 `app.audit`。
- **记忆有三道闸**：写入有门槛（任务完成才提醒写、正文 ≤ 300 字、同一任务只留一条）、
  读取有预算（提示词里最多 5 条）、总量有上限（50/100/200 条，超了把**同代数**最老 20 条
  折叠成一条阶段总结，折叠代数硬上限 `MAX_DEPTH = 3`；到上限后改为丢最老的原始条目）。
  三层各自独立，互不挤占。见 `src/domain/memory.ts`。

## 4. 通信：怎么写、谁被叫醒

这是整个系统最反直觉的部分，值得单独一节。

### 4.1 三条铁律

1. **写频道 ≠ 唤醒所有人**。消息先落库，然后由 `recipientsOf()`（纯函数）算出「该叫醒谁」。
2. **投递失败不能让消息丢**。消息已经在库里了，投递失败只影响「它什么时候看到」，不影响「它能不能看到」。
3. **每条投递都带未读摘要**。没被叫醒的人下次因任何原因醒来，输入开头就有「你有 N 条未读」。

### 4.2 谁会被唤醒

```
被 @ 的人              → 唤醒
老板发言且没 @ 人       → 唤醒该频道 owner
wakeOnAll 的成员       → 唤醒
（永远不唤醒发送方自己）
```

为什么这么保守：**15 人公司群，每条消息都唤醒 15 个 agent，成本会瞬间爆炸。**
所以默认「说话不叫醒任何人，@ 才叫醒」。

### 4.3 有四种频道

| 频道 | 成员 | 用途 |
|---|---|---|
| `company` | 全体 + 老板 | 公司大群 |
| `leadership` | 老板 + CEO + 管理层 | 领导层 |
| `proj:<slug>` | 老板 + 负责人 + 该项目员工 | 项目群（默认工作场所） |
| `dm:<id>` | 老板 ↔ 某一个人 | 私聊（**不用 @**，两个人说话说给谁听是显然的）；右上角展开是本人的角色档案与工作流水 |

**注意：agent 之间没有私聊**。两个 agent 要说话，得在共同群里（项目群/领导层/公司群）。
这是当前设计的一个明确边界，不是疏漏（见 §10）。

### 4.4 两条原语，别的都是它们的组合

| 原语 | 做什么 | 等回复吗 |
|---|---|---|
| `postToChannel` | 消息写进频道 + 调 `deliver()` | — |
| `deliver()` | 把消息投进目标会话的队列（`whenBusy: "steer"`） | **不等** |

`whenBusy: "steer"` 的意思是「插进它当前这一轮」，不用 `followUp`（那要等整轮答完，群里一条问题可能十几分钟才被看见）。

### 4.5 成本模型

每次唤醒一个 agent = 一次完整推理 = 一次完整输入 token 账单。
所以系统的很多「克制」都是为了这件事：

- 说话不 @ 就不叫醒人
- 派任务不等回复（避免一个 agent 挂着等另一个）
- 待决问题休眠而不是轮询
- 工具延迟加载（CEO 25 个工具只直接给 12 个，其他靠 `tool_search` 现搜）
- 角色提示词必须是**常量字符串**，否则每轮都击穿 prompt cache（cacheRead 便宜 10 倍，cacheWrite 贵 1.25 倍）

## 5. 任务：怎么保证「说了就要做完」

一条任务长这样：

```
id, 项目, 标题, 需求说明, 验收标准（必填）, 指派人, 负责人, 优先级, 依赖
状态: todo → doing → review/done, 或 blocked → doing, 或 cancelled
进度记录: 谁在什么时候说了什么
完成证据: 文件路径 / 测试输出 / 提交号（报 done 必须有）
```

三条硬规则：

1. **必须有验收标准**。没有验收标准的任务建不出来。
2. **报 done 必须带证据**。不给证据会被拒绝并提示。
3. **状态变化由系统写，不由模型写**。模型调 `task_update` 只改状态机，写进频道的那条报告是系统生成的——所以不存在「模型忘了汇报」这种路径。

## 6. 决策：一个问题该谁拍

三层路由，**只按事项类别判定，不看问题正文**（因为「重要性」是主观的，模型会用它给自己授权）：

| 事项类别 | 谁拍 |
|---|---|
| 立项 / 砍项目 / 预算上限 / 对外承诺 / 组织架构 | **老板独占** |
| 技术选型、需求优先级、预算内支出、招聘 | 对应领域的管理层（超阈值 → CEO） |
| 本项目内的排期、拆活、人员调配、退回不合格产出 | 项目负责人 |
| 说不清归谁 | 沿汇报线上行，最终到 CEO |

「老板独占」那一条还有一个额外规则：**老板级待办只能由 CEO 递上去**。
任何 agent 都不能直接把问题抛到老板面前。

### 升级链的工作方式

```
员工 escalate
  → 创建一条持久化任务（durable task），checkpoint = { phase: "ask", level: 谁 }
  → 把问题写进 app.pending，标记「等这一级答」
  → 任务休眠（不占执行名额、可跨天、进程重启后从当前 checkpoint 继续）
  → 这一级 answer_pending
  → 任务醒来，读答复：答了 → 收口；说「拍不了」→ level = nextLevelUp(level)，继续休眠
  → ...
  → 到老板：等人类在网页上答
```

**只有一个阶段**（`phase: "ask"`），`level` 字段说「现在停在谁那儿」。
上一级算谁由纯函数 `nextLevelUp(org, level)`（`src/domain/membership.ts`）决定，
它只对 `level === "ceo"` 返回 `"owner"`——所以「老板级待办只能由 CEO 递」这条硬规则
只有一处实现（ADR-033），阶段机自己不判层级。

每一级跃迁都写检查点，所以崩溃重开从当前级继续，不会从头再问一遍。
老库里 v1 的三阶段 checkpoint（`ask-manager` / `ask-ceo` / `ask-owner`）
由 `EscalationTask.migrate` 机械映射到 v2 的单阶段（ADR-038）。

## 7. 员工为什么挂在一个「任务」上

这是一个底层约束，不是设计选择：

> pi-durable 里，一个会话想「自己动起来」，必须在后台任务里有归属；否则它只能被动等消息。

所以每个员工身边都有一个 `app.anchor` 任务：创建后立即结束（终态），唯一作用是给会话一个「后台归属」。

副作用：**终止项目时必须穿透后台边界停会话**（`conversation.abort(ctx, { background: true })`），否则员工停不下来。

## 8. 自愈：卡住了怎么办

系统会卡住。这不是假设，是已发生的事实。三种卡法：

| 卡法 | 现象 | 谁来收 |
|---|---|---|
| 工具中断后会话永远「在忙」 | `pi.generation` 停在 `waiting`，之后所有派活都排队 | 看门狗中断 |
| 消息投递失败 | 消息在库里，但没人被叫醒 | 看门狗排空队列 |

> 「同步等待成环」这一类已经不在了：同步派活（`delegation.ts`）整块删除，见 ADR-037。
> 现在没有任何 agent 会等另一个 agent 跑完整轮，环从结构上不可能形成。

**看门狗**每 30 秒巡检一次，做七件事：

1. **判定**：哪些任务真在跑，哪些只是僵住的 `waiting`
2. **收尾**：超期/僵住的中断或重试（**同一条任务最多自动动手 2 次**，之后如实标 error 并停手——无限重试只是把卡死变成抖动）
3. **排空**：会话空闲但队列里还压着消息 → 主动投一次
4. **升级没回音的问题**：群里 @ 某人长时间没人答 → 升级给上一级
5. **提醒卡住的任务**：太久没进度 → 提醒负责人
6. **老板的消息没人理** → 告警并重投
7. **投递回执**（ADR-034）→ 消息发出去了但接收方的 submission 结算成
   `unanswered`（通常是 `no_model`：模型不可用），说明**这条消息根本没被处理过**。
   每 30 秒查一次，最多重投 2 次，之后只告一次警并停手。生产库里这类消息有 69 条，
   最老的一条等了几个月没人发现——「投递成功」曾经被当成「已读」。

**每一次动手都写一条 `app.alert` 进会话流。**
理由：老板必须看得见「系统自己做了什么」，否则「自动恢复」和「悄悄吞掉」在界面上没有区别。

还有一层：**崩溃自愈**。底层报告运行时失败时，入口会重新打开数据库、重跑巡检与初始化，然后继续。

## 9. 几个反直觉的点（都是真实事故换来的）

1. **不能同步等另一个 agent**。改前的写法是「提交 → 等 180 秒 → 捞回复」，会成环挂死全机。现在 `deliver()` 投完立刻返回，答案通过频道异步回来；那条老路径（`delegation.ts` / `delegation-guard.ts`）已彻底删除，见 ADR-037。
2. **相对路径会翻车**。执行环境会把相对 `cwd` 和进程目录再拼一次，结果是 `进程目录/相对cwd/相对cwd`，全部报「目录不存在」。所以项目的 `workspace` 必须是绝对路径。
3. **提交回调里不能 await 任何会话 API**（快照/查任务/嵌套提交），会间歇性死锁。
4. **提示词不能随时间变**。角色描述里嵌个当前时间 → 每次都追加 system delta → 彻底破坏 prompt cache。
5. **能力包名字必须唯一**。底层按名字存「这个会话选了哪些能力包」，所有员工共用一个名字会互相覆盖，表现是「某些员工莫名没有任何工具」。
6. **新建会话必须显式指定能力包**。不指定则默认选中全部已注册的——CEO 会拿到 CHRO 的招聘工具。
7. **`entries()` 默认倒序**；`tx` 的读必须发生在第一次表写之前，否则报 `ReadAfterWrite`。

## 10. 当前的边界（明确知道但还没做的）

写在这里，避免以后把「限制」当成「bug」来修：

| 边界 | 影响 | 绕法 |
|---|---|---|
| **agent 之间没有私聊** | 两个 agent 只能靠共同群说话 | 建一个临时项目群；或用 `ask_role`（会落到共同群） |
| **`assign_task` 只能从上到下** | 平级/向上派活不允许 | 用 `ask_role`（通信不限方向） |
| **「已按默认暂搁」不进待办列表** | `listPending` 会滤掉已处置项，老板在待办里看不到「这条被机器替你决定了」 | 到「已处理」归档区查；提醒到点时下达人会收到一条 alert |
| **没被 @ 就不唤醒** | 没有「广播」能力 | 逐个 @ |
| **能力定义是代码** | 加工具要改代码 + 重启 | 无 |
| **层级写在代码里** | 改组织形状要改代码 | 无 |
| **预算检查是软的** | `budget_check` 只报告，不拦截 | 无 |
| **单进程单库** | 第二个实例会被独占锁拒绝 | 无（这是刻意的） |
| **网页服务没有鉴权** | 只能跑在可信内网 | 见 [DEPLOY](DEPLOY.md) |

## 11. 一个项目 = 一个文件夹

```
workspace/
  company.sqlite        全部数据
  projects/
    <slug>/
      PROJECT.md        立项文档（需求、目标、验收）
      ...               负责人和员工的工作目录，就是这里
  uploads/              老板上传的附件
  logs/                 事件日志
```

`<slug>` 与项目显示名分离（显示名可以改，slug 不变，否则路径会断）。
所有会话的 `cwd` 指向自己的目录，所以「写文件」「跑命令」都发生在项目里。
